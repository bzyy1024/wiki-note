# 12 泛型：为什么迟到十年，类型集、约束、单态化取舍

## 开篇提问

Go 是 2009 年发布的，但**泛型直到 2022 年的 Go 1.18 才落地**——整整迟到了十三年，是 Go 历史上被讨论最久、争议最大、最难产的特性。

先问你一个问题，这个问题决定了你对整个泛型争论的理解深度：

**Go 团队拖延十三年，是因为他们"做不出来"吗？还是他们"不想做"？或者，是他们在"性能/简洁/复杂"之间，一直找不到一个符合 Go 价值观的方案？**

提示一下：Go 的作者 Robert Griesemer、Rob Pike、Ken Thompson，就是泛型理论里"类型参数""鸭子类型"这些概念的重量级人物。他们不是不懂泛型，恰恰是**太懂了**，所以迟迟不敢下手。

想清楚这个问题，再往下看。这一章要讲的，是"一个语言特性从需求到落地，中间要熬过多少取舍"的完整过程。

---

## 子主题一：为什么需要泛型——真实的痛点

先明确泛型解决什么问题。没有泛型之前，Go 程序员面对"写一份逻辑、适配多种类型"的需求，只有两条路：

**路一：复制粘贴。** 给 `int` 写一个 `MaxInt`，给 `float64` 写一个 `MaxFloat64`，给 `string` 再写一个……代码重复，改一个 bug 要改 N 处。

**路二：interface{} + 类型断言 + 反射。** 写一个 `Max(a, b interface{})`，里面用 type switch 或反射判断类型。能用，但：
- 编译期不检查类型，运行时才崩；
- 装箱开销（上一章讲过）；
- 代码丑陋，全是断言和反射。

泛型要解决的，就是让 Go 程序员能**用编译期类型安全的方式，写"适配多种类型"的代码**：

```go
func Max[T constraints.Ordered](a, b T) T {
    if a > b { return a }
    return b
}
```

`Max(1, 2)`、`Max(1.5, 2.5)`、`Max("a", "b")` 都能用，且编译期就知道类型对不对。

这个需求是真实的——标准库里的 `sort`、`sync`、各种容器，社区里无数的"泛型工具库"，都在用 interface{} + 反射硬扛。泛型的价值，不用怀疑。

## 子主题二：为什么拖了十三年——三座大山

Go 团队不是不做，是卡在三个巨大的取舍上，每一个都直指 Go 的核心价值观：

**大山一：实现方式——单态化还是装箱？**

泛型有两种经典实现：

- **单态化（monomorphization）**：编译器为每一种实际用到的类型，生成一份专门的代码（`Max[int]`、`Max[float64]` 各编译一份）。运行快（和手写代码一样快），但编译慢、二进制大。C++ 模板、Rust 泛型走这条路。
- **装箱（boxing / 字典传递）**：只编译一份通用代码，运行时通过"类型字典"传递类型信息。编译快、二进制小，但运行慢（有间接调用）。Java 泛型（类型擦除）、C# 泛型（混合）偏这条路。

Go 的选择，必须同时满足它的两条立身之本：**编译要快**、**运行要快**。单态化运行快但编译慢（代码爆炸），装箱编译快但运行慢——**没有一条路能同时满足两条。** 这是最核心的挣扎。Go 1.18 最终选了"**部分单态化 + 字典传递混合**"的折中方案（GC shape stenciling），试图在两者之间找平衡。即便如此，它也带来了编译变慢、二进制变大的代价——这是泛型落地后社区最常抱怨的两点。

**大山二：类型约束怎么表达——interface 的二次利用。**

泛型需要"约束"：告诉编译器 `T` 必须支持哪些操作（比如 `T` 必须可比较、可排序）。Go 团队不想引入一套全新的"约束语法"，于是**二次利用了 interface**：把 interface 从"方法集"扩展成"类型集合"。

```go
type Ordered interface {
    ~int | ~float64 | ~string   // 类型集合：这些类型（及其底层类型）都算
}
```

这个设计很巧妙（沿用已有概念，减少新语法），但代价是**interface 的语义变得复杂了**——它现在既是"方法集"，又是"类型集合"，学习曲线变陡。这又是一个取舍。

**大山三：会不会毁掉 Go 的"简单"？**

这是最根本的焦虑。泛型是出了名的"复杂度放大器"——C++ 模板的报错地狱、类型系统被模板搞复杂的前车之鉴，都在眼前。Go 团队极度担心：加一个泛型，会不会让 Go 从"简单到人人都能读懂"变成"复杂到只有专家敢碰"？

所以 Go 1.18 的泛型设计，做了**大量克制**：

- 不支持泛型方法（方法不能有自己的类型参数）；
- 不支持"变长类型参数"（可变模板参数）；
- 不支持运算符重载；
- 类型约束刻意保持简单。

每一条"不支持"，都是 Go 团队在说"我们宁可不给，也不要复杂"。这种克制，正是泛型拖了十三年的根本原因——**不是技术做不出来，而是价值观上迟迟不肯妥协。**

## 子主题三：类型集、约束、底层类型——泛型的核心机制

泛型的核心概念，值得你精确掌握：

**类型参数（type parameter）：** `func F[T any](x T)` 里的 `T`。调用时由编译器推断或显式指定。

**约束（constraint）：** 限制 `T` 能是什么类型的东西。`any` 是最宽松的约束（等价于 `interface{}`，任何类型都行）。

**类型集（type set）：** 约束的本质是"一组类型的集合"。`interface{ int | string }` 的类型集是 {int, string}；带方法的接口，类型集是"所有实现了这些方法的类型"。

**底层类型（underlying type）与 `~`：** `~int` 表示"底层类型是 int 的所有类型"，包括 `type MyInt int` 这种自定义类型。`~` 让约束能覆盖"基于某类型的自定义类型"，非常实用。

**类型推断（type inference）：** 调用 `Max(1, 2)` 时，编译器从参数推断 `T = int`，你不用写 `Max[int](1, 2)`。这让泛型代码用起来和普通代码一样自然。

## 子主题四：泛型的代价与边界——什么时候别用

泛型不是免费的，它的代价你要心里有数：

**代价一：编译变慢、二进制变大。** 单态化（stenciling）会为每种类型组合生成代码，导致编译时间上升、可执行文件膨胀。这是泛型落地后，Go 社区最直接的感受。

**代价二：泛型不是"万能抽象"。** 泛型适合"算法和容器"（sort、map/filter/reduce、泛型缓存、泛型队列），不适合"所有场景"。如果一个函数只是把两个不同类型硬凑在一起，用 interface{} 反而更简单。

**代价三：约束设计的复杂度。** 类型集合、`~`、`any`、`comparable`……这些概念让 interface 变得更难懂。写约束本身就是一门手艺，写不好会让泛型代码更难读。

社区逐渐形成的共识：**泛型应该用在"确实需要跨类型复用算法/容器"的地方，而不是为了炫技到处用。** 具体说，`slices`、`maps` 这类标准库的泛型函数，是好的用法；而"为了少写一个 interface{} 就上泛型"的代码，往往得不偿失。

## 子主题五：类型参数与实例化——编译器到底替你干了什么

上一节我们站在"要不要用"的层面看泛型。现在把镜头怼进编译器内部：**写下 `func Max[T constraints.Ordered](a, b T) T` 之后，到 CPU 真正执行一条比较指令，中间发生了什么？**

别急着往下读，先回答一个问题：

**`Max(1, 2)` 和 `Max(1.5, 2.5)` 这两次调用，运行时执行的是同一段机器码吗？**

如果你的答案是"是"，那为什么 `int` 和 `float64` 的 `>` 指令完全不同（一个是整数比较，一个是浮点比较）还能共用代码？如果你的答案是"不是"，那 `Max` 就有了两份代码——可你只写了一份。

这就是泛型最核心的机制问题：**一份源码，如何变成 N 份可执行代码。**

### 5.1 两个世界：定义侧与实例化侧

先建立精确的心智模型。泛型代码存在于两个世界：

**定义侧（generic code）：** 你写在源文件里的 `func Max[T Ordered](a, b T) T`。这一刻 `T` 是个"洞"，编译器只知道它落在约束的类型集里，不知道它具体是啥。定义侧的代码会被**做一次完整的类型检查**——这是 Go 泛型和 C++ 模板的一个关键差异，后面讲对照时会展开。

**实例化侧（instantiation）：** 每个调用点，编译器把 `T` 替换成实参类型，得到 `Max[int]`、`Max[float64]`……具体生成多少份、每份长什么样，取决于实现方式（子主题八细讲）。

一个容易忽略的事实：**类型参数不止能出现在函数上，也能出现在类型上。**

```go
type Stack[T any] struct {   // 泛型类型
    items []T
}

func (s *Stack[T]) Push(v T) { s.items = append(s.items, v) }
func (s *Stack[T]) Pop() (T, bool) {
    if len(s.items) == 0 {
        var zero T   // 零值的正确写法
        return zero, false
    }
    v := s.items[len(s.items)-1]
    s.items = s.items[:len(s.items)-1]
    return v, true
}
```

看 `var zero T` 这一行。你写不了 `return 0`，也写不了 `return nil`——因为 `T` 可能是 `string`，可能是 `struct{}`，可能是 `*Foo`。**`var zero T` 是泛型里获取零值的唯一通用姿势**，这个细节值钱：它意味着"零值"在 Go 里是类型系统的一等概念，而不是"某个具体的值"。

顺手注意 `func (s *Stack[T]) Push` 的写法——**方法本身不能有自己的类型参数，但可以声明"我的接收者是 `Stack[T]`，这里 T 是类型上的参数"。** 这是 Go 里让方法"沾上"泛型的唯一合法路径，很多人第一次写会本能地敲成 `func (s *Stack[T]) Convert[U any]() Stack[U]`，然后被编译器抽。为什么不行？子主题十会讲清楚。

### 5.2 类型推断：编译器怎么知道 T 是什么

你几乎从不写 `Max[int](1, 2)`。**凭什么？** 凭类型推断。Go 的推断有三层，层层递进：

**第一层：函数实参推断（unification）。** 最直观的：把实参类型 `int` 和形参类型 `T` 做模式匹配（ unification），得出 `T = int`。多个实参都贡献同一个 `T` 时，必须推出一致的结果：

```go
Max(1, 2)        // T = int，一致，OK
Max(1, int64(2)) // int vs int64 → 不一致，编译错误
```

注意 `Max(1, 2)` 里两个实参都是**无类型常量（untyped constant）**。这时候推断给 `T` 用的是常量的**默认类型**（`int`），这也是 `Max(1, 2.5)` 报错的原因——先把 1 默认成 `int`，2.5 默认成 `float64`，两者打架。

**第二层：约束类型推断（constraint type inference）。** 这一层是 Go 泛型的隐藏实力，也是很多"为什么这个能编译"的答案。

```go
func Map[S ~[]E, E any](s S, f func(E) E) S {
    r := make(S, len(s))
    for i, v := range s {
        r[i] = f(v)
    }
    return r
}

xs := []int{1, 2, 3}
ys := Map(xs, func(v int) int { return v * 2 })
```

你只传了 `xs`（类型 `[]int`）和一个 `func(int) int`，**`S` 和 `E` 两个类型参数都被推断出来了**，一个都没手写。怎么做到的？两步走：

1. 先做实参推断：从 `xs` 匹配 `S`，得 `S = []int`；`E` 暂时没着落。
2. 再做约束类型推断：已知 `S = []int`，而 `S` 的约束是 `~[]E`，把 `[]int` 和 `~[]E` 结构对齐 → `E = int`。

**约束类型推断的本质是"用结构匹配从已知类型参数反推未知类型参数"。** 它让 `Map` 这种"返回同类型切片"的签名成为可能——`ys` 的类型是 `[]int` 而不是 `[]any`，类型信息一点没丢。这个能力是 Go 泛型能否写出顺手代码的分水岭：没有它，你每次都得写 `Map[[]int, int](xs, f)`，丑到没人愿意用。

顺便引出两个硬概念：

- **`make(S, len(s))` 为什么合法？** 因为 `S` 的约束是 `~[]E`，所有元素的底层类型都是 `[]E`，这个联合有**核心类型（core type）** `[]E`。`make`、`len`、`append`、索引、切片这些操作，要求类型参数拥有对应的核心类型。这是 Go 规范里的一条硬规则，记不住没关系，但你得知道**"为什么某些泛型代码里 `make(T, n)` 编译不过"**——因为你的约束是个大杂烩联合（比如 `~[]int | ~[]string`），没有唯一核心类型。

- **`~[]E` 而不是 `[]E` 的意义**：允许 `type IntList []int` 这种自定义切片类型传进来，并且返回的还是 `IntList`。少了 `~`，`Map` 就只能吃裸 `[]int`，逼着调用方做转换。

**第三层：Go 1.21 起的上下文推断。** 一个历史遗留痛点被修掉了：

```go
var f func(int) int = Abs   // Go 1.21+ 可以从目标类型推断出 T = int
```

在此之前，把泛型函数赋给一个函数类型的变量/返回它，编译器会一脸茫然地让你手写参数。这条改进看着小，实际上决定了泛型函数能不能当一等公民传来传去（比如塞进函数表、做中间件包装）——**一个特性如果不能被赋值传递，它就永远是个二等公民。**

### 5.3 推断失败的四种典型场景

推断不是万能的。以下四种情况，你必须显式写出来，别跟编译器较劲：

```go
func Zero[T any]() T { var z T; return z }
Zero[int]()        // ① 类型参数只出现在返回值，实参里没有任何线索

func New[T any](v ...T) *T { ... }
New[string]()      // ② 变参为空，推断不出

func Convert[From, To any](v From) (To, error) { ... }
Convert[int, string](1)  // ③ 多个类型参数，只推断得出 From

func Fill[S ~[]E, E any](s S, v E) S { ... }
Fill([]int{}, 0)   // ④ 无类型常量 + 空切片字面量，默认类型可能不是你要的
```

这里有个**必须记住的硬规则：Go 不支持部分指定类型参数。** 要么一个都不写（全靠推断），要么**全部**写出来。`Max[int](1, 2)` 可以，`Convert[int, ](1)` 是语法错误。这条规则和 TypeScript、C# 都不一样，很多人第一次踩会觉得"这也太笨了"——但换个角度想，**Go 在逼你把接口设计成"可完全推断"的形状**，这本身就是一种设计约束：好的泛型 API，调用方永远不需要手写类型参数。

**判断一个泛型 API 设计得好不好的土办法：看调用点需不需要显式类型参数。需要，就说明你的签名漏了线索。**

### 5.4 实例化：生成什么、什么时候生成、生成几份

概念上，编译器在实例化时做三件事：

1. **类型检查实例化后的代码。** 用实参类型替换 `T`，重新验证泛型函数体里用到的每个操作（`<`、`make`、方法调用）都合法。**注意：这一步在定义侧也做过一次**——定义侧检查"对所有类型集内的类型都成立"，实例化侧再核对一遍。Go 这么做是为了让泛型错误信息可读（你可以拿到"int 不满足约束"而不是几百行模板展开），代价是**编译时间直接翻倍地花掉**。

2. **生成（或复用）一份代码。** 按实现方式：全单态化是每类型一份；Go 的混合方案是按"GC shape"分组——内存布局/指针分布相同的类型共用一份代码，这个后面专门讲。

3. **生成并传递字典（dictionary）。** 一份代码要服务多个类型，就必须知道"我这次是在给谁干活"。类型特有的信息（类型描述符、约束方法的实现地址、比较/哈希函数等）被打包成一个运行时结构，在调用时传进去。这就是**字典传递**。

打个比方压一下这个模型：

> 单态化 = 给每位客人量身定制一套西装。合身到极致（零开销），但客人一多，裁缝（编译器）先累死，仓库（二进制）先爆。
> 装箱 = 均码工服。一人一件，仓库省了，但胖子绷、瘦子晃，穿着跑不快（间接调用）。
> Go 的混合 = 按体型分成 S/M/L 三档（shape），同档共用一套版型，再给每个人发个胸牌（字典）写上名字和特殊要求。**合身程度接近定制，成本接近均码。**

那么问题来了：这个"折中"是不是白嫖？当然不是。子主题八和九，我们把账单摊开算。

## 子主题六：约束语法全展开——类型集、联合、`~`、`any`、`comparable`

子主题三给了一张速查表，现在把每个概念**拆到能写进生产代码的精度**。

先抛一个反直觉的问题：

**`interface{}` 和 `any` 是同一个东西吗？如果是，那 `comparable` 呢——它长得也像个接口，能不能写 `var x comparable`？**

### 6.1 一句总纲：约束就是接口，接口就是类型集

Go 1.18 之后，**每一个接口都同时拥有一个类型集**。以前的接口只有方法集，那不过是一种"描述类型集的方式"：

```go
type Stringer interface{ String() string }
```

在旧心智里：Stringer 是"有 String 方法的类型"。在新心智里：**Stringer 的类型集 = { 所有实现了 `String() string` 的类型 }**。两者说的是同一件事，只是后者能和其他描述方式（联合、`~`）**求交并**。

于是约束的完整语法，就是接口语法的一个超集：

```go
type MyConstraint interface {
    ~int | ~int64 | ~string   // 类型元素：联合（union）
    fmt.Stringer              // 方法元素：嵌入一个方法集接口
    comparable                // 嵌入预声明约束
}
```

一个接口里可以放三类东西，**多个元素之间是"交集"不是"并集"**：

```go
type StringyInt interface {
    ~int          // 底层类型是 int
    String() string  // 且实现了 String 方法
}
```

`StringyInt` 的类型集 = 底层类型为 `int` 的类型 ∩ 实现了 `String()` 的类型 = 只有 `type MyInt int` 且带 `String()` 方法那种。交集理解错了，约束就写不对。

### 6.2 联合 `|`：并集与它的四条禁令

`A | B` 表示类型集的并集。但联合有**实现层面的四条禁令**，每一条都有理由：

1. **联合（元素多于一个时）不能包含带方法的接口。** 写 `interface{~int | fmt.Stringer}` 是错的。为什么？因为这种混合类型集没法确定唯一核心类型，编译器做不了 `make`/索引等操作的类型检查，而且字典构造会变得极其复杂。
2. **联合不能包含 `comparable`。** `interface{ comparable | ~int }` 非法。
3. **非接口元素的类型集必须两两不相交。** `int | ~int` 非法（重叠），`~int | ~int64` 合法。
4. **联合元素不能是类型参数。** 你不能写 `[T any, U T | ~string]`。

这些禁令看着烦，但它们**反向告诉你 Go 的类型集计算在哪里会失控**。真踩到了，通常的信号是：你的约束设计得太花哨了，该拆成两个。

### 6.3 `~`：底层类型，而不是"兼容类型"

`~T` 读作"底层类型为 `T` 的所有类型"。

```go
type Celsius float64
type UserID  int

interface{ ~int }      // 包含 int 和 UserID
interface{ float64 }   // 只包含 float64，不包含 Celsius
```

为什么需要 `~`？因为 **`type Celsius float64` 定义的是一个全新类型，它不等于 `float64`。** 没有 `~`，你的泛型函数就拒绝了一个语义上完全合理、甚至正是为了类型安全而存在的类型（`Celsius` 存在的目的就是防止你把温度当重量用）。有了 `~`，泛型才能"穿透"这层命名，看到底层布局。

`~` 的规则：
- `~T` 中的 `T` 必须是**它自己的底层类型**（不能再被展开），且不能是类型参数；
- 实践中 `~` 后面基本放**基础类型或具体复合类型**：`~int`、`~string`、`~[]byte`、`~map[string]int` 都合法；
- `~error` 这种拿接口类型去 `~` 的用法没有意义（接口的底层类型就是它自己）。

一个实战判断：

```go
func Sum[T ~int | ~int64](xs []T) T
func Sum2[T int | int64](xs []T) T
```

哪个更好？**绝大多数情况 `~` 版更好**，因为它接纳用户的自定义类型。但有一个例外：如果你的函数需要把 `T` 转成具体类型使用（比如要 `int(v)` 传给某个只吃 `int` 的第三方库），`~` 会让转换在语义上变得可疑（你正在把一个"有名字的类型"脱掉名字）。**`~` 是能力，也是诱惑——它让你更容易写出"看起来通用、实际破坏用户类型语义"的代码。**

### 6.4 `any` 与 `comparable`：长得像，性格完全不同

**`any`：** 就是 `interface{}` 的**别名**（alias，不是新类型），Go 1.18 预声明。它的类型集是**所有类型**。做约束时它表示"零要求"，于是泛型函数体内对 `T` 几乎什么都干不了——不能比较（除非用 `comparable`）、不能做算术、只能赋值、传参、放进 `[]T`/`map[K]T`、用反射。

顺带一个常见误解：`any` 是别名不是新类型，所以 `*any` 就是 `*interface{}`，`any` 和 `interface{}` 可以互相赋值、类型完全相同。写 `any` 只是**可读性**（强调"任意类型"），没有类型系统层面的新语义。

**`comparable`：** 预声明标识符（**不是关键字**，可以被局部变量遮蔽——这是个坑，别在代码里写 `comparable := ...`）。它的类型集是**所有严格可比较（strictly comparable）类型**：能安全使用 `==` 和 `!=` 且保证不 panic 的类型。

关键细节，一个比一个阴：

```go
func KeysOf[K comparable, V any](m map[K]V) []K { ... }

var m map[any]int            // 编译 OK：map 的 key 允许接口类型
KeysOf(m)                    // 编译错误！any 不满足 comparable
```

为什么？**因为 `any` 不是严格可比较**：你可以把 `[]int` 塞进 `any`，两个 `any` 用 `==` 比较就会在运行时 panic。`comparable` 排除了这种"比较可能炸"的类型，而 map 的 key 类型检查用的是"可比较"（宽松版），允许接口，代价是把 panic 留到运行时。

于是得到一个很实用的结论：**`comparable` 的使用场景几乎只有一个——做 map 的 key 类型参数，以及做 `slices.Contains`/`Index` 这类需要相等判断的泛型函数的约束。** 如果你在 `comparable` 之外还想做大于小于，那是 `cmp.Ordered` 的活儿。

还有一条：`comparable` **不能当普通变量的类型用**，`var x comparable` 编译不过；同理，任何**包含类型元素（联合/`~`）的接口都不能当普通类型用**，只能当约束。这是 interface 语义分裂后留下的疤痕——同一个语法，两种身份。

### 6.5 空类型集：能声明，不能用

```go
type Impossible interface {
    int
    string
}
```

`Impossible` 的类型集 = {int} ∩ {string} = ∅。它**声明合法**（编译器不会在声明处报错），但**任何类型都无法满足它**，所以：

```go
func F[T Impossible](x T) {}   // 编译 OK
F(1)                           // 编译错误：int 不满足 Impossible
```

这有什么用？**它证明了 Go 的类型集是一套真正可计算的集合代数**，有并、有交、有补（通过 `~`）、有全集（`any`）、有空集。理解这一点，你才能读懂复杂的约束组合，也才能在多人协作时看懂同事写的那坨 `interface{~[]E | ~map[K]V, comparable}` 到底在说什么。

### 6.6 一个必须想透的问题：为什么需要类型集，而不是"运算符方法"

Rust 里你这么写排序约束：`T: Ord`，`Ord` 是个 trait，里面有 `fn cmp(&self, other: &Self) -> Ordering`。比较操作通过**方法**表达。

Go 里呢？`cmp.Ordered` 长这样：

```go
type Ordered interface {
    ~int | ~int8 | ~int16 | ~int32 | ~int64 |
        ~uint | ~uint8 | ~uint16 | ~uint32 | ~uint64 | ~uintptr |
        ~float32 | ~float64 | ~string
}
```

**一长串枚举。** 丑吗？丑。但为什么只能这样？

因为 **Go 没有运算符重载，也拒绝引入它。** `a < b` 在 Go 里永远是一条内建指令，永远不能被用户定义为方法。那么泛型函数体内的 `a < b` 要合法，唯一的办法就是**在编译期枚举出所有支持 `<` 的类型**——也就是把类型集显式列出来。

这带来一个深远影响，值得你刻进脑子里：

> **在 Rust/C++ 里，泛型操作的合法性来自"方法/trait 实现"；在 Go 里，它来自"类型集枚举"。**

后果是什么？

- **好处：** 语义绝对明确，没有运算符重载带来的"这个 `<` 到底在比什么"的心智负担（想想 C++ 里 `a + b` 可能是字符串拼接、矩阵加法、或者是某个疯子重载的文件追加）。
- **坏处：** 你**不能让自定义类型"接入" `<`**。`type Money struct{ cents int64 }` 永远无法满足 `cmp.Ordered`，哪怕它语义上完全可排序。你只能走另一条路：`slices.SortFunc(moneys, func(a, b Money) int { ... })`——**传比较函数，而不是实现接口。**

所以 Go 的泛型世界分裂成两类 API：**基于类型集的（快、内联友好、但类型封闭）和基于回调函数的（通用、但每次调用都是一次间接调用）。** `slices.Sort` vs `slices.SortFunc` 就是这个分裂的标准答案。理解了这个分裂，你就理解了为什么标准库的泛型 API 总是成对出现。

## 子主题七：泛型与 interface 的关系——什么时候该用谁

这是实践中最容易搞混的一节。先做个小测试，别急着看答案：

```go
// A
func PrintAll[T any](xs []T) { for _, x := range xs { fmt.Println(x) } }
// B
func PrintAll(xs []any)      { for _, x := range xs { fmt.Println(x) } }
```

**这两个函数，调用方式和运行行为有什么本质区别？如果调用方手里有一个 `[]int`，哪个能用？**

答案是：**B 根本吃不下 `[]int`。** `[]int` 和 `[]any` 是两个完全不同的类型，Go 不做协变转换，你得手动 O(n) 拷一份 `[]any`。而 A 直接吃 `[]int`、`[]string`、`[]Money`。

这一个例子就切开了两者的根本差异：**泛型是编译期的"同构"抽象，接口是运行期的"异构"抽象。**

### 7.1 同构 vs 异构

- **泛型（同构）：** `[]T` 里的元素**必须全是同一个 T**，编译器知道 T 是谁。函数体内可以做 `a < b`、`a + b` 这种需要"两边类型一致"的操作。
- **接口（异构）：** `[]Shape` 里可以放 Circle、Square、Triangle 混着来，**具体类型要到运行时才知道**，唯一能做的是调用接口声明过的方法（动态分派）。

所以判断准则其实很朴素，三条问句：

1. **你需要"多个值之间类型必须一致"吗？** 需要 → 泛型。（`Max(a, b T)` 里 a 和 b 必须同类型，用 `interface{}` 就得运行时检查）
2. **你需要"一个容器里装不同具体类型"吗？** 需要 → 接口。（插件、策略模式、异构事件流）
3. **你需要的只是"调用某个方法"吗？** 只是这样 → **接口就够了，别上泛型。**

第三条是最常被违反的。看这个反模式：

```go
// 反模式：用泛型做了接口能做的事
func Save[T interface{ Save() error }](v T) error { return v.Save() }

// 正解
func Save(v interface{ Save() error }) error { return v.Save() }
```

泛型版本**毫无收益**：你没有跨类型复用任何算法，只是把一次动态分派换成了……还是一次动态分派（走字典）。但代价呢？二进制多了一份实例化代码、编译变慢、错误信息变复杂。**这是纯亏。**

再进一步看这个"看似有收益"的版本：

```go
func SaveAll[T interface{ Save() error }](vs []T) error {
    for _, v := range vs { if err := v.Save(); err != nil { return err } }
    return nil
}
```

这个有收益吗？有一点点：`vs` 保证是同构切片，调用方不用构造 `[]interface{ Save() error }`。但如果调用方本来就要装异构对象呢？泛型版本反而逼他做不了。**所以判断的钥匙在调用方手里，不在实现方手里：你的调用方手里拿的是什么形状的容器？**

### 7.2 一个更尖锐的问题：泛型能替代接口做依赖倒置吗

不能，而且理由很硬。

依赖倒置（DIP）的核心是"高层模块不依赖低层模块的具体类型，运行时可以替换实现"。这需要**运行期的多态**——也就是说，我得能在**不知道具体类型的情况下**持有一个对象。泛型在编译期就把 T 钉死了，`Service[MySQLRepo]` 和 `Service[MemRepo]` 是两个不同的类型，你没法把它们放进同一个 `[]Service[?]`，也没法在配置文件里读一个字符串就决定 T 是啥。

一句话总结这个边界：

> **接口解决"我不知道这是什么"；泛型解决"我知道这是一类东西，但不确定是哪一种"。**

前者是运行时的不确定性，后者是编译期的不确定性。搞反了，代码就会长出奇怪的形状。

### 7.3 组合使用：真正的高手写法

真实项目里，两者是配合的，不是对立的：

```go
// 泛型负责"算法"，接口负责"可替换的行为"
func ProcessAll[T any](xs []T, h func(T) error) error {
    for _, x := range xs {
        if err := h(x); err != nil { return err }
    }
    return nil
}

// 调用方决定 h 是什么：可以是个接口方法，可以是闭包，可以是 mock
ProcessAll(orders, func(o Order) error { return repo.Save(o) })
```

再看一个更典型的：泛型容器 + 接口元素。

```go
type Queue[T any] struct { items []T }

var q Queue[io.Reader]   // 泛型提供"同构、类型安全、无反射"的容器
                         // 接口提供"运行时多态"的元素
```

`Queue[io.Reader]` 是 Go 泛型最舒服的用法之一：**容器逻辑（入队出队扩容）对元素类型一无所知，所以适合泛型；元素本身需要多态，所以适合接口。** 两层各司其职，没有任何一方被勉强。

## 子主题八：实现方式的取舍深入——单态化、装箱，与 Go 的混合账本

子主题二讲了"Go 卡在单态化和装箱之间"。这一节把这笔账算细：**为什么 Java 那套（擦除）Go 学不来？为什么 C++ 那套（全单态化）Go 也不敢学？混合方案到底省在哪、亏在哪？**

### 8.1 三种方案的完整对比

| 维度 | 全单态化（C++/Rust） | 装箱/字典（Java 擦除） | Go 的混合（部分单态化 + 字典） |
|---|---|---|---|
| 编译时间 | 最慢（每类型一份代码） | 最快（一份） | 中（按 shape 分组，份数少于全单态化） |
| 二进制体积 | 最大 | 最小 | 中 |
| 运行时性能 | 最快（零间接、可内联） | 最慢（装箱 + 动态分派） | 接近全单态化，走约束方法时有字典间接调用 |
| 值类型（int、struct） | 原生支持，无装箱 | 必须装箱（Java 的 Integer） | 原生支持 |
| 运行时类型信息 | 无（已消失） | Java 侧被擦除，需反射技巧 | 保留（通过字典/类型描述符） |
| 典型语言 | C++、Rust、Zig、Odin | Java（擦除） | Go、C#（思路相近） |

### 8.2 为什么 Go 不能走 Java 的擦除路线

一句话：**Go 有值类型，而且把值类型的性能当成命根子。**

Java 的擦除之所以能成立，是因为 `List<Integer>` 在运行时就是 `List<Object>`，元素被装箱成对象、塞进堆、通过引用访问。慢，但语义上"一切皆对象"是自洽的。

Go 呢？想象一下如果擦除：

- `[]int` 变成 `[]interface{}`？**内存布局直接崩了。** `[]int` 是 8 字节一个元素紧密排列、缓存友好、零 GC 扫描；`[]interface{}` 是 16 字节的接口头（类型指针 + 数据指针），且指向堆上装箱后的 int。数组从 80MB 变成 160MB + 一千万个堆对象，GC 压力爆炸。
- 更致命的是**语义**：Go 里 `type Celsius float64` 这种自定义值类型、结构体嵌套、`sync.Mutex` 不能拷贝……全都建立在"值就是那块内存"的前提上。擦除会摧毁这个前提。

所以**擦除在 Go 里根本不是一个选项**，它是 Java 特定历史包袱（兼容 1.4 之前的字节码）下的产物，不是通用最佳实践。

### 8.3 为什么 Go 也不走全单态化

那全单态化呢？性能最优，C++/Rust 都验证过。Go 不干，理由也很硬：

**理由一：编译速度是 Go 的核心卖点。** Go 从诞生起就在跟 C++ 的编译时间对着干（还记得 Rob Pike 那句"Go 的编译速度应该让人感觉不到等待"吗）。全单态化意味着一个被广泛使用的泛型函数会在几十个包里各生成一份，编译时间随使用面线性甚至超线性增长。**在百万行级的 monorepo 里，这是灾难。**

**理由二：二进制体积。** Go 的二进制本来就"胖"（自带运行时 + 调度器 + GC + 所有依赖静态链接）。全单态化再叠一层代码复制，对容器镜像、Lambda 冷启动、移动端分发都是实打实的成本。

**理由三：代码爆炸的恶性循环。** 泛型函数调用泛型函数（比如泛型 Map 里调泛型 Filter），全单态化下组合数会乘起来。这个"实例化爆炸"在 Rust 里是真实存在的问题（社区用 `Box<dyn Trait>` 手动降爆），Go 想从根上避免。

### 8.4 混合方案：按 shape 分组 + 字典传递

Go 的方案（社区常称 GC shape stenciling），**概念上**分两步：

**第一步：按"GC shape"分组做单态化。**

所谓 GC shape，直觉理解就是**"这个类型在内存里长什么样、GC 该怎么扫它"**。具体点说：类型的大小、对齐、以及**哪些字（word）里装的是指针**。

- `*int`、`*string`、`*os.File`、`func()` —— 都是"一个指针"，shape 相同 → **共用一份代码**
- `int`、`int64`、`float64`、`uintptr` —— 都是"一个非指针的字"，shape 相同 → **共用一份**
- `string`（两字：指针 + 长度）、`[]int`（三字：指针 + 长度 + 容量）、`complex128`、`struct{a, b int}` —— 各自是一个 shape

于是 `Stack[*User]`、`Stack[*Order]`、`Stack[*Item]` 只生成**一份**机器码，而不是三份。**所有指针类型塌缩成一份，这是最大的一处节省**——而 Go 程序里泛型容器装指针的场景又特别多。

**第二步：把"shape 不知道的事"装进字典传进去。**

同一份机器码要服务 `*User` 和 `*Order`，总会碰到一些"因类型而异"的信息：这个类型的类型描述符（`_type`）、约束里声明的方法到底在哪（方法指针表）、需要比较/哈希时对应的函数、make new 一个对象时该用哪个 GC 位图。**这些被打包成一个运行时结构（字典），在调用点作为参数传入**（概念上你就当它是个隐藏的额外参数）。

> 打个比方：shape 分组是"按体型发同一版型的衣服"，字典就是"别在胸口的工牌"——版型不知道你是谁，但工牌上写着你的名字、你的权限、遇到紧急情况该打给谁。

**什么时候走字典会有开销？** 关键判断：

- **纯值操作**（赋值、比较基础类型、算术、切片索引）：shape 相同则指令相同，**没有字典开销**，性能和手写专用代码基本一致。
- **通过约束调用方法**（`func F[T Stringer](x T) { x.String() }`）：要**先从字典里取出方法指针再间接调用**。这是一次运行时间接跳转，无法内联、无法静态绑定，和接口方法调用一个量级。

**这就是为什么"约束里带方法"的泛型函数，性能上并不比"直接传接口"强多少**——两者都是间接调用。泛型的性能红利，主要在**值类型的容器与算法（避免装箱、避免反射）**，而不在"带方法的约束"。这个结论很重要，很多性能预期错误都源于没想明白这一点。

### 8.5 混合方案的代价：省了什么，亏了什么

诚实地说，混合方案不是白嫖：

**省下的：** 相比全单态化，实例化份数大幅下降（尤其指针类型），二进制体积和编译时间显著改善；相比纯装箱，值类型无需装箱，性能保住了。

**亏掉的：**
- **编译仍然变慢了。** 类型检查要做两遍（定义侧 + 实例化侧）、字典要生成、实例化结果要跨包传递和去重。**这是社区抱怨最集中点：用了泛型的大型项目，构建时间肉眼可见地变长。**
- **二进制仍然变大了。** 每个 shape 一份代码，一个被广泛使用的泛型库仍会贡献可观的体积。
- **字典间接调用挡住了内联和优化。** 走字典的方法调用，编译器无法静态知道目标函数，内联、常量传播、逃逸分析都会退化。
- **调试体验下降。** 栈回溯里出现的是实例化后的符号，断点调试时"一份源码对应多份代码"的心智负担是真的。

一句话总结这一节：**Go 用"一部分编译时间和体积"，换来了"值类型不装箱 + 类型安全 + 写法自然"。这是一笔划算的交易，但它确实有账单。**

## 子主题九：性能代价的实测视角——怎么测、测出什么、值不值

理论讲完，来点工程味儿：**你该怎么在自己的项目里量化泛型的代价？** 别信网上那些"泛型快 3 倍"或"泛型慢 50%"的截图，那些基准几乎都测错了对象。

### 9.1 一个正确的对比实验设计

假设你要评估"求和函数要不要泛型化"，正确的做法是**三组对照**，而不是两组：

```go
// A：手写专用版（性能上界）
func SumInt(xs []int) int { s := 0; for _, x := range xs { s += x }; return s }

// B：泛型版
func Sum[T ~int | ~int64 | ~float64](xs []T) T {
    var s T
    for _, x := range xs { s += x }
    return s
}

// C：接口 + 反射版（老办法，性能下界）
func SumAny(xs any) int { /* reflect.ValueOf ... */ }
```

对照矩阵应该是 **A vs B**（回答"泛型相对手写亏多少"）和 **B vs C**（回答"泛型相对老办法赚多少"）。**只测 B vs A 会得出"泛型没用"的错误结论，只测 B vs C 会得出"泛型神速"的错误结论。** 两个都测才有意义。

一般性的定性结论（**具体数字请在你自己的机器和业务数据上测**）：

- **A vs B：在纯算术/遍历这类场景，差距通常很小。** 因为两边都被单态化成了专用代码，都可能被内联，指令几乎一样。如果你测出巨大差距，先怀疑你的基准写错了（比如忘了 `b.ReportAllocs()`、忘了存回结果导致被优化掉、切片太小测的是循环开销）。
- **B vs C：差距通常是数量级的。** 反射版的开销在类型检查、`reflect.Value` 装箱、接口方法调用上，几十到上百纳秒一次；泛型版接近裸循环。**泛型的收益主要在这里——消灭反射，而不是超越手写。**
- **带约束方法的泛型（如 `[T Stringer]`）vs 直接传接口：差距很小，甚至可能更慢**（多一层字典间接）。

### 9.2 三个容易被忽略的性能细节

**细节一：内联。** 现代 Go 编译器对泛型函数的内联支持在持续改进，但**走字典的方法调用是无法内联的**。所以一个经验法则：

> **泛型函数体越小、越少通过约束调方法，越容易被内联，性能越接近手写；反之，泛型函数体膨胀，就变成了"每个 shape 一份还没被内联的大函数"，体积和性能双输。**

这也解释了为什么标准库的 `slices` 包里那些函数普遍短小——**泛型函数天然应该保持短小**，这既是可读性要求，也是性能要求。

**细节二：逃逸与分配。** 泛型本身不引入额外堆分配（这是它相对 `interface{}` 的巨大优势），但要注意两个陷阱：

```go
func Bad[T any](v T) any { return v }     // 装箱！T 逃逸到堆
func Good[T any](v T) T   { return v }    // 零分配
```

**只要你的泛型函数返回 `any`、或把 `T` 塞进接口/`[]any`，装箱就回来了。** 泛型省下的分配，能被一行 `any` 全还回去。

**细节三：二进制体积怎么测。** 别靠感觉，直接测：

```bash
go build -o a-generic ./cmd/app && ls -l a-generic
# 然后把泛型实现换成 interface{} 实现，再编一次，比大小
go tool nm a-generic | grep 'yourpkg\.' | wc -l   # 看看多出多少实例化符号
```

更实用的观察点：**用 `go tool nm` 或直接看符号表，数一数你的泛型类型被实例化了多少个 shape。** 如果你看到几十个 shape 实例，就该考虑"是不是该收敛成非泛型实现 + 少量手写重复"了。

### 9.3 什么时候这笔账值得算

给你一张决策清单，**按顺序问自己**：

1. **这个逻辑会被几种类型用到？** 只有一种 → **别用泛型**，写具体类型。两种以上 → 继续问。
2. **不用泛型的替代方案是什么？** 如果是"复制粘贴三份"→ 泛型赢（维护成本）。如果是"interface{} + 反射"→ 泛型大概率赢（性能 + 安全）。如果是"一个接口就能解决"→ **接口赢**，别上泛型。
3. **它在热路径上吗？** 是 → 必须 benchmark，关注内联和字典调用。不是（配置解析、初始化、管理接口）→ 泛型的可读性收益优先，性能无所谓。
4. **调用频率高吗？** 每秒百万次的小函数 → 泛型化后注意函数体大小，别让内联失效。
5. **团队能读懂约束吗？** 这条最现实：**如果你的约束写得比实现还长，而团队里没几个人能一眼读懂，那它的维护成本可能已经超过收益了。**

### 9.4 一句大实话

关于"泛型值不值"，最诚实的版本是：

> **泛型的主要收益是"消灭复制粘贴"和"消灭 interface{}+反射"，而不是"让代码跑得更快"。** 如果你的代码里没有这两个痛点，泛型大概率给你带来的是编译变慢、二进制变大、可读性下降——纯亏。

把这句话记牢，你就不会成为那种"为了用泛型而用泛型"的人。

## 子主题十：泛型的适用边界与 Go 的硬限制清单

知道了怎么权衡，还需要一份"禁区地图"。Go 1.18 的泛型是**刻意砍过一刀**的，那些"不支持"的地方，你要提前知道，否则会在设计阶段撞墙。

### 10.1 适合用泛型的四类场景（甜区）

1. **算法：** 排序、查找、最值、去重、归约、集合运算。`slices`、`cmp` 就是样板。特征是**"逻辑与具体类型无关，只依赖少数几个操作"**。
2. **容器/数据结构：** 栈、队列、堆、链表、Set、LRU Cache、跳表、泛型树。特征是**"容器对元素一无所知"**。
3. **消除 interface{}+反射的胶水层：** 以前用 `interface{}` + `reflect` 写的通用工具（比如通用去重、深拷贝、校验框架），泛型化后编译期安全且快很多。
4. **类型安全的"空壳"包装：** `Result[T]`、`Optional[T]`、`Future[T]`、`Event[T]`。这类东西在别的语言里是标配，Go 里以前只能用 `interface{}` 硬扛，泛型让它们终于有了类型安全的写法。

一个实战例子，泛型 Set：

```go
type Set[T comparable] struct { m map[T]struct{} }

func NewSet[T comparable](vs ...T) Set[T] {
    s := Set[T]{m: make(map[T]struct{}, len(vs))}
    for _, v := range vs { s.m[v] = struct{}{} }
    return s
}
func (s Set[T]) Add(v T)      { s.m[v] = struct{}{} }
func (s Set[T]) Has(v T) bool { _, ok := s.m[v]; return ok }
func (s Set[T]) Len() int     { return len(s.m) }
```

注意 `struct{}` 做 value（零内存开销），注意 `comparable` 而非 `any`（map key 要求），注意 `~` 不出现在约束里（Set 不需要接纳底层类型）。**这几处都是约束设计的分寸感。**

### 10.2 不适合用泛型的六类场景（雷区）

1. **只有一种实例化类型。** 写了泛型但只用过 `Foo[int]` → 你只是给自己加了编译负担。
2. **纯粹的行为抽象。** 只有一个方法要调 → 用接口（回顾子主题七）。
3. **需要运行时决定类型。** 配置里读一个字符串决定用哪种实现 → 接口 + 工厂，泛型在编译期就钉死了。
4. **需要异构集合。** `[]Shape` 混装 → 接口。
5. **需要反射能力的场景。** 序列化/ORM 这类要读 struct tag、遍历字段的地方，泛型帮不上忙（**Go 的泛型不能替代反射去"看穿"结构体字段**），反而可能让代码更绕。有人用泛型 + 反射混着写，结果拿到了两者的缺点。
6. **约束写得比实现复杂。** 如果你写了十几行 `interface{~[]E | ~map[K]V, ...}` 只为了省三行代码，**这笔买卖亏了。** 复杂度守恒：省在实现，必然加到约束上。

### 10.3 Go 泛型的硬限制清单（1.18 至今）

这些不是"还没实现"，大部分是**设计上的明确拒绝**：

| 限制 | 表现 | 为什么 |
|---|---|---|
| **不支持泛型方法** | `func (s Stack[T]) Map[U any]() Stack[U]` 非法 | 方法要进方法集/itable，带类型参数的方法会让方法集无限膨胀，且接口无法表达 |
| **不支持变长类型参数** | 没有 `Foo[T...]` | 复杂度爆炸（C++ 可变模板是重灾区） |
| **不支持特化（specialization）** | 不能为 `Foo[int]` 单独写一个更快的实现 | 特化是 C++ 复杂度的主要来源之一，Go 明确拒绝 |
| **不支持运算符重载** | `Money` 无法接入 `<` | 见 6.6：这正是类型集存在的理由 |
| **不支持部分指定类型参数** | 要么全写，要么全推断 | 见 5.3 |
| **类型参数不能作为方法的接收者类型独立存在** | 只能依附在泛型类型的接收者上 | 同"不支持泛型方法" |
| **包含类型元素的接口不能当普通类型用** | `var x interface{~int}` 非法 | interface 语义分裂的疤痕 |
| **不支持协变/逆变** | `[]Dog` 不是 `[]Animal` | Go 坚持容器不协变，避免类型系统复杂化 |

**怎么绕开"不支持泛型方法"？** 标准答案：写成**包级泛型函数，把接收者当第一个参数**。

```go
// 想要 s.Map[U](f) 但做不到 → 改成
func MapStack[T, U any](s Stack[T], f func(T) U) Stack[U] { ... }
```

丑一点，但可行。**当你发现自己在为"泛型方法"绞尽脑汁时，通常的信号是：这个设计该用普通函数组合了，而不是该用泛型方法。**

另一个值得知道的变化：**Go 1.24 起支持泛型类型别名**（`type Alias[T any] = Other[T]`），这让一些泛型重构（比如把一个泛型类型从一个包迁移到另一个包并保持兼容）终于有了干净写法。

## 子主题十一：标准库的泛型化——`cmp`、`slices`、`maps`

Go 1.18 发泛型，但标准库**一个泛型函数都没加**。为什么？**因为没人知道正确的 API 形状长什么样。** 团队选择把 `constraints`、`slices`、`maps` 先放进 `golang.org/x/exp` 里接受社区蹂躏，等形态稳定了再进标准库。**这个"先实验库、后标准库"的流程本身就是一条工程方法论：新语法的配套 API，比语法本身更需要时间去沉淀。**

Go 1.21，`slices`、`maps`、`cmp` 三个包正式进入标准库，`cmp.Ordered` 取代了 `constraints.Ordered`。

### 11.1 `cmp`：三个函数 + 一个约束

```go
type Ordered interface { /* 就是 6.6 那一长串 */ }

func Compare[T Ordered](x, y T) int  // x<y → -1, x==y → 0, x>y → +1
func Less[T Ordered](x, y T) bool
func Or[T comparable](vals ...T) T   // 返回第一个非零值，全零返回零值
```

`cmp.Compare` 是**三路比较**的官方约定（返回 -1/0/+1），你写自己的 `CompareFunc` 时应该遵守这个约定，这样就能无缝对接 `slices.SortFunc`、`slices.BinarySearchFunc`、`slices.CompareFunc`。**标准库的泛型 API 是通过"函数约定"而非"接口实现"串联起来的**——回看 6.6，这正是 Go 没有运算符重载的必然结果。

`cmp.Or` 看着不起眼，实际很实用：`timeout := cmp.Or(cfg.Timeout, defaultTimeout)` 一行替代 if 链。

### 11.2 `slices`：泛型能力的主战场

```go
// 排序（基于类型集，最快）
slices.Sort(xs)                             // [S ~[]E, E cmp.Ordered]
slices.SortFunc(xs, func(a, b T) int {...}) // 自定义比较
slices.SortStableFunc(xs, cmp)
slices.IsSorted(xs) / slices.IsSortedFunc(xs, cmp)

// 查找
slices.Contains(xs, v)                      // 需要 comparable
slices.Index(xs, v) / slices.IndexFunc(xs, func(T) bool)
slices.BinarySearch(xs, v)                  // 有序切片，返回 (idx, found)
slices.BinarySearchFunc(xs, v, cmp)

// 变换
slices.Clone(xs) / slices.Compact(xs) / slices.Concat(xs, ys...)
slices.Delete(xs, i, j) / slices.Insert(xs, i, vs...)
slices.Reverse(xs) / slices.Grow(xs, n) / slices.Clip(xs)
slices.Replace(xs, i, j, vs...)
slices.Equal(xs, ys) / slices.EqualFunc(xs, ys, eq)
slices.Min(xs) / slices.Max(xs) / slices.MinFunc / slices.MaxFunc
```

**注意 `slices.Delete` 的签名陷阱**：它返回新切片（`s = slices.Delete(s, i, j)`），但它**不会**帮你把尾部元素置零——被删掉的位置仍持有原值的引用，可能拖住不该存活的对象（内存泄漏的经典来源）。这类"泛型 API 不管生命周期"的细节，是精通的标志。

`Compact` 只去重**相邻**重复元素（所以要先 `Sort`），这是 API 设计上的诚实取舍：不假装帮你做全量去重（那需要 `comparable` 且要建临时 map）。

### 11.3 `maps`

```go
maps.Clone(m) / maps.Copy(dst, src)
maps.Equal(m1, m2) / maps.EqualFunc(m1, m2, eq)
maps.DeleteFunc(m, func(K, V) bool)
```

就这四个（早期版本）。**少得让人意外对不对？** 这正是克制的体现：map 的绝大多数操作用内建语法（`delete`、索引、range）就够了，泛型包只补"语言没提供的那几个"。

**Go 1.23 起**，`maps.Keys`/`maps.Values` 随 range-over-func 迭代器加入，返回的是 `iter.Seq[K]` / `iter.Seq[V]`（**不是切片**），配合 `slices.Collect` 使用：

```go
keys := slices.Sorted(maps.Keys(m))   // 拿到排序后的 key 切片
for k, v := range m { ... }           // 普通遍历还是直接 range 最清晰
```

注意 `x/exp/maps` 里的老 `Keys` 返回切片，标准库版返回迭代器——**从实验库迁移到标准库时 API 变了**，这是"先实验"策略必须付的学费。

### 11.4 写自己的泛型工具时，怎么与标准库对齐

三条实操建议：

1. **比较函数一律用 `func(a, b T) int`（三路），不要用 `func(a, b T) bool`（less-than）。** 前者能直接喂给 `slices.SortFunc`/`BinarySearchFunc`。
2. **容器约束优先用 `~[]E` 而不是 `[]E`**，让用户的自定义切片类型能用。
3. **能返回同类型就返回同类型**（`Map[S ~[]E, E any](s S, f func(E) E) S`），别返回 `[]any`——类型信息一旦丢给用户，用户就得写断言，你等于白泛型化了。

一个对齐标准库风格的例子：

```go
// 按 key 分组，风格对齐 slices/maps
func GroupBy[S ~[]E, E any, K comparable](s S, key func(E) K) map[K][]E {
    m := make(map[K][]E, len(s))
    for _, v := range s {
        k := key(v)
        m[k] = append(m[k], v)
    }
    return m
}
```

三个类型参数，调用时**一个都不用手写**（`S` 从实参推，`E` 用约束类型推断从 `S` 推，`K` 从 `key` 函数的返回值推）。**这就是"好的泛型 API"的手感：调用点看不到类型参数。**

## 业界对照

**C++ 模板：** 编译期单态化，最强大、也最复杂。模板元编程图灵完备，能编译期算一切，但报错是"一屏幕的天书"，编译极慢。C++ 的泛型是"能力无上限、心智无下限"的极端。

**Rust 泛型 + trait：** 默认单态化（`Monomorphization`），配合 trait 约束，编译期检查极强。Rust 的泛型性能好、类型安全强，代价是编译慢、以及 trait 系统的学习成本。

**Java 泛型（类型擦除）：** 运行时类型擦除，泛型只是编译期糖。好处是兼容旧字节码，坏处是运行时拿不到泛型类型信息（不能 `new T()`）、装箱拆箱开销（基本类型）。Java 泛型是"向后兼容"优先的产物。

**C# 泛型（reified）：** 运行时保留类型信息（reification），且对值类型做单态化、对引用类型装箱，是"性能"和"灵活"的混合。C# 泛型被普遍认为是"泛型实现得最舒服"的语言之一。

Go 的泛型，可以说是"在 C++/Rust 的单态化性能，和 Java 的简单之间，找了一条折中的路"——为此付出了编译时间和二进制体积的代价，换来了比 interface{} 更安全的类型检查和更自然的写法。

## 子主题十二：业界对照再深入——四种泛型实现的横切面比较

上面那张速写还不够。我们用一个**更狠的视角**重看一遍：不是"它们各自怎么实现泛型"，而是——**"当泛型遇上这四个具体的难题，每门语言分别怎么回应？"** 难题才是照妖镜。

**难题一：值类型（int / 自定义 struct）能不能不装箱地进泛型容器？**

- **C++：** 能。`vector<int>` 就是裸 int 数组，零装箱，零额外内存。这是 C++ 性能神话的基石，也是它必须把模板定义全塞进头文件的原因（每个实例化点都要看见完整定义）。
- **Rust：** 能。`Vec<i32>` 同理，单态化到专用代码。Rust 甚至更进一步：零大小类型（ZST）在容器里完全不占空间。
- **Java：** **不能。** `List<Integer>` 里装的是装箱后的对象，这是 Java 泛型最著名的性能伤疤。Valhalla 项目（value types + 泛型特化）折腾了十几年，就是想修这个。
- **C#：** **能。** `List<int>` 会被 JIT 单态化出专用代码，不装箱。引用类型则共享一份代码（反正都是引用，shape 相同——**看到了吗，这和 Go 的 shape 分组是同一个思路**）。
- **Go：** **能。** 这是 Go 拒绝擦除的根本原因（回顾 8.2）。

**难题二：泛型代码里能"看穿"类型吗？运行时还有类型信息吗？**

- **Java：** 擦除了。`new T()` 做不到（只有 `T.class` 传进来的技巧）；`instanceof T` 不行；`T[]` 数组创建要绕。社区因此发明了 **TypeToken 模式**（`new TypeToken<List<Foo>>(){}` 靠匿名子类把泛型信息留在字节码里），Gson/Jackson 全靠它——**一个编译期缺陷，长出了一整个生态的补丁。**
- **C#：** **reified（具体化）**，类型信息在运行时完整保留。`typeof(T)`、`new T()`、`T is SomeType` 全都能写，反射能拿到泛型实参。这是 C# 泛型被公认为"最舒服"的核心原因。
- **C++：** 信息在编译期全在（这就是模板元编程能做的事），运行时什么都不剩——但 C++ 本来也不太在乎运行时信息。
- **Rust：** 编译期全在（`T::some_assoc_type`），运行时通过 `TypeId`（需 `'static` 约束）能拿到有限的类型身份。
- **Go：** 运行时**保留了类型信息**（通过字典里的类型描述符），所以泛型函数里可以 `any(v).(SomeType)`、可以用 `reflect.TypeOf`。**这是 Go 相对 C++/Rust/Java 的一处隐性优势**：你不会因为泛型化而失去反射和类型断言的能力。

**难题三：约束/契约怎么表达？**

- **C++：** 历史上靠 **SFINAE + `enable_if`** 这种"模板技巧的副产品"表达约束，报错信息是几屏天书；**C++20 引入 Concepts**（`template<Ordered T>`），才有了正经的约束语法和像样的报错。C++ 用了整整一代人的时间才补上这一课——**这就是"没有约束的泛型"的真实代价。**
- **Rust：** **trait bound**（`T: Ord + Clone`），约束是类型系统的核心，且是"结构化"的（你为自己的类型 impl 一个 trait 即可接入）。配合关联类型和 where 子句，表达力极强。代价：**orphan rule（孤儿规则）**——你不能给别人的类型 impl 别人的 trait，这套一致性规则本身就是学习成本。
- **Java：** 类型边界（`<T extends Comparable<T>>`），形式简单，但受限于擦除。
- **C#：** 约束（`where T : IComparable, new()`），可能是最直白的写法，还额外支持 `new()`、`class`、`struct` 这些"非类型"约束。
- **Go：** **类型集接口。** 表达力刻意受限：能列举类型（`~int | ~string`）、能要求方法（`fmt.Stringer`）、能求交集，但**不能表达"关联类型"、不能表达"这个类型有某个运算符"**。

这里有个值得品味的对照：**Rust 的 trait 是"开放"的（任何人能为自己的类型 impl Ord，让它接入所有排序函数）；Go 的类型集是"封闭"的（`<` 只能用于规范里枚举的那些内建类型）。** 开放带来表达力，封闭带来可预测性。Go 又一次选了后者——**代价是 6.6 讲的那个分裂：`slices.Sort` 和 `slices.SortFunc` 必须成对出现。**

**难题四：编译时间。**

这是所有单态化语言的共同诅咒：

- **C++：** 最严重。模板定义必须在头文件里，每个翻译单元独立实例化，再由链接器去重。一个重度模板化的项目，编译几十分钟是常事。
- **Rust：** 也严重。单态化 + trait 求解 + borrowck，编译慢是 Rust 最大的抱怨点。社区的缓解手段是**手动降爆**：把部分泛型函数改成 `&dyn Trait`（动态分派）来换取编译速度——**"用运行时开销换编译时间"，这是单态化路线绕不开的交易。**
- **Java/C#：** 几乎不受影响（一份代码 / JIT 负责）。
- **Go：** 受影响，但因为按 shape 分组，比 C++/Rust 轻。**Go 的混合方案，本质上就是"用一点点运行时字典开销，买回一大块编译时间和二进制体积"**——和 Rust 社区手动做的降爆，是同一笔交易，只是 Go 把它做进了编译器。

### 横切面总表

| | C++ 模板 | Rust 泛型 | Java 泛型 | C# 泛型 | **Go 泛型** |
|---|---|---|---|---|---|
| 实现 | 全单态化 | 全单态化 | 类型擦除 | 混合（值类型单态化） | **混合（shape 分组 + 字典）** |
| 值类型装箱 | 否 | 否 | **是** | 否 | 否 |
| 运行时类型信息 | 无 | 有限 | **被擦除** | 完整（reified） | 保留 |
| 约束机制 | Concepts（C++20） | trait bound | extends 边界 | where 约束 | **类型集接口** |
| 约束是否开放 | 开放 | 开放 | 开放 | 开放 | **封闭（基于类型集枚举）** |
| 编译时间影响 | 极大 | 大 | 小 | 小 | 中 |
| 元编程能力 | **图灵完备** | 宏（另一套） | 无 | 有限 | **无（刻意）** |
| 错误信息可读性 | 差（Concepts 后改善） | 好 | 好 | 好 | 中（两遍检查的红利） |

### 最后一句对照

Go 在这个坐标系里的位置很清晰：

> **它要的是"能写类型安全的容器和算法"，不要的是"能写编译期程序"。**

C++ 模板元编程可以在编译期算斐波那契数列、可以在编译期做单位检查、可以搞出表达式模板——这些 Go 一概不要。**Go 的泛型是一把螺丝刀，不是一台机床。** 螺丝刀不能铣零件，但它不会在你手里变成一堆啃不动的错误信息。

判断这个取舍好不好，取决于你要造什么：造飞机发动机（高频交易引擎、游戏引擎、数值库），你会想念 C++ / Rust 的表达力；造微服务、中间件、业务系统（Go 的主场），你会发现 Go 这把螺丝刀**刚刚好**——而那台机床，你根本不需要。

## 版本演进小结

- 2009~2017：泛型被反复提案、反复否决。核心是"没有方案能同时满足编译快 + 运行快 + 保持简单"。
- 2018~2020：Ian Lance Taylor 的"类型参数 + 约束"设计逐渐成熟，社区草案（generics draft）发布，广泛讨论。
- 2022 Go 1.18：泛型正式落地（类型参数、约束、`any`、`comparable`、`~`）。
- 2023 Go 1.20/1.21：`slices`、`maps`、`cmp` 从 `golang.org/x/exp` 转正进标准库；`cmp.Ordered` 取代 `constraints.Ordered`；类型推断增强（泛型函数赋值给函数类型变量时可推断）；`min`/`max` 内建函数加入。
- 2023 Go 1.23：`iter` 包 + range-over-func，标准库迭代器化（`slices.Values`/`All`、`maps.Keys`/`Values` 返回 `iter.Seq`）。
- 2024/2025：泛型类型别名（Go 1.24，`type A[T any] = B[T]`）等收尾补强，编译器侧持续优化泛型的实例化与编译开销。

主线：**Go 泛型十三年的拖延，本质是一场"价值观 vs 需求"的拉锯——需求是真实的，但 Go 团队宁可迟到，也不愿意用一个"毁掉简单性"的方案。最终落地的是"克制的泛型"：能力被刻意砍掉一部分，换来了与 Go 整体气质的一致。** 这一课的价值，远超泛型本身：**一个优秀的设计决策，往往不是"做更多"，而是"为了不破坏核心价值，敢于拒绝、敢于等待"。**

## 本章思考题

【思考题】

1. Go 泛型拖延十三年，最根本的原因是什么？"不是做不出来"这句话怎么理解？

2. 单态化和装箱两种泛型实现，各自的优缺点是什么？Go 为什么选了折中方案？

3. 泛型里 interface 的角色发生了什么变化？`interface{ int | string }` 和传统"方法集"接口的本质区别是什么？

4. 泛型落地带来了哪些代价？在什么场景下"宁可不用泛型"？

5. 调用 `Map(xs, f)`（签名 `func Map[S ~[]E, E any](s S, f func(E) E) S`，其中 `xs` 是 `[]int`）时，编译器是如何把 `S` 和 `E` 都推断出来的？这种推断叫什么，它的关键价值是什么？

6. `~int` 和 `int` 当约束的区别是什么？`cmp.Ordered` 为什么必须写成 `~int | ~int8 | ...` 这样一长串枚举，而不能像 Rust 那样写一个 `Ord` trait？

7. `any` 和 `comparable` 都长得像接口，它们的类型集分别是什么？为什么 `map[any]int` 能编译，但 `func F[K comparable, V any](m map[K]V)` 传 `map[any]int` 却不行？

8. 下面两个函数，哪个该用泛型、哪个该用接口？为什么另一个是反模式？
   ```go
   func Save[T interface{ Save() error }](v T) error { return v.Save() }
   func Save(v interface{ Save() error }) error     { return v.Save() }
   ```

9. Java 的类型擦除为什么在 Go 里根本不可行？请从内存布局和语义两个层面说明。

10. Go 的"部分单态化 + 字典传递"混合方案，按什么分组生成代码？什么情况下走字典会有运行时开销，什么情况下几乎没有？

11. 有人说"泛型能让代码跑得更快"，这句话对吗？请设计一个正确的对比实验，并给出你预期的定性结论。

12. Go 1.18 刻意不支持哪些泛型能力（至少列出四项）？其中"不支持泛型方法"会带来什么设计上的后果，通常怎么绕开？

【参考答案】

1. 根本原因是价值观：泛型要在"编译快、运行快、保持简单"三条立身之本之间做取舍，而单态化（运行快但编译慢）、装箱（编译快但运行慢）都只能满足一半。Go 的作者们正是泛型理论的重镇（Griesemer、Pike），他们太懂泛型会带来什么复杂度（C++ 模板的报错地狱前车之鉴），所以迟迟不肯用一个"毁掉简单性"的方案。是"价值观上的不肯妥协"，不是"技术上的做不出来"。

2. 单态化：为每种类型生成专门代码，运行快、零间接调用，但编译慢、二进制膨胀（代码爆炸）。装箱/字典传递：只编译一份，运行时传类型字典，编译快、二进制小，但运行有间接调用、慢。Go 选了"部分单态化 + 字典传递"的混合（GC shape stenciling），试图兼得，但代价仍是编译变慢、二进制变大。

3. interface 从"方法集"扩展成了"类型集合"。`interface{ int | string }` 表示"int 或 string 的集合"，本质是一组类型的集合，不再关心"实现了哪些方法"。它沿用了 interface 的"结构化匹配"思想——泛型实例化时，类型参数要匹配约束的类型集合。这是一次语义的自然延伸，但也让 interface 更复杂了。

4. 代价：编译变慢、二进制变大（单态化代码膨胀）、interface 语义更复杂（类型集合、~、any 等新概念）。"宁可不用泛型"的场景：只是把两种类型硬凑一起（用 interface{} 更简单）、为了炫技到处套泛型、约束写得比实现还复杂的地方。社区共识是泛型用在"确实需要跨类型复用算法/容器"（sort、容器、缓存）处，而不是到处滥用。

5. 两步：先做**函数实参推断**（unification），从 `xs` 的类型 `[]int` 匹配形参 `S`，得 `S = []int`；此时 `E` 未知，再做**约束类型推断**——已知 `S = []int`，`S` 的约束是 `~[]E`，把 `[]int` 与 `~[]E` 做结构对齐，推出 `E = int`。它的关键价值是：**返回值能保持调用方的具体类型**（`[]int` 而不是 `[]any`），而且让调用点一个类型参数都不用手写——这是"泛型 API 手感"的分水岭。没有它，`Map` 每次都要写成 `Map[[]int, int](xs, f)`，丑到没人愿意用。

6. `int` 只包含 `int` 本身；`~int` 包含**底层类型为 int 的所有类型**，包括 `type UserID int` 这类自定义类型。为什么不能写 `Ord` trait：因为 **Go 没有运算符重载，也拒绝引入**，`a < b` 永远是一条内建指令。泛型函数体内的 `<` 要合法，只能靠**编译期枚举所有支持 `<` 的类型**，也就是显式列出类型集。后果是**约束封闭**：自定义类型（如 `type Money struct{ cents int64 }`）永远无法接入 `<`，只能改用 `slices.SortFunc` 传比较函数——这就是 `Sort`/`SortFunc` 必须成对出现的原因。（对照 Rust/C++：操作合法性来自"trait/方法实现"，Go 里来自"类型集枚举"。）

7. `any` 是 `interface{}` 的**别名**（不是新类型），类型集是**所有类型**；`comparable` 是预声明标识符（不是关键字，可被遮蔽），类型集是**所有严格可比较类型**（`==`/`!=` 保证不 panic）。`map[any]int` 能编译，因为 map 的 key 要求的是宽松的"可比较"，允许接口类型，代价是把 panic 留到运行时（你往 `any` 里塞一个 `[]int` 再比较就炸）。而 `comparable` 排除了这类"比较可能炸"的类型，所以 `any` **不满足** `comparable`，传给 `[K comparable]` 就是编译错误。另外注意：`comparable` 及任何含类型元素（联合/`~`）的接口**都不能当普通变量的类型用**，只能当约束。

8. 第二个（接口版）是对的，第一个是反模式。理由：泛型版本没有跨类型复用任何算法，函数体只做了一次 `v.Save()` 调用——这是**动态分派**，走字典间接调用，和接口版是同一个量级，性能上没有半点收益；却额外付出了"多一份实例化代码 + 编译变慢 + 约束语法更复杂 + 错误信息更难读"的代价，纯亏。判断准则：**泛型是编译期的"同构"抽象（多个值类型必须一致），接口是运行期的"异构"抽象（具体类型运行时才知道）。只调一个方法 → 接口；需要多个值之间类型一致、或需要避免装箱 → 泛型。** 补充：如果签名是 `SaveAll[T interface{ Save() error }](vs []T)`，则有一点收益（保证同构切片、调用方不用构造 `[]interface{ Save() error }`），前提是调用方本来就持有同构切片。

9. 内存布局层面：`[]int` 是 8 字节一个元素紧密排列、缓存友好、GC 完全不用扫描；擦除后变成 `[]interface{}`，每个元素是 16 字节的接口头（类型指针 + 数据指针）且指向堆上装箱对象，体积翻倍、缓存失效、GC 压力爆炸。语义层面：Go 的类型系统建立在"值就是那块内存"之上——`type Celsius float64` 这类自定义值类型、结构体嵌套、`sync.Mutex` 不可拷贝等语义，全部依赖值的内存表示；擦除要求"一切皆对象"，会摧毁这个前提。结论：**擦除从来不是通用最佳实践，它是 Java 为兼容 1.4 之前字节码而背的历史包袱；Go 有值类型且把值类型性能当命根子，擦除在 Go 里根本不是一个选项。**

10. 按 **GC shape** 分组——直觉理解是"类型在内存里长什么样、GC 怎么扫它"（大小、对齐、哪些字是指针）。`*int`/`*string`/`*os.File` 都是"一个指针"，共用一份代码；`int`/`int64`/`float64` 都是"一个非指针的字"，共用一份。**shape 不知道的事**（类型描述符、约束方法的实现地址、比较/哈希函数等）被打包成**字典**在调用时传入（概念上就当它是个隐藏的额外参数）。开销判断：**纯值操作**（赋值、基础类型比较、算术、切片索引）在 shape 相同时指令完全一致，**几乎没有字典开销**，接近手写；**通过约束调用方法**（`func F[T Stringer](x T){ x.String() }`）要先从字典取方法指针再间接跳转，**无法内联、无法静态绑定**，和接口调用一个量级——所以"带方法的约束"并不比直接传接口快，泛型的性能红利主要在**值类型容器与算法（免装箱、免反射）**上。

11. 这句话**基本是错的**。泛型的首要收益是"消灭复制粘贴"和"消灭 interface{}+反射"，不是让代码跑得更快。正确实验要**三组对照**，而不是两组：A 手写专用版（性能上界）、B 泛型版、C interface{}+反射版（下界）。同时测 **A vs B**（回答"相对手写亏多少"）和 **B vs C**（回答"相对老办法赚多少"）——只测前者会得出"泛型没用"，只测后者会得出"泛型神速"，都是错的。预期定性结论：A vs B 在纯算术/遍历场景**差距很小**（两边都单态化、都可能内联）；B vs C **差距是数量级的**（反射的装箱 + 动态分派是几十到上百纳秒级开销）。另外要注意三个细节：① 泛型函数体越小越容易内联，越大越容易"体积性能双输"；② 一旦返回 `any` 或把 `T` 塞进 `[]any`，装箱就回来了，泛型省下的分配全还回去；③ 基准要 `b.ReportAllocs()`、要把结果存回变量防止被优化掉，否则测的是循环开销而不是泛型开销。

12. 刻意不支持的（列出主要几项）：**泛型方法**（方法不能有自己的类型参数）、**变长类型参数**、`Foo[T...]`、**特化/specialization**（不能为 `Foo[int]` 单独写更快的实现）、**运算符重载**、**部分指定类型参数**（要么全写要么全推断）、**协变/逆变**（`[]Dog` 不是 `[]Animal`）、**含类型元素的接口当普通类型用**。其中"不支持泛型方法"的后果：`Stack[T]` 上写不出 `s.Map[U](f)` 这种链式方法，很多"流畅 API"设计直接做不了；且根因很硬——方法要进方法集/itable，带类型参数的方法会让方法集无限膨胀，接口也无法表达。**绕法：写成包级泛型函数，把接收者当第一个参数**，`func MapStack[T, U any](s Stack[T], f func(T) U) Stack[U]`。丑一点但可行；而且当你开始为"泛型方法"绞尽脑汁时，真正的信号通常是：这个设计该用普通函数组合，而不是该用泛型方法。（补充：Go 1.24 起支持泛型类型别名 `type A[T any] = B[T]`，迁移泛型类型的重构终于有了干净写法。）
