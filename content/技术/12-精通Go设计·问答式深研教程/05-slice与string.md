# 05 slice 与 string：共享底层数组的甜与雷

## 开篇提问

先看一段代码，让你当回"预言家"：

```go
a := make([]int, 0, 4)
a = append(a, 1, 2, 3)
b := a[0:2]

b = append(b, 99)

fmt.Println(a)  // 输出什么？
fmt.Println(b)  // 输出什么？
```

别急着跑代码。你先在脑子里模拟一遍，把答案说出来，再说说为什么。

这道题能答对，说明你对 slice 的底层模型是真的懂，而不是"会用 append"。这道题答错，也别慌——它是 Go 里最经典的"看起来会、其实没懂"的题目之一。

这一章，我们就把 slice 和 string 这两个"看起来简单、坑全在底层"的东西，彻底讲透。

---

## 子主题一：slice 的三要素

一个 slice 在内存里，本质是一个**三字段的小结构体**：

```go
type slice struct {
    ptr *T     // 指向底层数组的指针
    len int    // 当前长度（你"看得见"的元素个数）
    cap int    // 容量（底层数组从 ptr 开始能容纳的元素个数）
}
```

这三个字段，是理解一切 slice 行为的钥匙。记住三个要点：

1. **slice 是"视图"，不是"容器"。** 多个 slice 可以共享同一个底层数组，它们只是"指向同一块内存的不同窗口"。
2. **len 和 cap 是两回事。** len 决定你能访问 `[0, len)`；cap 决定 append 时还能塞多少而不需要重新分配。
3. **slice 赋值是"浅拷贝"。** `b := a` 复制的是那个三字段结构体（ptr/len/cap），不是底层数组。所以 `b` 和 `a` 共享同一块数据。

理解了这三点，回看开篇的题：`a` 的底层数组容量 4，`a = append(a, 1,2,3)` 后 len=3、cap=4。`b := a[0:2]` 让 b 共享同一个底层数组，len=2、cap=4。`b = append(b, 99)` 时，b 的 len=2 < cap=4，所以**不需要扩容，直接在共享数组的第 3 个位置写入 99**——而这个位置，恰好是 `a` 的第 3 个元素 `3` 所在的位置。

所以答案是：`a = [1 2 99]`，`b = [1 2 99]`。b 的 append 把 a 的数据覆盖了。

这就是共享底层数组的"雷"：**你以为 b 是独立的，其实 b 和 a 是同一块内存的两个窗口，b 往里写，a 也跟着变。**

## 子主题二：append 的扩容规则

再看 append 的扩容，这是另一个高频考点。

当 append 时 len 已经等于 cap，slice 就会扩容：**分配一块更大的新数组，把旧数据复制过去，返回指向新数组的 slice。** 关键问题：新数组多大？

Go 的扩容规则（历史上有过调整，这里讲现代版本的规律）：

- 当原容量较小（约 256 以内），新容量约为**旧容量的 2 倍**；
- 当原容量较大（超过 256），增长因子会**逐渐降下来**（约 1.25 倍，且更精确地按"目标容量"计算，避免过度浪费）；
- 扩容后的实际容量还会**按 size class 向上取整**（分配器按档位给内存，不会精确给）。

这个"小容量翻倍、大容量放缓"的曲线，背后是**摊还分析**（第一章思考题讲过）：翻倍增长让 append 的摊还成本是 O(1)，但大容量还翻倍会浪费太多内存，所以放缓到 1.25 左右平衡。

这里藏着两个最常见的坑：

**坑一：扩容会"脱钩"。** 一旦 append 触发扩容，返回的 slice 指向的是**新的底层数组**，和旧数组彻底无关。所以下面这段代码，很多新手会写错：

```go
func appendOne(s []int) {
    s = append(s, 1)   // 可能扩容，改了副本 s，但调用方的 s 没变
}

a := make([]int, 0, 1)
appendOne(a)           // a 还是空的！
```

因为 slice 传参传的是三字段结构体的**值**，函数里的 `s = append(...)` 只是改了函数内的局部变量；扩容后新数组的指针只存在函数里，调用方的 `a` 依然指向旧数组。要真正修改，得返回新 slice 或用指针。

**坑二：cap 的"幽灵空间"。** 即使你没扩容，append 也可能写到"看不见但存在的"共享空间里（就像开篇那道题），污染共享数组。这是"共享底层数组"最隐蔽的副作用。

## 子主题三：子切片、make 的陷阱与最佳实践

**子切片共享内存**：`b := a[1:3]` 后，b 和 a 共享底层数组，修改 b 会影响 a。这有时是有意为之（零拷贝），有时是坑（不小心改了共享数据）。

**一个著名的大坑：slice 引用大数组的小部分，导致大数组无法被 GC。**

```go
func getFirstLine(big []byte) []byte {
    return big[:10]   // 只想要前 10 字节
}
```

这里返回的 slice 只有 10 字节，但它底层数组指向的是那个巨大的 `big`。**只要这个小 slice 还活着，整个大数组就活着，GC 收不掉。** 如果 `big` 是 1GB，你就因为持有一个 10 字节的视图，永久占着 1GB。

正确做法是复制一份：

```go
func getFirstLine(big []byte) []byte {
    line := make([]byte, 10)
    copy(line, big[:10])
    return line
}
```

**make 与 nil slice**：`var s []int` 是 nil slice（ptr 为 nil），`make([]int, 0)` 是空 slice（ptr 非 nil）。它们行为几乎一样，但 `s == nil` 的判定不同，且序列化（JSON）时 `nil slice` 编成 `null`、空 slice 编成 `[]`。这是 API 兼容性上会咬人的细节。

**最佳实践**：能用 `copy` 就别共享；能预分配容量（`make([]T, 0, n)`）就别让 append 反复扩容；持有一个小视图时，想清楚它是否"绑架"了一整块大内存。

## 子主题四：string 的不可变与转换

string 在 Go 里是**不可变（immutable）**的：一旦创建，内容不能改。它的内存布局和 slice 很像，但没有 cap，且没有"改"的接口：

```go
type stringHeader struct {
    ptr *byte
    len int
}
```

不可变带来几个重要设计意义：

**第一，字符串可以安全共享。** 因为谁都不能改，所以 `s1 := s2` 只是复制一个 header，两个 string 指向同一块只读内存，零拷贝、无副作用。这是不可变类型的经典好处。

**第二，string 是 map 的理想 key。** 因为不可变，string 的 hash 值一旦算出就永久有效，不会出现"key 内容变了 hash 对不上"的灾难。这也是为什么 map 的 key 类型要求"可比较且（值）稳定"。

**第三，`string` 与 `[]byte` 的转换。**

```go
s := string(b)   // []byte -> string
b := []byte(s)   // string -> []byte
```

**早期的 Go，这两种转换都是"复制"**——因为 string 不可变，[]byte 可变，两者不能共享内存（否则你改了 []byte，string 就"变"了，破坏不可变契约）。复制是正确性的代价。

但有特殊场景可以**零拷贝转换**：编译器对某些纯读场景做了优化（比如 `string(b)` 用于比较、做 map key 时，可能直接在原地用，不复制）。此外，`unsafe` 可以实现真正的零拷贝转换，但要承担"改了底层导致 string 变长/变短"的风险——官方明确警告这是不安全用法。

**第四，strings.Builder。** 因为 string 不可变，拼接字符串 `s += x` 每次都要分配新内存、复制旧内容，O(n²) 是著名的性能坑。`strings.Builder` 内部用一个可增长的 []byte 缓冲，最后一次性转成 string，把拼接降到 O(n)。这是"用可变缓冲 + 延迟转换"解决"不可变 + 频繁拼接"的经典范式。

## 子主题五：UTF-8 与 rune——Go 的字符模型

这个问题经常被忽视，但它最能体现 Go 的务实。

Go 的 string 是**字节序列**，不是字符序列。`len(s)` 返回的是**字节数**，不是字符数。对一个中文串 `"你好"`，`len` 是 6（每个汉字 3 字节），不是 2。

Go 原生用 **UTF-8** 编码（也是 Ken Thompson 和 Rob Pike 当年一起发明的），它把 Unicode 码点编码成 1~4 字节的变长序列。于是 Go 引入了 `rune`（即 `int32`，代表一个 Unicode 码点）来遍历"真正的字符"：

```go
for _, r := range s {   // 按 rune 遍历
    fmt.Println(r)
}

for i := 0; i < len(s); i++ {   // 按字节遍历
    fmt.Println(s[i])           // 这是字节，不是字符
}
```

这个设计的精妙在于：**Go 把"字节"和"字符"明确分层**——底层是字节（和网络、文件、内存天然对齐），需要字符时用 range 按 UTF-8 解码出 rune。它既没有像 Python 3 那样"默认一切是字符、字节要特殊处理"（对网络编程略别扭），也没有像 C 那样"全是字节、字符你自己猜"。在"字节的朴实"和"字符的便利"之间，Go 找了一个很平衡的位置。

## 子主题六：扩容规则的三代演变——为什么"简单翻倍"不够用

先别看答案，你来当一次标准库作者。

**需求**：实现一个能自动增长的连续容器。约束只有两条——(1) 单次 append 的摊还成本要 O(1)；(2) 别浪费太多内存。

你的第一反应大概率是：

```
newcap = old.cap * 2
```

简单、漂亮、摊还 O(1)。那我问你三个问题：

- 容量 1000 万时翻倍，一次要新申请多大？旧数组在复制完成前还不能释放，**峰值内存占用是"旧 + 新"**——你算过这个尖峰吗？
- 翻倍之后，分配器真的给你"精确 2 倍"的字节数吗？不可能，它按档位（size class）给。那你翻倍之后的取整余量，是白送给谁的？
- 如果 `old.len` 比 `old.cap` 小很多（做过 reslice，或者上一次容量被 size class 放大过），按 `old.cap` 放大的基准，是"需求"还是"幻觉"？

Go 的扩容规则，就是把这三个问题逐个回答掉的历史。

**第一代：翻倍。**

早期的实现基本就是"两倍"，外加一个保底：如果一次 append 多个元素，两倍还不够，就直接取"实际需要的容量"。这一代解决了"能不能用"的问题：几何级增长保证了摊还 O(1)，逻辑也极简。但它同时继承了上面三个问题——大容器翻倍的内存尖峰、与分配器档位脱节造成的双重浪费、以及按 cap 而非按需求放大带来的偏差。

**第二代：阈值 + 平滑过渡曲线。**

这一代引入的核心思想是：**增长因子不该是常数，而该随容量增大而放缓。**

- 容量小的时候，继续保持约 2 倍增长。为什么小的时候敢翻倍？因为绝对浪费量小（100 变成 200，多占 400 字节，无感），而且翻倍能让扩容次数最少、摊还常数最小。
- 容量大到某个量级（注意：**具体阈值在历史上调整过，不要背数字，只记"量级在几百个元素"这个感觉**）之后，增长因子明显放缓，逐渐趋向约 1.25 倍。

等等，1.25 倍不会破坏摊还 O(1) 吗？不会。摊还分析要求的是"增长因子大于 1 的几何增长"，1.25 和 2 一样满足，只是摊还常数更大（扩容次数更多）。这笔账很好算：小对象省钱不如省次数，大对象省次数不如省钱。

而"平滑过渡"是这一代最容易被忽略的细节：如果直接在阈值处从 2 倍切到 1.25 倍，扩容行为会在那个点发生**跳变**——同一个循环，元素个数刚过阈值时容量曲线突然塌一下。所以实现里加了一个随容量增大的过渡项，让增长因子连续地滑下来，而不是硬切。

**第三代：基于目标容量精确计算 + 按 size class 取整。**

这一代改的是"计算的起点和终点"：

1. **起点改成真实需求**：先算"这一刀 append 完至少需要多少"= `old.len + num`，而不是拿 `old.cap` 放大。这修正了"len 远小于 cap"时的偏差，也避免了"扩完了发现还不够"的尴尬。
2. **中间套增长曲线**：在真实需求的基础上，再按上面的小容量翻倍、大容量放缓的曲线放大（放大的目的是为了"以后几次 append 不用再扩容"，不是为了这次）。
3. **终点交给分配器**：把目标容量换算成字节数，调用分配器的 size class 取整函数向上对齐到真实会分配的内存档位，**再把取整后的字节数换算回元素个数，作为最终 cap**。

第 3 点是个很妙的小优化：既然分配器反正要向上取整，那多出来的那些空间就别浪费了，直接算进 cap 里。你申请 1000 字节、分配器给你 1024，那 cap 就应该是能装 1024 字节的那个值，而不是 1000 字节对应的值。

这一代还顺手处理了溢出保护和超大容量的上界问题——毕竟 `newcap * elemsize` 在大 slice 上是真能溢出的。

**一句话总结这条演变史**：从"按容量的比例放大"，到"按需计算 + 贴合分配器"，权衡的对象始终是**扩容次数 vs 内存浪费**，而随着版本推进，计算基准越来越贴近"真实需求"和"分配器实际给出的内存"。

那作为使用者，你从这条演变史里能拿走什么？不是那些阈值，而是三条硬结论：

1. **永远不要依赖 cap 的具体数值。** 它是实现细节，跨版本会变。任何写 `s[:cap(s)]` 去"偷用多余容量"的代码，都是在赌运行时实现，别写。
2. **预分配永远是最优解。** `make([]T, 0, n)` 直接跳过整条增长曲线，一次分配搞定。你在热路径上能拿到的最大一笔优化，往往就是这一行。
3. **大 slice 扩容有真实的内存尖峰。** 扩容瞬间新旧两块并存，峰值接近"旧 + 新"。如果你在处理几百 MB 级别的 slice，靠 append 慢慢长大是个危险动作——先估算上界，一次到位。

## 子主题七：append 的三大经典 bug 现场

理论讲完了，来看凶案现场。下面这三段代码都能编译、都能跑、都不 panic，但都错。我建议你看一段、停一下，先在脑子里跑一遍结果。

### 现场一：循环里复用 buffer，所有元素都指向同一个视图

```go
func getFields(records [][]string) [][]string {
    out := make([][]string, 0, len(records))
    row := make([]string, 0, 4)   // "复用一个缓冲，省分配" —— 好心办坏事
    for _, r := range records {
        row = row[:0]             // 窗口缩回 0，复用底层数组
        row = append(row, r[0], r[1])
        out = append(out, row)    // ← 存进去的是什么？
    }
    return out
}
```

你以为 out 里是 N 行不同的数据。实际上 **out 的每一个元素都是同一个底层数组的视图，内容全部等于最后一轮写入的值**。

为什么？`out = append(out, row)` 复制的是 slice 的三字段结构体，ptr 指向的还是 `row` 那块数组。而 `row = row[:0]` 只是把窗口缩回 0，下一轮 append 又从偏移量 0 开始写——把上一轮的内容**原地覆盖**了。所有"存起来的视图"同时看到这次覆盖。

生活类比：你只有一块白板。每写完一次，你举着相机对着白板"拍一张"。但你拍的不是照片，你只是记下了"相机对准白板左上角这块区域"这个取景框。等你看相册时，24 张取景框里显示的都是白板现在的内容。

这类 bug 在真实代码里有几个常见马甲：

- **函数返回内部缓冲区**：`func (r *Reader) Bytes() []byte { return r.buf[r.off:r.end] }`——下一次 Read 就会覆盖它。`bufio.Scanner.Bytes()` 就是这种语义，官方文档明确写了"有效期到下一次 Scan 调用为止"。这是刻意的、有性能理由的设计，但你必须知道它。
- **表驱动测试里复用临时 slice**。
- **把 `s[:0]` 后的 slice 塞进结构体或 map 长期持有**。

修复有两条路：

```go
// 方案一：每轮新建（最直白）
for _, r := range records {
    row := make([]string, 0, 2)
    row = append(row, r[0], r[1])
    out = append(out, row)
}

// 方案二：只在"落地"的那一刻复制（Go 1.21+）
for _, r := range records {
    row = row[:0]
    row = append(row, r[0], r[1])
    out = append(out, slices.Clone(row))   // 复制一份独立的
}
```

方案二保留了"内层循环零分配"的收益，只在真正要留住的时候付一次复制的代价——这是处理这类问题的通用姿势。

### 现场二：指针 slice 的 append，让旧指针集体"过期"

```go
type Item struct{ Name string }

items := make([]Item, 0, 2)
var ptrs []*Item
for i := 0; i < 5; i++ {
    items = append(items, Item{Name: fmt.Sprint(i)})
    ptrs = append(ptrs, &items[len(items)-1])   // 记住每个元素的地址
}

// 之后：
ptrs[0].Name = "changed"
fmt.Println(items[0].Name)   // 是 "changed" 吗？
```

答案是：**可能是，也可能不是，取决于某一次 append 有没有触发扩容。**

一旦某次 append 触发扩容，底层数组整体搬家，而 `ptrs` 里此前收集的那些地址，全部留在**旧数组**上。从那一刻起，`ptrs[k]` 和 `items[k]` 就再无关系：你通过旧指针写，改的是一个没人再看的孤儿数组；`items` 里的数据纹丝不动。

这个 bug 的可怕之处在于它的"安静"：不 panic、不报错、类型完全正确，只是数据静默地不一致。它往往在你的第 30 万行日志里冒出一个字段不对，然后你花两天。

顺便说个 GC 层面的副作用：那些残留的旧指针**会吊住整个旧数组**，让本该回收的内存活下来——这和子主题三讲的"小 slice 绑架大内存"是同一个机理，只不过这里绑架者是一批过期的指针。

那 `&s[i]` 什么时候才安全？只有当你能保证：**取完这个地址之后，这个 slice 再也不会发生扩容**。

三条实践出路，按推荐度排序：

1. **存索引，不存指针。** `idx := append(idx, len(items)-1)`。索引对扩容、重排都更宽容，而且它是值，不参与 GC 的引用图。讽刺的是，这也是 Rust 社区绕开借用检查最常用的手段之一。
2. **把容量一次性开够。** `items := make([]Item, 0, hardUpperBound)`，保证整个生命周期永不扩容，指针就永远有效。前提是上界真的存在且不算太大。
3. **全程用 `[]*T`，别混。** 如果元素本身就是指针，`append` 搬的是指针数组，`Item` 本体在堆上纹丝不动，`*Item` 永远有效。

**一句话规则**：不要在同一段代码里既存 `&s[i]`、又继续 append 这个 `s`。要么全程值 + 索引，要么全程指针，二选一，别混血。

### 现场三：多 slice 共享底层，改到了不该改的地方

开篇那道题就是这一类。再看几个变体：

```go
// 变体 A：函数把参数切一刀再 append，动了调用方的数组
func takeTwo(s []int) []int {
    return append(s[:2], 99)   // cap 有富余时，直接写进调用方的底层数组
}

// 变体 B：构造二维结构时共享了同一行
row := []int{0, 0, 0}
matrix := make([][]int, 3)
for i := range matrix {
    row[0] = i                 // 以为在改第 i 行
    matrix[i] = row            // 其实三行是同一块内存的三个视图
}

// 变体 C：并发下共享
go func() { a[0] = 1 }()       // a 和 b 共享底层数组
go func() { b[0] = 2 }()       // 这就是赤裸裸的 data race
```

变体 C 值得多说一句：即使两个 goroutine 写的是"自己范围内"的元素，只要共享同一条 cache line，就还有 **false sharing** 的性能问题（两边互相使对方的缓存失效）。这已经不是正确性问题，而是"正确但慢得莫名其妙"的问题。

**防御三件套**，这是你该刻进肌肉记忆的东西：

1. **三索引切片全表达式**：`s[low:high:max]`，结果的 cap 被钉死为 `max - low`。

   ```go
   b := a[0:2:2]      // len=2, cap=2 —— append 必定扩容，必定脱钩
   ```

   这是语言层面提供的"我要断开共享"的声明式写法，比写个 clone 更轻（省一次分配，因为你本来就要扩容）。

2. **显式复制**：`slices.Clone(s)`（Go 1.21+），或老写法 `append([]T(nil), s...)`。

3. **代码评审规则**：任何"把参数 slice 的子切片返回出去 / 塞进结构体长期持有"的地方，都必须显式复制，除非注释里写清楚了共享是故意的。

最后反问一句：**为什么 Go 不干脆让 append 永远复制？** 那 slice 就不存在了——每次 append 都是 O(n)，也就没有零拷贝切片这套玩法，没有 `buf[:n]` 这种高性能解析。零拷贝是 Go 明确选择的设计目标，代价就是：这套规则得长在你脑子里，编译器不会替你记。

## 子主题八：string 与 []byte 转换——编译器在哪些地方偷偷省了那次拷贝

先复习一下代价：`string(b)` 默认要 **一次分配 + 一次 memmove**。单次几纳秒到几十纳秒，但放在协议解析、路由匹配、日志字段提取这种每秒跑几百万次的热路径上，它就是你 profile 里最显眼的那一行。

那编译器凭什么敢省掉这次复制？**两个条件同时成立**：

1. 转换出来的 string **没有逃逸出当前表达式**（不赋值给变量、不存进 map、不返回、不传给可能保存它的函数）；
2. 从转换到使用完毕这段时间内，底层的 `[]byte` **不可能被修改**（中间没有函数调用、没有 goroutine 同步点的"缝隙"）。

满足这两条的典型场景：

```go
// 1. 比较
if string(b) == "GET" { ... }

// 2. switch
switch string(b) {
case "GET", "HEAD": ...
}

// 3. map 只读查找（取值，不插入）
if v, ok := m[string(b)]; ok { ... }
```

这三个场景的共同点是：**用完即死**。那个临时 string 的生命周期只存在于这一条语句内，语句执行完它就消失了，此后 `b` 怎么改都影响不到任何还活着的东西。

运行时里专门为这类场景提供了一对临时转换函数（在 `runtime/string.go` 里，名字带 `tmp` 后缀），它们内部不做分配，只是重新解释同一块内存的头部。二者的注释都写得很明白：**只有在编译器能证明临时值不逃逸、且源切片不会被修改时才能用**。换句话说，这是编译器和运行时之间的一个"私人约定"，不是给你手动调用的公共 API。

现在反过来挑战几个边界，看看这套优化的分界线到底画在哪：

**问：`m[string(b)] = v` 会零拷贝吗？** 不会。插入会把 key **存进** map 长期持有，逃逸了，必须复制。这就是分界线：**读安全，写不安全。**

**问：如果我把 `string(b)` 的结果传给一个函数呢？** 一般不优化。跨函数之后，编译器无法证明调用方不保存它（除非内联后能看穿，但别依赖这个）。所以 `len(string(b))`、`strings.HasPrefix(string(b), "x")` 这类写法，老老实实付那次分配。真想省，用 `bytes.HasPrefix(b, []byte("x"))`。

**问：反方向 `[]byte(s)` 有优化吗？** 有，同样的道理——**只读遍历**场景下编译器可以不复制，直接扫 string 的字节。但凡你要往里写一个字节，立刻复制。

**问：那我能不能自己封装一个"快函数"骗过编译器？**

```go
func fastStr(b []byte) string { return string(b) }   // 以为省了？
```

不能。优化只在编译器能看见全部用法的**同一个函数内**做。你的函数返回了 string，这在编译器眼里就是"逃逸"，必复制。所谓零拷贝优化，本质是"编译器把一次转换和一次使用融合掉了"，不是"转换变快了"。

**验证方法**：别背八股，写 benchmark 看 `B/op` 和 `allocs/op`。想知道你的某段代码有没有被优化，`go test -bench . -benchmem` 两秒钟就出结果，比任何博客都可信。不同 Go 版本的优化范围还在变，测出来的才算数。

### unsafe 的"真零拷贝"：能用，但你得先签免责协议

```go
func b2s(b []byte) string {
    return *(*string)(unsafe.Pointer(&b))
}

func s2b(s string) (b []byte) {
    sh := (*[2]uintptr)(unsafe.Pointer(&s))
    bh := (*[3]uintptr)(unsafe.Pointer(&b))
    bh[0], bh[1], bh[2] = sh[0], sh[1], sh[1]
    return b
}
```

第一个能工作，是因为 `[]byte` 的头三个字和 `string` 的头两个字布局一致（ptr、len、cap vs ptr、len），转过去只是把 cap 那一段"视而不见"。第二个必须手动补齐 cap，因为 string 里没有第三个字。

风险清单，请完整读完再决定要不要用：

1. **破坏不可变契约。** 你拿到了一个和可变 buffer 共享内存的 string。写 buffer = 改 string。
2. **悬垂引用。** 如果底层 buffer 来自 `sync.Pool`、被归还后又被人拿到改写了，你手里那个 string 的内容会在毫无征兆的情况下变化。这是最难查的一类 bug——它依赖分配器的复用时序。
3. **只读段崩溃。** 常量字符串放在只读段，通过 `s2b` 拿到的 []byte 去写它，直接 SIGSEGV。
4. **移植性。** 依赖的是当前运行时的内存布局，官方从未承诺它稳定。

Go 1.20 起 `unsafe.String` / `unsafe.StringData` / `unsafe.SliceData` 提供了稍微"正名"一点的写法，但约束一个字没少：**转换后不得修改源 buffer，且不得让 string 活过 buffer 的生命周期**。

结论：**只有在热路径（有 benchmark 证明）、生命周期完全受控、且代码里有大段注释说明的前提下才考虑。** 其余一律复制。省下的那点纳秒，不值得你花两个通宵去查一个偶发的字段错乱。

## 子主题九：strings.Builder——给不可变类型开的可变后门

问题抛给你：string 不可变，那怎么高效地拼 10000 段字符串？

先说为什么 `s += x` 是灾难：每次 `+=` 都要分配一块"旧长度 + 新长度"的新内存、把旧内容复制过去、再把新内容复制过来。拼 n 段，第 k 次要复制 O(k) 的数据，总复制量是 O(n²)。拼 1 万段和拼 10 万段的耗时差距不是 10 倍，是 100 倍。这就是著名的"字符串拼接 O(n²) 陷阱"。

Builder 的解法很朴素：**内部藏一个可增长的 []byte，先把所有内容写进去，最后一次性转成 string。** 把"n 次分配 + O(n²) 复制"变成"O(log n) 次扩容 + O(n) 复制"。

来看它的结构（Go 源码级别）：

```go
type Builder struct {
    addr *Builder   // 哨兵：指向自己，用于检测"被值拷贝"
    buf  []byte
}
```

两个字段，各藏了一个设计亮点。

### 亮点一：`addr` 自引用——防止值拷贝的土办法

`addr` 是个"指向自己的指针"。Builder 第一次被写入时，会把 `addr` 设成 `&b`（指向自己）。之后每次 `Grow`/`Write` 之前，都会检查一下：

```go
if b.addr == nil { b.addr = &b; ... }
else if *b.addr != b { panic("strings: illegal use of non-zero Builder copied by value") }
```

如果你把 Builder **按值拷贝**了一份，副本的 `addr` 字段仍然指向**原对象**——于是 `*b.addr` 是原对象，而 `b` 是副本，两者不等，当场 panic。

生活类比：你在箱子上贴了张封条，写着"我是原箱，编号 0x7ffd..."。有人拿复印件去用，复印件上的封条还写着原箱的地址，一比对，地址对不上——当场拆穿。

为什么要这么设计？因为 Builder 内部持有 `buf`，值拷贝会让两个 Builder 共享同一个 `buf`，然后各自 append，互相踩踏，产生和子主题七现场一一样的 bug。`addr` 把这个坑从"静默错乱"升级成了"立刻 panic"。这是 Go 标准库里一个很典型的"用一点点运行时成本换取调试友好性"的取舍。

注意一个细节：**零值 Builder 的 `addr` 是 nil**，所以"复制一个还没写过任何东西的 Builder"是允许的（检查里 `b.addr == nil` 分支会把它初始化）。但别利用这个特性——**Builder 一律用指针传递，永远不要值拷贝**。

### 亮点二：`String()` 是零拷贝的

```go
func (b *Builder) String() string {
    return *(*string)(unsafe.Pointer(&b.buf))
}
```

它直接把 `buf` 的头部重新解释成 string，**不分配、不复制**。这是它比 `bytes.Buffer` 快的关键之一——`bytes.Buffer.String()` 是老老实实的 `string(b.buf)`，要复制一次。

但代价是什么？代价是：**返回的 string 和 `buf` 共享同一块内存。** 所以官方约定——**`String()` 之后就不要再写这个 Builder 了**（除非先 `Reset`）。

不信你看这段：

```go
var b strings.Builder
b.WriteString("hello")
s := b.String()
b.WriteString("world")   // ← 危险
```

如果 `buf` 还有富余容量，"world" 会被**原地写进**那块内存，`s` 指向的字节就变了（虽然 `s` 的 len 还是 5，你看到的内容却可能已经不是 "hello"）；如果这次写入触发了扩容，`buf` 搬家，`s` 就安然无恙。

也就是说，**结果取决于容量够不够——依赖于实现细节，行为不确定。** 这比"一定出错"更糟，因为它可能在你本地测试时永远没事，上线后在某个特定长度下突然发作。

正确姿势：**`String()` 就等于这个 Builder 寿终正寝了。** 要复用就 `Reset()` 重开一轮。

### Grow：把"未知"变成"已知"

```go
func (b *Builder) Grow(n int)
```

语义是：**保证接下来再写 n 个字节时，不需要扩容。**

实现逻辑很直接：如果 `buf` 的富余容量（`cap - len`）已经 ≥ n，直接返回；否则按目标容量 `make` 一块新的，把旧数据 copy 过去。

几个容易搞错的细节：

- **`Grow` 不改变 `Len()`**，只改变 `Cap()`。它不往里写任何东西。
- **`Grow` 给的不一定正好是你要的量**，底层还是走分配器的 size class 取整（呼应子主题六）。所以不要指望 `Cap()` 精确等于预期值。
- **`Grow(n)` 里的 n 是"接下来还要写多少"，不是"总共多少"。** 已经写了 100 字节、还要写 50 字节，就 `Grow(50)`。
- **反复小量 Grow 等于没 Grow。** 每次 Grow 不够都要 copy 一遍已有的，累积起来还是 O(n²)。要就一次算准。

所以正确用法是：**先扫一遍算出总长度，再一次性 `Grow(total)`。**

```go
// 拼接一个 []string，用分隔符连接
func join(ss []string, sep string) string {
    if len(ss) == 0 { return "" }

    total := len(sep) * (len(ss) - 1)
    for _, s := range ss { total += len(s) }   // 第一遍：算长度

    var b strings.Builder
    b.Grow(total)                               // 一次到位
    b.WriteString(ss[0])
    for _, s := range ss[1:] {
        b.WriteString(sep)
        b.WriteString(s)
    }
    return b.String()
}
```

（顺带一提：生产里直接用 `strings.Join` 就行，它内部就是这套逻辑。这里写出来是为了让你看清"两遍扫描换一次分配"这个范式。）

**两遍扫描值得吗？** 几乎总是值得。第一遍只做整数加法（极便宜、缓存友好、无分配），换来的是第二遍零扩容、零复制。唯一不划算的情况是：第一遍的成本本身很高（比如要先把每个元素 stringify 一遍才能知道长度），那就退而用估算值——估个稍大的量，多出的容量只是暂时多占点堆内存，用完丢掉即可。

### 什么时候用 Builder，什么时候不用

- **2~3 个固定片段**：直接 `a + b + c`。编译器会把连续的 `+` 合并成一次 concat 调用，可读性好，性能也够。
- **循环里累加**：必须用 Builder。这是它的主场。
- **需要 `io.Reader`/`io.Writer` 互操作**：用 `bytes.Buffer`（Builder 只实现了 `io.Writer`，没实现 Reader）。
- **需要格式化**：`fmt.Fprintf(&b, ...)` 可以（Builder 满足 `io.Writer`），但 `fmt` 有反射和装箱成本，热路径上不如手写 `WriteString` + `strconv`。
- **需要并发写**：都不行，自己加锁。`sync.Pool` 复用 Builder 是常见优化，但记得 `Reset()` 之后再放回池子，并且注意 `Reset()` 会丢弃底层数组（释放内存），复用的是 Builder 结构体本身。

顺带澄清一个流传很广的误解：**`bytes.Buffer` 并不比 `Builder` 慢"很多"**，两者写入路径几乎一样。真正的差距只有一处——`String()` 时的一次分配。所以当你需要 Buffer 的其他能力时，别为了这点差距委屈自己。

## 子主题十：UTF-8 的字节魔术——变长、自同步，以及为什么偏偏是它

先给你一道思考题：如果让你设计一套字符编码，你会怎么干？

最省事的方案是"每个字符固定 2 字节"（UCS-2）。简单、O(1) 随机访问、定长。为什么没被采用？两个致命问题：

1. **所有英文文本的体积直接翻倍。** 而当时（以及现在）互联网上绝大部分字节是 ASCII。
2. **2 字节最多 65536 个码位，装不下 Unicode 全集。** 后来 Unicode 扩展到 17 个平面，UCS-2 只能靠"代理对"（surrogate pair）打补丁——于是它既不是定长（语义上），也没了简单性。**Java 和 C# 早期都栽在这上面**：一个 emoji 在字符串里占 2 个 `char`，`s.length()` 返回 2，`s.charAt(0)` 返回半个代理对。

那 4 字节定长（UTF-32）呢？英文文本变 4 倍，没人接受。

UTF-8 给出的答案是：**变长 1~4 字节，用首字节的前缀位标明这个字符占几个字节。**

| 首字节前缀 | 总字节数 | 后续字节 | 码点范围 |
| --- | --- | --- | --- |
| `0xxxxxxx` | 1 | — | U+0000 ~ U+007F |
| `110xxxxx` | 2 | 1 × `10xxxxxx` | U+0080 ~ U+07FF |
| `1110xxxx` | 3 | 2 × `10xxxxxx` | U+0800 ~ U+FFFF |
| `11110xxx` | 4 | 3 × `10xxxxxx` | U+10000 ~ U+10FFFF |

规则极简：首字节里 **1 的个数**就是总字节数（0 个 1 表示单字节），后续每个字节一律以 `10` 开头。

这张表背后，藏着七个值得逐一咀嚼的设计点，每一个都是"为什么 UTF-8 赢了"的理由：

**1. ASCII 完全透明。** 所有 ASCII 字节都 < 0x80，在 UTF-8 里原样保留。这意味着：HTTP 头、正则、文件路径、JSON 语法、`strstr`、`strcmp`、C 的标准库——**全部照常工作，无需改写**。这是 UTF-8 击败 UTF-16 最大的现实理由：它不需要生态迁移。

**2. 自同步（self-synchronizing）。** 你从字节流的任意位置取一个字节，看它的前缀就知道：这是某个字符的开头，还是某个字符的续字节。**续字节永远是 `10xxxxxx`，永远不会和首字节的模式混淆。** 于是：

- 从中间截断后，最多往后跳 3 个字节就能找到下一个字符边界；
- 丢掉一个字节，只毁掉一个字符，后面的解码自动重新对齐；
- **最实用的推论**：用字节扫描去查找 ASCII 字符（`:`、`/`、`@`、空格、换行）**永远是安全的**，绝不会误命中某个多字节字符内部的字节——因为多字节字符的每个字节都 ≥ 0x80。

  这一点极其重要，很多写 Go 多年的人都没意识到：**`strings.IndexByte`、`bytes.IndexByte`、手写 `for i := range len(s) { if s[i] == ':' }` 做协议解析，在 UTF-8 下是天然正确的**，不需要先解码成 rune。这是自同步性质送给我们的一份大礼。

  类比：一队人排队，队长戴红帽、队员戴蓝帽。你半路插进队伍，往前后各看一两个人，就能找到下一位队长在哪。

**3. 前缀码，无歧义。** 任何一个合法字节序列只有**唯一一种**切分方式。不存在"这两字节可以这样解、也可以那样解"的情况。

**4. 字节序无关。** 没有大端小端之分，不需要 BOM。UTF-16 必须声明 endian，UTF-8 不用。对网络协议和文件格式来说，少一个"到底是大端还是小端"的配置项，就少一类 bug。

**5. 字节字典序 == 码点字典序。** 这是个精心设计的性质：按字节比较的结果，和按 Unicode 码点比较的结果完全一致。它意味着排序、二分查找、B-tree/LSM 索引可以**直接用 memcmp，不需要解码**。数据库和 KV 存储爱死这个了。

**6. NUL 安全。** 只有真正的 U+0000 才会产生 `0x00` 字节。而 UTF-16 里任何一个 ASCII 字符都会带来一个 `0x00` 字节——直接把 C 字符串截断。历史上有一大类 bug 和安全漏洞源于此。

**7. 代价。** 变长意味着不能 O(1) 随机访问第 n 个字符（必须从头扫）；中文 3 字节比 UTF-16 的 2 字节费空间（但英文省一半，全球平均下来 UTF-8 更省）；插入删除要按边界对齐。Go 坦然接受这些代价。

**那 Go 为什么选 UTF-8？** 除了上面这些工程理由，还有一条人情因素：**UTF-8 是 Ken Thompson 和 Rob Pike 在 1992 年设计的**（有个著名传说是他们在一块餐巾纸上定下了这套编码，随后 Plan 9 全盘采用）。Go 的三个创始人里有两个是 UTF-8 的作者——这就不难理解为什么 Go 的源码、标识符、string 字面量全部原生 UTF-8。

更本质的是：**Go 的 string 本质是字节序列，而 UTF-8 让"字节序列"和"文本"在编码层面统一了。** 你不需要像 UTF-16 语言那样维护两套表示，也不需要解释"为什么 `length()` 和字符数不一致"。

### rune 遍历 vs 字节遍历：什么时候用哪个

```go
s := "你好,world"

for i, r := range s {        // 按 rune 遍历：i 是字节偏移，r 是 rune(int32)
    fmt.Printf("%d %c\n", i, r)
}

for i := 0; i < len(s); i++ {  // 按字节遍历
    fmt.Printf("%d %x\n", i, s[i])
}
```

关键认知：

- **`for range` 出来的 `i` 是字节偏移量，不是字符序号。** 第一次迭代 `i=0`（'你'），第二次 `i=3`（'好'），不是 1。很多人在这里翻车。
- **字节遍历并没有错，它只是"不认识字符"。** 在找 ASCII 分隔符、算哈希、做 base64、判断是否以某 ASCII 前缀开头这些场景下，字节遍历是最快也最正确的选择（上面第 2 点论证过）。
- **字符数怎么算？** `utf8.RuneCountInString(s)`——O(n) 且不分配。别用 `len([]rune(s))`，那会分配一整个 []int32 切片（除非你确实需要那个 []rune）。
- **索引和切片都是字节偏移。** `strings.Index` 返回字节下标，`s[i:j]` 按字节切。`s[:2]` 去切 "你好" 会得到半个字符的垃圾。要"取前 N 个字符"，必须自己按 rune 走一遍累计字节数。
- **字符串反转** 必须走 rune：`[]rune(s)` 收集 → 倒序 → `string(...)`。按字节反转会彻底毁掉多字节字符。

### 非法 UTF-8：Go 不保证你的 string 是合法的

这是 Go 和 Rust 的一个硬差异：**Go 的 string 不保证是合法 UTF-8。** `s := string([]byte{0xff, 0xfe})` 完全合法，能存、能传、能拼接，只是解码时会出问题。

`for range` 遇到非法字节时的行为是：返回 `utf8.RuneError`（即 U+FFFD，`'\uFFFD'`，那个著名的"菱形问号"），**并且宽度为 1**。

于是有个很容易踩的坑：你看到一堆 U+FFFD，怎么区分"原文里真的有个 U+FFFD 字符"和"原文里有一段非法字节"？

判别技巧非常漂亮，值得记住：

```go
r, size := utf8.DecodeRuneInString(s[i:])
if r == utf8.RuneError && size == 1 {
    // 这是非法字节（合法的 U+FFFD 编码是 3 字节 ef bf bd，size 会是 3）
}
```

因为 U+FFFD 这个码点本身的 UTF-8 编码是 3 字节，所以 `size == 1` 就排除了"真字符"的可能。一行代码，毫不含糊。

工程上的处理策略：

- **在系统边界校验。** 读文件、收网络包、取 DB 字段时，用 `utf8.ValidString(s)` 校验一次，非法就拒绝或替换。**内部代码一律假设合法**——否则你的每个函数都要处理非法输入，代码会烂掉。
- **需要清洗时用 `strings.ToValidUTF8(s, "\uFFFD")`（Go 1.13+）**，把非法序列替换掉。
- **`strings.ToUpper`/`ToLower` 只做简单的 Unicode 大小写映射，不做 locale 特殊规则。** 最典型的例子是土耳其语：小写的 `i` 大写后不是 `I` 而是 `İ`（U+0130）。如果你的服务面向土耳其用户，这类转换要用 `golang.org/x/text/cases` 并显式指定语言标签。

## 子主题十一：nil slice 与 empty slice——那些"看起来一样"的不一样

先把这段代码在你脑子里跑一遍：

```go
var a []int          // nil slice
b := []int{}         // empty slice（字面量）
c := make([]int, 0)  // empty slice（make）

fmt.Println(a == nil, b == nil, c == nil)
json.Marshal(a)   // ?
json.Marshal(b)   // ?
reflect.DeepEqual(a, b)  // ?
slices.Equal(a, b)       // ? (Go 1.21+)
```

答案：

- `a == nil` → `true`；`b == nil`、`c == nil` → `false`
- `json.Marshal(a)` → `null`；`json.Marshal(b)` → `[]`
- `reflect.DeepEqual(a, b)` → `false`
- `slices.Equal(a, b)` → `true`（它按元素逐个比较，不看 nil，两个都是 0 个元素）

注意最后两条是**相反**的。这俩函数语义不同，别搞混：`slices.Equal` 比的是"内容"，`DeepEqual` 比的是"结构（含 nil 与否）"。

### 内存层面：差一个指针

- **nil slice**：ptr = nil，len = 0，cap = 0。
- **empty slice**：len = 0，cap = 0，但 **ptr 不是 nil**——它指向运行时里一个全局的零大小哨兵对象（你不需要记它的名字，只要知道"有个共享的空壳地址"）。

这个区别的实践意义接近于零：两者都不持有任何可写数据，`&s[0]` 对两者都 panic，append 时两者都要真正分配。Go 官方博客讲得很清楚：**nil slice 和空 slice 在语言层面应当能互换使用。**

### 行为层面完全等价的部分

`len`、`cap`、`range`（都是 0 次迭代）、`append`、`copy`、`s[:0]`（对 nil slice 也合法，结果仍是 nil）、作为函数参数、`clear(s)` 之后——**全部一样**。

尤其是 `append(nil, x)` 完全合法，这是 Go 最舒服的设计之一：

```go
var out []Result          // 不用初始化！
for _, r := range input {
    if match(r) {
        out = append(out, r)   // 直接用
    }
}
```

对比一下 Java/C++ 里"声明了还得 new 一个"的别扭，你会明白 Go 把"零值可用"当成一条设计原则在贯彻。

### 有差异的地方，逐个点名

1. **`s == nil` 判定。** 这是最直接的差异，也是所有 bug 的源头。
2. **JSON 序列化：nil → `null`，empty → `[]`。** 这是最常见也最伤人的事故。你的 Go 服务返回 `{"items": null}`，前端 `items.map(...)` 直接白屏；或者另一个 Go 服务反序列化到 `[]T` 时拿到 nil，后续 `len()` 能用但语义含混。**这是 API 兼容性上最经典的坑之一。**
3. **`reflect.DeepEqual` 不相等**（单元测试里写期望值时经常撞上）。
4. **`fmt.Println` 打印两者都是 `[]`**——**看不出来！** 调试时你打印两个变量，输出一模一样，但一个 nil 一个不是。这个坑很隐蔽。
5. **`slices.Equal` 返回 true**，与 `DeepEqual` 相反（上面说过）。
6. **其他序列化协议**：gob、protobuf 对 nil 与 empty 的处理各有讲究（比如 proto3 的 repeated 字段，nil 和 empty 序列化结果一致，但 `optional` 的 message 字段有 has 位区分"未设置"和"设置了空值"）。跨语言时一定要查清楚。

### 工程建议（这才是重点）

**1. 判断"有没有数据"，永远用 `len(s) == 0`，不要用 `s == nil`。**

除非你真的要区分"这个字段压根没被初始化"和"初始化了但是空的"这两种**业务状态**。绝大多数情况下你不需要区分，用 `len` 就行了——而且 `len` 对两者都正确。

**2. 对外 JSON API 返回空列表时，返回 `[]T{}`，不要返回 nil。**

让 `null` 只表示"字段缺失 / 值未知"，让 `[]` 表示"有这个列表，但它是空的"。语义干净了，前端就不需要写 `items || []` 这种补丁。实践上常见的兜底写法：

```go
if resp.Items == nil {
    resp.Items = []Item{}
}
```

**3. 包内部要统一。** 一个包里有的函数返回 nil、有的返回 `[]T{}`，调用方写的 `== nil` 判断就会时灵时不灵。挑一个，全包统一。

**4. `omitempty` 对两者行为一致**（都是 `len == 0` 就省略整个字段）。所以如果你希望"空数组也要输出"，就别加 `omitempty`；如果希望"空就不输出"，加上它，此时 nil/empty 无所谓。

**5. 需要表达三种状态（无值 / 空 / 有值）时，slice 不够用。** 上 `*[]T`，或者加一个独立的 bool / 指针字段。这是 GraphQL、PATCH 语义里经常遇到的需求。

## 子主题十二：把 slice 和 string 用对的工程自检清单

知识学完了，得能落进手指头里。下面是我在 code review 时会逐条过的清单，每一条都对应前面讲过的某个雷。

### 写 slice 之前，问自己 6 个问题

1. **这个 slice 的容量我能估算出来吗？** → 能就 `make([]T, 0, n)`，跳过整条扩容曲线。
2. **算出来的上界会不会太大？** → 大 slice 扩容有"旧 + 新"的内存尖峰，宁可分块处理，也别让它靠 append 慢慢长大。
3. **这个切片会被长期持有吗（塞进结构体、缓存、map）？** → 会的话检查它是否绑架了一整块大内存 → `slices.Clone` 复制一份小的。
4. **我要把参数的子切片返回出去 / 存起来吗？** → 用 `s[low:high:high]` 三索引钉死 cap，或显式 Clone。
5. **我取了 `&s[i]` 之后还会 append 这个 s 吗？** → 会就改成存索引，或者全程用 `[]*T`。
6. **循环里复用 buffer 了吗？** → 存进去的是视图还是副本？视图 = bug。

### 写 string 之前，问自己 5 个问题

1. **拼接发生在循环里吗？** → 是就 Builder，并且能算总长就先算总长再 `Grow`。
2. **`String()` 之后还会写这个 Builder 吗？** → 会就是 bug，重开一个或 `Reset`。
3. **热路径上有 `string(b)` 吗？** → 换个纯读写法（比较 / switch / map 查找）让它被优化掉；或者用 `bytes` 包的函数避开转换。拿不准就写 benchmark 测。
4. **我在用索引切字符串吗？** → 记住索引是**字节偏移**。切非 ASCII 之前先按 rune 走一遍。
5. **这些字符串来自外部吗？** → 入口处 `utf8.ValidString` 校验一次，内部假设合法。

### 三条"宁可啰嗦"的守则

- **宁可多一次 copy，也别留一个共享的隐患。** 一次 copy 是几纳秒；一个共享 bug 是两天。
- **宁可写 `len(s) == 0`，也别写 `s == nil`。** 前者永远对，后者只对一半的情况对。
- **宁可写 benchmark，也别背"哪个更快"。** 编译器优化在变、运行时实现在变，测出来的才是你的。

## 业界对照

**C：** 数组和指针不分家，没有 slice 这种"带长度和容量的视图"抽象，越界是未定义行为，一切靠程序员。C 的字符串是 `\0` 结尾的字节数组，没有长度字段，`strlen` 是 O(n)，还能被截断攻击。

**C++：** `std::string` 可变、`std::string_view` 类似 Go 的 slice（非拥有视图，同样有"引用大内存"的坑）；`std::vector` 类似 Go 的 slice（连续、可增长）。C++ 的抽象更强，但选择更多、心智负担更重。

**Java：** `String` 不可变（和 Go 一样），有 `StringBuilder`（对应 strings.Builder）；集合有 `ArrayList`（类似 slice）。但 Java 没有"子串共享底层"这种零拷贝视图（子串是复制），因为不可变 + 复制更安全。

**Rust：** `&str` 是 UTF-8 字节切片（不可变、借用），`String` 可变拥有。Rust 用所有权和生命周期，在编译期就杜绝了 Go 里"子切片共享导致数据竞争/大内存绑架"的坑——但换来的是借用检查的心智成本。

## 子主题十三：业界对照补强——别人的坑，我们的镜子

前面粗略扫了一圈，这里把 C++ 和 Rust 这两面镜子擦亮，因为它们照出的恰好是 Go 的两个"反面教材"和一个"正面教材"。

### C++17 `std::string_view`：一把更快的刀，也更容易割到自己

`string_view` 是什么？就是 `{const char* ptr, size_t len}`——一个非拥有的只读视图。**和 Go 的 string 结构一模一样**（Go 的 string 也是 ptr + len）。区别是：Go 的 string 背后的内存由 GC 托管，而 C++ 的 `string_view` 背后是什么，全靠你自己记。

看两段"能编译、能通过 review、能上线、然后在某个深夜炸掉"的代码：

```cpp
std::string_view getName() {
    std::string s = computeName();
    return s;              // 返回局部对象的视图 —— 函数返回即悬垂
}

std::string_view v = std::string("a") + std::string("b");
// 临时对象在完整表达式结束时销毁，v 立刻变野指针
```

编译器**不负责**检查这个（部分编译器有 `-Wdangling` 之类的警告，但不保证、不跨翻译单元）。于是这些"悬垂引用"（dangling reference）成了 C++ 里最经典的一类内存安全缺陷。

有意思的是，把它和 Go 的陷阱并排放在一起看，你会发现三种截然不同的失败模式：

| 场景 | C++ | Go |
| --- | --- | --- |
| 小视图引用大对象 | 对象若在栈上/被 delete → **野指针，未定义行为** | GC 保住大对象 → **只是内存占用变大** |
| 容器扩容后旧引用 | 旧元素被析构 → **悬垂** | GC 保住旧数组 → **只是"过期"，读写都安全但没意义** |
| 取元素地址后继续增长 | `vector` 的引用/迭代器失效规则（复杂、条件多） | 规则只有一条：扩容就搬家 |

看清了吗？**Go 的 GC 不是万能的，但它把最坏情况从"未定义行为"降级成了"浪费内存"。** 同样一个错误，在 C++ 里是 security vulnerability，在 Go 里是 pprof 上的一条内存曲线。这就是"用一点运行时开销换确定性"这笔交易的实际收益。

反问一句：那是不是说明 Go 更安全？**在"内存安全"这个维度上，是的。** 但别得意——Go 把问题从"崩溃"变成了"静默错乱"，后者有时候更难查。

**`vector` 扩容与迭代器和 Go 的指针 slice** 是同一个物理事实的两种表述：连续容器容量不够时必须搬家，搬家之后旧地址指向的就是一块"仍然合法但已经不重要"的内存。C++ 选择让旧地址**失效**（于是你必须背诵一整套"什么操作会让什么失效"的规则表）；Go 选择让旧地址**继续有效**（代价是 GC 得多活一段时间）。

**顺带说一个 Go 里根本不存在的坑：SSO（Small String Optimization）。** `std::string` 为了省一次堆分配，会把短字符串直接存在对象内部的栈空间里；一旦字符串变长超过阈值，就搬到堆上——**于是你之前取的 `data()` 指针和所有迭代器全部失效**。这个坑的隐蔽性在于：它只在字符串长度跨过阈值的那一刻出现，你用短字符串测试永远测不出来。

Go 为什么没这个问题？因为 Go 的 slice/string header 永远是那固定的几个字段，**数据永远在别处**，不存在"值语义容器内联数据"这回事。少一个优化，少一类 bug——这是 Go 一贯的取舍风格。

### Rust：把"共享可变"变成编译错误

先看结构，你会发现一个令人意外的事实：

```rust
// Rust 的 String（拥有）：ptr + len + capacity
// Rust 的 &str（借用）：ptr + len，没有 capacity
```

- **`String`** 的三要素，和 Go 的 slice **结构完全一样**：ptr、len、cap。
- **`&str`** 是胖指针：ptr + len，**没有 capacity**——和 Go 的 string **结构完全一样**。

所以：**Rust 和 Go 在数据布局上几乎没有区别，区别全在规则上。**

Rust 的规则只有一条核心约束：**对同一块数据，要么同时存在多个不可变借用，要么只存在一个可变借用，二者不能共存，且借用的生命周期必须被证明有效。**

于是，把我们在子主题七里剖析的三个 Go 事故现场搬到 Rust：

- **现场一（循环复用 buffer，存的全是同一视图）**：你想把 `&row` 存进 `Vec<&Vec<T>>`，而下一轮又要修改 `row` —— 可变借用与已存在的不可变借用冲突，**编译错误**。
- **现场二（指针 slice 扩容后旧指针过期）**：你想持有 `&items[0]` 的同时 `items.push(x)` —— 同上，**编译错误**。
- **现场三（共享底层数组的意外修改）**：想在持有 `&s[..2]` 的同时改 `s[2]` —— **编译错误**。
- **返回局部对象的引用**：生命周期不满足 —— **编译错误**。

也就是说，Go 里那一整类"能编译、能跑、但数据静默错乱"的坑，在 Rust 里几乎全部被提到了编译期。这是实打实的工程价值，不是营销话术。

**代价是什么？** 三样东西：

1. **生命周期标注的心智成本。** `'a`、`'static`、生命周期省略规则、NLL（非词法生命周期）——这些概念的学习曲线是陡峭的。
2. **为了绕过借用检查而引入的模式。** `Rc<RefCell<T>>`、`Arc<Mutex<T>>`、arena 分配、以及最常用的一招——**存索引而不是存引用**。
3. **编译时间。** 借用检查是有成本的。

看到第 2 点里的"存索引"了吗？**这正是我们给 Go 现场二开的药方。** 两个语言在"如何让引用关系变得可控"这个问题上，殊途同归地走向了同一个答案。这很能说明问题：当编译器逼你理清所有权时，你最终会采用的方案和"自己心里有数"的 Go 程序员采用的方案是一样的——只不过 Rust 是强制的，Go 是自愿的。

**另一个硬差异：UTF-8 有效性。**

- Rust 的 `String` 和 `&str` **在类型层面保证内容是合法 UTF-8**。唯一的例外是 `unsafe` 构造（`String::from_utf8_unchecked`）。所以 `s.chars()` 永远解码成功，`s[0]` 这种下标访问甚至被**直接禁止**（因为变长编码下 O(1) 下标语义不明确，Rust 选择不提供）。
- Go 的 string **不保证**合法 UTF-8，`s[0]` 返回的是第一个字节，`for range` 遇到非法字节会吐出 U+FFFD。

这是两种哲学的分野：

- **Rust："非法状态不可表示"。** 校验前移到类型边界——`String::from_utf8(v)` 返回 `Result<String, FromUtf8Error>`，你**必须**处理非法的情况才能拿到一个 `String`。一旦拿到，就永远合法。
- **Go："务实，给逃生舱"。** string 就是字节袋，合法与否是你自己的事。好处是零成本抽象（不需要在每次构造时校验）；代价是非法数据可以一路流到解码的地方才暴露。

**最后一个反问，也是这一章我最想让你带走的：那 Go 是不是"更差"？**

不是。Go 的选择是**降低心智门槛 + 保留逃生舱**：没有借用检查器、没有生命周期标注、编译飞快、内存模型一眼能看穿。代价由程序员承担。

而"精通 Go"的标志，恰恰就是——**在没有编译器帮忙的情况下，你脑子里自带那套规则**：看到 `big[:10]` 会想到大内存，看到循环里的 `append(out, buf)` 会想到共享，看到 `&s[i]` 后面跟着 append 会警觉，看到热路径上的 `string(b)` 会想去写个 benchmark。

这些规则 Rust 用类型系统强制执行，Go 交给你自己执行。**这就是"精通"二字的分量。**

## 版本演进小结

- string 与 []byte 的转换：从"总是复制"到"编译器对纯读场景做零拷贝优化"。
- append 扩容规则：从早期简单的"翻倍"到现代"小容量翻倍、大容量放缓、按 size class 取整"的精细曲线。
- strings.Builder：Go 1.10 引入，统一了此前 bytes.Buffer 等拼接手段。
- clear/min/max 内建：Go 1.21 引入 `clear`（清零 map/slice），让"清空 slice"有了官方高效写法。
- slices / maps 标准包：Go 1.21 把泛型工具函数收编进标准库，`slices.Clone` 让"断开共享"有了官方写法，`slices.Equal` 也明确了"按元素比较、不区分 nil 与空"的语义。
- unsafe.String / unsafe.StringData / unsafe.SliceData：Go 1.20 为 string 与 []byte 的零拷贝转换提供了比手写指针转换更"正名"的入口，但"不得修改源 buffer、不得让 string 活过 buffer"的约束一个字没少。

主线依然是那条：**Go 的 slice/string 设计，始终在"零拷贝的高效"和"共享带来的风险"之间走钢丝，用一套简单一致的规则，把复杂度压到"你只需要理解三字段 + 不可变"这个程度。**

【参考答案】

1. 因为 `a` 和 `b` 共享同一个底层数组，`b` 的 cap 还有剩余（cap=4 > len=2），append 不需要扩容，直接写到共享数组的下一个位置，而这个位置正是 `a[2]` 所在，于是覆盖了 `a` 的第三个元素。只有当 `b` 的 append 触发**扩容**（len 达到 cap、分配新数组）时，`b` 才和 `a` 脱钩，不再影响 `a`。

2. slice 的三字段里，ptr 指向底层数组的**起始位置**，len/cap 只是窗口大小。`big[:10]` 返回的 slice 虽然窗口只有 10 字节，但 ptr 指向的是 big 整个大数组，所以 GC 判断"这个大数组仍被引用"，不会回收。解法是 `make` 一个小 slice + `copy`，让新 slice 拥有自己的小数组，从而释放对大数组的引用。

3. 因为 string 不可变、[]byte 可变，若共享内存，改 []byte 就会"改到" string，破坏不可变契约，所以默认复制保证正确性。编译器对某些纯读场景（比如 `string(b)` 仅用于比较或做 map key）可能优化为零拷贝（直接在原地读，不复制）。`unsafe` 强转可以实现零拷贝，但风险是：改了底层会让 string 的内容/长度变卦，破坏不可变假设，官方明确警告不要这么做。

4. 是 6，因为 `len` 返回字节数，"你好" 两个汉字各占 3 字节（UTF-8），共 6。要按字符遍历，用 `for _, r := range s`（按 rune/码点遍历），或者 `utf8.RuneCountInString(s)` 得到真正的字符数。这背后的设计是：string 是字节序列，字符语义通过 UTF-8 解码的 rune 来表达。

5. 三代演变：

   - **第一代（翻倍）**：`newcap = old.cap * 2`，一次 append 多个元素不够时取实际所需。解决了"能用"的问题，几何增长保证摊还 O(1)。遗留三个问题：大 slice 翻倍导致"旧 + 新"的内存尖峰；与分配器 size class 脱节造成"翻倍 + 取整"双重浪费；按 `old.cap` 而非真实需求放大导致基准偏差。
   - **第二代（阈值 + 平滑过渡）**：小容量继续约 2 倍，超过某个量级后增长因子逐渐放缓到约 1.25 倍，并且用过渡项让曲线**连续下滑**而不是在阈值处硬跳变。解决了"大容器浪费"的问题。注意 1.25 倍仍然满足摊还 O(1)（只要是 >1 的几何增长即可），只是摊还常数变大。
   - **第三代（按目标容量精确计算 + size class 取整）**：起点从 `old.cap` 改成**真实需求** `old.len + num`；中间套增长曲线；终点把目标容量换算成字节数交给分配器的 size class 向上取整，**再把取整后的字节数换算回元素个数作为最终 cap**——把"取整多出来的空间"还给 cap，不再白给。顺带处理了溢出与超大容量上界。

   使用者的三条实践结论：(1) **永远不要依赖 cap 的具体数值**，它是会跨版本变的实现细节，别写 `s[:cap(s)]` 这种偷用多余容量的代码；(2) **预分配永远最优**，`make([]T, 0, n)` 一次跳过整条曲线；(3) **大 slice 别靠 append 长大**，扩容瞬间新旧并存，峰值接近"旧 + 新"，先估上界一次到位。

6. 错在 `out = append(out, row)` 存进去的是 **row 这个视图（三字段的浅拷贝）**，而不是 row 内容的副本。`row = row[:0]` 只是把窗口缩回 0，下一轮 append 又从偏移量 0 开始**原地覆盖**，于是 `out` 里所有元素（共享同一底层数组）看到的内容全部等于最后一轮写入的值。本质就是子主题七现场一讲的"一块白板 + N 个取景框"。

   修复一（每轮新建，最直白）：

   ```go
   for _, r := range records {
       row := make([]string, 0, 2)
       row = append(row, r[0], r[1])
       out = append(out, row)
   }
   ```

   修复二（只在落地那一刻复制，保留内层零分配）：

   ```go
   for _, r := range records {
       row = row[:0]
       row = append(row, r[0], r[1])
       out = append(out, slices.Clone(row))   // Go 1.21+；老写法 append([]string(nil), row...)
   }
   ```

7. 因为 append 在容量不足时会**整体搬家**底层数组，而你此前收集的 `&s[i]` 全部留在**旧数组**上。此后通过这些指针读写，操作的是一个没人再看的孤儿数组，`s` 里的数据毫发无损——不 panic、不报错、类型正确，只是数据静默不一致。另外这些残留指针还会**吊住整个旧数组**，让本该回收的内存活下来。

   替代方案（按推荐度）：(1) **存索引而非指针**（`idx = append(idx, len(s)-1)`），索引对扩容和重排都更宽容，且不参与 GC 引用图；(2) **容量一次性开够**（`make([]T, 0, hardUpperBound)`），保证永不扩容；(3) **全程用 `[]*T`**，元素是指针时 append 搬的是指针数组，对象本体在堆上不动。核心规则：别在同一段代码里既存 `&s[i]` 又继续 append 这个 `s`。

8. 它解决的是"子切片继承了过多 cap，导致 append 时写进共享的幽灵空间、污染原 slice"的问题（即开篇那道题）。`s[low:high:max]` 的结果 len = `high - low`、**cap = `max - low`**。把 max 设成 high，cap 就等于 len，此后任何 append 都必然触发扩容、必然脱钩，等于用一句语法声明了"我要断开共享"。它比 Clone 更轻，因为少一次分配（反正你 append 时也要分配）。

9. 能省掉拷贝的是**纯读且结果不逃逸**的场景：`string(b) == "xxx"` 比较、`switch string(b)`、`m[string(b)]` 的**只读查找**。安全的理由是：转换出来的临时 string 生命周期不超过这条语句，语句结束即死，此后 `b` 怎么改都影响不到任何还活着的东西；且这段时间内没有函数调用或同步点的"缝隙"能让 `b` 被改动。运行时里为此专门提供了一对临时转换函数（名字带 `tmp`），其注释明确要求"编译器必须证明临时值不逃逸且源切片不被修改"——这是编译器与运行时的内部约定，不是可手动调用的公共 API。

   `m[string(b)] = v` 不行，因为**插入会把 key 存进 map 长期持有**，逃逸了，必须复制。这条分界线就是：**读安全，写不安全。** 同理，把 `string(b)` 的结果传给函数、赋给变量、返回，一律会复制——别指望自己封装个"快函数"能骗过编译器。

10. `String()` 的实现是 `*(*string)(unsafe.Pointer(&b.buf))`，直接把内部 `buf` 的头部重新解释成 string，不分配不复制（对比 `bytes.Buffer.String()` 是 `string(b.buf)`，要复制一次）。代价是返回的 string 与 `buf` **共享内存**。

    因此禁忌是：**`String()` 之后就不要再写这个 Builder**。若继续 Write 且 `buf` 还有富余容量，新内容会被原地写入，已经返回出去的那个 string 的内容会被改动（len 不变但内容变了）；若这次写入触发扩容，`buf` 搬家，旧 string 就没事——**行为取决于容量够不够，依赖实现细节，不确定**。这比"一定出错"更危险。要复用就 `Reset()`。

    `Grow(n)` 的正确用法：语义是"保证接下来再写 n 字节不需要扩容"，**n 是"还要写多少"而不是"总共多少"**。它不改变 `Len()` 只改变 `Cap()`；给的量会走 size class 取整，不要指望精确；**反复小量 Grow 等于白 Grow**（每次都要 copy 已有内容，累积仍是 O(n²)）。正确姿势是：先扫一遍算出总长度，一次性 `Grow(total)`，然后无扩容地写完。两遍扫描几乎总是值得——第一遍只做整数加法。

11. `addr` 是一个"自引用哨兵"，用于**检测 Builder 被按值拷贝**。原理：Builder 第一次被写入时会把 `addr` 设成 `&b`（指向自己）；此后每次 `Grow`/`Write` 前检查——若 `b.addr == nil` 就初始化它，否则比较 `*b.addr != b`，不等就 panic `illegal use of non-zero Builder copied by value`。因为值拷贝出来的副本，其 `addr` 字段仍指向**原对象**，于是 `*b.addr`（原对象）与 `b`（副本）不相等，当场暴露。

    这么设计的必要性在于：Builder 内部持有 `buf`，值拷贝会让两个 Builder 共享同一个 `buf` 并互相踩踏（就是子主题七现场一那类 bug）。`addr` 把它从"静默错乱"升级成"立刻 panic"。注意零值 Builder 的 `addr` 是 nil，所以复制一个从未写过的 Builder 不会被抓到——别利用这个特性，Builder 一律用指针传递。

12. **自同步**：任意一个字节，看它的高比特位就能判断它是"某个字符的首字节"还是"续字节"——续字节一律以 `10` 开头，永远不会与首字节模式混淆。好处有三个：(1) 从中间截断后最多跳几个字节就能找到下一个字符边界；(2) 丢一个字节只毁一个字符，解码会自动重新对齐（UTF-16 则会整体错位）；(3) **最实用的一点**——多字节字符的每一个字节都 ≥ 0x80，所以用字节扫描查找 ASCII 分隔符（`:`、`/`、`@`、空格、换行）**永远不会误命中**，因此 `bytes.IndexByte`、手写 `if s[i] == ':'` 这类协议解析写法在 UTF-8 下天然正确，无需先解码成 rune。

    "字节序 == 码点序"意味着：按 memcmp 排序的结果与按 Unicode 码点排序完全一致。**排序、二分查找、B-tree/LSM 索引可以直接对原始字节做比较，不需要解码**。对数据库和 KV 存储来说，这直接省掉了索引路径上的一次解码开销，也让"前缀扫描"这类操作变得自然。

13. 用 `utf8.DecodeRuneInString(s[i:])` 同时看返回值和宽度：

    ```go
    r, size := utf8.DecodeRuneInString(s[i:])
    if r == utf8.RuneError && size == 1 {
        // 非法字节
    }
    ```

    原理：U+FFFD 这个码点本身的合法 UTF-8 编码是 **3 字节**（`ef bf bd`），所以如果 `size == 1`，就排除了"原文里真的有个 U+FFFD 字符"的可能，只可能是解不出东西、被替换成了宽度为 1 的 RuneError。（补充背景：`for range` 遇到非法字节时返回 U+FFFD 且宽度为 1；整串校验用 `utf8.ValidString`，清洗用 `strings.ToValidUTF8`。）

14. **完全一样的部分**：`len`、`cap`、`range`（0 次迭代）、`append`、`copy`、`s[:0]`、作为函数参数、`clear` 之后——行为一致，官方明确要求二者可互换使用。尤其是 `append(nil, x)` 合法，这是"零值可用"设计的体现。

   **有差异的部分**：(1) `s == nil` 的值不同（nil slice 的 ptr 为 nil，empty slice 的 ptr 指向运行时一个全局零大小哨兵对象）；(2) **JSON：nil → `null`，empty → `[]`**，这是最常见的 API 事故；(3) `reflect.DeepEqual` 认为不等；(4) `fmt` 打印两者都是 `[]`，**调试时看不出来**；(5) `slices.Equal` 认为相等（按元素比，不看 nil），与 DeepEqual 相反；(6) gob/protobuf 等协议各有自己的 nil/empty 语义。

   **工程选择**：判断"有没有数据"一律用 `len(s) == 0`，不要用 `s == nil`（除非真要区分"未初始化"和"已初始化但为空"两种业务状态）；对外 JSON API 返回空列表用 `[]T{}` 而非 nil，让 `null` 只表示"字段缺失/未知"；一个包内部要统一；`omitempty` 对两者行为一致（都是 len==0 就省略）；需要表达"无值/空/有值"三态时 slice 不够用，改用 `*[]T` 或额外的 bool 字段。

15. 三者的答案分别是：

   - **C++ `string_view`**：给你 `{ptr, len}` 的非拥有视图，快，但**生命周期完全由程序员负责**，编译器基本不检查。返回局部对象的视图、绑定临时量、容器扩容、`std::string` 的 SSO 搬迁——都会产生悬垂引用，属于**未定义行为**，往往是安全漏洞。
   - **Go**：同样是非拥有视图，但**内存由 GC 托管**。于是同样的错误，表现从"野指针/UB"降级成了"数据过期但读写安全"和"大内存被绑架收不掉"——是浪费、是静默错乱，但不是崩溃、不是漏洞。规则极简（一条"扩容就搬家"），代价由程序员在脑子里执行。此外 Go 没有"值语义容器内联数据"（无 SSO），天然少一类失效场景。
   - **Rust**：结构和前两者几乎一样（`String` = ptr/len/cap 同 Go slice；`&str` = ptr/len 同 Go string），但用**所有权 + 借用检查**在编译期强制"要么多个不可变借用、要么唯一可变借用，且生命周期必须可证"。于是 Go 里那三个"能编译能跑但数据静默错乱"的现场，在 Rust 里全是编译错误。代价是生命周期标注的心智成本、编译时间，以及为绕过检查引入的 `Rc<RefCell<T>>`、arena、**存索引**等模式——有意思的是，"存索引"也正是 Go 程序员自愿采用的方案，Rust 把它变成了强制。

   **为什么说 Go 的 GC 把最坏情况从 UB 降级成了浪费内存**：GC 保证"只要还有任何指针指向一块内存，那块内存就有效"。于是 C++ 里"引用已释放对象"的未定义行为，在 Go 里被替换成了"引用一个仍然有效但语义上已经过期/过大的对象"——前者可能让程序做任何事（崩溃、被利用），后者最坏也只是内存占用偏高或数据不合预期。这就是"用运行时开销换确定性"这笔交易的实际收益。但也要清醒：Go 把问题从"崩溃"变成了"静默错乱"，后者有时更难查。
