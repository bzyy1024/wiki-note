# 18 编译器优化：内联、逃逸、边界检查消除、devirtualization

## 开篇提问

先问你一个看似简单的问题：

**Go 的编译器，为什么要做优化？它不优化，你的代码不也能跑吗？**

再问深一层：**你有没有想过，为什么同一段 Go 代码，不同版本编译出来的性能不一样？为什么有时候你只是把一个函数调用的写法改了一下，性能就翻倍了？**

答案全在**编译器优化**里。编译器优化，是 Go 性能叙事里最"看不见"的部分——它不像 GC、调度器那样有名字响亮的机制，但它决定了你写的每一行代码，最终在 CPU 上跑得有多快。

这一章，我们拆开 Go 编译器（gc）最核心的几类优化，讲清楚它们**为什么能加速、在什么条件下生效、以及你写代码时该怎么"配合"它们**。

---

## 子主题一：内联（inlining）——消掉函数调用的开销

内联是最基础、也最有效的优化：**把一个函数的调用，直接替换成函数体本身**，省掉"函数调用"的开销（压栈、跳转、返回、寄存器保存恢复）。

```go
func add(a, b int) int { return a + b }

// 内联后，x = add(1, 2) 直接变成 x = 1 + 2
```

内联的好处不止"省一次调用"，它还有一个巨大的**连锁效应**：

**内联之后，函数体"暴露"给了调用点，其他优化才有机会介入。** 比如：

- 内联后，参数变成常量，可以做**常量折叠**（`add(1,2)` 直接算成 `3`）；
- 内联后，局部变量不再"逃逸"（没有真正的跨函数调用了），**逃逸分析能把对象留栈**（第二章讲过"内联和逃逸分析互相放大"）；
- 内联后，方法的接收者类型暴露，可以做**去虚拟化**（后面讲）。

所以内联被称为"优化之母"——**它本身省不了多少，但它为其他优化打开了大门。**

Go 的内联策略是**保守**的：只内联"足够小"的函数（有内联预算，函数体太大就不内联）。为什么保守？因为内联会让二进制变大、编译变慢，且过度内联会膨胀代码、降低指令缓存命中率。Go 在"内联收益"和"代码膨胀"之间取了一个平衡。

**对你的启发**：**小而简单的函数更容易被内联。** 热路径上，把核心逻辑写成"小而可内联"的函数，比写一个大函数更容易被编译器优化。

## 子主题二：逃逸分析——第二章的"优化"视角

逃逸分析我们在第二章专门讲过，但那是从"内存管理"角度。这里换个角度，从"优化"视角再看它一次：

逃逸分析是**决定"对象住栈还是住堆"的优化**。它带来的性能收益，本质是：

- **栈分配 vs 堆分配**：栈分配是"SP 指针移动"，堆分配要走分配器 + 将来要 GC。前者快几个数量级。
- **减少 GC 压力**：留栈的对象不进 GC 账本，GC 不用扫它。

所以逃逸分析是 Go 性能优化里"收益最大的一类"——**让对象留栈，是 Go 性能优化的头号手段。**

**怎么配合它**？写代码时，尽量避免让对象"无谓逃逸"：

- 不要在热路径上把具体类型塞进 `interface{}`（装箱导致逃逸）；
- 不要无谓地返回局部变量的指针（除非真的需要）；
- 不要用 `reflect` 和 `fmt` 碰热路径数据（它们让逃逸分析失效）。

判断一个对象有没有逃逸，用 `go build -gcflags='-m'` 看编译器的判决书，这是每个 Go 性能优化者必备的技能。

## 子主题三：边界检查消除（bounds check elimination）

Go 的一个著名特性是**数组/slice 访问有边界检查**——`a[i]` 时，编译器会插入"检查 i 是否越界"的代码，越界就 panic。这是 Go 内存安全的重要保障。

但边界检查是有代价的：**每次访问 slice，都要多几条"比较 + 分支"指令。** 在热循环里，这个代价累积起来很可观。

边界检查消除（BCE）就是：**当编译器能证明"i 一定不会越界"时，把边界检查去掉。**

什么时候能证明？最常见的情况：

```go
for i := 0; i < len(a); i++ {
    _ = a[i]   // 编译器知道 i < len(a)，所以 a[i] 不越界，检查被消除
}
```

因为循环条件 `i < len(a)` 保证了 `i` 一定在范围内，编译器就能放心删掉 `a[i]` 的边界检查。

**怎么配合它**？关键技巧是**用循环条件"告诉"编译器 i 的范围**：

- 用 `for i := range a` 或 `for i := 0; i < len(a); i++`，让编译器能推断 i 的界限；
- 避免在循环里用"编译器看不透"的索引（比如从外部传进来的、可能越界的值）；
- 访问前先做一次显式的长度检查，编译器可能据此消除后续检查。

边界检查消除，是"编译器基于数据流分析，证明安全后删掉冗余保护"的典型优化。理解它，你能写出"既安全又不牺牲性能"的循环。

## 子主题四：去虚拟化（devirtualization）

这是接口方法调用相关的优化，和第十一章呼应。

回顾第十一章：接口方法调用，要经过"itab 查表 + 间接跳转"，比直接调用慢。**去虚拟化（devirtualization）**就是：**当编译器能确定接口背后的具体类型时，把"间接调用"变成"直接调用"。**

什么时候编译器能确定？最常见的是：

```go
var s io.Reader = &MyReader{}
s.Read(p)   // 编译器看到 s 是 &MyReader{} 赋的，能确定 s 背后的具体类型
```

如果编译器能证明 `s` 一定是 `*MyReader`（比如赋值就在眼前、没有被改变），它就能把 `s.Read` 直接调成 `(*MyReader).Read`，省掉 itab 查表的间接跳转。

去虚拟化的最大价值在于**配合内联**：去虚拟化后，具体方法可以被内联，从而触发更多优化。这是一个典型的"优化连锁反应"——**去虚拟化 → 内联 → 逃逸分析 → 边界检查消除**，一层解开一层。

**怎么配合它**：热路径上，如果接口变量背后的具体类型是确定的、且编译器能看透，就能享受去虚拟化。这也是为什么"热路径尽量用具体类型而不是接口"的另一个理由——**接口不仅装箱，还会挡住去虚拟化和内联。**

## 子主题五：编译器的哲学——Go 的"够好"主义

学完这四类优化，你会注意到一个贯穿的哲学：**Go 的编译器优化，是"保守"的、追求"够好"的，而不是"激进"的、追求"极致"的。**

这和 C++/Rust 的编译器（clang/llvm、rustc 的 LLVM 后端）形成鲜明对比——那些编译器做极其激进的优化（自动向量化、循环展开、复杂的逃逸分析），代价是**编译极慢**、**二进制大**、**调试难**。

Go 的选择是：

- **编译要快**：Go 的编译速度是它的一大卖点，所以优化不能太激进（太激进的优化要花大量编译时间）。
- **二进制要小**：不做激进内联、不做代码膨胀。
- **可预测**：Go 代码的性能行为相对可预测，不会出现"改一行代码性能天翻地覆"（C++ 里很常见）。

这是 Go"简单、务实"哲学在编译器上的体现：**不做"最优"的编译器，做一个"足够好、足够快、足够可预测"的编译器。** 理解这一点，你就能理解为什么 Go 的性能有时不如手写 C++/Rust，但它的开发体验和可维护性，是那些"极致优化"语言给不了的。

## 子主题六：SSA 后端——所有现代优化的地基

先抛一个尖锐的问题：**Go 1.7 之前，Go 编译器也有内联、也有逃逸分析。那凭什么说"SSA 才是分水岭"？内联和 SSA，谁先谁后？**

答案有点反直觉：**内联和逃逸分析都发生在 SSA 之前，但它们的"收成"取决于 SSA 之后的世界；而边界检查消除这类优化，在没有 SSA 的年代根本做不干净。**

### SSA 到底是个什么东西

一句话：**每个变量只被赋值一次（static single assignment）。**变量第二次被写，编译器就给它换个新名字 v1、v2、v3……在分支汇合处，用一个叫 **phi 节点**的特殊指令来"选择"值到底来自哪条分支。

```go
// 源码
x := 1
if cond { x = 2 }
use(x)

// SSA 形状（示意）
v1 = 1
if cond { goto B2 } else { goto B3 }
B2: v2 = 2; goto B3
B3: v3 = phi(v1, v2)   // 汇合：来自左边用 v1，来自右边用 v2
use(v3)
```

**为什么这一个小改动能撬动整个优化体系？**

因为优化的本质是：**证明一个事实，然后基于这个事实改写代码。**而"证明"要靠数据流分析。在普通 IR 上，你想知道"这一行的 x 是多少"，得回溯"此前所有可能写过 x 的地方"，在控制流图上反复迭代到不动点；在 SSA 上，**定值唯一，每条 use 用一根指针直接指向它的 def**，定义-使用链是现成的。

生活类比：普通 IR 像一屋子人共用一块白板，你问"白板上这个 a 现在是多少"，你得追问"谁在什么时候擦改过"；SSA 像是给每个人发一张自己的纸，你想知道谁的，直接看他那张。**前者要开个会核对，后者瞄一眼就行。**

### Go 的 SSA 流水线（简化版）

1. 语法树 → 类型检查 → 中间 IR
2. **逃逸分析**（跑在 IR 上，早于 SSA）
3. **内联**（跑在 IR 上，早于 SSA）
4. 转成"通用 SSA"（generic 阶段）
5. 通用优化轮次：几十个 pass 反复跑
6. **降级（lowering）**：把通用操作改写成具体架构的指令形态
7. 架构专属优化轮次
8. 寄存器分配
9. 生成汇编

Go 的一个设计特色值得单独说：**SSA 的优化规则不是手写 Go 代码，而是用 `.rules` 文件声明式描述的**（`generic.rules` 加各架构的 `AMD64.rules`、`ARM64.rules` 等），构建时由生成器翻译成 Go 代码：

```text
// 规则形如（示意，非原文）：
(Mul64 (Const64 [2]) x) => (Add64 x x)     // x*2 改写成 x+x
```

好处是规则可维护、可批量审查、可对齐各个架构；代价是它天然偏"局部重写"，跨大范围的重排型变换（激进的循环变换、大规模向量化）不容易表达。**这从工程机制上解释了 Go 为什么不做激进优化——不只是"不想"，是它的优化框架选了"规则化、快、可维护"这条路。**

### 几个你要记住名字的 pass

- `deadcode`：删掉不可达、无用的代码。
- `cse`：公共子表达式消除，同一个表达式算两次的，合并成一次。
- `fuse`：指令融合，比如把"比较 + 分支"压成一条更便宜的指令。
- **`prove`：这是边界检查消除的发动机。**它沿控制流传播"事实"——`i < len(s)`、`p != nil`、`v 的取值区间 [min,max]`。凡是被 prove 判定为恒真的检查，就可以直接删掉。
- `nilcheck`：nil 检查消除，和 prove 同源同理（你写 `p.x` 时编译器插的 nil 检查，很多能被证明多余后删掉）。
- `decompose builtin`：把 `copy` / `append` / `make` 这些内置操作拆成机器能吃的形状。
- 寄存器分配：Go 1.17 前后这一块（配合**调用 ABI 从栈传参改为寄存器传参**）有明显改进，官方给出的实测提升在 5% 上下。

### 所以 SSA 的价值到底是什么

**SSA 本身不直接给你性能，它给编译器"看得见"的能力。**

- 边界检查消除要证明索引区间 → 需要 prove，prove 活在 SSA 上；
- 去虚拟化要知道接口值的具体类型沿控制流怎么流 → 需要 SSA 上的值流分析；
- 更精确的逃逸/指针分析 → def-use 链清晰才做得动。

没有 SSA，这些优化要么做不了，要么只能做"就近的小聪明"（比如只在同一个基本块内认 `if i < len(s)`）。**Go 1.7 先把 SSA 后端落在 amd64 上，随后几个版本铺开到全部架构，从此 Go 的优化能力才谈得上"现代"。**

顺带修正一个常见误解：**逃逸分析和内联并不是"靠 SSA 才做出来的"**，它们在 SSA 之前就存在。Go 的逃逸分析跑在 IR 上，本质是一个基于"位置（location）"的、流不敏感的图分析（不考虑语句顺序，只看赋值边）。这也解释了它为什么会"过度保守"——**有些对象其实只在某段代码里逃逸，但流不敏感的分析看不见"某段"这种概念，只能一刀切判逃逸。**这跟第二章说的"内联和逃逸分析互相放大"是一回事：内联把跨函数变成同函数，等于替流不敏感的分析消除了它最怕的那种模糊性。

## 子主题七：内联的决策机制——预算、代价模型，以及为什么不无限内联

问题很自然：**既然内联是"优化之母"，为什么不把预算拉满、所有函数全内联，世界清净？**

三种答案，从浅到深。

浅的一层：**二进制会炸。**每个调用点都复制一份函数体，代码量指数级膨胀。

深的一层：**指令缓存会炸。**CPU 取指令不是一条条取，是按 cache line（常见 64 字节）从 L1i 整块取。你的热循环如果因为内联膨胀到跨好几个 cache line，每轮取指都要等；而一次函数调用的开销也就几条指令。**"省了跳转，赔了取指"，是过度内联最典型的翻车。**

最深的一层，也是最多人没意识到的：**寄存器压力会反弹。**函数被内联后，两个函数的局部变量挤在同一套寄存器里分配。通用寄存器就那么十几个，变量一多，分配器就得把一部分 spill（溢出）到栈上——**你省掉了 call/ret，却换来一堆 load/store。**

生活类比：内联就像把下属的活全揽到自己身上。沟通成本（call）省了，但你桌上同时摊开的事变多，脑子（寄存器）装不下，就得时不时翻本子（spill 到栈）。**揽活省下的时间，被翻本子的时间吃掉了。**所以优化圈有句老话：**内联不是免费的，它只是把成本从"调用"挪到了"分配"。**

### Go 的预算机制

Go 用的是一个简明的 **cost 预算**模型：给函数体的每个节点算一个 cost（不同语句权重不同），总 cost 超过预算就不内联。默认预算是 **80**（编译器源码里就叫 inline budget）。

```bash
$ go build -gcflags='-m -m' ./...
./main.go:3:6: can inline add with cost 4 as func(int, int) int { return a + b }
./main.go:9:6: cannot inline heavy: function too complex: cost 142 > budget 80
```

注意：**`-m` 只说结论，`-m -m` 才给 cost。**想知道"差多少才能进"，必须两遍 `-m`。

除了 cost，还有一批"硬性不可内联"的情形，你在输出里会看到形如 `cannot inline f: unhandled op ...` 的判决：

- **递归函数**（自己调自己——内联到第几层算完？）；
- 含 `go` / `defer` / `select` 等复杂控制结构的函数；
- 被显式标记 `//go:noinline` 的函数。

再提醒一次：**哪些语法结构属于"不可内联"是随版本变化的**（历史上 `for` 循环、闭包都曾属于这一类，后续版本逐步放开了一部分）。**别背结论，看你手上那个 Go 版本的 `-m` 输出。**

### 中栈内联（mid-stack inlining）

Go 1.12 引入了 **mid-stack inlining**，这是个非常"Go 味"的改进：以前只有"叶子函数"（不调用别人的函数）容易被内联，现在**一个函数即使调用了别的函数，只要整体 cost 合适，也能被内联**。

这直接成全了一个经典写法——**快路径模式**：

```go
func Write(p []byte) (int, error) {
    if fast(p) {           // 快路径：极短，希望被内联
        return len(p), nil
    }
    return slowWrite(p)   // 慢路径：单独一个函数，不污染快路径的代码密度
}
```

没有 mid-stack inlining 时，`Write` 因为调了 `slowWrite`，基本与内联无缘；有了它，`Write` 可以被内联进调用点，热路径只留下最短的那几行，慢路径那一支甚至有机会被判定为冷代码。**这解释了为什么你在标准库里总能看到"快路径 + 慢路径外提"的写法——它不只是可读性，它是在给内联铺路。**

### 怎么配合

- **热路径上的小函数，保持小。**一个 30 行、逻辑简单的函数，比一个 200 行的大函数更容易进预算，也就更容易触发后续那一串连锁优化。
- 反过来，**别为了"可内联"把大函数硬拆成十个互相调用的小函数。**调用链一长，cost 累加，反而可能一个都进不去；而且拆出来的函数如果各自都让对象逃逸，收益更差。**拆分的目的是让"热的那一小段"变短，不是让总行数变少。**
- 想强制某函数不被内联，用 `//go:noinline`（写基准对照时很好用）。
- 想知道内联到底贡献了多少，直接 A/B：`go test -bench . -gcflags='-l' ./pkg` 和默认构建对比。**这是量化内联收益最省事的办法，比盯着 `-m` 猜强一百倍。**

## 子主题八：边界检查消除的精确规则

先在开头把话说诚实，免得你把力气花错地方。

**`a[i]` 的边界检查在汇编里大致就是 `cmp` + 一条条件跳转，两条指令，而且它几乎永远预测正确**（越界是异常路径）。所以单次检查的绝对成本极小。真正值得消除的场景是：**紧密循环里，每轮多出的那条比较和那条分支，会占用分支预测器项数、增加基本块数量、干扰指令调度；循环展开后更是成倍放大。**

实测通常是**几个百分点**，不会翻倍。**BCE 是"顺手拿的最后一分"，不是"从 0 到 1 的银弹"。**别为了它把代码写得面目全非。

说清楚这个，再看规则。

### 编译器凭什么敢删

靠 prove pass 维护的**区间事实**：它为每个整数值维护一个取值区间（下界/上界），沿控制流传播，并对循环里的归纳变量做推导。凡是被证明"必然在区间内"的检查，直接删掉。

### 能删的典型情形

**（1）支配性条件**

```go
if i < len(a) {
    _ = a[i]      // 检查被删：能走到这行，说明 i < len(a) 成立
}
```

关键词是**支配（dominate）**：条件必须"支配"使用点，也就是走到 `a[i]` 之前必然经过这个判断。反过来写也一样有效：

```go
if i >= len(a) { return }
_ = a[i]          // 照样能删：能活着走到这，说明 i < len(a)
```

**（2）循环归纳变量**

```go
for i := 0; i < len(a); i++ { _ = a[i] }        // 删
for i := range a            { _ = a[i] }        // 删（range 语义本身就保证）
for i := len(a) - 1; i >= 0; i-- { _ = a[i] }   // 也能删：prove 能处理递减归纳变量
```

第三种要小心：**如果 `i` 被声明成 `uint`，`i >= 0` 恒真，递减到 0 之后再减就下溢，循环直接失控。**这是无符号索引的经典陷阱，别顺手写。

**（3）切片收敛后再索引**

```go
n := len(a)
if n > len(b) { n = len(b) }
a, b = a[:n], b[:n]
for i := 0; i < n; i++ {
    _ = a[i] + b[i]     // 两次检查都能删
}
```

**（4）把检查"提到循环外"——最实用的一招**

看这个：

```go
for i := range a {
    _ = b[i]      // b 够长吗？编译器证不出来 → 每轮都查
}
```

`a` 和 `b` 的长度关系编译器推不出来。两个改法：

```go
// 改法一：先显式断言，把事实带进循环
if len(b) < len(a) { return err }
for i := range a { _ = b[i] }      // 循环内检查被删

// 改法二：用"哨兵索引"把检查提到循环外（一行搞定，很 Go）
_ = b[len(a)-1]                     // 只查一次；能过，就说明 b 至少有 len(a) 个
for i := range a { _ = b[i] }      // 循环内检查被删
```

第二种看着像黑魔法，本质其实很朴素：**一次提前断言，换 N 次循环内检查的免除。**代价是循环前多一次检查，收益是循环内 N-1 次没了。这个技巧在 Go 标准库里出现过，值得记住。

### 什么会破坏它

- **索引来自编译器看不见的地方**：函数返回值、接口方法返回值、map 里的值、被闭包捕获且在循环内被改写的变量。
- **循环里改了长度**：`for i := 0; i < len(a); i++ { a = append(a, x) }`——`len(a)` 不再是循环不变量，prove 证不动。
- **索引被循环内改写**：`for i := 0; i < len(a); i++ { if c { i++ }; _ = a[i] }`——`i` 不再是规则的归纳变量。
- **无符号索引**：符号性会让下界推导变得棘手。
- **复合切片表达式**：`s[lo:hi]` 要同时证明 `0 <= lo <= hi <= cap(s)`，三个条件缺一不可；`s[lo:hi:max]` 还要额外证明 `max <= cap(s)`。

### 怎么验证

```bash
$ go build -gcflags='-d=ssa/check_bce/debug=3' ./...
# 输出会报告哪些 IsInBounds / IsSliceInBounds 被 proved，哪些没能消除
```

这是唯一能"看见" BCE 结果的方式。**记住一条纪律：看不见就别假设。**很多"我这样写应该会被优化掉"的自信，拿这个标志一照就碎了。

## 子主题九：去虚拟化的条件——编译器什么时候能"看穿"接口

先把收益说实话：**省掉一次 itab 加载和一次间接跳转，本身很便宜**（itab 是只读数据，缓存友好）。去虚拟化的真正价值只有一个：**把间接调用变成直接调用之后，它就能被内联，整条优化链才启动。**

那么问题来了：**编译器凭什么知道接口背后是谁？**

### 能看穿的情形

**（1）赋值就在眼前，且值流可达**

```go
type MyReader struct{ b []byte }
func (r *MyReader) Read(p []byte) (int, error) { /* ... */ }

func f() {
    var r io.Reader = &MyReader{b: buf}
    r.Read(p)     // 编译器知道 r 就是 *MyReader
}
```

在 SSA 上，`r` 这个接口值的类型来源唯一，可沿值流一路追到那个 `&MyReader{}` 的构造点，没有第二个来源。于是 `r.Read(p)` 被改写成 `(*MyReader).Read(r, p)`；如果 `Read` 足够小，**再直接内联进来，itab 连加载都省了。**

**（2）内联把"具体类型"从调用方带进来**

```go
func call(r io.Reader) { r.Read(p) }   // 孤立地看，编译器不知道 r 是谁

func main() {
    call(&MyReader{})                   // 但 call 被内联进 main 后，r 就是 &MyReader{}
}
```

**这就是内联和去虚拟化的双向奔赴**：内联常常是去虚拟化的前提（把具体类型暴露到调用点），去虚拟化又常常是更深层内联的前提（把间接调用变成直接调用）。两者互相喂饭，所以你才会碰到"改了一个函数的写法，性能突然翻倍"这种魔幻现象——**你不是省了一次查表，你是解开了一整条链。**

### 看不穿的情形（这才是重点）

- **接口值有多个来源（SSA 上出现 phi 汇合）：**

```go
var r io.Reader
if cond { r = &A{} } else { r = &B{} }
r.Read(p)      // 两种可能 → 不能去虚拟化
```

有意思的是：**把分支拆成两条各自调用的路径，反而各自都能去虚拟化。**

```go
if cond { (&A{}).Read(p) } else { (&B{}).Read(p) }   // 两个调用点各自去虚拟化
```

**编译器怕的不是"分支"，是"合流"。**记住这一句，很多接口性能问题就有解了。

- **来自堆、全局或数据结构**：`s.Reader` 结构体字段、`[]io.Reader` 的元素、`map[string]io.Reader` 的值、全局变量里的接口——编译器无法证明内容，一律放弃。它的接口类型传播是**流敏感但作用域有限**的分析，跨内存写入的一律不推断。

  **这就是为什么"热路径用具体类型"永远是稳赢的建议——不是因为查表慢，是因为它挡住了整条链。**

- **接口值被重新赋值过**（哪怕只在某个分支里）。
- **从函数参数传进来，且那个函数没被内联**（前面 `call(r io.Reader)` 的孤立情形）。

### PGO 的补位

**静态看不穿，就让运行时数据说话。**Go 1.21 起的 PGO 支持基于 profile 的去虚拟化：如果 profile 告诉你"这个调用点 99% 都是 `*MyReader`"，编译器就生成类似这样的形状：

```text
if 当前 itab == (*MyReader).itab {
    调用 (*MyReader).Read      // 直接调用，可内联
} else {
    走原来的间接调用           // 兜底，保证语义永远正确
}
```

**这就是"投机优化"——但注意 Go 的投机永远带着兜底分支：猜错了只是慢一点，绝不会错。**这一点在子主题十四讲 JIT 时会形成关键对照。

## 子主题十：PGO——让 profile 告诉编译器"哪儿热"

问一个根本问题：**Go 是 AOT（提前编译）的。二进制在用户机器上跑，而编译器在编译那一刻，怎么知道哪个分支热、哪个循环跑得多、哪个接口背后最常见？**

**它不知道。**这就是 AOT 相对 JIT 的结构性劣势：JIT 有运行时，AOT 没有。PGO（Profile-Guided Optimization）就是给 AOT 编译器补一张考卷——**先跑一次真实负载收集 profile，再拿这份 profile 重新编译，让编译器按真实热度做决策。**

类比：**AOT 是闭卷考试，PGO 是发你一本往年真题。题不会一模一样，但重难点分布八九不离十。**

### 版本与用法

- **Go 1.20**：PGO 以预览形式引入，需要显式指定 profile（形如 `go build -pgo=xxx.pprof`）。
- **Go 1.21**：**默认开启**。构建时会自动查找主包目录下的 `default.pprof`，找到就用（等价于 `-pgo=auto`）。想关掉用 `-pgo=off`，想指定路径用 `-pgo=/path/to/cpu.pprof`。

典型流程：

```bash
# 1. 从真实负载采集 CPU profile（生产 pprof 或基准测试都行）
curl -o default.pprof "http://prod/debug/pprof/profile?seconds=60"
# 或者：go test -bench=. -cpuprofile default.pprof ./...

# 2. 把 profile 放到主包目录（package main 所在目录）
mv default.pprof ./cmd/server/

# 3. 正常构建，编译器自动使用
go build ./cmd/server
```

### PGO 到底改变了什么

在 Go 编译器里，PGO 目前主要驱动两类决策：

1. **更激进地内联热调用点**：对 profile 里很热的调用边，编译器会放宽内联预算——**那个在冷路径上超限的大函数，在热调用点上可能被内联进去。**
2. **基于 profile 的去虚拟化**：如上一节所说，给热接口调用点生成"快路径直接调用 + 兜底间接调用"。

官方给出的收益量级是**个位数百分比**（典型区间约 2%~7%，因负载而异），但它有个巨大优点：**你几乎不用改代码。**

### 代价和坑

- **profile 必须有代表性。**拿压测 profile 去优化一个真实流量模式完全不同的服务，可能反而变慢。**PGO 是"按你给它的世界"做优化——你给错世界，它就优化错地方。**
- **构建不再只依赖源码。**profile 成了构建输入，得版本化管理、得随负载演进更新，否则半年后你手里的 profile 是古董。
- **存在反馈回路**：优化后性能变了，热点分布也可能变，理论上要重新采样。实务上定期（一个季度、或大版本迭代后）刷新一次就够。
- **可复现性**：同一份源码、不同 profile，产出的二进制性能不同。**排查性能问题时别忘了先问一句："这个是开着 PGO 构建的吗？"**

一句话总结：**PGO 是"零代码改动的性能红利"，但它是有状态的红利——你得养着那份 profile。**

## 子主题十一：编译器标志实操——你的"编译器听诊器"

先把工具摆齐（这些都是日常能用的，不是考古）：

| 标志 | 作用 |
|---|---|
| `-gcflags='-m'` | 打印内联与逃逸决策（一遍 `-m`：只给结论） |
| `-gcflags='-m -m'` | 更详细：打印内联 cost、逃逸的数据流细节 |
| `-gcflags='all=-m'` | 对**所有包**（含依赖和标准库）生效；不加 `all=` 只作用于命令行指定的包 |
| `-gcflags='-N'` | **关闭优化**（保留变量、禁用大部分 SSA 优化） |
| `-gcflags='-l'` | **关闭内联** |
| `-gcflags='all=-N -l'` | 调试标配（配 delve）：变量不被优化掉、栈帧不被内联打乱 |
| `GOSSAFUNC=函数名 go build` | 生成 `ssa.html`，可视化每个 SSA pass 前后的变化 |
| `-gcflags='-d=ssa/check_bce/debug=3'` | 打印边界检查消除的判定结果 |

几个使用要点：

1. **注意 `-gcflags` 的作用域是"命令行包"。**你想看标准库或第三方依赖的内联/逃逸，必须写 `all=-m`；反过来，`all=` 会吐出海量噪音，排查自己代码时先别加。
2. **`go test` 也能带**：`go test -run XXX -gcflags='-m' ./pkg` 是很方便的探查姿势。
3. **想量化"某个优化贡献了多少"，就用 A/B 构建**：

```bash
go test -bench . -benchmem ./pkg                 # 基线
go test -bench . -benchmem -gcflags='-l' ./pkg   # 关掉内联，看差多少
go test -bench . -benchmem -gcflags='-N' ./pkg   # 关掉优化
```

4. **`GOSSAFUNC` 是终极武器。**`GOSSAFUNC=myFunc go build ./...` 会在当前目录生成 `ssa.html`，浏览器打开后能看到 SSA 从构造到寄存器分配的每一个 pass 前后的变化。**去看一眼 `prove` 之后那一步，你对边界检查消除的理解会立刻从"听说"变成"看见"。**

## 子主题十二：如何读 `-m` 输出——把编译器的判决书翻译成人话

先给一段真实风格的输出，然后逐行翻译：

```text
./main.go:3:6:   can inline add with cost 4 as func(int, int) int { return a + b }
./main.go:9:6:   cannot inline heavy: function too complex: cost 142 > budget 80
./main.go:15:6:  cannot inline walk: unhandled op RANGE
./main.go:20:14: inlining call to add
./main.go:20:11: moved to heap: buf
./main.go:25:10: buf escapes to heap
./main.go:30:9:  leaking param: p
./main.go:33:9:  leaking param content: q
./main.go:38:12: r does not escape
```

逐条翻译：

- **`can inline X with cost N`**：预算评估**通过**，这个函数有资格被内联。**注意这只是"资格"，不代表真的内联了。**
- **`inlining call to X`**：这是**行为**——在这个调用点，真的内联了。**只有这一行才是收益兑现的证据。**看到 `can inline` 却找不到对应的 `inlining call to`，说明这次没吃到。
- **`cannot inline X: function too complex: cost 142 > budget 80`**：超预算。要么精简函数，要么接受它不被内联。
- **`cannot inline X: unhandled op ...`**：函数里有当前内联器不处理的语法结构。**清单随版本变，别背结论，看你自己的输出。**
- **`moved to heap: x`**：这个**变量**本身被放到堆上了（不是"变量的值"，是变量本身，通常因为它被取地址并且地址逃逸了）。
- **`x escapes to heap`**：这个**值**逃逸了。
- **`leaking param: p`**：参数 `p` **自己**漏出去了（被存进结构体、被返回、被塞进 interface 等）。它会让**调用方**传进来的东西跟着一起逃逸——所以改签名往往是根治办法。
- **`leaking param content: q`**：`q` 这个指针**本身**没逃，但 `q` **指向的内容**逃了（典型：`*q = somethingThatEscapes`）。
- **`does not escape`**：好消息，可以留栈。

### 推荐的阅读顺序

别一上来通读，会被淹死。按这个顺序过滤：

```bash
go build -gcflags='-m' ./pkg 2>&1 | grep 'cannot inline'                 # 1. 热函数为什么没内联
go build -gcflags='-m' ./pkg 2>&1 | grep 'moved to heap\|escapes to heap' # 2. 分配热点在哪
go build -gcflags='-m' ./pkg 2>&1 | grep 'leaking param'                 # 3. 是谁把对象带出去的
```

**一句经验之谈：`-m` 的输出是"编译器的判决书"，它只说结论不说推理。**想知道"为什么"→ 用 `-m -m` 看数据流；想知道"到底优化了没有"→ 用 `GOSSAFUNC` 看 SSA、或者直接跑基准测试对照。**三者结合，才叫真的读懂。**

## 子主题十三：用 `-N` / `-l` 定位"优化相关 bug"

场景：**一个 bug 只在 release 构建里出现，一加 `-N -l` 就消失；或者反过来。**这是最让人心慌的一类问题，第一反应往往是"编译器有 bug"。

先泼盆冷水：**绝大多数情况下，不是编译器的锅。**

三类真实原因，按概率从高到低：

**（1）你的代码本来就有数据竞争或未定义行为，只是被优化暴露了。**

```go
go func() { data = 42; ready = true }()
for !ready { }   // 编译器可能把 !ready 当循环不变量提升 → 死循环
use(data)
```

这不是编译器错，是 Go 内存模型不保证这种写法能工作。**优化只是把"偶然能跑"变成了"必然不跑"。**

**（2）内联改变了逃逸分析的结果，进而改变了对象生命周期。**

内联让"跨函数"变成"同一函数"，某些对象于是不再逃逸、分配从堆变栈。**正常情况下这只会变快**；但如果你依赖了 `unsafe`、依赖对象的 finalizer、或者依赖"对象何时被 GC"的副作用，就可能观察到行为差异。

**（3）真正的编译器 bug。**存在，但很罕见。判断依据：**能在最新稳定版上复现 + 有最小复现代码 + 在 `-race` 下依然复现。**

### 排查套路（二分法）

```bash
go build -gcflags='-l' ./...          # 只关内联，还复现吗？
go test  -gcflags='-N' ./pkg          # 只关优化
go test  -gcflags='all=-N -l' ./...   # 全关
go test  -race ./pkg                  # 先排除竞争，再谈别的
```

如果 `-l` 就不复现了，说明问题与内联相关；接着用 `//go:noinline` 逐个标记嫌疑函数，二分定位到具体是哪一个内联点导致的。

**记住这条纪律：提交 issue 之前，先在最新稳定版 + `-race` 下复现一遍。**（顺带一句：`-race` 会顺手打开 `checkptr` 检查，专门抓 `unsafe.Pointer` 的非法转换——用 unsafe 的项目尤其该跑。）

## 子主题十四：业界对照补强——为什么别人能"激进"，Go 只能"够好"

把对照做深一层，核心问题只有一个：**为什么 JVM 和 V8 敢做那么激进的投机优化，而 Go 不敢？**

答案藏在"有没有逃生舱"里。

### GCC / Clang-LLVM：`-O2` 是什么量级的激进

- `-O2` 是一整套 pass pipeline：内联、常量传播、循环不变量外提、循环展开、**自动向量化（SIMD）**、尾调用优化、C++ 的虚函数投机去虚拟化……几百个 pass，一个接一个地扫。
- `-O3` 更激进（更长的展开、更多向量化），`-Ofast` / `-ffast-math` 甚至牺牲浮点标准和 NaN/Inf 语义来换速度。
- **LTO（Link Time Optimization）**：把优化推迟到链接期，跨编译单元内联。**这是 Go 不做的**——Go 的编译单元是包，没有链接期优化。
- **AutoFGO / BOLT**：基于采样的反馈式优化与链接后优化，本质和 PGO 同宗。
- 代价：**编译时间是分钟到小时级**；调试时变量被优化掉、执行顺序被重排，"源码行"和"机器指令"的对应关系被彻底打乱。

一句话概括：**C/C++/Rust 把"优化"当成编译器的主要任务；Go 把"编译快"当成编译器的主要任务。**

### JVM：分层编译 + 去优化逃生舱

HotSpot 的执行阶梯大致是：

1. **解释器**逐条执行，同时统计调用次数、分支命中率、类型分布；
2. 热点方法交给 **C1（客户端编译器）**：快速编译，带**性能计数探针**，继续收集 profile；
3. 更热的方法交给 **C2（服务端编译器）**：拿着 C1 收集的 profile 做激进优化——深度内联、**逃逸分析 + 标量替换**（把不会逃逸的对象整个拆成几个局部变量，连分配都省了）、循环展开、基于类型分布的**投机去虚拟化**。

关键在最后一步：**C2 的优化是"投机"的**——它假设"这个调用点永远只见到 `*MyReader`"。万一运行时来了别的类型怎么办？——**去优化（deoptimization）**：丢弃这段机器码，退回解释器或 C1 重新执行，并更新 profile 重新编译。

**这个"逃生舱"就是 JIT 敢激进的底气。**

代价同样清楚：启动慢、有预热期、稳态性能受历史 profile 影响，"这个 benchmark 要跑几轮才算数"成了一门学问。

### V8：hidden class 与内联缓存

JavaScript 连静态类型都没有，凭什么快？靠两样东西把"动态"伪装成"静态"：

- **Hidden class（隐藏类 / Map）**：`{a:1}` 和 `{a:1,b:2}` 在 V8 内部属于不同的隐藏类，**属性访问的编译结果依赖隐藏类**。你顺序不一致地构造对象、或者运行时动态加属性，隐藏类就分裂，之前优化过的代码全部作废。
- **Inline cache（内联缓存）**：每个属性访问点缓存"上次见到的隐藏类 → 属性偏移"，命中就直接取偏移，不命中就退化成慢路径查表。

编译阶梯：Ignition 解释器 → Sparkplug 基线编译器 → Maglev 中层 → TurboFan 优化编译器；同样带 **deopt** 逃生舱。

**这里有个对 Go 程序员极其有用的迁移经验：V8 里"保持对象形状稳定"能大幅提速——Go 里其实同理，只是机制不同。**结构体字段顺序影响内存布局和对齐，把相同类型的字段挨着放能减少 padding；把大结构体拆成"热字段 + 冷字段"能提升 cache line 利用率。**不同的机制，同一个道理：让运行时的"预期"保持稳定，优化才生效。**

### 回到 Go：为什么它必须保守

Go 是 **AOT，没有逃生舱**。它不能投机——**因为猜错了没法退回重来**，只能靠静态证明。而静态证明是有成本的：证明得越深，编译越慢、分析越复杂、性能行为越难预测。

所以 Go 的保守不是偷懒，是**在"没有 deopt 兜底"这个前提下唯一自洽的选择**。它的取舍清单是：

- **编译要快**（开发者体验是 Go 的核心卖点）；
- **二进制要小**（部署友好）；
- **性能要可预测**（不要"改一行快三倍，改另一行慢三倍"）；
- 在此基础上，用 **PGO 这种"带证据的优化"安全地多加一点点**。

**PGO 其实就是 Go 对 JIT 的一次静态模仿：JIT 用运行时 profile，Go 用离线 profile；JIT 猜错了能 deopt，Go 只能靠兜底分支保证正确。**

| | 优化时机 | 信息源 | 投机 → 去优化 | 典型短板 |
|---|---|---|---|---|
| Go（gc） | AOT | 静态证明 + 离线 PGO | 不支持（只有兜底分支） | 峰值性能上限较低 |
| GCC/Clang | AOT | 静态 + LTO + FGO | 不支持 | 编译慢、调试难 |
| JVM HotSpot | JIT 分层 | 运行时 profile | 支持（C2 deopt） | 启动慢、预热期波动 |
| V8 | JIT 分层 | 隐藏类 + IC + profile | 支持（TurboFan deopt） | 形状不稳定就退化 |

## 子主题十五：优化心智模型——你和编译器是合作关系

最后收个尾，把这一章串成一套能天天用的东西。

### 第一原则：让编译器"看得见"

Go 编译器是个**保守的证明者**：它只做能用静态证据证明的优化。所以你的任务不是替它优化，而是**把证据摆到它眼前**：

- 想内联 → 把热路径写短、写直白；
- 想留栈 → 别让对象漏出去（别塞 `interface{}`、别无谓返回指针、别用 `reflect` / `fmt` 碰热数据）；
- 想消边界检查 → 用循环条件或前置断言把索引区间说清楚；
- 想去虚拟化 → 用具体类型，或者把具体类型暴露在调用点附近；
- 想更准 → 喂一份真实 profile（PGO）。

**一句话：编译器负责"证明"，你负责"让它看得见"。**

### 第二原则：收益排序别搞反

按真实收益从大到小，大致是：

1. **算法与数据结构**（量级差异）；
2. **减少分配 / 让对象留栈**（逃逸分析，常常是几十个百分点）；
3. **减少系统调用、锁竞争、goroutine 切换**；
4. **消除间接调用**（去虚拟化 → 内联，连锁收益）；
5. **边界检查消除**（通常个位数百分点）；
6. **指令级微调**（最不划算，且极易被下一个 Go 版本抹平）。

**很多人一上来就抠第 6 层——那是把力气花在了最不值钱的地方。**

### 第三原则：先量，再改，再量

```bash
go test -bench . -benchmem -cpuprofile cpu.out -memprofile mem.out ./pkg
go tool pprof -http=:0 cpu.out          # 找热点
go build -gcflags='-m -m' ./pkg         # 看编译器在热点上做了什么决策
# 改 → 再 bench → 对比
```

**没有基准测试的优化，都叫"我觉得"。**

### 第四原则：优化是有保质期的

Go 每个版本都在改进内联、逃逸、BCE、寄存器分配。**你今天为了绕开某个编译器限制写出的怪代码，明年可能就是负优化。**所以：

- 怪写法必须写注释，说明"我在绕什么"；
- 大版本升级后，重新验证你的优化是否还成立；
- 优先写"编译器友好且人类可读"的代码——**在 Go 里，这两者大多数时候是同一件事。**

## 业界对照

**GCC/Clang（C/C++）：** 极其激进的优化（-O2/-O3），自动向量化、循环展开、函数内联（甚至跨编译单元 LTO）、逃逸分析。性能极致，但编译慢、二进制大、优化导致调试困难（变量被优化掉、执行顺序被重排）。

**LLVM（Rust 后端）：** Rust 用 LLVM，享受激进的优化，且 Rust 的"零成本抽象"承诺依赖编译器的深度优化来兑现。Rust 的编译慢是出了名的，但换来了接近 C 的性能。

**JVM（Java）：** 优化靠**JIT（即时编译）**，在运行时做——热点代码被 JIT 编译成机器码并逐步优化（方法内联、逃逸分析、去虚拟化）。Java 的优势是"越跑越快"（JIT 有运行时信息），劣势是启动慢、预热期性能不稳。Go 是**AOT（提前编译）**，一次编译、启动即快，但少了"运行时优化"的机会。

**V8（JS）：** 和 JVM 类似，JIT + 分层编译，靠运行时 profiling 做优化。JS 的动态性让它的优化更依赖"形状（hidden class）稳定"等运行时假设。

## 版本演进小结

- Go 1.7：引入 **SSA（静态单赋值）** 后端，这是 Go 编译器优化的分水岭——SSA 让大量现代优化（边界检查消除、去虚拟化、更精确的逃逸分析）成为可能。此前 Go 编译器优化能力很弱。
- Go 1.8+：基于 SSA，持续增强内联、逃逸分析、边界检查消除。
- Go 1.12：**mid-stack inlining** 落地，成全了"快路径 + 慢路径外提"的写法；去虚拟化、内联策略持续增强。
- Go 1.17 前后：寄存器分配改进 + **调用 ABI 从栈传参改为寄存器传参**，实测性能提升约 5%。
- Go 1.20：**PGO 预览**（需显式指定 profile）。
- Go 1.21：**PGO 默认开启**（自动查找主包目录下的 `default.pprof`），并支持基于 profile 的去虚拟化。
- 持续：每次 release 的"性能提升"背后，都是这些优化的持续打磨。

主线：**Go 编译器优化的能力，从 Go 1.7 引入 SSA 后端开始有了质的飞跃，之后持续在"内联、逃逸、边界检查、去虚拟化"这几个方向上精进。但它始终守着"编译快、二进制小、可预测"的底线，宁可"够好"，不追"极致"。**

12. JVM 和 V8 能做"投机优化 + 去优化（deopt）"，Go 为什么不做？PGO 用的 profile 和 JIT 用的 profile 有什么本质区别？

【参考答案】

1. 内联把函数体"暴露"给调用点，让其他优化有机会介入：参数变常量可常量折叠；局部变量不再逃逸可留栈；接收者类型暴露可去虚拟化；去虚拟化后又可进一步内联。所以内联本身省不了多少，但它为逃逸分析、去虚拟化、边界检查消除等打开了大门，形成连锁反应，故称"优化之母"。

2. 边界检查消除是：当编译器通过数据流分析，证明某次 `a[i]` 的 i 一定不会越界时，删掉那条"比较+分支"的检查指令。配合它的关键是让编译器能推断 i 的范围——用 `for i := range a` 或 `for i := 0; i < len(a); i++` 这种"循环条件本身约束 i"的写法；避免用编译器看不透的索引；访问前做显式长度检查。这样既安全又不牺牲性能。

3. 去虚拟化是：当编译器能确定接口背后的具体类型时，把"itab 查表 + 间接跳转"变成"直接调用具体方法"。它和内联是连锁关系：去虚拟化后，具体方法可被内联，进而触发逃逸分析等更多优化。热路径用具体类型的原因之一，就是接口不仅装箱，还会挡住去虚拟化和内联——用具体类型让编译器"看得透"。

4. 因为 Go 的取舍是"编译快、二进制小、可预测"优先。激进优化（自动向量化、循环展开、深度逃逸分析）会让编译极慢、二进制膨胀、性能行为不可预测、调试困难。Go 宁可做一个"够好、够快、够可预测"的编译器，换取极快的编译速度和良好的开发体验。这是"简单务实"哲学在编译器上的体现，也是它和 C++/Rust 路线的分野。

5. SSA（静态单赋值）要求每个变量只被赋值一次，第二次写就换新名字，分支汇合处用 phi 节点选择来源。它的关键性质是**定值唯一、use 直接指向 def**，定义-使用链是现成的，不必在控制流图上反复迭代求不动点。边界检查消除（prove pass）就是一个典型依赖：它要为每个整数值维护取值区间并沿控制流传播，对循环归纳变量做上下界推导；没有 SSA 的清晰 def-use 结构，这种事实传播只能做"同一基本块内"的小聪明，跨块跨循环就证不动。补充：内联和逃逸分析其实跑在 SSA 之前，但它们的"收成"依赖 SSA 之后的世界（内联触发去虚拟化、去虚拟化再触发更深内联），所以 SSA 是整个优化体系的地基，而不是某一种优化本身。

6. Go 给函数体的每个节点算 cost，总 cost 超过预算（默认 80）就不内联；递归、含 `go`/`defer`/`select` 等复杂结构的函数、以及被 `//go:noinline` 标记的函数属于硬性不可内联。用 `go build -gcflags='-m -m'` 可以看到 `cost 142 > budget 80` 这样的判决。不把预算调大的理由除了"二进制膨胀"，还有两条更深的：**（a）指令缓存**——CPU 按 cache line 取指，膨胀后的热循环跨多个 cache line，每轮取指都要等，省下的 call/ret 远不够赔；**（b）寄存器压力反弹**——内联后两个函数的局部变量挤在同一套寄存器里，变量过多会触发 spill，把省下的调用开销换成一堆 load/store。所以内联不是免费的，它只是把成本从"调用"挪到了"分配"。

7. 三种典型破坏写法与改法：**（a）索引来自编译器看不见的地方**（函数返回值、map 值、闭包内被改写的变量）→ 把值先取到局部变量并配合显式长度断言，或改成 `for i := range` 的归纳变量形式；**（b）循环里修改了长度**，如 `for i := 0; i < len(a); i++ { a = append(a, x) }`，`len(a)` 不再是循环不变量 → 把长度先存进局部常量，或改写成先收集后 append 的两段式；**（c）两个 slice 的长度关系无法证明**，如 `for i := range a { _ = b[i] }` → 要么循环前显式断言 `if len(b) < len(a) { return err }`，要么用哨兵索引 `_ = b[len(a)-1]` 把检查提到循环外。另外 `uint` 索引和复合切片表达式 `s[lo:hi]`（需证明 `0<=lo<=hi<=cap(s)`）也是常见的失效点。诚实评价：单次边界检查只有两条指令且分支几乎永远预测正确，BCE 的实际收益通常在**几个百分点**的量级，只在紧密循环里明显；它是"顺手拿的最后一分"，不是从 0 到 1 的银弹，不值得为它把代码写得面目全非。

8. 原因是 `r` 在 SSA 上有两个类型来源，汇合处产生 phi 节点，编译器无法证明唯一的具体类型，于是放弃去虚拟化。改法是**避免合流**——把调用拆进各自的分支：`if cond { (&A{}).Read(p) } else { (&B{}).Read(p) }`，此时每个调用点的类型来源唯一，都能被去虚拟化并进一步内联。要点：**编译器怕的不是"分支"，是"合流"。**同理，接口值来自结构体字段、slice 元素、map 值、全局变量，或来自未被内联的函数参数，也都无法去虚拟化。

9. 根本问题：Go 是 AOT 编译，编译时不知道运行时哪个分支热、哪个循环跑得多、哪个接口背后最常见——这是 AOT 相对 JIT 的结构性劣势；PGO 就是给 AOT 编译器补一张"往年真题"。启用方式：**Go 1.20 为预览**，需要显式指定 profile（`-pgo=xxx.pprof`）；**Go 1.21 起默认开启**，构建时自动查找主包目录下的 `default.pprof`（等价 `-pgo=auto`），可用 `-pgo=off` 关闭或 `-pgo=path` 指定。它主要驱动两类决策：放宽热调用点的内联预算、基于 profile 的去虚拟化（生成"判断 itab → 直接调用 + 兜底间接调用"）。代价与坑：profile 必须有代表性（用压测 profile 优化流量模式不同的服务可能变慢）；profile 成了构建输入，需要版本化管理并定期刷新；同一份源码配不同 profile 产出性能不同，排查性能问题时要先确认"是否开着 PGO 构建"。官方给出的收益量级是个位数百分比（典型约 2%~7%）。

10. 用 `go build -gcflags='-m -m' ./pkg` 看判决：`can inline f with cost N` 说明有资格，`cannot inline f: function too complex: cost 142 > budget 80` 说明超预算，`cannot inline f: unhandled op ...` 说明含当前版本不处理的语法结构。**`can inline` 不等于真的内联了**——它只是预算评估通过（"资格"）；真正的证据是输出里的 **`inlining call to f`** 这一行（"行为"）。只看到前者而找不到后者，说明这个调用点没吃到内联。想看 SSA 层面究竟发生了什么用 `GOSSAFUNC=f go build` 生成 `ssa.html`；想量化内联贡献用 `go test -bench . -gcflags='-l'` 与默认构建 A/B 对比。

11. 排查顺序：**(1)** 先跑 `go test -race ./pkg` 排除数据竞争——绝大多数"关优化就好"的问题本质是未定义行为被优化暴露（例如无同步的 `ready` 标志被提升为循环不变量），不是编译器的锅；**(2)** 二分定位：`-gcflags='-l'`（只关内联）、`-gcflags='-N'`（只关优化）、`all=-N -l`（全关），看在哪一步消失；**(3)** 若 `-l` 就不复现，用 `//go:noinline` 逐个标记嫌疑函数，缩到具体内联点；**(4)** 检查是否依赖了 `unsafe` 的非法转换（`-race` 会顺带打开 checkptr），或依赖对象逃逸/GC 时机的副作用——内联会改变逃逸结果从而改变生命周期；**(5)** 只有在**最新稳定版 + 最小复现 + `-race` 下依然复现**时，才考虑是真正的编译器 bug 并附最小复现提交 issue。

12. 因为 Go 是 AOT，**没有 deopt 逃生舱**：JIT 可以投机地假设"这个调用点永远只见到 `*MyReader`"，一旦假设被破坏就丢弃这段机器码、退回解释器或基线编译器重新执行并更新 profile；Go 猜错了无法退回重来，只能靠静态证明，而证明越深，编译越慢、行为越难预测——这与 Go"编译快、二进制小、性能可预测"的核心取舍直接冲突。所以 Go 的保守不是偷懒，是没有兜底前提下的唯一自洽选择。profile 的本质区别：**JIT 的 profile 是线上实时采集、随执行动态更新、并能驱动去优化重编译的；PGO 的 profile 是离线采集、静态喂给编译器的构建输入**，因此它必须被版本化管理、定期刷新，而且 Go 的投机永远带着"兜底间接调用"分支——猜错只是慢一点，绝不会出错。PGO 本质上是 Go 对 JIT 的一次静态模仿。
