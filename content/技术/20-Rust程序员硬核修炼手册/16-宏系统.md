# 第十六章 宏系统：不是文本替换，是代码的"模具"

你有没有遇到过这种尴尬：同一个逻辑要写五遍，每遍只差一个类型名；你想抽个函数，结果发现函数表达不了——因为你要的是"在编译期按某种规律生成代码"，而不是"运行时调一段现成代码"。这时候函数摊手说"这活儿我接不了"，谁上？

我是墨叔，机房里泡了二十年。写别的语言时，这种活儿要么靠复制粘贴（然后五处一起改、改漏一处就是 bug），要么靠"代码生成器"这种额外工具链。Rust 把这件事做进了语言里，叫**宏（macro）**。但 Rust 的宏，和你脑子里那个"宏 = 文本替换"的印象，差了十万八千里。这一章，我们把宏的本质掰开，让你明白它到底是啥，又为什么"难但值得"。

先抛结论省得你迷路：**Rust 的宏是"基于结构化输入、在编译期生成 AST（抽象语法树）片段"的元编程工具——它不是字符串拼接，而是代码操作代码。** 这个区别，是理解宏的命门。

## 一、为什么函数不够用，需要宏

先说清一个前提：能写函数就别写宏。宏的调试、报错都更难，能不用则不用。但有些事函数真的无能为力，三类典型：

第一，**参数个数不定**。比如 `println!("{} {}", a, b)` 和 `println!("{}", a)` 是同一个宏，参数数量可变。函数做不到"参数数量随调用变化"（Rust 没有 C 那种可变参数函数）。

第二，**操作"语法结构"本身**。比如你想写 `vec![1, 2, 3]` 生成一个 `Vec`，或者 `println!` 里那个 `{}` 占位符要被翻译成对 `Display` 的调用——你需要在"代码写出来之前"就改写代码的结构，函数只能在"代码已经存在、运行时"才执行。

第三，**类型参数待定、要按模式铺开**。比如 `vec![1, 2, 3]` 既能造 `Vec<i32>` 也能造 `Vec<&str>`，宏可以根据传入字面量推导。

打个比方。函数像是"菜谱里的一步操作"——你给了明确原料，它按固定流程加工出成品。宏像是"一套能根据订单自动排版的模具"——它操作的是"菜谱该怎么写"，先于真正做菜。你要的是"生成菜谱"，那就不是菜谱里的一步能解决的。

如果你写过 C/C++ 的 `#define`，这里的"心智要重装"很关键：C 的宏是**纯文本替换**，预处理器把 token 当字符串盲目拼接，经常因为运算符优先级、多次求值出玄学 bug（经典的 `MAX(a++, b)` 自增两次）。Rust 的宏完全不是这回事，它看到的是**解析过的语法树**，不会盲目替换。等会儿讲到"元编程而非文本替换"那一节，你就知道这差别有多致命。

## 二、声明宏 macro_rules!：模式匹配的代码生成器

Rust 最常用、也最该先学的宏，是声明宏（`macro_rules!`）。它的核心机制特别像 `match`：你写一组"模式"，调用宏时编译器拿你给的 token 去逐条匹配，命中哪条就展开哪条对应的代码模板。

```rust
// 一个简化版 vec!：把一串元素收集成 Vec
macro_rules! my_vec {
    // 模式一：匹配零个或多个用逗号分隔的表达式
    ( $( $x:expr ),* $(,)? ) => {
        {
            let mut temp = Vec::new();
            // 对每一个匹配到的表达式 $x，重复下面这行
            $(
                temp.push($x);
            )*
            temp
        }
    };
}

fn main() {
    let v = my_vec![1, 2, 3];          // 三个表达式
    let w = my_vec![String::from("a")]; // 一个表达式也能匹配
    println!("{:?} {:?}", v, w);
}
```

拆开看几个关键点：

- `$( $x:expr ),*` 这是宏的"捕获 + 重复"语法。`$x:expr` 表示"捕获一个表达式，命名为 x"；`$( ... ),*` 表示"前面的模式重复零次或多次，用逗号分隔"。`$(,)?` 那个问号是"可选的尾逗号"，让你写 `my_vec![1, 2, 3,]` 也不报错——这是个很体贴的细节。
- 在 `=> { ... }` 的模板里，`$( temp.push($x); )*` 表示"对前面捕获到的每一个 `$x`，都把这句重复一遍"。宏在编译期就把这段展开成 `temp.push(1); temp.push(2); temp.push(3);`。

所以声明宏的本质：**它是编译期的"模式匹配 + 模板展开"，匹配的对象是经过解析的语法片段（expr、ident、ty、pat 等"片段类型"），而不是裸字符串。**

再看一个能体现"类型安全"的例子——C 的 `#define SQUARE(x) ((x)*(x))` 会因为参数被多次求值而炸，Rust 的声明宏天然规避：

```rust
macro_rules! sq {
    ($x:expr) => { {
        let _v = $x;   // 先把表达式算一次，存进局部变量
        _v * _v        // 无论 $x 多复杂，只求值一次
    } };
}
fn main() {
    let mut n = 2;
    let r = sq!(n + 1);  // 展开为 let _v = n + 1; _v * _v，n+1 只算一次
    println!("{}", r);   // 9
}
```

注意我们用 `let _v = $x` 把表达式先绑定一次，于是 `n+1` 这种带副作用的入参也只算一遍。这正是"宏看到的是结构化语法"带来的好处——它知道 `$x` 是个 expr，可以合法地塞进 `let` 绑定，而不是像文本替换那样傻乎乎地把 `n+1` 复制两遍。

## 三、过程宏：当声明宏不够表达时

声明宏够用，但有个天花板：它的"模式"能力有限，匹配的是固定形状。如果你想做更重的活——比如"读一个 struct 的定义，自动给它生成 `Debug`/`Serialize` 实现""根据一个属性标注改写整个函数"——声明宏就力不从心了。于是有了**过程宏（procedural macro）**。

过程宏的本质：**它是一个编译期运行的 Rust 函数，输入是一段 TokenStream（语法令牌流），输出也是一段 TokenStream，编译器把输出的令牌流当成你写的代码拼回去。** 它不再靠"模式匹配"，而是你用真正的 Rust 代码去解析、分析、构造新的代码。这就给了你图灵完备的能力——你甚至可以在宏里做复杂的逻辑判断、循环、查表。

过程宏分三类，各管一摊：

### 1. 派生宏（derive macro）：`#[derive(...)]`

最常用。你写 `#[derive(Debug)]`，编译器就把这个 struct/enum 交给对应的派生宏，宏生成一份 `impl Debug for 你的类型` 的代码。标准库的 `Debug`、`Clone`、`Copy`、`Default`、`Hash` 都是派生宏。

### 2. 属性宏（attribute macro）：`#[xxx]`

它能接收整个被标注的项（函数、module、struct），可以改写或包裹它。比如 `#[tokio::main]` 就是把你的 `async fn main()` 改写，包上一层运行时启动代码。它比 derive 自由——derive 只能给类型加 impl，attribute 能重写整个项。

### 3. 函数式宏（function-like macro）：`xxx!(...)`

长得像声明宏的调用，但内部是过程宏——即"像函数一样调用、但能操作语法树"。`sqlx::query!` 就是典型：它在编译期连数据库、校验 SQL、生成类型安全的代码。

## 四、#[derive] 的底层原理

很多人用 `#[derive(Debug)]` 用了很久，但不知道它背后发生了什么。墨叔给你把这个过程拆成几步，你就再也不会把它当魔法了：

第一步，你写 `#[derive(Debug)]` 在一个 struct 上。编译器在语义分析阶段，认出这是个派生宏的调用。

第二步，编译器把**这个 struct 的语法树（定义）**作为 TokenStream 喂给你的派生宏函数。

第三步，你的宏函数（比如 `derive_debug`）解析这段输入，拿到字段名、字段类型，然后**用字符串拼接/构造的方式，生成一段新的代码**——大致是：

```rust
// 宏为你生成的（示意，非你手写）：
impl Debug for Point {
    fn fmt(&self, f: &mut Formatter<'_>) -> fmt::Result {
        f.debug_struct("Point")
         .field("x", &self.x)
         .field("y", &self.y)
         .finish()
    }
}
```

第四步，编译器把这段生成的代码，像你亲手写的一样，编译进你的 crate。

所以 `#[derive]` 的真相是：**它是一段运行在编译期的代码，读你的类型定义，吐出一份实现代码。** 你省下的，是手写那堆样板（boilerplate）的功夫。而且因为生成代码发生在编译期，零运行时开销——生成的 impl 和你手写的在 release 下毫无区别。

这里必须点破一个常见误解：`#[derive(Clone)]` 不等于"我的类型自动能 clone 了"那么简单。如果字段里有某个类型自己不能 Clone，derive 会直接编译报错——因为宏生成的 `impl Clone` 里会逐个 `field.clone()`，那个不能 clone 的字段会让生成的代码通不过编译。所以 derive 是"按规则自动生成"，规则卡住时它也会老实报错，不是无脑放行。

## 五、为什么宏是"元编程"，而不是"文本替换"

这一节是整章的命门，墨叔多啰嗦几句。

所谓"文本替换"（C 的 `#define`）：预处理器完全不理解你写的代码是什么意思，它只把 token 当字符序列做查找替换。**它不知道哪个是表达式、哪个是类型、哪个是标识符，更不知道作用域和优先级。** 这就导致 C 宏的经典灾难：参数被多次求值、运算符优先级错乱、作用域污染（宏里定义的临时变量名撞上你的变量名）。

所谓"元编程"（Rust 的宏）：宏操作的是**抽象语法树（AST）层面的片段**，每个捕获都带"片段类型"（`expr`、`ty`、`ident`、`pat`、`block` 等）。编译器在喂给宏之前，已经把代码解析成了有结构的东西。于是：

- 宏知道 `$x:expr` 是一个完整的表达式，能合法地放进 `let` 绑定，不会瞎拆；
- 宏生成的代码，会重新经过编译器的正常解析和类型检查——生成出来的代码如果有类型错误，照样在编译期报给你，而不是像文本替换那样"拼完就跑了，运行时才炸"；
- 宏有自己独立的作用域，不会和你外面的变量名打架（声明宏里 `let _v` 这种临时名，编译器会处理掉冲突）。

一句话总结区别：**文本替换是"盲拼字符串"，宏是"理解语法后、在编译期重写代码"。** 前者是打字机，后者是懂语法的编辑；前者出错在运行期，后者出错在编译期。这就是 Rust 宏"难但安全"的根基——它难，是因为你要学一套"操作语法树"的思维；它安全，是因为生成的代码仍要过编译器那一关。

再打个比方。文本替换像你找了个不识字但手快的秘书，你说"把所有'老王'换成'老李'"，他就真的一字不差替了，哪怕那句话是"老王八"他也愣头青地改成"老李八"。宏像找个懂中文的编辑，他知道"老王"在句子里是主语还是人名的一部分，只在合适的地方改。区别就是"认不认字"。

## 六、给读者的务实预期：宏很难，但值得

写到这儿，墨叔得给你泼点清醒水，也给你点定心丸。

先说难在哪：

- 声明宏的 `$()`、`*`、`+`、`?`、各种片段类型，初次看像天书，报错信息也常让人摸不着头脑（"no rules expected this token"）。
- 过程宏要引入额外的 crate（`syn` 解析 AST、`quote` 构造代码），还要放在独立的 `proc-macro = true` 的 crate 里，工程结构有门槛。
- 宏一旦写错，展开后的代码出错位置常常指向生成物而非你写的宏，调试要费点劲。

但为什么值得？

- **消灭样板**。想想 `serde` 的 `#[derive(Serialize, Deserialize)]`——没有它，你给每个 struct 手写 JSON 序列化得累死，且极易写错字段名。一个 derive 顶你几百行手工代码，而且和字段定义永远同步。
- **把"不变量"焊进编译期**。比如 `sqlx::query!` 在编译期就校验 SQL 和表结构的列类型是否匹配，数据库改了字段，你的代码编译不过——这层保护，函数和普通库代码给不了。
- **DSL 与表达力**。宏让你在 Rust 里造出领域特定语言（比如 `tokio::select!`、`vec!`），让代码既安全又贴近业务语义。

墨叔的实操建议：

1. **先熟练 `macro_rules!`**。它覆盖你 80% 的"重复代码"需求，没必要一上来就啃过程宏。
2. **过程宏别自己从零造轮子**，先享受 `serde`、`thiserror`、`derive_more` 这些现成 derive 的红利；真要自己写，从 `cargo new --lib` + `proc-macro = true` 的标准模板起步。
3. **宏的文档要写清楚"展开成什么"**。因为调用者看不到展开后的代码，好的宏文档会给出"等价于手写如下代码"的示例，降低维护者的认知负担。
4. **能用函数/泛型解决，就别上宏**。宏是重武器，留着打那些函数打不下的仗。

说到底，宏是 Rust 给你的"代码的代码"能力。它难，是因为它在更高的抽象层上工作；它值得，是因为它能把重复、易错、靠人肉维护的东西，固化成编译期自动完成、且与源码永远同步的工序。等你哪天为一个 30 字段的 struct 手写第 5 份几乎一样的 impl 时，你会想起墨叔今天这句话：那一刻，宏不是炫技，是救命。

【思考题】

1. 声明宏 `macro_rules!` 里，捕获 `$x:expr` 用的是 `expr` 这个"片段类型"。请你推一下：如果 C 的 `#define` 把 `SQUARE(n++)` 这种写法替换成 `((n++)*(n++))`，自增会执行几次？而 Rust 的 `sq!(n+1)`（用我们上面 `let _v = $x` 的写法）为什么能让 `n+1` 只求值一次？这背后体现的是"文本替换"和"结构化片段"的什么差别？

2. `#[derive(Clone)]` 加在一个含有"某个字段类型本身不实现 Clone"的 struct 上时，会发生什么？请推演：宏生成的 `impl Clone` 代码长什么样，又为什么会导致编译错误而不是悄悄生成一份错误的实现？这说明了 derive 的什么本质？

3. 过程宏是一段"在编译期运行、输入 TokenStream 输出 TokenStream"的 Rust 函数。既然它本质是 Rust 函数，那它生成的代码在通过编译器后，和你手写的代码在运行时有区别吗？为什么墨叔说"零运行时开销"？反过来，过程宏本身在编译期运行，这会不会拖慢编译？你怎么看这个权衡？

【参考答案】

1. C 的 `SQUARE(n++)` 经文本替换变成 `((n++)*(n++))`，而 `n++` 是"先用后增"表达式，在乘号的左右两边各出现一次，所以 `n++` 这个带副作用的表达式被**求值了两次**，n 自增两次。这是文本替换的灾难：预处理器不懂"这是个有副作用的表达式、不该被复制两遍"，它只做盲目字符替换。Rust 的 `sq!` 因为我们写了 `let _v = $x; _v * _v`，宏把整个 `$x`（即 `n+1`）作为**一个结构化表达式**捕获，然后只把它放进一次 `let` 绑定里——`$x` 在模板里虽然写了两遍（`_v * _v`），但 `_v` 是绑定后的局部变量，不是原来的 `$x`，所以原始表达式 `n+1` 只被计算一次。差别的根源在于：C 宏操作裸 token、会机械复制；Rust 宏理解"expr 是完整表达式单元"，并通过 `let` 绑定把它"物化"一次，从而消除重复求值。这正是"结构化片段"胜过"文本替换"的铁证。

2. 当 struct 的某个字段类型 `T` 不实现 `Clone` 时，`#[derive(Clone)]` 会**编译失败**，而不是生成错误实现。推演生成的代码：宏会为每个字段生成 `field: Clone::clone(&self.field)`，对那个 `T` 字段就会写出 `field: Clone::clone(&self.field)`。由于 `T: Clone` 不成立，`Clone::clone` 这个调用过不了类型检查，编译器报"the trait bound `T: Clone` is not satisfied"。这说明 derive 的本质是**"按固定规则自动生成普通的 impl 代码"**，生成出来的代码要重新走正常编译流水线——它没有任何"绕过类型系统"的特权。所以它不会"悄悄生成一份错的"，而是"生成的代码通不过编译就老实报错"。这恰恰印证了上一节的核心：宏生成的代码依然受编译器全部规则约束，宏只是帮你省了手写的体力，安全闸门一道没少。

3. 过程宏生成的代码，在通过编译器之后，和你手写的代码在运行时**毫无区别**——因为生成的 TokenStream 被拼回 AST 后，和普通代码走完全相同的类型检查、借用检查、优化、代码生成流程。所谓"零运行时开销"，是指宏本身不在最终二进制里留下任何痕迹，它只是编译期的一段"代码加工厂"，出厂的产品（生成代码）和你手写的等价。代价是：过程宏作为 Rust 函数，确实在**编译期**运行，会消耗编译时间和内存——复杂的过程宏（如 `serde` 派生、`sqlx` 编译期查库）确实会拖慢编译。这个权衡是"编译期贵、运行期免费"：你用一次性的编译成本，换来运行时的零开销 + 类型的强保证。对绝大多数项目，这个买卖划算；但宏用得越重，编译越慢，所以工程上要给宏"瘦身"，把复杂逻辑尽量挪到运行时库函数里，让宏只做"最小的代码拼接"。

## 小结

Rust 的宏是编译期操作语法树的元编程，而非 C 那种盲目的文本替换；声明宏靠模式匹配展开，过程宏靠 Rust 函数读写 TokenStream；`#[derive]` 的本质是按规则自动生成仍受编译器约束的 impl 代码——它难，是因为工作在更高抽象层，但值得，因为它把重复与易错固化成了与源码同步的工序。
