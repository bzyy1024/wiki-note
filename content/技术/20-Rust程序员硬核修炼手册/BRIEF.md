# BRIEF —《Rust 程序员硬核修炼手册》

> 本文件是写作总纲。所有写作代理必须先读本文，再动笔。样章见 `01-为什么是Rust.md` 与 `02-所有权.md`，风格以样章为准。

## 一、项目目标

- **总字数**：≥ 120,000 字符（含代码与标点，以 Python `len(open(f,encoding='utf-8').read())` 计；不是中文字数，技术书含大量代码与标识符）。
- **定位**：独立成体系的 Rust 硬核修炼手册。不假设读者是 Go 程序员，不写"在 Go 里你这样做、在 Rust 里那样做"的对照栏目；读者默认是**有几年经验的程序员**（懂变量、栈堆、指针、并发的基本概念），但 Rust 从零讲起、讲到深。
- **精神**：像机房泡了二十年的老兵带徒弟——循循善诱、多反问、不直接喂结论。先把问题问对，再层层剥开。案例要生动、生活化（快递柜、餐厅后厨、图书馆借书、合租公寓、装修合同都是好比喻），不要干巴巴复述文档。

## 二、读者与语气

- 读者：工作 3-8 年的后端/系统程序员，会用一门语言，但"会用不精通"，想真正吃透 Rust 的设计意图。
-  narrator 人设（墨叔）：住在协议栈里的老兵。可以调侃、可以反问、可以骂一句"你这想法危险"。不用 emoji。
- 风格：导师 vs 读者对谈。大量使用反问（"你觉得呢？""为什么编译器非得管这么宽？""换成你会怎么设计？"），但反问之后自己把思考路径铺开，不真的把读者晾着。

## 四、每章固定结构（写作代理务必遵守）

1. **开篇一句话问题**：用一句带反问的话把读者钩住（例："如果一门语言在你写错的时候拒绝编译，而不是运行时崩溃，你会觉得它烦，还是觉得它靠谱？"）。
2. **核心论述**：分 3-6 个小节，层层推进。每个难点先用生活比喻，再回到代码。代码少而准——只为锚定理解，不堆示例。
3. **特定读者连接**：在章中某处，点一下"如果你写过 X 语言，这里的心智要重装"，但不展开成对照表。
4. **章末标记（强制、成对出现）**：
   - `【思考题】` 后跟 2-3 个生活化/设计向问题（不是考背诵，是逼读者自己推一遍）。
   - `【参考答案】` 后跟对应解答（读者把答案当学习材料看，所以写详细、写推导，不要只给结论）。
   - 标记写法：方头括号直接跟文字，独立成行，`## 思考题` / `### 思考题` 这类也统一成 `【思考题】`。
5. **小结**：一句话收住本章主旨。

## 五、写作风格硬要求

- 对话讨论式，多反问，不直接给结论。
- 案例生活化（快递柜、餐厅、图书馆、合租、装修合同、停车场）。系统概念用比喻讲清后再上代码。
- 讲设计意图，不讲条文罗列。知道 Rust 为什么这么设计，比背下所有规则有用。
- 代码少而准，用 Rust 真实语法（```rust 代码块），注释用中文。代码只用来"钉"住理解。
- 不用 emoji。标点用 ASCII 或中文全角。
- 把读者当聪明人：不啰嗦已懂的，专攻半懂和误区。

## 六、禁止事项

- 禁止写成 API 文档搬运 / 教程流水账。
- 禁止堆砌代码而无讲解。
- 禁止在正文行内写"【思考题】"字样当普通词（会被校验脚本误判），标记只用于章末独立成行。
- 禁止出现"记住就行"——必须讲 why。
- 禁止假设读者是 Go 程序员做系统性对照（角度已定为独立体系）。

- 每章 ≥ 6,000 字符（含代码）。不足必须扩展，不得糊弄。
- 校验命令（用 Python，因为本机 bash 的 wc 不可用）：

  ```python
  p = r"C:\Users\admin\Desktop\Rust程序员硬核修炼手册\<文件名>.md"
  t = open(p, encoding="utf-8").read()

  ```

- 代理返回：所写文件清单 + 每个文件的字符数。

## 八、质量底线

- 跑题、水字数、把思考题当摆设——一律重写。
- 思考题必须有"逼读者自己推导"的锐度；参考答案必须给出完整推导，不是一句话结论。
