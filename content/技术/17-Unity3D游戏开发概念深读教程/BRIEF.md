# BRIEF —— 本教程的写作规范（给后续撰写者 / 子代理）

> 本文件是《Unity3D 游戏开发概念深读教程》的统一规范。任何续写章节、并行代理、或后续迭代，都必须先读本文件并严格遵守。

## 一、读者定位
- 懂编程逻辑（会写 Go / 基础算法 / 变量数组函数概念），但对**游戏、计算机图形、音频 DSP、3D 数学**是全新领域。
- 因此：可以用编程类比（变量、数组、循环、函数、内存）来桥接，但图形 / 声音 / 3D 概念必须从零讲。
- **不适用**"禁技术词"规则（那是给普通职场人书库用的）。本教程读者是程序员，术语可用，但第一次出现必须解释。

## 二、统一写作方法（溯源学习法）
每一章 / 每一核心概念，固定走：
```
自然现象  →  现实中遇到的问题  →  工程师拿出的方案  →  方案落进引擎成了哪些参数
```
章节末尾读者应能回答三句话：
1. 这个东西在现实世界里对应什么？
2. 没有它会出什么岔子？
3. 引擎给了哪几个旋钮来对付它？

## 三、固定章节结构
每章文件：
- 一级标题 `# 第 X 章 标题`
- 开头用 1–2 段"导师对谈"引入（用"你""我"对话感，多反问）
- 主体分小节（`## 1.x` 或 `### 1.x`），每节讲清"现象→问题→方案→参数"
- 章末必须有且只有一对标准标记，独立成行、不加空格：
  - `【思考题】` 后跟 2–4 个问题
  - `【参考答案】` 后跟对应答案（答案可再反问，引导深入）
- 避免空话、避免堆术语、避免"记住就行"。

## 四、标记规范（硬性）
- 章末标记必须写作：`【思考题】` 和 `【参考答案】`（方头括号，无前缀、无空格）。
- 正文里**不要**用 `【思考题】` 当普通文字（会被校验误判）。
- 每个教学章必须同时含这两个标记，且数量配对。

## 五、风格要求
- 导师人称：我用"我"，读者称"你"。语气：循循善诱、多反问、生活化类比（邮局、快递柜、餐厅、合同、地图）。
- 类比要狠且准，但类比完必须落回技术本质。
- 参数讲解必须落到"它解决什么问题"，再给典型取值与调参直觉。
- 不灌水：宁可一节讲透，不铺十节水词。

## 六、质量与字数
- 每章目标中文 6000–12000 字（按 `len(re.findall(r'[一-鿿]', t))` 计中文字数，非总字符）。
- 核心章（坐标 / 雾化 / 音频采样 / 音频格式）可到 10000–12000。
- 写完后用 Python 自验中文字数，不足则扩写。

## 七、文件与命名
- 目录：`C:\Users\admin\Desktop\Unity3D游戏开发概念深读教程\`
- 文件名：`01-开场.md`、`02-坐标.md` … 两位序号 + 短横线 + 中文标题，去 `/ \ : * ? " < > |`。
- `00-导读.md` 是全书的 TOC 与指南（已存在），续写不要覆盖。
- 所有章节的相对链接以 `00-导读.md` 为根。

## 八、禁止事项
- 不写"本教程将介绍…"这类空洞导语超过两句。
- 不堆砌 Unity 菜单路径当正文（可提，但必须解释背后原理）。
- 不用 emoji。
- 不复制粘贴官方文档，要转成"为什么"的讲解。
