# 案例库 · 第二类：真实攻击事件

> **这一类练什么：** 一场真实的入侵是怎么打穿的。用「攻击链」找失守点，用「四要素」复盘"哪一环断了"。
>
> **读法：** 每个案例先问自己——"如果我是这个公司的安全负责人，我哪里做错了？"
>
> **本类口诀：** 真正的失守点，几乎都不在技术，在**流程**和**信任边界**。你被攻破，往往不是因为你技不如人，而是因为你"信任了不该信任的东西"。

---

## 案例 06：SolarWinds 供应链攻击

**问题：** 如果你的软件供应商自己被人黑了，你怎么防？

**案例：** 2020 年底，IT 管理软件厂商 SolarWinds 的 Orion 平台被黑客入侵，攻击者在软件的**更新包**里植入后门（SUNBURST）。随后数月，这个"带毒更新"被推送给约 1.8 万家企业客户，包括美国多个政府部门和微软、FireEye 等安全巨头——**受害者是"主动把攻击者请进家门的"**。

**一般人怎么想：** "我的监控做得够好了，服务器、网络、端点都盯得死死的，谁还能进来？"

**咱们怎么想：** 你的监控再强，也看不到**供应商的构建服务器**里发生了什么。这个案例打的是"信任"——**你不设防的那些东西，恰恰是攻击者最爱的入口**。

**分析过程：**

1. **这是一次"威胁"的错位**：攻击者不打你，打你的上游。你的"看"（监控）能力，部署在自己边界内；而攻击发生在**你的边界之外**——SolarWinds 的编译环境里。**你的防御半径，根本没覆盖到威胁的实际来源。**
2. **信任边界被攻破**：威胁建模（STRIDE）里有一个容易被忽略的边界——**"信任边界"不只在你系统内部，还延伸到你的供应商、你的第三方组件**。你信任了 SolarWinds 的更新，就等于信任了它的整条供应链——包括它那些可能已经被黑的分包商、构建服务器、签名流程。
3. **影响为何这么大**：中招的是"安全公司 FireEye 自己"和一堆政府机构。**连顶级安全团队都没第一时间发现**，说明这类攻击的"隐蔽性"几乎让传统检测失效——因为它走的是"你主动信任的通道"。
4. **怎么办（事后行业补的课）**：SBOM（软件物料清单）+ 供应链审计 + 二进制完整性校验——核心目的就一个：**让"你装的这个更新，到底是不是厂商签名的原版"变得可验证**。也就是给"信任"装上"验证"。

**一句话启发：** 你防御体系里的"信任"，往往就是最大的攻击面。凡是"你无条件信任的外部输入"——供应商、组件、插件、镜像——都值得重新审视。**信任不是免费的，它需要被验证。**

## 案例 07：Equifax 1.47 亿人数据泄露

**问题：** 一个已经有补丁的漏洞，怎么让信用巨头赔了 7 亿美元、CEO 下台？

**案例：** 2017 年，美国信用机构 Equifax 被攻击，泄露 1.47 亿人的社保号、驾照号等敏感数据。攻击者利用的正是**案例 02 里的 Struts2 S2-045**——而这个漏洞的补丁，Equifax **早该打但没打**。事后调查发现，内部补丁管理和漏洞扫描都形同虚设。

**一般人怎么想：** "信用巨头啊，肯定是遇到了什么顶尖的黑客、用了什么惊天动地的 0day 吧？"

**咱们怎么想：** 恰恰相反——**没有任何高级技术，就是捡漏。** 这个案例最有冲击力的地方，是它证明了"被攻破"和"技术强弱"几乎无关。

**分析过程：**

1. **攻击链极短**：扫到 Equifax 的 Struts2 服务 → 打 S2-045 → RCE → 拖库。**三步，全是"已知漏洞的老套路"。**
2. **失守点在哪**：不在"看"——漏洞早就公开、NVD 早就有分数、扫描器早就能扫出来。**失守在"想"和"做"断了链**：知道了漏洞（想），却没有把"打补丁"变成强制执行的动作（做）。
3. **根因是流程**：事后调查发现，Equifax 内部其实有漏洞扫描和补丁管理流程，但**流程"形同虚设"**——扫描了没人盯、派发了没人验收。**安全不是"知道"就行，是"闭环"。**
4. **影响**：1.47 亿人的社保号——这是"一辈子改不了"的身份数据（不像密码可以重置）。**影响不只是"钱"，是"不可逆的身份泄露"。**

**一句话启发：** 绝大多数真实入侵，用的都是"老掉牙的已知漏洞"。你不是被天才打败，你是被自己的"补丁拖延"和"流程空转"打败。**闭环，比技术更值钱。**

## 案例 08：Target 7000 万信用卡泄露

**问题：** 攻击者是怎么从"一家空调维修公司"打进零售巨头的？

**案例：** 2013 年，美国零售商 Target 的 7000 万张信用卡信息泄露。攻击的起点让人瞠目结舌：黑客先入侵了 Target 的**空调（HVAC）供应商 Fazio**，拿到了供应商连入 Target 网络的凭证，然后从这条"低权限通道"进入内网，**横向移动**到 POS 收银系统，植入内存抓取器偷刷卡数据。

**一般人怎么想：** "Target 这种大公司，防御肯定固若金汤，黑客一定用了 0day 才进去的吧？"

**咱们怎么想：** 又一次，**没有 0day**。攻击者最爱的从来不是"没人知道的漏洞"，而是"你没看住的信任通道"和"一张平的内网"。

**分析过程：**

1. **攻击链完整拆一遍**（Kill Chain）：侦察 → 拿下空调供应商 → 用合法凭证进入 → 横向移动 → 安装抓取器 → 数据外传。**注意：攻击者几乎每一步都"看起来是正常行为"**——用合法凭证登录、在内网正常访问，这让"检测"极难。
2. **两个致命设计缺陷（都是"信任边界 + 影响半径"问题）**：
   - ① **供应商通道没做隔离**：一个修空调的账号，能一路摸到核心 POS 网络。**你信任了供应商，却没限定"它只能访问它该访问的东西"。**
   - ② **内网是平的**：进来就能横向移动，没有分段。**影响没有被"切块"，导致一个入口点炸开全网。**
3. **最讽刺的失守点**：Target 其实装了威胁检测设备，**告警也响过**，但被海量告警淹没了、没人研判。**这又回到"想"——告警不是能力，研判才是。**

**一句话启发：** 攻击者最爱的不是 0day，是"你的供应商"和"你的平网络"。**把信任边界想清楚、把影响半径切小，比买多少安全产品都管用。**

## 案例 09：Capital One S3 桶泄露（1 亿条）

**问题：** 一个不起眼的 SSRF，怎么演变成 1 亿条银行用户数据泄露？

**案例：** 2019 年，Capital One 银行被曝泄露 1 亿条用户申请数据，全存在 AWS 的 S3 存储桶里。攻击者的入口是一个 **SSRF**：利用 Capital One 某台 Web 服务器的服务端请求伪造能力，去访问 AWS 的**元数据服务**（一个只有内网机器能访问的固定地址 `169.254.169.254`），从里面读出这台机器的 **IAM 临时凭证**，然后用这个凭证把 S3 桶里的数据全下载了。

**一般人怎么想：** "SSRF？不就是服务器能替别人发个请求吗，这种小漏洞，危害能大到哪去？"

**咱们怎么想：** 单个 SSRF 看着不致命，但你要看的是**它连起来的"链"**——漏洞的价值，很多时候不在它自己，在它能摸到的东西。

**分析过程：**

1. **完整的链**：SSRF → 读云元数据 → 拿 IAM 凭证 → 访问 S3。**SSRF 在这里不是终点，是跳板。** 单独看 SSRF 是"小脆弱性"，但放在云环境里，它成了"打开云资产保险箱的钥匙"。
2. **认知盲区在哪**：很多安全团队还在用"内网=安全"的老思路。但在云里，`169.254.169.254` 这个"内网地址"里住着"能开启一切的凭证"。**威胁变了，认知没跟上，就是最危险的脆弱性。**
3. **影响为何是 1 亿条**：因为那个被偷的 IAM 凭证**权限太大**——它本不该有"读整个 S3 桶"的权限。**如果它只有最小权限，攻击者偷到了也只能看到皮毛。**
4. **三层防御的教训**：SSRF 修复（堵脆弱性）+ **IAM 最小权限**（限制凭证的权能）+ 元数据服务防护 IMDSv2（给那个保险箱加锁）。**防御要分层，不能只堵入口——因为入口总会漏。**

**一句话启发：** 云时代的攻击链变了：一个 SSRF 值钱的不是它自己，是它能摸到的"元数据"和"凭证"。**最小权限，是最后一道、也是最重要的一道防线——它决定你被偷时，损失的是"一条"还是"一亿条"。**

## 案例 10：Uber 两次被黑（2016 + 2022）

**问题：** 一家顶级的科技公司，为什么能被"一次社工"和"一个硬编码密钥"打穿？

**案例：** Uber 是安全圈的"反面教材专业户"。2016 年，黑客在 Uber 工程师的 **GitHub 仓库里翻到了硬编码的 AWS 密钥**，用它登录云账号，拖走了 5700 万用户和司机的数据——事后 Uber 还试图隐瞒，被重罚。2022 年，一个 18 岁的黑客用 **MFA 疲劳攻击**（反复弹验证码，直到受害者烦了点了"确认"）+ 社工，拿到了内部 VPN 凭证，一路摸到了 Uber 的核心系统。

**一般人怎么想：** "Uber 这种公司，工程师都是顶尖的，代码肯定写得特别好，安全肯定没话说吧？"

**咱们怎么想：** 代码写得好不好，跟会不会被黑，是两码事。**两次被黑，都不是靠高深的技术，而是打"人"的漏洞和"配置"的漏洞。**

**分析过程：**

1. **两个失守点，都不在代码**：硬编码密钥（**配置**问题）、MFA 疲劳 + 社工（**人**的问题）。**威胁建模不能只盯着"代码漏洞"，还要盯"凭据管理"和"人的行为"。**
2. **用四要素定位**：STRIDE 里的 S（欺骗/冒充）和 I（信息泄露），很多时候是由"密钥泄露"和"社工"造成的，而不是代码 bug。**你的"脆弱性"不只在代码里，也在密钥管理和员工意识里。**
3. **影响**：两次都是海量用户数据。而且第二次（2022）距离第一次（2016）隔了 6 年，**同类问题（凭据管理）没被根除**——第一次栽在密钥，第二次栽在凭证。**复盘没做透，教训就会重演。**

**一句话启发：** 安全的最短板常常不是技术，是"人"和"配置"。代码写得再好，一个硬编码密钥就能让一切归零。**别只盯着代码里的漏洞，你的"漏洞"也可能躺在 GitHub 仓库、环境变量、和一个半夜被烦到点了"确认"的员工手里。**

## 本类小结：五个事件，一个真相

| 案例 | 失守点在哪 | 一句话 |
|------|-----------|--------|
| SolarWinds | 信任边界（供应商） | 你信任的，就是你的攻击面 |
| Equifax | 流程空转（补丁没闭环） | 知道 ≠ 做到 |
| Target | 供应商 + 平网络 | 把信任边界想清楚、影响半径切小 |
| Capital One | 凭证权限过大 | 最小权限是最后防线 |
| Uber | 密钥 + 人 | 最短板在人不在代码 |

**发现没？五场入侵，没有一场是靠"0day"打穿的。** 全是"已知漏洞""供应商""硬编码密钥""社工"。这告诉我们一个反直觉的真相：

> **攻击者不跟你拼技术，他跟你拼"疏忽"。** 你花大价钱买的先进设备，防不住"一个密钥没删""一个补丁没打""一个供应商没隔离"。

所以，把"威胁"想清楚，很多时候不是"敌人多高明"，而是"**你还有多少没看住的信任通道**"。
