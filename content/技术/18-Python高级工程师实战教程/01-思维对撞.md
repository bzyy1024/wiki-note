# 第 1 章 Python 与 Go 的思维方式对撞

> 这一章不教你任何「新语法」，而是先把你脑子里那套 Go 思维，和 Python 的设计哲学对上表。对不上表，后面所有特性你都只会「照着抄」，抄完还是不懂为什么。

墨叔：老哥，先问你一个扎心的问题。你在 Go 里写 `var x int = 5`，编译器盯着你；在 Python 里写 `x = 5`，解释器啥也不管，跑的时候才说事儿。你觉得，Python 这种「不管类型」是偷懒，还是另有算盘？

老哥：……我以前觉得是偷懒。动态嘛，灵活但是容易出事。

墨叔：这是最常见的误解。把「动态类型」理解成「不严谨」，你就永远学不会 Python 的精髓。今天咱们把根上的三件事掰开：**动态 vs 静态、鸭子类型、还有 EAFP vs LBYL**。这三样，决定了你写 Python 时每一个习惯，也决定了你代码长什么样。

## 一、动态类型不是「没类型」，是「类型跟着值走」

先破一个执念。Python **有类型**，而且很严格——它不是「没有类型检查」，是「类型检查发生在运行时，不在编译期」。

```python
x = 5
print(type(x))        # <class 'int'>
x = "hello"
print(type(x))        # <class 'str'>
```

你看，`x` 在某一刻是 `int`，下一刻是 `str`。类型没丢，只是**绑在值上，不绑在变量名上**。Go 反过来：类型绑在变量声明上，值必须符合同一个类型，想换个类型？重新声明一个变量。

> 墨叔：你品品这句话——「Go 是变量有名分，Python 是值有名分」。名分这词俗，但准。

这带来什么实质区别？Go 里你写错类型，编译都过不了，错误死在出厂前，根本进不了生产。Python 里，类型错误要等代码**真的跑到那一行**才炸。所以 Python 的工程化重点，不在「编译器帮你拦」（它没有），而在「测试 + 类型注解 + 运行习惯」三件套——后面第 2 章专门讲类型注解怎么补这块短板。

```python
def add(a, b):
    return a + b

print(add(1, 2))        # 3
print(add("a", "b"))    # "ab"
print(add([1], [2]))    # [1, 2]
```

同一个 `add`，对整数、字符串、列表行为完全不同。Go 里你得写三个函数或者用泛型加约束。Python 里「`+` 能干啥，值自己说了算」。这叫**多态靠值，不靠声明**。好处是代码短、适配广、写起来爽；代价是「传给它个奇怪的东西，跑起来才发现问题，而且问题可能在很深的调用栈里才爆」。

再给你一个更扎心的例子——变量可以指向完全不兼容的东西：

```python
x = 10
x = "now a string"
x = lambda: 42
x = [1, 2, 3]
```

Go 编译器看到这个会直接红。Python 完全允许。这不是 bug，是特性：**名字只是个便利贴，贴在谁身上谁说了算**。你作为高级工程师要养成的直觉是——别滥用这种自由，用类型注解把「这里应该是什么」写下来，既是给 mypy 看，更是给三个月后的自己看。

## 二、鸭子类型：看着像鸭子、叫得像鸭子，那就是鸭子

墨叔：老哥，Go 里你要让一群东西「都能叫」，得先定义接口 `type Quacker interface { Quack() }`，然后让类型**显式地**去实现它（哪怕 Go 是隐式实现，编译器也要在赋值那一刻确认）。Python 里压根不用声明——只要一个对象有 `quack()` 方法，你就能当鸭子使。这叫**鸭子类型（duck typing）**。

```python
class Duck:
    def quack(self):
        return "嘎"

class Person:
    def quack(self):
        return "我模仿鸭子：嘎"

def make_it_quack(thing):
    return thing.quack()   # 不关心 thing 是什么类，只要有 quack 就行

print(make_it_quack(Duck()))     # 嘎
print(make_it_quack(Person()))   # 我模仿鸭子：嘎
```

关键点：**`make_it_quack` 没有、也不需要声明参数类型**。它只依赖「你传进来的东西恰好有个 `quack()` 方法」这个事实。这就是「约定优于声明」——不用写 interface，大家心照不宣。

老哥：等等，那 Go 的 interface 不也是「只要有这些方法就算实现」吗？隐式实现啊，也没见你写 `implements`。

墨叔：问得好，这里有个精妙的分歧，你抓住要害了。Go 的 interface 是**静态、编译期校验**的——编译器在 `var q Quacker = Duck{}` 这一刻，确认 `Duck` 真的有 `Quack()` 才让你赋值。Python 的鸭子类型是**运行时、按次调用**才校验：你传个没 `quack` 的对象，函数定义时不报错，执行到 `thing.quack()` 那一行才抛 `AttributeError`。

一个是「出厂前验明正身」，一个是「用的时候才验」。所以 Python 写大型项目时，光靠鸭子类型会心虚——这正是 **`typing.Protocol`**（第 2 章）存在的理由：它用静态类型把「鸭子类型」重新变得可检查。你看，Python 社区不是不知道痛，是在用 Python 自己的方式补，而不是照搬 Go。

真实项目里鸭子类型长这样——一个插件系统，每个插件只要实现 `handle()` 就能被统一调度，没人去定义中央接口：

```python
plugins = [EmailPlugin(), SmsPlugin(), WebhookPlugin()]
for p in plugins:
    p.handle(event)   # 各自 handle 实现不同，调度方一概不关心
```

## 三、EAFP vs LBYL：两种「防错姿势」

这是 Go 思维和 Python 思维分歧最大、也最影响你代码长相的地方。

- **LBYL（Look Before You Leap，先看后跳）**：做事前先检查。「跳之前先确认地面没问题。」
- **EAFP（Easier to Ask for Forgiveness than Permission，请求原谅比请求许可容易）**：直接干，出错了再捕获。「先跳，摔了再说。」

Go 是典型的 LBYL 文化：`if err != nil` 本质就是「先确认没出错再继续」，层层防御。Python 官方哲学（Zen 里那句 *It's easier to ask for forgiveness than permission*）推崇 EAFP，靠异常机制实现。

```python
# EAFP 风格（Python 推荐）
try:
    value = d["key"]
except KeyError:
    value = default

# LBYL 风格（也能写，但 Python 里略显啰嗦）
if "key" in d:
    value = d["key"]
else:
    value = default
```

为什么 Python 偏爱 EAFP？两个实在理由：

1. **竞态更小（TOCTOU 问题）**。LBYL 里「检查」和「使用」是两步走，中间可能出事——你 `if "key" in d` 检查完，另一个线程把 key 删了，你再用 `d["key"]` 照样炸。EAFP 把「检查+使用」合成一步（解释器保证原子性），反而更安全。
2. **正常路径更干净**。`try` 里是「正常业务」，异常分支处理意外，读代码时一眼看清主线。LBYL 把「防御代码」和「业务代码」搅在一起，正常逻辑被淹没在 `if/else` 里。

但墨叔得泼盆冷水：**EAFP 不等于「到处 try」**。它适用于「意外、罕见、确实异常」的情况。如果是正常的业务分支（比如「用户没登录就跳登录页」），那不是异常，别用异常当流程控制——这是新手最爱犯的错，第 12 章细聊。另外，EAFP 的异常捕获有微小性能成本，热路径上别滥用。

## 三·补、一张对照表：把思维翻译过来

光说不练假把式，给你一张「Go 习惯 → Python 写法 → 要注意的坑」的速查表，后面每章都会反复印证：

| 你在 Go 里的习惯 | Python 对应思路 | 别踩的坑 |
|---|---|---|
| `var x int`，类型绑变量 | 名字只是便利贴，类型绑值 | 别假定变量「一直是 int」，用注解写明意图 |
| `if err != nil` 层层判断 | `try/except` 一把收异常（EAFP） | 别把正常业务分支写成异常 |
| 显式实现 `interface` | 鸭子类型，有方法就能用 | 返回类型/语义靠默契，大项目用 `Protocol` 补 |
| `defer f.Close()` | `with open(...) as f:` | 资源释放交给上下文管理器，别手写 |
| `go func()` 起协程 | `asyncio`/`threading`/`multiprocessing` | GIL 挡着，选错模型白忙（第 14 章） |
| `package` + 显式导入路径 | `import` + 模块/包 | 循环导入、`sys.path` 暗坑（第 9 章） |
| `testing.T` + 表驱动测试 | `pytest` + `parametrize` | 测试文化不同，但思路相通（第 21 章） |

这张表不是让你「用 Python 写 Go」，而是给你一个**翻译层**：遇到不会写的 Python，先想「Go 里我怎么干」，再找 Python 的对应物，最后注意差异。差异才是你该重点学的地方。

## 四、把三件事串起来：一个贴近项目的例子

假设你在写一个「根据配置决定用什么存储后端」的工厂。看 Python 怎么用上面三件武器：

```python
class LocalStore:
    def save(self, key, value): ...

class S3Store:
    def save(self, key, value): ...

def get_store(config):
    # 鸭子类型：不关心具体类，只要 .save 能用
    backend = config.get("backend", "local")
    stores = {"local": LocalStore, "s3": S3Store}
    try:
        return stores[backend]()      # EAFP：拿不到就 KeyError
    except KeyError:
        raise ValueError(f"未知存储后端: {backend}")
```

这里：类型动态（返回啥类都行）、鸭子类型（`get_store` 的调用方只依赖 `.save` 方法）、EAFP（用 try/except 处理非法配置）。换成 Go，你得先定义 `Store` 接口、写类型 switch、显式返回 error——更啰嗦，但编译期全锁死，重构时编译器帮你查所有调用点。

**没有谁更好，只有谁更合适。** 这个项目要快速试错、存储后端经常加，Python 这套就省事；要强契约、多人维护、错了宁可编译不过，Go 那套更稳。高级工程师的本事，就是能根据团队规模、迭代速度、出错代价，选对武器——而不是「哪个语言我熟就用哪个」。

## 四·补、真实项目里你会踩的三个坑

讲完哲学，给你三个「动态类型 + 鸭子类型」组合拳打出来的真实坑，都是我见人栽过的：

1. **可变默认参数的幽灵**。你可能写出 `def connect(hosts=[]): hosts.append(...)`，以为每次调用拿到新列表，结果所有调用共享同一个列表——因为默认参数是在函数**定义时**就创建一次的对象。正确写法是 `hosts=None` 然后在函数里 `hosts = hosts or []`。这坑根子上是「Python 对象是引用」，和你 Go 里「切片/map 是引用」一个道理，但默认参数的求值时机是 Python 独有（第 18 章还会碰）。

2. **`==` 和 `is` 的混淆**。Go 里你比的是值（或指针地址）。Python 里 `==` 比「值相等」，`is` 比「是不是同一个对象」。`a = [1,2]; b = [1,2]; a == b` 是 `True`（值同），`a is b` 是 `False`（两个对象）。但小整数和短字符串有「驻留」优化，`1 is 1` 可能是 `True`——别依赖这个，永远用 `==` 比值，`is` 只用来比 `None`（`x is None`）。

3. **属性访问 vs 字典取值的语义差**。Go 结构体字段 `u.Name` 和 Python `u.name`（属性）看起来一样，但 Python 属性背后可以是一段计算逻辑（`@property`，第 8 章）。你以为在取字段，其实在调函数——这既是威力也是陷阱：赋值给「看起来像字段的东西」可能触发校验或报错。

这三个坑的共同点：**动态语言把「看起来简单的操作」背后藏了更多机制**。高级工程师不是不踩坑，是提前知道哪里有坑、写代码时绕开、测试时专门验。

## 五、你现在该带走的三句话

1. Python 的「松」是设计选择，不是缺陷——类型在运行时校验，靠测试+注解补。
2. 鸭子类型让你少写接口声明，但大型项目要用 `Protocol` 把灵活变可检查。
3. 写 Python 默认 EAFP，但只在「真异常」时用异常，别当 if-else 用。

## 六、把这一章变成肌肉记忆（练习）

光读不练，过三天就忘。给你三个马上能做的练习，每个都不超过十分钟：

1. **翻译一段 Go 代码**。找你上周写的一个 Go 函数（带 `if err != nil` 的），用 Python 重写，刻意用 `try/except` 替代错误判断，体会主线变干净的过程。写完问自己：和原版比，哪版你更愿意维护？

2. **故意制造一个鸭子类型场景**。写一个 `notify(sender)` 函数，不声明任何类型，让一个 `EmailSender` 和一个 `SlackSender` 都能传进去，只要它们有 `send(msg)`。然后故意传一个没有 `send` 的对象，看报错在哪一行、报什么错——把「运行时才验身」这件事刻进肌肉。

3. **给变量加类型注解**。把你练习 1 的 Python 函数，用 `typing` 把参数和返回值都标上类型（哪怕函数体没变）。用你编辑器或 mypy 跑一下，感受「动态语言也能有静态检查」的甜头。这一步直接为第 2 章铺路。

做完这三个，你对「Python 不是 Go 的劣化版，是另一套设计哲学」这句话，就不是听我说的，是自己摸过的了。

【思考题】
1. 你在 Go 里习惯写 `if err != nil` 链。现在让你用 Python 写「读文件、解析 JSON、取字段」三步，每步都可能失败。你会怎么组织代码？EAFP 和 LBYL 两种都写写看，比较哪种读起来主线更清楚。
2. 鸭子类型说「不关心类，只关心方法」。那如果团队里两个人，一个写了 `save()` 返回 `None`，另一个写了 `save()` 返回写入的字节数，调用方依赖返回值，会发生什么？这暴露了鸭子类型的什么代价？怎么用类型注解缓解？
3. 有人说「Python 的动态类型是 for 原型，Go 的静态类型是 for 生产」。你同意吗？结合你自己的项目经历，什么时候你会宁愿要编译期检查，什么时候你宁可要运行时的灵活？

【参考答案】
1. LBYL 写法：`if not os.path.exists(p): ...; if not os.path.isfile(p): ...; with open(p) as f: text = f.read(); try: data = json.loads(text) except: ...; if "field" in data: ...`。问题：每一步检查都把「正常流程」切碎，而且「检查」和「使用」之间有竞态（文件可能被别的进程删）。EAFP 写法：
   ```python
   try:
       with open(p) as f:
           data = json.load(f)
       value = data["field"]
   except (OSError, json.JSONDecodeError, KeyError) as e:
       # 统一兜底，主线清晰
       raise ConfigError(f"读取配置失败: {e}") from e
   ```
   主线（open→load→取字段）一眼看完，意外全收在 except。这就是 EAFP 在「IO + 解析」这类天然易错场景的优势。注意把多个异常合并处理，并用 `from e` 保留原始异常链（第 12 章讲）。
2. 鸭子类型只看「方法名在不在」，不看「返回什么」。两个 `save()` 同名不同返回，调用方若写 `n = store.save(k, v); log(n)` 拿到 `None` 或 `int`，下游逻辑就崩——而且**编译期/静态期发现不了**，只有跑到那行才炸。代价就是「结构契约靠默契，不靠强制」。缓解办法：`from typing import Protocol` 显式声明返回值：
   ```python
   class Store(Protocol):
       def save(self, key: str, value: bytes) -> int: ...
   ```
   再上 mypy，返回值不一致直接报错。这就把「鸭子类型」升级成「可静态检查的结构子类型」，兼顾灵活与安全。
3. 这个说法太绝对了。动态类型确实上手快、适合原型，但「for 生产」与否取决于工程纪律，不取决于语言：Python 项目用 mypy + 严格测试 + CI，照样能扛生产；Go 项目如果测试稀烂，编译过了照样线上炸。正确问法是「这个项目的出错代价、团队规模、迭代节奏，配哪种类型策略更划算」。高速试错的单人脚本，Python 动态类型爽；多人长期维护的核心服务，Go 的静态检查更省心。高级工程师按场景选，不被语言宗教绑架。
