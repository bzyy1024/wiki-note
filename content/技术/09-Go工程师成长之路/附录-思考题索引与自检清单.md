## 第一部分：全书自检清单汇总

用法：找一个安静的时间，一条一条读。**每一条都要能举出具体的例子、说出具体的人名或数字。说不出来，就不算。**

### 01-P4-执行篇-把交代的事做对

- [ ] 我能够说清楚"做完"和"交付"的区别，并且能列出我自己认可的交付标准（不少于八条）
- [ ] 我能够在我最近完成的三个任务里，至少举出一个"我主动想到了需求方没提到的边界情况"的具体例子
- [ ] 我能够在我说"做完了"之后，不需要再被人追问"那 X 情况你处理了吗"
- [ ] 我能够独立完成一次上线，包括配置变更、验证方式、回滚方案，并且提前把它们写下来
- [ ] 我能够写出让人不需要猜的代码：函数名能准确描述它做的事，参数类型不会让人传错顺序
- [ ] 我能够解释我写的每一个 `if` 是为了处理什么情况，并且能在测试里找到对应的用例
- [ ] 我能够用表驱动的方式写测试，覆盖正常路径、边界值和至少一种异常情况
- [ ] 我能够在提交之前跑完 `gofmt`、`go vet`、`go test`，并且养成习惯而不是靠提醒
- [ ] 我能够在提问之前，先把问题描述成"现象、条件、我试过的、我的猜测"四段
- [ ] 我能够在收到让我不舒服的评审意见时，先复述对方的观点再回应，而不是立刻反驳
- [ ] 我能够写出一条合格的提交信息：一句话说清改了什么，正文说清为什么，以及怎么验证
- [ ] 我能够在给别人的 PR 留评论时，区分"必须改"和"可以不改"，并且明确标注出来
- [ ] 我能够说出，我做的东西是给谁用的，以及那个人最头疼的是什么
- [ ] 我能够举出一个例子，是我主动把一件事做到"够好"就停手，而不是做到自己满意

### 02-P5-独立篇-让一块地归我负责

- [ ] 我能够说出我负责的每一个接口的线上真实数据：QPS 峰值、P99、错误率，以及出现过入参最大值
- [ ] 我能够说出我负责的功能"最多能处理多少"，并且在这个上限被突破时，系统有明确的行为（拒绝、排队、还是降级）
- [ ] 我能够给我负责的功能配出至少三个指标（流量、延迟、错误），并且知道它们异常时的第一处理动作
- [ ] 我能够说出我负责的功能上一次出故障是什么时候、原因是什么、当时怎么修的
- [ ] 我能够在功能上线之前，就写好"上线后我在哪里看到它、什么数字说明它坏了、坏了我第一件事做什么"这三句话
- [ ] 我能够给我负责的模块定义一套领域错误，并且让 `database/sql`、`net/http` 这类基础设施错误不泄露到业务层
- [ ] 我能够解释我写的每一个 `fmt.Errorf` 为什么用 `%w` 而不是 `%v`，以及调用方会怎么用 `errors.Is` / `errors.As`
- [ ] 我能够说出我项目里每一个 `_ = xxx()` 的理由，或者把它们全部补上
- [ ] 我能够做到"只在边界记一次日志"，并且日志带上足够的上下文（哪个用户、哪个操作、哪一层、什么原因）
- [ ] 我在写 `go func() { ... }()` 的时候，能够同时回答：它什么时候结束、谁通知它、它结束谁会知道、它不结束会不会拖垮别人
- [ ] 我能够给异步任务设并发上限，并且说明这个上限是怎么算出来的
- [ ] 我能够给我的服务配好连接池参数（最大连接数、最长生命周期），并且说出每一个值背后的理由
- [ ] 我能够在测试里检测 goroutine 泄漏（用 `runtime.NumGoroutine` 或 goleak），并且这个测试在 CI 里跑
- [ ] 我能够说出我项目里每一个接口存在的原因，并且删掉那些"只有一个实现且没有测试需求"的接口
- [ ] 我能够做到"接口定义在使用方那一侧"，并且接口的规模不超过我需要的最小集合
- [ ] 我能够给我负责的核心逻辑写表驱动测试，并且这些测试能够活过一次内部重构（即：测行为，不测实现）
- [ ] 我能够不用 mock 框架，只用标准库和少量 fake 完成单元测试
- [ ] 我能够在接到需求的当天，问出"谁用、多久一次、最大多少、失败会怎样、怎么知道坏了"这五个问题
- [ ] 我能够给我负责的每一个写操作设计幂等键，并且说清楚"什么算同一个意图"
- [ ] 我能够与我的 SRE / 运维至少聊过一次，问过"过去三个月我这块给你添过什么麻烦"
- [ ] 我能够写出一份"这块地的履历表"：它是什么、依赖什么、出过什么事、有什么已知隐患、出问题第一件事做什么
- [ ] 我能够打开我三个月前写的任意一个文件，不看 git log 就说清楚每一个 `if` 是为了挡住什么
- [ ] 我写的注释里，"为什么"多于"做了什么"，并且每一条 TODO 都有责任人和截止日期
- [ ] 我能够保证我写的函数不需要滚动屏幕就能读完，或者能够说明它为什么不能更短
- [ ] 我能够对标准库的高频坑（时间格式与时区、字符串拼接、`json` 解码、金额表示）说出正确的用法和错误用法的后果
- [ ] 我能够说出"我做完了"和"它跑起来了"的区别，并且举出我自己的一个真实例子
- [ ] 我能够举出一个我主动去做、没人要求、做完也没特意说的事
- [ ] 我能够说出我这块地的边界在哪，以及边界上有哪些"没人管的排水沟"

### 03-P6-独立负责篇-让一块地真正属于我

- [ ] 我能够说出我负责的每个模块的 P99、QPS、错误率的当前数值，以及它们一周前的数值，误差在 10% 以内。
- [ ] 我能够在五分钟之内，说出我负责的模块最近一次线上影响的金额、笔数和商户数量——不需要现写 SQL，因为那条语句我已经提前写好并保存了。
- [ ] 我能够列出我负责模块的全部外部依赖，并且说出每一个的超时时间、是否有降级方案、挂掉的时候我的服务是快速失败还是跟着拖死。
- [ ] 我能够在一个从没接过手的模块出问题时，不先问"这是谁写的"，而是先问"影响面多大"和"数据对不对"。
- [ ] 我能够在五分钟之内，对我负责的服务抓出 goroutine、heap、CPU 三份 profile，并且知道这三份分别该看哪个指标（`alloc_objects` 而不是 `inuse_space`，状态而不是数量）。
- [ ] 我能够在我的服务里找出分配量最大的那个函数，并且说出它每次调用分配几个对象、每个对象为什么逃逸。
- [ ] 我能够说出我代码里每一个 `sync.Pool` 的用途，并且回答三个问题：对象丢了会怎样、Get 出来后在哪 Reset、有没有大小上限。
- [ ] 我能够说出我服务里每一个长期运行的 goroutine 的退出条件，并且知道没有任何一个是"进来就不出来"的。
- [ ] 我能够指出我代码里所有 `context.Background()` 的位置，并且对每一处都说得出"为什么这里不能从上游接一个 ctx 下来"。
- [ ] 我能够说出我服务里并发度最高的那个 fan-out 的并发上限，并且说得清这个数字是压测得来的、算出来的，还是抄来的。
- [ ] 我的 CI 里跑着 `go vet`、`go test -race` 和 staticcheck，而且我不会在它们报红的时候绕过它们提交代码。
- [ ] 我能够在拒绝一个需求的时候，同时给出一个替代方案——我说的是"不这样做"，而不是"不归我"。

### 04-P7-设计篇-问题由我定义

- [ ] 我能够说出我手上正在做的项目"要改变的那个数字"是多少，以及这个数字是我问出来的还是别人给的。
- [ ] 我能够把一段模糊的需求，拆成三条以上带来源标注的约束，并且标出其中哪几条是我推测的、还没有确认过。
- [ ] 我能够说出我负责的每一个写接口的幂等键是什么，以及这个键的粒度对应的是"同一个请求"还是"同一笔业务"。
- [ ] 我能够说出我的服务里每一个并发度相关数字（连接池、worker 数、`GOMAXPROCS`、消费者并发）的依据，且依据来自下游容量而不是"默认值"或"试出来的"。
- [ ] 我能够说出一个我最近做的设计里，哪一个决定是最难改的，以及我为这个不可逆性准备了什么（降低不可逆性 / 延迟决策 / 迁移预案，三选一）。
- [ ] 我能够说出我负责的服务，堆内存峰值、GC 频率、以及分配速率最高的那个接口是哪个。
- [ ] 我能够在一次评审会上，主动说出"我最没把握的是 X"，并且给出具体的、让评审者能下嘴的位置。
- [ ] 我能够列出我团队里所有的口头规范，并且说出其中有几条已经被变成了 CI 里会红的检查。
- [ ] 我能够说出我带过的人里面，有谁学会了某样我不会的东西，并且我在他学会的那一天是什么反应。
- [ ] 我能够举出一个我主动删掉的代码（或设计），说出删掉了多少，以及删的时候我心里是什么感觉。
- [ ] 我能够说出我为"将来可能需要"而写的代码，有多少真的被用上了；如果举不出三个例子，我能够说出第二个使用者出现的概率是多少。
- [ ] 我能够在没有一个清晰问题的时候，先不写代码，而是先去问三个问题：现在没有它的时候他们怎么干的、做完之后哪个数字会变、如果只能做一半是哪一半。

### 05-P8-负责篇-为结果兜底

- [ ] **我能够把一个业务目标拆成一张表。** 不是拆成模块，是拆成点。比如"超时率从 8.9% 降到 3.0%"，这 5.9 个点里，每个点归谁、他现在为什么做不到、做到需要什么、什么时候能看出来。拆不出来，说明你还没读过题。
- [ ] **我能够在没有管辖权的情况下，让两个以上部门的同事为我做事。** 并且我能说出他们每个人图的是什么。如果我只能说"这是公司的事"，说明我还没有推动能力，我只有汇报能力。
- [ ] **我能够把技术债换算成钱。** 用一句话说清楚：还这笔债，投多少人月，换回什么，什么时候能看出来。说不出来，说明我申请的其实不是资源，是心情。
- [ ] **我能够写一份 ADR，里面有两节不是套话。** 一节叫"我们可能错在哪儿"，一节叫"什么情况下这套方案要被推翻"。写不出这两节，说明我不是在做决策，我是在做记录。
- [ ] **我能够在评审会上说"这个我做不到"，同时给出至少两个替代方案和各自的代价。** 如果我说完"做不到"就结束了，那不叫取舍，那叫推诿。
- [ ] **我能够为我的系统定义 SLO，并且说清三件事。** 这个数是怎么来的、业务认不认、超了之后谁会疼。三件里缺一件，这个 SLO 就是个符号。
- [ ] **我能够说出我负责的系统里，哪几个接口是不允许挂的，哪几个是挂了也没关系的。** 并且这个清单和代码里的 `Critical` 标记是一致的。如果两者对不上，说明我的降级设计只存在于我的脑子里。
- [ ] **我能够在三十秒内说出一个正在发生的故障的影响面。** 多少用户、多少单、多少钱、预计多久恢复。四个数缺一个，说明我没有为这件事提前准备过。
- [ ] **我能够在出事之后，不等人问，主动把坏消息说给该知道的人。** 并且说清楚我打算怎么办、需要谁配合、要花多少钱。如果我总是等它自己好，我不是在兜底，我是在赌。
- [ ] **我能够让一个我带的人，独立完成一件我做只要两小时、他做要两天的事。** 全程不抢过键盘，只在他说"我做完了"之后提问。做不到，说明我还在用改代码代替带人。
- [ ] **我能够把我脑子里"只有我知道"的东西，搬三条出来，变成会失败的代码。** 校验、启动自检、CI 检查、一条 golden test。一条都搬不出来，说明我的不可替代性不是因为我强，是因为我懒得写。
- [ ] **我能够说出明年这个目标完不成，公司会损失多少钱。** 如果我说不出来，那我要么从来没问过，要么这个目标本来就没那么重要。

### 06-P9-影响篇-让别人因我而不同

- [ ] 我能够说清楚：如果我明天开始请三个月假，我负责的这块业务会具体发生什么。我不需要猜，因为我有过去三个月的数据（事故数、交付周期、值班响应次数）支撑我的判断。
- [ ] 我能够点名说出我团队里每一个人在过去一年里新增的能力，并且能说出这个能力是在哪个具体的事情上被验证过的。
- [ ] 我能够列出至少三条"我推动过、且我今年一次都没再提、但它仍在发生"的机制。如果一条都列不出来，我去年是在救火，不是在建能力。
- [ ] 我能够列出至少三个我没有参与、但按我设定的标准做出来的技术决策。这三条里，至少要有一条是我事先没想到的用法。
- [ ] 我团队里至少有一条规范，是"所有人都在遵守，但没人记得是谁定的"。
- [ ] 我团队的技术规范里，遵守它的成本低于违反它的成本。我知道每一条规范落在哪一层：默认生成的、强制检查的、提醒的、还是只写在文档里的。
- [ ] 我手上的内部工具/包，至少有一个被我不认识的人用在了我没设想过的场景里。如果全部只在我自己的团队里用，我做的是框架，不是平台。
- [ ] 我能够说出至少一个"因为陌生人的一句话而改了自己的设计"的例子。这个例子可以来自开源 issue、社区讨论、或者跨部门的反馈。
- [ ] 我在过去半年里，至少有一次当众承认自己的判断是错的，并且说清楚了当时漏掉了什么。
- [ ] 我身边至少有一个人，在某一个具体的技术领域比我强，而且我今年至少请教过他一次。
- [ ] 我到现在还在写代码，或者在做一件"我会亲自承受后果"的技术活动。我知道这件事不是为了产出，是为了校准。
- [ ] 我能够用三句话，向一个不认识我的同行说清楚：我这支团队解决了一个什么别人也会遇到的问题。
- [ ] 我能够说出我明年打算交给别人的三件事，以及如果这三件事交出去之后我被边缘化了我该怎么办。

### 07-P10-布局篇-选择解决哪些问题

- [ ] 我能够说清楚：我押过的注里，哪一个已经验证成功了，哪一个是失败的。我说得出具体的时间、金额、人数，而不是"我当年做过一个项目"。
- [ ] 我手上至少有一件"我知道要五年才有结果，而我现在已经在做"的事。如果没有，我目前所有的投入都还在五年以内的尺度里。
- [ ] 我能够列出我做的决策中，哪些是不可逆的，以及我在每一个上面花了多少时间。如果这个比例是颠倒的（可逆的花了 95% 的时间），我知道问题在哪。
- [ ] 我能够说出我所在行业里，未来三到五年会发生的一件事，并且说出我这个判断的**证伪条件**。说不出证伪条件的判断，不是判断，是愿望。
- [ ] 我在过去两年里，至少有一次主动叫停过一件自己发起的事。如果从来没有，我是一个"永不认错"的人，而这在更高层级是致命的。
- [ ] 我能够说出：如果我现在负责的这件事失败了，谁会替我付代价。我能说出他们的名字，而不只是"团队"。
- [ ] 我做过的抽象里，至少有一个是"存在超过一年、但只有一个实现"的。我知道它每年的维护成本是多少，并且我做过一次删掉它的尝试（成功或失败都算）。
- [ ] 我维护的对外接口/协议/数据格式里，有明确的兼容性承诺文档，写清楚了"什么情况下会破坏兼容"和"提前多久通知"。
- [ ] 我手上有一件东西，是"我做过、但我不为它署名"的。如果一件也没有，我目前的全部产出都挂在我的名下，而这意味着它们会随我一起消失。
- [ ] 我带过的人里，至少有一个改过我定下的东西，而且改得比我原来的好，让我沉默过一次。
- [ ] 我至少留下过一个"不依赖我在场也能工作"的东西：一份被反复查阅的文档、一套契约测试、一条 CI 上的红线、一份反例集。
- [ ] 我能够在一个所有人都看着我、等我给方向的时候，说出"我还不知道，我们再等三个月"，并且承受得住随之而来的失望。
- [ ] 我知道我这一级最怕什么。我能用一句话说出来。如果说不出来，说明我还没有真正面对过它。

## 第二部分：全书思考题索引

用法：题目按章节排列。**不要顺着往下刷**——挑一个你现在正卡住的问题，想三天，再去看参考答案。

### 01-P4-执行篇-把交代的事做对

题一　你帮朋友搬家，把东西都搬上楼了，堆在客厅。朋友说"谢谢啊"。这时候你觉得自己做完了吗？如果你觉得没做完，那还差什么？

## 第三部分：怎么用这两份东西

### 关于思考题

全书共 114 道生活思考题。它们的设计初衷，是让你在**刷牙、通勤、等外卖**的时候还在想。

三个提醒：

**第一，不要顺着往下刷。** 一口气读完 100 多道题，只会带来一种"我好像懂了"的幻觉。挑一道你现在真正卡住的问题，想三天。

**第二，先写下来再看答案。** 拿手机备忘录，用自己的话写三行。写完再看参考答案——你会立刻看到自己漏了哪一层。这个"看到自己漏了"的瞬间，才是真正的学习。

**第三，参考答案不是标准答案。** 它们只是老陈会怎么想。你完全可以有更好的答案，前提是你能说清楚为什么更好。

### 关于自检清单

全书共 104 条自检项。建议这样做：

**打印出来，手写打勾。** 别在心里过，别在屏幕上划。手写的动作会逼你诚实。

**每半年做一次，保存好。** 一年之后对比两次的结果，你会看到自己真正在哪些地方动了，哪些地方只是"以为自己动了"。

**打不了勾的条款，就是你的下一份学习计划。** 不要从清单里挑容易的开始，挑那个让你最不舒服的。

### 最后

老陈在书里说过一句话：

> "这本书里有 7 套自检清单，加起来 70 多条。如果你全部都能诚实打勾，那你不需要这本书。如果你打完勾发现有一半是空的——恭喜，你找到起点了。"

现在，你知道起点在哪了吗？
