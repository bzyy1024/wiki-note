# K8s 系统研发从 0 到 1 · 目录与导读

> 用「如果让你从零设计一个容器编排系统」的视角，重走 Kubernetes 的设计之路。
> 每一章不告诉你「K8s 怎么用」，而是告诉你「当年那个设计决策，有哪几条路、各自代价是什么、为什么最后选了这条」。

## 一、这个教程在讲什么

**一句话结论**：Kubernetes 的精华，不在 `kubectl` 命令，而在它背后那一套**用 Go 写的分布式系统设计思想**——声明式 API、控制器模式、etcd 一致性、调度、网络、扩展机制。这些东西是「用 Go 造系统」的顶级教材，正好接得上你「自己造 ES、给行业提供方案」的目标。

我们会一起做一件事：**假设你手里什么都没有，只有一堆跑着容器的机器，怎么一步步把它们变成一个能自愈、能扩展、能让人放心交托业务负载的编排系统。**

## 二、K8s 的「身世」：先搞清它从哪来

K8s 不是凭空设计的，它有一个重要的血统——**Google 的 Borg**（内部大规模容器管理系统）。理解这个身世，很多设计决策就「为什么」了：

- Borg 管理 Google 数十万台机器、上百万容器，跑了十几年。
- K8s 是 Borg 的经验「开源化 + 通用化」的产物，创始团队很多就是 Borg 的人。
- 所以 K8s 的设计处处透着「在大规模、真实生产环境里被验证过」的克制——**它不追新，它求稳。**

> 记住这句话：**K8s 的很多「看起来保守」的设计，是因为它在为「几万台机器、几百万容器、十几年运行」这种尺度做设计，而不是为「本地跑个 demo」做设计。** 读它的时候，时刻问自己：这个设计在 10 万台机器上还成立吗？

## 五、阅读建议

1. **按顺序读**。第 02 章的「声明式」是后面一切设计的地基，跳过它，后面的「控制器」「etcd」「Operator」都会失去支撑。
2. **伪代码是 Go 风格**。K8s 本身就是 Go 写的，所以这次伪代码直接用 Go 语法——对你不是负担，反而是「这套思想在 Go 里怎么落地」的直接示范。
3. **每章有「思考的分叉」和「思考题 + 参考答案」**。参考答案是「一种站得住的推导」，欢迎反驳——反驳本身就是在建立你的系统判断。
4. **关键决策点有「思维流重放」**。在第 02、03、05、13、14、16 章，除了「结论 + 论证」，还各有一段「如果我是当年的设计者」的第一人称重放——带你从直觉出发，经历试错、卡壳、反转，一步步走到结论。**「论证」告诉你答案为什么对，「重放」告诉你答案是怎么想出来的**，后者才是能迁移到你系统里的思考能力。
4. **重点盯「为什么」而不是「是什么」**。K8s 的命令查文档就有，但「为什么这么设计」才是能迁移到你自己系统里的硬通货。

## 六、几个贯穿全文的约定

- **「编排」的定义**：跨多台机器，自动地「调度 + 自愈 + 扩缩容 + 服务发现 + 滚动更新」一组容器，而不是单机 `docker run`。
- **「声明式」的定义**（先埋个钩子，第 02 章展开）：你描述「我要什么状态」，系统自己负责「怎么达到这个状态」——和「命令式」（你一步步指挥系统做什么）相对。
- **案例来源**：真实的设计决策、KEP（Kubernetes Enhancement Proposal，K8s 的「RFC」）、以及 release note / issue 里能考证到的事实。
