# 第 10 章 · 演进到最新版：1.35 → 1.37 的设计逻辑

**一句话结论**：看 K8s 的最新版本，不要只看「加了什么功能」，要看**「为什么这些功能在这个时间点被加进来」**。1.35~1.37 的演进，本质上是在回应三个越来越强的真实需求——**「资源要用得更精细」「安全要做得更内建」「要服务 AI/批量这些新负载」**。每个新特性的背后，都是一个「老问题憋了多少年、最后怎么解」的故事。

---

## 1. 先看一条「主脉络」：K8s 在回答哪三个问题

把 1.35~1.37 的几十个增强串起来，能看出三条清晰的主线：

| 主线 | 代表特性 | 它要解决的「憋了很久的老问题」 |
|---|---|---|
| **资源精细化** | in-place resize、Pod 级资源、HPA 可调容差 | 资源要么浪费、要么一改就重启，太粗放 |
| **安全内建** | user namespaces、Pod 证书、更细的 kubelet 授权 | 安全以前靠「外挂」，现在要「内建」 |
| **新负载支持** | gang scheduling、DRA、Memory QoS、HPA scale-to-zero | AI/批量/GPU 工作负载，老调度模型不够用 |

下面挑三个最有「思考价值」的讲透。

---

## 2. 案例一：in-place resize——「改个内存为什么要重启？」憋了 7 年

**老问题**：Pod 的资源（CPU/内存 request 和 limit）在创建后就「焊死」了。你想给一个运行中的服务加内存，唯一办法是**重建 Pod**——而重建意味着**服务中断**。

这个痛点有多痛？生产环境里太常见了：业务涨了，发现内存不够，要么忍受 OOM，要么接受一次重启的中断。

**为什么憋了这么多年才解决**：因为「原地改资源」牵扯到**内核 cgroup 的运行时调整**，以及**调度器的配合**（改大资源后，节点还够不够？）——它不是「改个数字」那么简单，而是要从 kubelet 到调度器贯通一整套机制。

**K8s 的解法**（KEP-1287，从 1.27 alpha 一路磨到 1.37 GA）：

```yaml
spec:
  containers:
  - name: app
    resources:
      requests: { cpu: "100m", memory: "128Mi" }
      limits:   { cpu: "200m", memory: "256Mi" }
    resizePolicy:                     # 关键：声明「改这个资源时怎么办」
    - resourceName: cpu
      restartPolicy: NotRequired      # 改 CPU：原地生效，不重启
    - resourceName: memory
      restartPolicy: RestartContainer # 改内存：只重启这一个容器
```

**这个设计教给我们什么**：**「要不要重启」不是一刀切的，而是「按资源类型」区分的**——有些资源（CPU）内核能原地调，就 `NotRequired`；有些（内存）必须重启容器才能生效，就 `RestartContainer`。**把「看似一回事」的操作，拆成「各自合适的处理策略」，是精细化设计的关键。**

而且注意它的演进节奏：**一个特性从 alpha 到 GA，走了 7 年、跨了 10 个版本**。这恰恰体现了 K8s 的克制——**「看起来简单的功能」背后可能是「牵一发动全身的系统改动」，宁可慢，不可错。**

## 3. 案例二：Pod 级资源 + HPA 可调容差——「粗放」的代价

**老问题一：资源按「容器」粒度声明，导致 sidecar 场景极其浪费。**

以前，资源是「每个容器各自声明」的。而现代 Pod 里常常塞一堆 sidecar（日志、监控、代理），每个 sidecar 都得「按最坏情况」预留资源，导致**一个 Pod 的资源被 sidecar 们白白吃掉一大块**。

**解法（KEP-2837，1.37 转 Stable）**：允许**在 Pod 层面**声明一个「共享预算」，容器们从里面按需取用，而不是各自预留最坏值。

```yaml
spec:
  resources:            # Pod 级资源（1.37 Stable）
    requests: { cpu: "1", memory: "1Gi" }
    limits:   { memory: "2Gi" }
  containers:
  - name: app
  - name: log-shipper    # 不再需要各自声明最坏值，从 Pod 预算里分
```

**老问题二：HPA 的扩缩容「容差」被写死成 10%，憋了十年。**

HPA 决定「要不要扩缩容」，靠的是「当前指标和目标的偏差」。但这个「偏差容忍度」被写死成 10% 整整十年——**所有负载共用一个容差**。结果就是：某个「敏感」负载在 10% 附近来回抖动（频繁扩缩），你没法单独调它。

**解法（KEP-4951，1.37 转 GA）**：容差变成**每个 HPA 可单独配置**。

```yaml
behavior:
  scaleUp:
    tolerance: 0.03     # 这个 HPA 对 3% 的变化就反应
  scaleDown:
    tolerance: 0.15     # 但缩容要懒一点，避免抖动
```

**这两个案例合起来教给我们什么**：**「写死的常量」和「一刀切的粒度」，在系统长大的过程中，几乎一定会变成「束缚」。** 一开始「10% 容差」「按容器粒度」是合理的简化，但当负载多样化、场景精细化之后，这些「简化」就成了「粗放」。**好系统的演进方向，往往是把「当初的合理简化」，在需求成熟时，变成「可配置、可细化」。**

## 4. 案例三：gang scheduling——为「AI 时代的负载」补课

**新问题**：AI 训练、分布式计算这类负载，有一个和传统 Web 服务**根本不同**的特征——**「要么全来，要么全不来」**。

比如一个分布式训练任务，需要 8 个 Pod **同时**拿到 GPU 才能开工。如果调度器「一个一个地」调度，可能出现「7 个 Pod 占着 GPU 干等第 8 个，而第 8 个永远排不上」的**死锁式僵局**——7 个白白占着资源，其他任务也用不了。

**解法（1.37 转 Beta 的 gang scheduling）**：引入「**要么一次性调度整组 Pod，要么一个都不调度**」的语义，避免「部分调度导致的资源僵持」。

**这个案例的价值**：它揭示了「**通用系统遇到新负载时，往往不是『加个参数』，而是『补一个缺失的语义』**」。K8s 当年为「无状态 Web 服务」设计，天然假设「Pod 之间独立、可以一个个调度」。而 AI 负载打破了「Pod 独立」这个假设——它们**强耦合、必须一起调度**。于是 K8s 要补的不是「更多资源类型」，而是「**调度语义的补丁**」。

> 类比：K8s 原来的调度，像「餐厅翻台——来一个安排一个座位」。而 AI 训练任务，像「10 人聚餐必须拼一桌才能坐下」——你不可能让 9 个人先占着位子等第 10 个。**当新场景打破了旧假设，系统的正确响应是「认识到假设变了」，而不是「在旧假设上硬凑」。**

---

## 5. 安全内建：user namespaces 与 Pod 证书

这条线更简短，但信号很强——**安全在从「外挂」走向「内建」**：

- **user namespaces（1.36 Stable）**：让容器内的 root 不再是宿主机 root，从内核层面隔离权限。以前做这个要靠「特权降级」的各种补丁，现在内建了。
- **Pod 证书（KEP-4317）+ 信任捆绑（KEP-3257，1.37 Stable）**：Pod 能直接申请 X.509 证书、集群能统一分发信任锚。**以前你为了给工作负载发证书、发信任根，可能得上一整套 service mesh 或 cert-manager，现在核心就给了原语。**

**信号**：当某类能力「从外挂走向内建」，说明它已经足够普遍、足够关键，值得成为平台的一部分。**这又是一个「抽象时机」的判断——什么时候该把生态里的常用方案，收编进核心。**

## 思考题

**Q**：这一章里反复出现一个词——「GA（General Availability，正式可用）」。K8s 的特性要走「alpha → beta → GA」的漫长门禁，一个特性动辄好几年。这么慢，是不是太保守了？如果让你设计一个系统的特性演进节奏，你会怎么平衡「快」和「稳」？

**参考答案**：

K8s 的慢，恰恰是它的「护城河」——因为它服务的是「几万台机器、几十万服务」的生产系统，**一个「为了快而快」的坏特性，会造成灾难性的破坏**。

它的「慢」背后有一套机制，而不是「拖延」：

1. **分级门禁（alpha/beta/GA）**：每个级别有明确的稳定性承诺（API 会不会变、能不能默认开启），用户在「尝鲜」和「求稳」之间**自主选择**。
2. **灰度验证**：特性先在真实集群里跑 beta、收集反馈、修 bug，才敢转 GA。
3. **可回退**：特性都是 feature gate（开关），出问题能一键关掉，不用回滚整个版本。

所以「快 vs 稳」的平衡，答案不是「选一个」，而是**「用分级 + 开关，把『快』和『稳』提供给不同的用户」**：

- 想尝鲜的激进用户 → 用 alpha（快，但不保证稳定）。
- 求稳的生产用户 → 只用 GA（慢，但经过验证）。

**核心心法：系统演进不是「一次性决定快或慢」，而是「设计一套让不同风险偏好的人各得其所的机制」。** 这也呼应了第 7、9 章的「抽象时机」——**好系统的演进能力，来自它把「变化」本身也设计成了可管理的过程。**
