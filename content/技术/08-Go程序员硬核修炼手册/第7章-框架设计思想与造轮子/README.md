## 为什么要学 Java 框架思想

### Go 生态的对应物

| Spring 概念 | Go 生态的对应物 |
|:---|:---|
| **IoC 容器** | `google/wire`（编译期）、`uber-go/dig`（运行期） |
| **依赖注入** | 构造函数注入（Go 的惯例） |
| **AOP** | 中间件（middleware）、装饰器 |
| **Bean 生命周期** | 构造函数 + `Close()` |
| **@Component 扫描** | 显式注册（Go 没有注解） |
| **事务管理** | 手动 or `sqlx` 的 Tx |
| **Spring MVC** | `gin`、`echo`、`chi` |

**关键洞察：思想是一样的，实现方式不同。**

```
Spring 的做法：
  用注解 + 反射 + 运行时的 Bean 容器
  → 灵活，但"魔法"多，启动慢，错误在运行时才暴露

Go 的做法：
  用代码生成（wire）或者显式注册（dig）
  → 简单，编译期检查，启动快，但没那么灵活
```

> 这正是第 1 章讲的"把信息提前到编译期几乎总是划算"在框架层面的体现。

## 贯穿全章的核心思想

### 思想 1：框架的本质是"控制反转"

```
不用框架:
  你的代码 ──调用──► 库函数
  （你控制流程）

用框架:
  框架 ──调用──► 你的代码
  （框架控制流程，你只填"回调"）
```

**这就是 IoC（Inversion of Control）——"好莱坞原则"：Don't call us, we'll call you.**

### 思想 2：复杂度要么在框架，要么在用户代码

```
Spring 的选择：
  复杂度在框架（反射、代理、容器）
  → 用户代码简单（加个注解就行）
  → 代价：启动慢、调试难、"魔法"多

Go 的选择：
  复杂度在用户代码（显式调用、显式注册）
  → 框架简单（就是几个函数）
  → 代价：样板代码多
```

**没有对错，只有取舍。** 理解了这一点，你就能判断"什么时候该引入框架，什么时候该自己写"。
