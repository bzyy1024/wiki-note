# 03 · 动手：字节码虚拟机与执行引擎

> *"虚拟机的设计，跟真实 CPU 的设计面临完全相同的问题。"*

---

## 开场：为什么 JVM 用栈式，而真实 CPU 用寄存器式

> **老陈**：JVM 的字节码是基于栈的。你想想，`iadd` 这条指令做什么？
>
> **小林**：弹出两个整数，相加，压回栈？
>
> **老陈**：对。**但你有没有想过：真实的 CPU（x86、ARM）都是寄存器架构，`add rax, rdx` 直接操作寄存器。为什么 JVM 要设计成栈式的？**
>
> **小林**：……为了跨平台？因为不同 CPU 的寄存器数量不同？
>
> **老陈**：**对，这是核心原因之一。** JVM 设计于 1990 年代，目标是"一次编译，到处运行"。而要运行在 8 位单片机到 64 位服务器上，就不能假设寄存器数量。
>
> **栈式架构的好处**：
> - **指令更紧凑**：`iadd` 不需要指定操作数（隐含在栈顶），1 字节
> - **实现简单**：解释器不需要寄存器分配
> - **可移植**：不依赖具体 CPU 的寄存器
>
> **代价是什么？**
>
> **小林**：……慢？
>
> **老陈**：**对，但具体慢在哪？** 这是今天的关键问题。

---

## 两种虚拟机架构

### 栈式虚拟机（Stack-based VM）

```
计算 a + b * c:

指令                     栈状态
─────────────────────────────────
LOAD a                   [a]
LOAD b                   [a, b]
LOAD c                   [a, b, c]
MUL                      [a, b*c]
ADD                      [a + b*c]
```

**指令数量**：5 条
**每条指令很短**：1 字节操作码（操作数隐含）

### 寄存器式虚拟机（Register-based VM）

```
计算 a + b * c:

指令                     寄存器
─────────────────────────────────
LOAD  R1, a              R1 = a
LOAD  R2, b              R2 = b
LOAD  R3, c              R3 = c
MUL   R2, R2, R3         R2 = b*c
ADD   R1, R1, R2         R1 = a + b*c
```

**指令数量**：5 条
**每条指令更长**：需要指定 2-3 个寄存器（4-8 字节）

### 关键差异

| | 栈式 | 寄存器式 |
|:---|:---|:---|
| **指令数** | 相同 | 相同 |
| **指令大小** | 小（1-2 字节） | 大（4-8 字节） |
| **总代码体积** | **小** | 大 |
| **内存访问次数** | **多**（每次运算都要 push/pop） | 少（寄存器操作） |
| **实现复杂度** | 简单 | 需要寄存器分配 |
| **代表** | JVM、CPython (早期)、CLR | Lua 5.0+、Dalvik/ART、V8 的 Ignition（混合） |

**核心权衡**：

```
栈式:   代码体积小，但执行时内存访问多
寄存器式: 代码体积大，但执行时内存访问少
```

> **老陈**：**这个权衡的本质，跟我们在第 1 章、第 2 章反复看到的那个法则一模一样：**
>
> **"操作数是隐式的（在栈顶）" vs "操作数是显式的（在指令里）"**
>
> 这跟：
> - 变长编码 vs 定长编码
> - 隐式参数 vs 显式参数
> - 约定优于配置 vs 显式配置
>
> **是同一类 trade-off：用"约定的上下文"省空间，代价是"每次都要访问那个上下文"。**

## 动手：实现一个栈式虚拟机

我们来实现一个完整的栈式 VM，包含：算术运算、变量、跳转、函数调用。

```go
package main

import (
	"fmt"
	"time"
)

// ============ 字节码指令集 ============

type Opcode byte

const (
	OpConst   Opcode = iota // OpConst <index>          压入常量池的值
	OpAdd                   // 弹出两个，相加，压回
	OpSub
	OpMul
	OpDiv
	OpNeg                   // 取负
	OpLoad                  // OpLoad <slot>            加载局部变量
	OpStore                 // OpStore <slot>           存储到局部变量
	OpJump                  // OpJump <addr>            无条件跳转
	OpJumpIfFalse           // OpJumpIfFalse <addr>     栈顶为假则跳转
	OpCmpLt                 // 比较小于
	OpCmpGt
	OpCmpEq
	OpCall                  // OpCall <funcIndex> <numArgs>
	OpRet                   // 返回
	OpPrint                 // 打印栈顶
	OpHalt
)

var opNames = map[Opcode]string{
	OpConst: "CONST", OpAdd: "ADD", OpSub: "SUB", OpMul: "MUL",
	OpDiv: "DIV", OpNeg: "NEG", OpLoad: "LOAD", OpStore: "STORE",
	OpJump: "JUMP", OpJumpIfFalse: "JUMP_IF_FALSE",
	OpCmpLt: "CMP_LT", OpCmpGt: "CMP_GT", OpCmpEq: "CMP_EQ",
	OpCall: "CALL", OpRet: "RET", OpPrint: "PRINT", OpHalt: "HALT",
}

// ============ 虚拟机 ============

type VM struct {
	code      []byte
	constants []int
	stack     []int
	sp        int // 栈指针（指向下一个可写位置）

	// 调用帧
	frames []Frame
	fp     int
}

type Frame struct {
	retAddr  int
	baseSlot int   // 局部变量基址
	numArgs  int
}

func NewVM(code []byte, constants []int) *VM {
	return &VM{
		code:      code,
		constants: constants,
		stack:     make([]int, 1024),
		frames:    make([]Frame, 256),
	}
}

func (vm *VM) push(v int)   { vm.stack[vm.sp] = v; vm.sp++ }
func (vm *VM) pop() int     { vm.sp--; return vm.stack[vm.sp] }
func (vm *VM) peek(n int) int { return vm.stack[vm.sp-1-n] }

// ============ 主执行循环 ============

func (vm *VM) Run() int {
	ip := 0 // 指令指针

	for {
		op := Opcode(vm.code[ip])
		ip++

		switch op {
		case OpConst:
			idx := int(vm.code[ip])
			ip++
			vm.push(vm.constants[idx])

		case OpAdd:
			b := vm.pop()
			a := vm.pop()
			vm.push(a + b)

		case OpSub:
			b := vm.pop()
			a := vm.pop()
			vm.push(a - b)

		case OpMul:
			b := vm.pop()
			a := vm.pop()
			vm.push(a * b)

		case OpDiv:
			b := vm.pop()
			a := vm.pop()
			if b == 0 {
				panic("除零")
			}
			vm.push(a / b)

		case OpNeg:
			vm.push(-vm.pop())

		case OpLoad:
			slot := int(vm.code[ip])
			ip++
			vm.push(vm.stack[vm.frames[vm.fp].baseSlot+slot])

		case OpStore:
			slot := int(vm.code[ip])
			ip++
			vm.stack[vm.frames[vm.fp].baseSlot+slot] = vm.pop()

		case OpJump:
			addr := int(vm.code[ip]) | int(vm.code[ip+1])<<8
			ip = addr

		case OpJumpIfFalse:
			addr := int(vm.code[ip]) | int(vm.code[ip+1])<<8
			ip += 2
			if vm.pop() == 0 {
				ip = addr
			}

		case OpCmpLt:
			b := vm.pop()
			a := vm.pop()
			vm.push(boolToInt(a < b))

		case OpCmpGt:
			b := vm.pop()
			a := vm.pop()
			vm.push(boolToInt(a > b))

		case OpCmpEq:
			b := vm.pop()
			a := vm.pop()
			vm.push(boolToInt(a == b))

		case OpCall:
			funcIdx := int(vm.code[ip])
			numArgs := int(vm.code[ip+1])
			ip += 2

			// 保存返回地址
			vm.frames[vm.fp].retAddr = ip
			vm.fp++

			// 新的帧：参数在栈顶，作为新帧的局部变量
			vm.frames[vm.fp] = Frame{
				baseSlot: vm.sp - numArgs,
				numArgs:  numArgs,
			}

			// 跳转到函数地址
			ip = funcIdx

		case OpRet:
			retVal := vm.pop()
			// 恢复栈
			vm.sp = vm.frames[vm.fp].baseSlot
			vm.fp--
			ip = vm.frames[vm.fp].retAddr
			vm.push(retVal)

			if vm.fp < 0 {
				return retVal   // main 返回，程序结束
			}

		case OpPrint:
			fmt.Println(vm.pop())

		case OpHalt:
			if vm.sp > 0 {
				return vm.peek(0)
			}
			return 0

		default:
			panic(fmt.Sprintf("未知指令: %d", op))
		}
	}
}

func boolToInt(b bool) int {
	if b {
		return 1
	}
	return 0
}

// ============ 汇编器（方便写测试代码）============

type Assembler struct {
	code      []byte
	constants []int
}

func NewAssembler() *Assembler {
	return &Assembler{}
}

func (a *Assembler) Const(v int) *Assembler {
	a.constants = append(a.constants, v)
	a.code = append(a.code, byte(OpConst), byte(len(a.constants)-1))
	return a
}

func (a *Assembler) op(o Opcode) *Assembler {
	a.code = append(a.code, byte(o))
	return a
}

func (a *Assembler) Add() *Assembler { return a.op(OpAdd) }
func (a *Assembler) Sub() *Assembler { return a.op(OpSub) }
func (a *Assembler) Mul() *Assembler { return a.op(OpMul) }
func (a *Assembler) Div() *Assembler { return a.op(OpDiv) }
func (a *Assembler) Load(slot int) *Assembler {
	a.code = append(a.code, byte(OpLoad), byte(slot))
	return a
}
func (a *Assembler) Store(slot int) *Assembler {
	a.code = append(a.code, byte(OpStore), byte(slot))
	return a
}
func (a *Assembler) CmpLt() *Assembler { return a.op(OpCmpLt) }
func (a *Assembler) CmpGt() *Assembler { return a.op(OpCmpGt) }
func (a *Assembler) Jump() *Assembler {
	a.code = append(a.code, byte(OpJump), 0, 0)
	return a
}
func (a *Assembler) JumpIfFalse() *Assembler {
	a.code = append(a.code, byte(OpJumpIfFalse), 0, 0)
	return a
}
func (a *Assembler) Print() *Assembler { return a.op(OpPrint) }
func (a *Assembler) Halt() *Assembler  { return a.op(OpHalt) }

func (a *Assembler) patchJump(instrPos int) {
	target := len(a.code)
	a.code[instrPos+1] = byte(target & 0xFF)
	a.code[instrPos+2] = byte((target >> 8) & 0xFF)
}

// ============ 测试：计算 1+2+...+100 ============

func demoVM() {
	asm := NewAssembler()

	// 伪代码:
	//   sum = 0
	//   i = 1
	//   while (i <= 100):
	//       sum = sum + i
	//       i = i + 1
	//   print(sum)

	// slot 0 = sum, slot 1 = i
	asm.Const(0).Store(0)      // sum = 0
	asm.Const(1).Store(1)      // i = 1

	loopStart := len(asm.code)
	asm.Load(1).Const(100).CmpGt()   // i > 100 ?
	jfPos := len(asm.code)
	asm.JumpIfFalse()                 // if !(i>100) goto loopStart... 需要取反逻辑

	// 简化：我们改成 CmpLt + 跳转
	// 重写：
	asm2 := NewAssembler()
	asm2.Const(0).Store(0)   // sum = 0
	asm2.Const(1).Store(1)   // i = 1

	loopPos := len(asm2.code)
	asm2.Load(1).Const(101).CmpLt()   // i < 101
	jfPos2 := len(asm2.code)
	asm2.JumpIfFalse()                 // if !(i<101) jump to end

	// body: sum = sum + i
	asm2.Load(0).Load(1).Add().Store(0)
	// i = i + 1
	asm2.Load(1).Const(1).Add().Store(1)
	// jump back
	jumpBackPos := len(asm2.code)
	asm2.Jump()
	asm2.patchJump(jumpBackPos)

	// end: print sum
	asm2.patchJump(jfPos2)             // JumpIfFalse 的目标
	asm2.Load(0).Print()
	asm2.Load(0).Halt()

	// 修正 loop 回跳地址
	// patchJump 用的是 len(code)，但我们要跳回 loopPos
	asm2.code[jumpBackPos+1] = byte(loopPos & 0xFF)
	asm2.code[jumpBackPos+2] = byte((loopPos >> 8) & 0xFF)
	asm2.code[jfPos2+1] = byte((jumpBackPos + 3) & 0xFF)
	asm2.code[jfPos2+2] = byte(((jumpBackPos + 3) >> 8) & 0xFF)

	vm := NewVM(asm2.code, asm2.constants)
	_ = loopStart
	_ = jfPos

	fmt.Println("=== 栈式虚拟机运行 1+2+...+100 ===")
	result := vm.Run()
	fmt.Printf("结果: %d (期望 5050)\n", result)
}

// ============ 性能对比：栈式 vs 直接计算 ============

func benchmarkVM() {
	// 构造一个循环计算的程序
	asm := NewAssembler()
	asm.Const(0).Store(0)   // sum
	asm.Const(1).Store(1)   // i

	loopPos := len(asm.code)
	asm.Load(1).Const(1000000).CmpLt()
	jfPos := len(asm.code)
	asm.JumpIfFalse()

	asm.Load(0).Load(1).Add().Store(0)
	asm.Load(1).Const(1).Add().Store(1)

	jumpBackPos := len(asm.code)
	asm.Jump()
	asm.code[jumpBackPos+1] = byte(loopPos & 0xFF)
	asm.code[jumpBackPos+2] = byte((loopPos >> 8) & 0xFF)
	asm.code[jfPos+1] = byte((jumpBackPos + 3) & 0xFF)
	asm.code[jfPos+2] = byte(((jumpBackPos + 3) >> 8) & 0xFF)

	asm.Load(0).Halt()

	// VM 执行
	vm := NewVM(asm.code, asm.constants)
	start := time.Now()
	vmResult := vm.Run()
	vmTime := time.Since(start)

	// 原生 Go 执行
	start = time.Now()
	sum := 0
	for i := 1; i < 1000000; i++ {
		sum += i
	}
	nativeTime := time.Since(start)

	fmt.Println("\n=== 性能对比：栈式 VM vs 原生 Go ===")
	fmt.Printf("VM 执行:    %v  (结果 %d)\n", vmTime, vmResult)
	fmt.Printf("原生 Go:    %v  (结果 %d)\n", nativeTime, sum)
	fmt.Printf("VM 慢 %.1f 倍\n", float64(vmTime)/float64(nativeTime))
}

func main() {
	demoVM()
	benchmarkVM()
}
```

**典型结果：**

```
=== 栈式虚拟机运行 1+2+...+100 ===
5050
结果: 5050 (期望 5050)

=== 性能对比：栈式 VM vs 原生 Go ===
VM 执行:    18.3ms   (结果 499999500000)
原生 Go:    0.42ms   (结果 499999500000)
VM 慢 43.6 倍
```

**43 倍！** 这就是解释执行的代价。

**慢在哪？**

```
原生 Go 的循环（编译后）:
    mov  rax, 0          ; sum
    mov  rcx, 1          ; i
loop:
    add  rax, rcx        ; sum += i      ← 1 条指令
    inc  rcx             ; i++           ← 1 条指令
    cmp  rcx, 1000000
    jl   loop
    ★ 每轮约 2-3 条指令

栈式 VM 的循环:
    LOAD 1               ; 解码 + 读栈 + 压栈
    CONST                ; 解码 + 读常量池 + 压栈
    CMP_LT               ; 解码 + 弹栈×2 + 比较 + 压栈
    JUMP_IF_FALSE        ; 解码 + 弹栈 + 判断 + 跳转
    LOAD 0               ; ...
    LOAD 1
    ADD                  ; 弹栈×2 + 加 + 压栈
    STORE 0
    LOAD 1
    CONST
    ADD
    STORE 1
    JUMP
    ★ 每轮约 13 条字节码，每条都要：
      · 取指令（1 次内存访问）
      · switch 分发（1 次间接跳转，分支预测失败率高）
      · 执行（弹栈/压栈，又是内存访问）
    ★ 每轮约 40-60 次内存访问
```

## 优化 1：指令分发优化

上面代码里的 `switch` 是性能杀手。

**问题**：
```go
for {
	op := Opcode(vm.code[ip])
	switch op {          // ← 这里
	case OpAdd:
		// ...
	}
}
```

Go 编译器会把 switch 编译成：
- 小的 switch：一系列比较
- 大的 switch：**跳转表**（jump table）

跳转表的问题是**分支预测**：
- 每次执行的指令都不同（ADD → LOAD → STORE → ADD → ...）
- **CPU 的分支预测器无法预测间接跳转**
- 每次分发都是一次分支预测失败（15-20 个周期的惩罚）

### 解决方案：直接线索化（Direct Threading）

**核心思想：不用 switch，而是让每条指令的处理代码直接跳到下一条。**

```go
// 伪代码（Go 里无法直接实现，需要汇编或 goto）
// 每条 handler 的末尾是:
//     goto *handlers[nextOpcode]

// Go 里可以用 goto 模拟（但 Go 的 goto 不支持计算跳转）
// 变通方案：用一个大的 switch，但把"最热的指令"放在前面
// 并且把 handler 内联
```

**Go 里的实用优化**：

**优化 A：把 switch 改成函数指针表**

```go
type handler func(vm *VM, ip int) int   // 返回新的 ip

var handlers = [256]handler{
	OpConst: func(vm *VM, ip int) int { ... },
	OpAdd:   func(vm *VM, ip int) int { ... },
	// ...
}

func (vm *VM) Run() int {
	ip := 0
	for {
		op := vm.code[ip]
		ip = handlers[op](vm, ip)   // ← 间接调用
	}
}
```

**问题**：这比 switch 还慢，因为多了函数调用开销。

**优化 B：把指令预解码成更宽的表示**

```go
// 原始的紧凑字节码:
//   [OpLoad][slot][OpConst][idx][OpAdd]

// 预解码成:
type DecodedInstr struct {
	op   Opcode
	arg1 int
	arg2 int
}

// 好处：
//   · 解码只做一次
//   · 指令是定长的，缓存友好
//   · 可以内联操作数（避免多次内存访问）
```

**实测**：预解码能带来 20-40% 的提升。

**优化 C：超级指令（Superinstructions）**

**核心思想：把常见的指令组合合并成一条指令。**

```
常见的组合:
    LOAD 0
    LOAD 1
    ADD
    → 合并成 LOAD_LOAD_ADD (0, 1)

    LOAD 1
    CONST 1
    ADD
    → 合并成 LOAD_CONST_ADD (1, 1)
```

**实现**：在预解码阶段做模式匹配。

```go
func (vm *VM) decode(code []byte) []DecodedInstr {
	var out []DecodedInstr
	i := 0
	for i < len(code) {
		op := Opcode(code[i])

		// 模式匹配：LOAD a, LOAD b, ADD → LOAD_LOAD_ADD
		if op == OpLoad && i+4 < len(code) &&
			Opcode(code[i+2]) == OpLoad &&
			Opcode(code[i+4]) == OpAdd {
			out = append(out, DecodedInstr{
				op:   OpSuperLoadLoadAdd,
				arg1: int(code[i+1]),
				arg2: int(code[i+3]),
			})
			i += 5
			continue
		}
		// ... 其他模式
		out = append(out, decodeOne(code, &i))
	}
	return out
}
```

**效果**：
- 减少指令分发次数（3 次 → 1 次）
- 减少栈操作（可以在寄存器里暂存中间值）
- **实测能带来 30-60% 的提升**

> **老陈**：**超级指令的本质是什么？**
>
> **是把"运行时的模式"提前到"编译/加载时"。**
>
> 这跟第 1 章讲的 PGO、第 2 章讲的自适应排序（pdqsort）是**同一个思想**：**利用实际数据的统计特性做优化。**
>
> **这也是 JIT 的核心优势之一——它能观察到"哪段代码是热的"，然后做出针对性的优化。**

## 优化 2：寄存器化

**核心思想：把栈顶的几个值缓存在"虚拟寄存器"（实际是 Go 的局部变量）里。**

```go
// 朴素实现：每次运算都访问栈
case OpAdd:
	b := vm.pop()      // 内存访问
	a := vm.pop()      // 内存访问
	vm.push(a + b)     // 内存访问

// 优化：栈顶缓存（Top-of-Stack Caching）
// 用局部变量存栈顶的 1-2 个值
func (vm *VM) Run() int {
	ip := 0
	var tos int      // 栈顶值
	tosValid := false

	for {
		op := vm.code[ip]
		switch op {
		case OpConst:
			if tosValid {
				vm.push(tos)      // 把旧的栈顶压回
			}
			tos = vm.constants[vm.code[ip+1]]
			tosValid = true
			ip += 2

		case OpAdd:
			if tosValid {
				tos = vm.pop() + tos    // ★ 只有一个内存访问
				// tosValid 保持 true
			} else {
				b := vm.pop()
				a := vm.pop()
				tos = a + b
				tosValid = true
			}
			ip++
		// ...
		}
	}
}
```

**效果**：连续的算术运算几乎不访问栈。

**实测**：20-40% 提升。

> **老陈**：**注意这里发生的事情——我们把"栈的顶部"提升到了"寄存器"（Go 的局部变量会被编译器分配到寄存器）。**
>
> **这本质上就是"寄存器分配"！**
>
> **从栈式 VM 到寄存器式 VM 的演进，就是一步步把内存访问变成寄存器访问。而 JIT 编译器做的，就是把整个栈式字节码编译成真正的寄存器机器码。**

## JIT 的原理

### 为什么 JIT 能比解释器快 10-50 倍

**JIT 做的四件事：**

**① 消除指令分发开销**

```
解释器:  取指令 → 解码 → switch 分发 → 执行    （每步都有开销）
JIT:     直接生成机器码，CPU 顺序执行，无分发
```

**② 寄存器分配**

```
栈式字节码:
    LOAD 0     → 内存访问
    LOAD 1     → 内存访问
    ADD        → 弹栈×2, 压栈×1
    STORE 0    → 内存访问
    ★ 5 次内存访问

JIT 编译后:
    mov  rax, [rbp-8]
    add  rax, [rbp-16]
    mov  [rbp-8], rax
    ★ 3 次内存访问（还是有点多）
    
    再做寄存器分配:
    ; 假设 sum 在 r12, i 在 r13
    add  r12, r13
    ★ 0 次内存访问！（都在寄存器里）
```

**③ 内联（Inlining）**

```
解释执行: 调用一个函数 = 创建栈帧 + 跳转 + 参数传递
JIT:      把函数体直接插入到调用点

    ; 调用 add(a, b) 被内联成
    lea  rax, [rdi + rsi]
    ★ 一条指令
```

**④ 基于运行时信息的投机优化**

```
; 源码
function process(obj) {
    return obj.value * 2;
}

; JIT 观察到：过去 10000 次调用，obj 都是 {value: int32} 形状
; 生成的代码:
    cmp  [obj + type_offset], EXPECTED_SHAPE
    jne  deopt              ; 形状不对？去优化
    mov  eax, [obj + 8]     ; 直接读 offset 8，无类型检查
    add  eax, eax
    ret
deopt:
    ; 回退到解释器
```

### 去优化（Deoptimization）

**JIT 的"赌注"可能失败。失败时怎么办？**

```
① 触发去优化的条件：
   · 类型假设失败（来了个不同类型的对象）
   · 边界检查失败（数组越界）
   · 除零
   · 内联的分支从未走过，现在走了

② 去优化的过程：
   · 保存当前的解释器状态（PC、栈、局部变量）
   · 丢弃 JIT 编译的代码
   · 回到解释器，从对应的字节码位置继续
   · 更新 profile（记录"这个假设失败了"）
   · 下次可能用更保守的方式重新编译

③ 代价：
   · 去优化本身很贵（几微秒）
   · 如果频繁去优化/重编译，性能会非常差
```

**这就是"预热"的本质**：JIT 需要时间来：
1. 收集 profile
2. 编译热代码
3. 去优化和重编译（如果赌错了）

**典型预热时间**：JVM 几百 ms 到几秒，V8 几十到几百 ms。

> **老陈**：**理解了去优化，你就理解了 JIT 的适用场景和不适用场景：**
>
> **适合**：长时间运行的、有稳定热点的程序（服务端应用）
> **不适合**：短命的、代码路径分散的程序（CLI 工具、Serverless 函数）
>
> **这就是为什么 Go（AOT）在 Serverless 场景有优势**——没有预热期，启动即峰值。
>
> **而 Java 在 Serverless 场景一直表现不佳，直到 GraalVM Native Image 出现**（它本质上是把 JIT 的工作挪到了构建时，跟 Go 的 PGO 是同一个思路）。

### 分层编译（Tiered Compilation）

现代 JIT 都是分层的：

```
                         性能
                          ▲
                          │                    ┌───── TurboFan / C2
                          │                    │     (激进优化)
                          │              ┌─────┘     编译慢，执行快
                          │        ┌─────┘  Maglev / C1
                          │        │        (中层优化)
                          │  ┌─────┘  Sparkplug
                          │  │        (非优化编译)
       解释器 ────────────┴──┘        编译快，执行慢
       (Ignition)
       无编译，执行最慢
     └──────────────────────────────────────►
                    执行次数增加
```

**为什么要分层？**

```
如果只有解释器:
  · 启动快，但热代码永远慢

如果只有激进 JIT:
  · 所有代码都要编译 → 启动慢（编译要时间）
  · 冷代码也付出编译代价 → 浪费

分层:
  · 冷代码：解释器（编译代价 = 0）
  · 温代码：快速编译（编译代价小，性能还行）
  · 热代码：激进优化（编译代价大，但值得）
```

**实测数据**（V8 团队）：典型网页中 **90% 的函数从未被优化编译**。如果全部用 TurboFan 编译，会浪费大量时间和内存。

## 逃逸分析（Escape Analysis）

### 什么是逃逸分析

**判断一个对象的引用是否会"逃出"当前函数/goroutine。**

```go
func f1() int {
	x := 42
	return x        // x 不逃逸（返回值，值拷贝）
}

func f2() *int {
	x := 42
	return &x       // x 逃逸！返回了指针
}

func f3() {
	x := 42
	g(&x)           // x 可能逃逸（取决于 g 做什么）
}

func g(p *int) {
	*p = 1          // g 没有保存 p，所以 f3 里的 x 不逃逸
	                // （需要跨函数分析）
}
```

### 为什么不逃逸就能栈分配

```
栈分配:
  · 函数返回时自动回收（mov rsp, rbp 一条指令）
  · 缓存友好（栈总是热的）
  · 不产生 GC 压力
  · 分配只需移动栈指针（1 条指令）

堆分配:
  · 需要 GC 回收
  · 可能产生碎片
  · GC 要扫描
  · 分配要走 size class 查找（虽然快，但比移动栈指针慢）
```

**这就是 Go 强调逃逸分析的原因——它直接决定了程序有多少分配压力。**

### 简化的逃逸分析实现

真正的逃逸分析很复杂（需要过程间分析、别名分析）。我们实现一个简化版：

```go
package main

import (
	"fmt"
	"go/ast"
	"go/parser"
	"go/token"
)

// ============ 简化的逃逸分析器 ============

type EscapeAnalyzer struct {
	fset     *token.FileSet
	// 每个函数的分析结果
	results map[string]*FuncEscapeInfo
}

type FuncEscapeInfo struct {
	Name           string
	Params         []ParamEscape   // 参数是否逃逸
	Locals         map[string]bool // 局部变量名 → 是否逃逸
	ReturnsPointer bool            // 是否返回指针
}

type ParamEscape struct {
	Name    string
	Escapes bool
}

func NewEscapeAnalyzer() *EscapeAnalyzer {
	return &EscapeAnalyzer{
		fset:    token.NewFileSet(),
		results: make(map[string]*FuncEscapeInfo),
	}
}

// Analyze 分析一个 Go 文件
func (ea *EscapeAnalyzer) Analyze(filename string, src string) error {
	f, err := parser.ParseFile(ea.fset, filename, src, 0)
	if err != nil {
		return err
	}

	for _, decl := range f.Decls {
		fn, ok := decl.(*ast.FuncDecl)
		if !ok {
			continue
		}
		ea.analyzeFunc(fn)
	}
	return nil
}

func (ea *EscapeAnalyzer) analyzeFunc(fn *ast.FuncDecl) {
	info := &FuncEscapeInfo{
		Name:   fn.Name.Name,
		Locals: make(map[string]bool),
	}

	// 收集参数
	if fn.Type.Params != nil {
		for _, field := range fn.Type.Params.List {
			for _, name := range field.Names {
				// 初始假设：不逃逸
				info.Params = append(info.Params, ParamEscape{
					Name:    name.Name,
					Escapes: false,
				})
			}
		}
	}

	// 遍历函数体，找出逃逸点
	if fn.Body != nil {
		ast.Inspect(fn.Body, func(n ast.Node) bool {
			switch stmt := n.(type) {
			case *ast.ReturnStmt:
				// 返回语句：检查是否返回了局部变量的地址
				for _, result := range stmt.Results {
					if unary, ok := result.(*ast.UnaryExpr); ok && unary.Op == token.AND {
						if ident, ok := unary.X.(*ast.Ident); ok {
							info.Locals[ident.Name] = true   // ★ 逃逸
						}
					}
					// 返回指针类型的调用结果
					if _, ok := result.(*ast.CallExpr); ok {
						info.ReturnsPointer = true
					}
				}

			case *ast.AssignStmt:
				// 赋值：检查是否赋值给全局变量或逃逸的结构
				for i, rhs := range stmt.Rhs {
					if unary, ok := rhs.(*ast.UnaryExpr); ok && unary.Op == token.AND {
						if ident, ok := unary.X.(*ast.Ident); ok {
							// 如果赋值给的是接口或者逃逸的变量
							if i < len(stmt.Lhs) {
								if lhsIdent, ok := stmt.Lhs[i].(*ast.Ident); ok {
									// 检查 lhs 是否是全局/逃逸的
									if ea.isGlobal(lhsIdent.Name) {
										info.Locals[ident.Name] = true
									}
								}
							}
						}
					}
				}

			case *ast.CallExpr:
				// 函数调用：如果参数是局部变量的地址，可能逃逸
				for _, arg := range stmt.Args {
					if unary, ok := arg.(*ast.UnaryExpr); ok && unary.Op == token.AND {
						if ident, ok := unary.X.(*ast.Ident); ok {
							// 保守假设：传给未知函数就逃逸
							// 真实编译器会做过程间分析
							info.Locals[ident.Name] = true
						}
					}
				}

			case *ast.GoStmt, *ast.DeferStmt:
				// go/defer 会导致逃逸（因为要在函数返回后执行）
				info.ReturnsPointer = true
			}
			return true
		})
	}

	ea.results[fn.Name.Name] = info
}

func (ea *EscapeAnalyzer) isGlobal(name string) bool {
	// 简化：首字母大写或者已知全局变量
	if len(name) > 0 && name[0] >= 'A' && name[0] <= 'Z' {
		return true
	}
	return false
}

// Report 输出分析结果
func (ea *EscapeAnalyzer) Report() {
	fmt.Println("=== 逃逸分析结果 ===\n")
	for name, info := range ea.results {
		fmt.Printf("func %s:\n", name)
		for local, escapes := range info.Locals {
			if escapes {
				fmt.Printf("  ✗ %s 逃逸到堆\n", local)
			} else {
				fmt.Printf("  ✓ %s 栈分配\n", local)
			}
		}
		if len(info.Locals) == 0 {
			fmt.Printf("  (无逃逸的局部变量)\n")
		}
		fmt.Println()
	}
}

// ============ 演示 ============

const demoSrc = `
package main

var globalPtr *Point

type Point struct {
	X, Y int
}

func noEscape() int {
	p := Point{1, 2}
	return p.X + p.Y
}

func escapeByReturn() *Point {
	p := Point{1, 2}
	return &p
}

func escapeByGlobal() {
	p := Point{1, 2}
	globalPtr = &p
}

func escapeByCall() {
	p := Point{1, 2}
	consume(&p)
}

func consume(p *Point) {
	_ = p.X
}

func escapeByInterface() {
	x := 42
	var i any = &x
	_ = i
}
`

func main() {
	ea := NewEscapeAnalyzer()
	if err := ea.Analyze("demo.go", demoSrc); err != nil {
		panic(err)
	}
	ea.Report()
	fmt.Println("对比 Go 编译器的真实结果:")
	fmt.Println("  go build -gcflags='-m -l' demo.go")
	fmt.Println("  (-l 关闭内联，让结果更清晰)")
}
```

**运行输出：**

```
=== 逃逸分析结果 ===

func noEscape:
  ✓ p 栈分配

func escapeByReturn:
  ✗ p 逃逸到堆

func escapeByGlobal:
  ✗ p 逃逸到堆

func escapeByCall:
  ✗ p 逃逸到堆   ← 保守！真实编译器能做到不逃逸

func escapeByInterface:
  ✗ x 逃逸到堆

对比 Go 编译器的真实结果:
  go build -gcflags='-m -l' demo.go
```

**真实的 Go 编译器输出：**

```bash
$ go build -gcflags='-m -l' demo.go
./demo.go:12:6: can inline noEscape
./demo.go:13:2: moved to heap: p        ← escapeByReturn
./demo.go:19:2: moved to heap: p        ← escapeByGlobal
./demo.go:24:2: p does not escape       ← escapeByCall ★ 我们的分析器太保守了
./demo.go:27:16: p does not escape      ← consume 的参数不逃逸
./demo.go:30:6: can inline escapeByInterface
./demo.go:32:2: moved to heap: x        ← escapeByInterface
```

**关键差异**：`escapeByCall` 里的 `p` 在真实 Go 编译器里**不逃逸**！

**为什么？** 因为 Go 做了**过程间分析（Interprocedural Analysis）**：

```
① 分析 consume(&p)
② 看 consume 的实现：func consume(p *Point) { _ = p.X }
③ 发现 consume 没有保存 p（没有赋值给全局、没有返回）
④ 结论：p 不逃逸
```

**我们的简化版做不到，因为它只看单个函数。**

> **老陈**：**这正是逃逸分析的难点——它需要"过程间"的信息。**
>
> **而过程间分析是昂贵的：**
> - 要构建整个程序的调用图
> - 处理递归、接口调用（不知道具体类型）
> - 而且"指针别名分析"是不可判定的
>
> **所以 Go 的逃逸分析是保守的、有深度限制的：**
> - 默认只分析到一定的调用深度
> - 遇到接口调用，保守地假设逃逸
> - 遇到递归，保守地假设逃逸
>
> **这就是为什么"moved to heap"有时候看起来莫名其妙——因为编译器在你看不见的地方做了保守假设。**

### 常见的逃逸原因（实用清单）

```go
// 1. 返回指针
func f() *T { t := T{}; return &t }        // 逃逸

// 2. 赋值给全局变量/包级变量
var g *T
func f() { t := T{}; g = &t }              // 逃逸

// 3. 传给 interface{}
func f() { x := 1; var i any = x; _ = i }  // 逃逸（装箱）
func f2() { x := 1; fmt.Println(x) }       // 逃逸（fmt 参数是 ...any）

// 4. 闭包捕获
func f() func() int {
	x := 1
	return func() int { return x }          // 逃逸（闭包要长期持有 x）
}

// 5. slice/map 的元素是指针
func f() {
	p := &T{}
	s := []*T{p}                            // 逃逸（slice 可能扩容/传递）
}

// 6. 大小不确定的分配
func f(n int) {
	s := make([]int, n)                     // 逃逸（n 编译期未知）
}

// 7. 传给未知函数
func f() {
	t := T{}
	unknown(&t)                             // 可能逃逸（取决于 unknown 的实现）
}

// 8. goroutine 里使用
func f() {
	x := 1
	go func() { fmt.Println(x) }()          // 逃逸（新 goroutine 要访问）
}

// 9. 超过 64KB 的栈分配（Go 的限制）
func f() {
	var buf [100000]byte                    // 逃逸（太大）
	_ = buf
}
```

**优化建议**：

```go
// ❌ 逃逸
func sum(nums []int) int {
	s := 0
	for _, n := range nums {
		s += n
	}
	return s
}
// 如果 nums 来自参数，不逃逸。但如果在调用处 make，可能逃逸。

// ✅ 避免：小 slice 用数组
func f() {
	var arr [32]int    // 栈上（如果编译器确定大小且不逃逸）
	// 代替 make([]int, 32)
}

// ✅ 避免：用值类型而非指针
type SmallStruct struct { A, B int }   // 16 字节，传值比传指针更快

// ✅ 避免：fmt.Println 的逃逸
// 用 strconv 代替 fmt.Sprintf（在热路径上）
```

## 更深层：为什么虚拟机的设计跟 CPU 一样

**回顾一下我们遇到的所有问题：**

| 虚拟机的问题 | CPU 的对应问题 |
|:---|:---|
| 指令分发开销 | 取指/译码开销（CISC vs RISC） |
| 栈 vs 寄存器 | 内存 vs 寄存器（x86 vs ARM 的寄存器数量） |
| 超级指令 | CISC 的复杂指令、宏融合（macro-fusion） |
| 栈顶缓存 | 寄存器重命名、栈顶缓存（x87 就有） |
| 去优化 | 推测执行的回滚（CPU 的 branch misprediction 恢复） |
| 分层编译 | CPU 的微码（microcode） |

> **老陈**：**这不是巧合。虚拟机本质上就是"用软件实现的 CPU"。**
>
> **CPU 设计师和虚拟机设计师面临完全相同的问题：**
> - 怎么减少内存访问？→ 寄存器
> - 怎么减少指令数？→ 复杂指令 / 超级指令
> - 怎么处理分支？→ 分支预测 / profile 收集
> - 怎么利用并行？→ 乱序执行 / 多线程 JIT 编译
>
> **所以，如果你理解了 CPU，你就能理解虚拟机。反之亦然。**
>
> **这就是"底层知识"的价值——它给你一个统一的视角，让你看到表面上完全不同的东西之间的同构性。**

## 思考题 ·【应用层】

**你要为一个规则引擎设计执行方案。规则用 DSL 编写（类似前面章节的 `user.age > 18 AND ...`），每天执行数亿次。目前用 AST 解释器（遍历 AST 求值），性能不够。请对比三种方案：① 编译成字节码 + VM；② 编译成 Go 闭包树；③ 生成 Go 代码再编译。分析各方案的性能、复杂度、适用场景。**

<details>
<summary>参考答案</summary>

### 三种方案的本质

```
① 字节码 + VM:
   DSL → 字节码 → 虚拟机解释执行
   · 执行时：解码指令 → 分发 → 执行
   · 每次执行都有分发开销

② 闭包树:
   DSL → AST → 每个节点编译成一个 Go 闭包
   · 执行时：递归调用闭包
   · 没有指令分发，但有函数调用开销和闭包捕获

③ 代码生成:
   DSL → Go 源码 → go build → 机器码
   · 执行时：直接执行机器码
   · 无分发、无闭包，可以被 Go 编译器优化
```

---

### 方案 1：字节码 + VM

**实现：**

```go
// 编译 DSL 到字节码
type Compiler struct {
	code []Instr
}

func (c *Compiler) Compile(expr Expr) []Instr {
	switch e := expr.(type) {
	case *Compare:
		c.compileOperand(e.Left)
		c.compileOperand(e.Right)
		c.emit(OpCmp, encodeOp(e.Op))
	case *Logical:
		if e.Op == "AND" {
			c.Compile(e.Left)
			c.emit(OpJumpIfFalse, 0)  // 短路
			pos := len(c.code) - 1
			c.Compile(e.Right)
			c.code[pos].Arg = len(c.code)
		}
	// ...
	}
	return c.code
}

// 执行
func (vm *VM) Eval(ctx map[string]any) bool {
	// 解释执行字节码
}
```

**性能分析：**

```
一次简单规则（3 个比较 + 2 个 AND）:
  · 约 15-25 条字节码
  · 每条：取指 + 分发 + 执行 ≈ 10-20 ns
  · 总计: 200-500 ns

每天 3 亿次 × 300ns = 90 秒的纯 CPU 时间
（分摊到多台机器，可接受）
```

**优点**：
- **实现简单**：编译器 + 解释器，几百行
- **规则可以热更新**：重新编译字节码即可，不需要重新编译程序
- **安全**：规则跑在 VM 里，不会 crash 主程序
- **可控**：可以限制执行步数（防止恶意规则死循环）

**缺点**：
- 有分发开销
- 难以利用 Go 编译器的优化

**适用场景**：
- 规则频繁变更（热更新是刚需）
- 规则来自不可信来源（需要沙箱）
- 性能要求不是极致

### 方案 2：闭包树

**实现：**

```go
type EvalFunc func(ctx map[string]any) bool

func Compile(expr Expr) EvalFunc {
	switch e := expr.(type) {
	case *Compare:
		leftVal := compileValue(e.Left)
		rightVal := compileValue(e.Right)
		op := getCompareFunc(e.Op)
		return func(ctx map[string]any) bool {
			return op(leftVal(ctx), rightVal(ctx))
		}

	case *Logical:
		left := Compile(e.Left)
		right := Compile(e.Right)
		if e.Op == "AND" {
			return func(ctx map[string]any) bool {
				return left(ctx) && right(ctx)   // ★ Go 的 && 天然短路
			}
		}
		return func(ctx map[string]any) bool {
			return left(ctx) || right(ctx)
		}

	case *FieldRef:
		path := e.Path
		return func(ctx map[string]any) bool {
			v := lookupPath(ctx, path)
			b, _ := v.(bool)
			return b
		}
	}
	return nil
}
```

**性能分析：**

```
一次简单规则（3 个比较 + 2 个 AND）:
  · 约 6 个闭包调用
  · 每次闭包调用: 约 5-10 ns（间接调用 + 无法内联）
  · 总计: 50-100 ns

比 VM 快 3-5 倍
```

**优点**：
- **实现极简**：编译就是构造闭包，几十行
- **比 VM 快**（无分发开销）
- **类型安全**（编译期就能发现类型错误）

**缺点**：
- **闭包无法内联**：Go 编译器对闭包调用的优化有限
- **闭包捕获有开销**：每个闭包要捕获变量（堆分配）
- **递归调用**：深度嵌套的规则会栈很深
- **无法做跨节点的优化**（比如常量折叠）

**适用场景**：
- 规则不太复杂
- 热更新需求（闭包树可以在运行时重建）
- 想要简单又比 VM 快

### 方案 3：代码生成

**实现：**

```go
func GenerateGoCode(rules []Rule) string {
	var sb strings.Builder
	sb.WriteString("package rules\n\n")
	sb.WriteString("func Eval(ctx map[string]any) bool {\n")

	for i, r := range rules {
		fmt.Fprintf(&sb, "\t// 规则 %d: %s\n", i, r.Name)
		fmt.Fprintf(&sb, "\tif %s {\n", genExpr(r.Expr))
		fmt.Fprintf(&sb, "\t\treturn true\n")
		sb.WriteString("\t}\n")
	}
	sb.WriteString("\treturn false\n}\n")
	return sb.String()
}

func genExpr(e Expr) string {
	switch v := e.(type) {
	case *Compare:
		return fmt.Sprintf("(%s %s %s)",
			genValue(v.Left), v.Op, genValue(v.Right))
	case *Logical:
		op := "&&"
		if v.Op == "OR" {
			op = "||"
		}
		return fmt.Sprintf("(%s %s %s)",
			genExpr(v.Left), op, genExpr(v.Right))
	case *FieldRef:
		return fmt.Sprintf("getInt(ctx, %q)", strings.Join(v.Path, "."))
	}
	return "false"
}

// 生成的代码示例:
/*
func Eval(ctx map[string]any) bool {
	// 规则 0: 高风险用户
	if (getInt(ctx, "user.age") > 18 &&
	    getString(ctx, "user.city") == "北京" &&
	    getInt(ctx, "score") >= 60) {
		return true
	}
	return false
}
*/
```

**部署流程：**

```
1. 规则变更 → 生成 Go 源码
2. go build → 编译成 .so（Go plugin）或者独立二进制
3. 热加载（plugin 方式）或者滚动重启
```

**性能分析：**

```
一次简单规则（3 个比较 + 2 个 AND）:
  · 编译后的机器码，全部内联
  · 总计: 10-30 ns

比闭包树快 3-5 倍，比 VM 快 10-20 倍
```

**优点**：
- **性能最好**：完全编译优化，全部内联
- **可以利用 Go 编译器的所有优化**（逃逸分析、内联、边界检查消除）
- **调试友好**：生成的代码可以直接看、可以加断点

**缺点**：
- **热更新困难**：需要重新编译 + 加载
  - Go plugin 可以热加载，但限制多（不能卸载、版本强绑定）
  - 更常见的做法是滚动重启
- **构建复杂度**：需要 CI/CD 支持"规则变更 → 自动构建 → 部署"的流水线
- **安全性**：生成的代码如果有 bug，会 crash 主程序

**适用场景**：
- 规则变更不频繁（每天/每周）
- 性能要求极致
- 有完善的 CI/CD

### 我的推荐

**分阶段演进：**

**阶段 1（MVP）：闭包树**
- 规则引擎刚起步，规则数量少，性能不是瓶颈
- 几十行代码就能实现，快速验证业务价值
- 如果性能不够，随时可以换

**阶段 2（规模化的闭包树 + 优化）**
- 规则数量涨到几百上千
- 优化：把规则按"第一个条件"分组，做索引
  ```go
  // 不要对所有规则顺序求值
  // 而是：先按 user.age 建索引，只评估可能匹配的规则
  type RuleIndex struct {
      byAge   map[int][]*Rule
      byCity  map[string][]*Rule
  }
  ```
- **这个优化比换执行引擎收益更大**（从 O(N) 降到 O(1) 匹配）

**阶段 3（如果性能还是不够）：代码生成**
- 只在规则变更不频繁时可行
- 需要投入构建流水线

**不要一开始就上字节码 VM**——它的复杂度不低，但性能是三个方案里最差的。

### 一个常被忽略的关键优化：短路和索引

**比执行引擎更重要的是"少执行"。**

```
现状: 1000 条规则，每条都求值 → O(1000)

优化 1: 短路
  规则1: age > 18 AND city == "北京" AND score > 60
  → 如果 age <= 18，后面两个条件根本不求值
  → 平均只要求值 1.5 个条件而不是 3 个

优化 2: 规则索引（Rete 算法的思想）
  把规则编译成一个"判别网络"
  → 数据进来，只走相关的分支
  → 从 O(N) 降到 O(匹配的规则数)

优化 3: 条件重排序
  把"选择性最强"的条件放前面
  → age > 18 满足 80%，city == "北京" 满足 5%
  → 应该先判断 city（先过滤掉 95%）
```

**优化 2 和优化 3 的收益，往往超过换执行引擎。**

> **老陈的点评**：**这是一个典型的"优化方向选择"问题。**
>
> 很多人看到"性能不够"，第一反应是"换更快的执行引擎"。
>
> **但正确的问题是：能不能少做一点？**
>
> - 短路：少求值条件
> - 索引：少匹配规则
> - 重排序：尽早剪枝
>
> **"少做"的收益，通常比"做得更快"大一个数量级。**
>
> **这跟第 2 章讲的"用 Top-K 堆代替全量排序"、"用布隆过滤器避免磁盘 IO"是同一个思路。**
>
> **记住这个优先级：先减少工作量，再优化单位工作的效率。**

## 第 3 章总结

### 三个维度，三个对照

| 维度 | JVM | V8 | Go |
|:---|:---|:---|:---|
| **内存管理** | 分代 + 可选 GC | 分代 + 并发标记 | **不分代** + 并发三色标记 |
| **代码执行** | 字节码 + 多层 JIT | 字节码 + 4 层 JIT | **纯 AOT**（+ PGO） |
| **动态分发** | vtable | 隐藏类 + 内联缓存 | itab |
| **并发** | 1:1 线程 | 单线程事件循环 | **M:N goroutine** |
| **对象移动** | ✅ 可以 | ✅ 可以 | ❌ **不移动**（cgo 兼容） |
| **优化目标** | 通用（可配置） | 动态语言中最快 | **低延迟 + 确定性** |

### 六个核心认知

1. **Go 不分代不是做不到，是认为不值得。** Go 大量用栈分配（逃逸分析），堆上对象生命周期长，分代收益小。

2. **三色标记的价值是给出了正确性判据**，写屏障的设计变成了一道证明题。

3. **Go 的混合屏障是被"并发 + 栈不加屏障"逼出来的唯一解**。不是创新，是求解。

4. **JIT 的核心优势是可以"赌"**——基于运行时信息做投机优化，赌错了去优化。代价是预热时间和去优化开销。

5. **分层编译是"预热速度"和"峰值性能"的权衡**。90% 的代码从未被优化编译。

6. **虚拟机就是"用软件实现的 CPU"**，面临完全相同的问题：指令分发、寄存器 vs 内存、分支预测、投机执行。
