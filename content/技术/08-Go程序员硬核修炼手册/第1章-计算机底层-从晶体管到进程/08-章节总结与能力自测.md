### 贯穿全章的六个"统一法则"

这六条法则在第 1 章反复出现，**后面 7 章还会继续出现**。记下它们：

| # | 法则 | 在第 1 章的出现位置 |
|:---|:---|:---|
| **1** | **让相关的东西物理上靠近** | 缓存行 → 内存页 → NUMA 节点；Go 的 size class；PGO 函数重排 |
| **2** | **层次化缓存：向下一层请求成本高时，本层批量缓存** | CPU L1/L2/L3 → 内存；TLB；Go 的 mcache/mcentral/mheap；分配器的批量切分 |
| **3** | **用约束换性能** | Arena 接受"生命周期一致"换取 O(1) 分配；栈单线程访问所以可用复制式增长 |
| **4** | **把信息提前到编译期几乎总是划算** | 编译期类型 vs 运行时 header；静态链接 vs 动态链接；AOT vs JIT |
| **5** | **操作"贵不贵"要看它破坏了什么状态** | 上下文切换的真正代价是 TLB 失效；GC 的 STW 让所有缓存变冷 |
| **6** | **理论约束塑造工程实践** | 正则无法计数 → 编译必须分层；CFG 通用分析 O(n³) → LL/LR 只做子集；逃逸分析不可判定 → 只能保守近似 |

## 二、能力自测（30 题）

**使用方法**：先自己答，再看答案要点。答对 20 题以上说明你掌握了，25 题以上说明你可以往下走了。

### A 组 · 内存与性能（第 01、03 节）

**A1.** 从 L1 缓存到远端 NUMA 节点，内存访问延迟差多少倍？

<details><summary>答案要点</summary>
约 **17 倍**（L1 ~3ns，远端 NUMA ~52ns）。中间层次：L2 ~3.5ns，L3 ~6-14ns，本地主存 ~26-30ns。
</details>

**A2.** 什么是 false sharing？为什么它会让程序慢 6 倍？

<details><summary>答案要点</summary>
两个不相关的变量碰巧在同一个 64 字节缓存行。多核修改各自变量时，MESI 协议导致缓存行在核心间反复失效。数据本身没共享，但缓存行共享了。
</details>

**A3.** `make([]byte, 1<<30)` 是 O(1) 还是 O(1GB)？为什么？

<details><summary>答案要点</summary>
**O(1)**。只在虚拟地址空间划出范围，不分配物理页。真正的物理页在首次访问时由缺页异常分配（按需分页）。这解释了 VIRT 大但 RSS 小的现象。
</details>

**A4.** Minor fault 和 major fault 的区别？代价差多少？

<details><summary>答案要点</summary>
- **Minor**：页已在物理内存，只是页表没映射。建立映射即可，~1-5μs
- **Major**：页不在内存，需要从磁盘读。~1-10ms，**慢 1000 倍**
</details>

**A5.** 为什么 4 级页表？如果只有 1 级会怎样？

<details><summary>答案要点</summary>
1 级需要 2^36 × 8B = **512GB** 的页表，比物理内存还大。多级页表把稠密数组变稀疏树，只为实际用到的地址空间分配下级页表，降到 **<1MB**。代价是查找从 1 次访存变 4 次（靠 TLB 缓解）。
</details>

**A6.** 大页（2MB）相对 4KB 页，TLB 覆盖率提升多少倍？

<details><summary>答案要点</summary>
**512 倍**。典型 L2 TLB 有 1536 项：4KB 页覆盖 6MB，2MB 页覆盖 3GB。
</details>

**A7.** NUMA 的本质是什么？为什么要有它？

<details><summary>答案要点</summary>
**用访问均匀性换总带宽**。单 CPU 能直连的内存通道数有上限，跨节点互连带宽增长远慢于核数增长。本地带宽 300GB/s vs 跨节点 50GB/s，差 6 倍。这是物理约束，不是软件设计缺陷。
</details>

**A8.** 为什么 Go 程序员特别容易踩 NUMA 的坑？

<details><summary>答案要点</summary>
三个放大效应：① goroutine 极度轻量，几千个在 64 核间被调度器搬运；② Go 用 mmap 一次要 64MB arena，物理页的 NUMA 归属在 mmap 时就定了，runtime 内部不感知 NUMA；③ GC 全堆扫描，跨节点访问叠加在 GC 停顿上。
</details>

### B 组 · 程序与链接（第 02 节）

**B9.** Go 程序启动时，CPU 执行的第一条指令在哪？

<details><summary>答案要点</summary>
**不在 main.main，也不在 Go 代码里**。ELF 的 `e_entry` 指向 `runtime._rt0_amd64_linux`（汇编），它调用 `runtime.rt0_go` → `schedinit` → `newproc(runtime.main)` → `mstart`。**main.main 是作为第一个 goroutine 被创建的。**
</details>

**B10.** 为什么 `main.main` 返回后整个进程就退出，其他 goroutine 也被杀死？

<details><summary>答案要点</summary>
`main.main` 是"主 goroutine"。它返回后 `runtime.main` 显式调用 `exit(0)`。这是 Go 的刻意设计——**明确退出，不做任何等待**。要等其他 goroutine 必须用 `sync.WaitGroup`/channel 显式表达。
</details>

**B11.** 为什么 Go 的 hello world 有 1.5MB，C 的只有 16KB？

<details><summary>答案要点</summary>
Go 二进制带着**整个 runtime**：GC、调度器、内存分配器、goroutine 栈管理、类型系统、反射支持、panic 机制。空程序就有 1.2MB。代价是不适合嵌入式/tiny 工具，收益是任何 Go 程序都有完整能力。
</details>

**B12.** 为什么在 Alpine 容器里 Go 程序可能起不来？

<details><summary>答案要点</summary>
一旦用了 cgo（或 net/os-user 等包），Go 会动态链接 glibc。Alpine 用 musl libc，不兼容。解法：`CGO_ENABLED=0` 静态编译，或用 distroless/scratch 基础镜像。
</details>

**B13.** ELF 里 `.bss` 段的 MemSize 远大于 FileSize，为什么？

<details><summary>答案要点</summary>
`.bss` 存未初始化的全局变量。**文件里不占空间**（只记大小），加载时内核直接分配清零的内存页。这就是"零初始化全局变量不占二进制体积"的原因。
</details>

**B14.** `-ldflags="-s -w"` 做了什么？代价是什么？

<details><summary>答案要点</summary>
去掉符号表（-s）和 DWARF 调试信息（-w），通常能减小 25~30%。代价：panic 时没有行号，pprof 看不到函数名。建议保留一份带符号的用于事后分析。
</details>

**B15.** 什么是 PGO？它优化的是什么层面的局部性？

<details><summary>答案要点</summary>
Profile-Guided Optimization。用真实 profile 重新排列函数在二进制里的**物理布局**，让热路径的函数挨在一起，减少缺页和 i-cache miss；还做去虚拟化（把高频的 interface 调用改成静态调用+快速路径）。Go 1.20+ 原生支持，实测 2~7% 提升。
</details>

### C 组 · 内存分配（第 04 节）

**C16.** 外部碎片和内部碎片的区别？size class 是哪种交易？

<details><summary>答案要点</summary>
- **外部碎片**：空闲内存总量够，但不连续，无法满足大请求
- **内部碎片**：分配了但用不完（如要 20 字节给了 32 字节）

**size class 是用内部碎片换外部碎片**。Go 用 67 档把最坏浪费控制在 12.5% 以内。
</details>

**C17.** 为什么 Bump Allocator "不能释放"却用得极广？

<details><summary>答案要点</summary>
适合**对象生命周期一致**的场景：一次请求处理、一个查询执行、一帧渲染、编译器 AST。它把 O(n) 次 free 变成 O(1) 次 reset，且完全无碎片、分配 O(1)。**这是"用约束换性能"的典范。**
</details>

**C18.** Go 的 mcache 为什么绑定 P 而不是 M？

<details><summary>答案要点</summary>
① M 数量动态（系统调用阻塞会创建新的），可能几百个，每个 mcache 都占内存；② P 数量固定（=GOMAXPROCS），内存可控；③ G 必须绑定 P 才能执行，从 P 取 mcache 是免费的。
**核心思想：P 是资源的所有权单位，M 只是执行能力。**
</details>

**C19.** 我们的"玩具"分配器比 Go 原生 make 快 3 倍，为什么不该在业务代码里用它？

<details><summary>答案要点</summary>
因为它**做得更少**——不维护 GC bitmap、不做逃逸处理、不触发 gcAssist、不加写屏障。通用方案一定比专用方案慢，因为它要为所有情况买单。自研前要回答三个问题：测过是瓶颈吗？能接受失去 GC 保护吗？团队能维护吗？
</details>

**C20.** 什么信号表明"该自己管内存了"？

<details><summary>答案要点</summary>
① GC 扫描成本高（大量长生命周期小对象）；② 需要精确内存布局（数据库页、ring buffer、DMA）；③ 内存需序列化/共享（mmap 多进程）。**反面信号**：生命周期不规则、团队不懂、没有测量证据。
</details>

### D 组 · 编译（第 05、06 节）

**D21.** 为什么 Go 的错误提示比 Rust 差？

<details><summary>答案要点</summary>
Go 用**递归下降**（预测式，只知道"我猜错了"），Rust 用 LR 系（归约式，知道"当前所有可能的 token"）。**信息量差异**。递归下降的代价是分析器简单、编译快，但错误提示模糊。
</details>

**D22.** 为什么递归下降不能处理左递归？怎么解决？

<details><summary>答案要点</summary>
`E ::= E "+" T` 写成递归下降会无限递归（还没消耗 token）。**改写成右递归 + 累积器**：`E ::= T E'`，`E' ::= "+" T E' | ε`，用参数传 `left` 恢复左结合语义。
</details>

**D23.** 优先级爬升里，为什么传 `prec + 1` 就得到左结合？

<details><summary>答案要点</summary>
`minPrec` 控制"什么时候停止吸收右侧运算符"。传 `prec+1` 意味着"只有比我优先级更高的运算符才能进入我的右子树"，从而实现左结合。传 `prec` 则右结合（用于赋值运算符）。
</details>

**D24.** 为什么正则无法解析 HTML？

<details><summary>答案要点</summary>
HTML 标签可任意嵌套，**嵌套 = 需要计数 = 需要栈 = 不是正则语言**。有限自动机没有无界记忆，嵌套超过一定深度必然失败。
</details>

**D25.** C 的 typedef 问题是什么？它说明了什么？

<details><summary>答案要点</summary>
`T * b;` 到底是声明还是乘法，取决于 `T` 是不是类型名——**纯语法无法确定，需要语义信息**。C 用"词法反馈"解决（维护类型名表）。
**说明：纯粹的分层在真实系统里总被打破。** Go 的解法是改语言设计避开歧义（声明用 var/type/func 开头）。
</details>

**D26.** 写 C 编译器时，哪三个"看起来很对但实际错"的坑必须注意？

<details><summary>答案要点</summary>
① **栈 16 字节对齐**：System V ABI 要求 call 时 rsp%16==8，否则被调用函数用 SIMD 指令会崩；② **参数弹出顺序**：栈是 LIFO，从左往右压就得从右往左弹；③ **`idivq` 的隐式寄存器**：`cqto` 会覆盖 rdx，所以除数要先挪到 rcx。
</details>

**D27.** 为什么 C 有那么多未定义行为（UB）？

<details><summary>答案要点</summary>
**UB 是给编译器的"优化许可证"**。编译器可以假设程序无 UB，从而大胆优化（如假设 `x+1 > x` 恒成立）。**收益是性能，代价是行为不可预测**。Go 消灭 UB 换确定性，Rust 划分 safe/unsafe 边界两者兼顾。
</details>

**D28.** 语法分析 + 朴素代码生成占真实编译器工作量的多少？剩下的是什么？

<details><summary>答案要点</summary>
约 **20%**。剩下 80% 是：IR + 优化 passes（常量折叠、死代码消除、内联、逃逸分析）、寄存器分配（图着色）、诊断（行号、代码片段、修复建议）、ABI 兼容性。
</details>

### E 组 · 操作系统（第 07 节）

**E29.** 上下文切换的真正代价是什么？为什么不是"切换本身的指令"？

<details><summary>答案要点</summary>
切换指令本身约 100ns，但**它破坏了 CPU 的缓存状态**——换 CR3 导致 TLB 全部失效，接下来几十次内存访问都要走 4 级页表（每次 ~40ns）。实测 1560ns 中大部分是这个。
**判断操作贵不贵，要看它破坏了什么状态。** PCID 技术正是针对这点（给 TLB 条目打进程标签）。
</details>

**E30.** Go 的 GMP 里，一个 goroutine 阻塞在系统调用上会怎样？

<details><summary>答案要点</summary>
① M 陷入内核阻塞；② runtime 检测到，把 M 和 P 解绑；③ 拿/建一个新 M 绑定到该 P；④ P 继续跑其他 G。**所以一个 goroutine 的阻塞 syscall 不会阻塞其他 goroutine。**
而**网络 IO 走 netpoller（epoll），根本不阻塞线程**——一个线程管所有连接。
</details>

## 四、这一章的"元能力"

除了具体知识，这一章更重要的是训练了三种**可迁移的能力**：

### 1. 向下追问的能力

遇到奇怪现象，能往下追三到四层：

```
现象：P99 延迟周期性飙升
  ↓ 第 1 层：应用代码有问题？→ 查了，没问题
  ↓ 第 2 层：GC？runtime？→ 监控正常
  ↓ 第 3 层：内核？调度？→ 看起来正常
  ↓ 第 4 层：硬件？NUMA？→ ★ 找到了
```

**大多数"诡异"的问题，根因都在你习惯的抽象层之下 2-3 层。**

### 2. 识别统一模式的能力

这一章反复出现的六个法则（层次化缓存、让相关的东西靠近、用约束换性能……）。

**当你在一个层次理解了一个模式，去找它在其他层次的表现。** 这是把知识从"点"连成"网"的唯一方法。

### 3. 权衡取舍的判断力

没有"最好的设计"，只有"最适合约束的设计"：

| 选择 | 收益 | 代价 |
|:---|:---|:---|
| Go 静态链接 | 部署原子性 | 二进制大 |
| Go 递归下降 | 编译快、可维护 | 错误提示差 |
| Go 用 UB 换取消 | 行为可预测 | 优化空间小 |
| Arena 分配 | O(1) 分配 | 生命周期必须一致 |
| 复制式 GC | 无碎片、O(1) 分配 | 浪费 50% 内存 |

**判断力 = 能说出"如果我去掉这个设计，具体哪一项指标会恶化多少"。**

- **工程视角的数据结构**：为什么数据库用 B+Tree 而不是红黑树？为什么 Redis 用跳表？
- **全部用 Go 实现**，含 benchmark 和 GC 友好的设计考量
