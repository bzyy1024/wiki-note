## 引入场景

你在Go中声明一个变量，它存在哪里？全局变量和局部变量在同一个地方吗？`make([]byte, 1024)` 分配的内存和 `var x int` 分配的内存在同一个区域吗？

理解进程内存布局，能帮你：
- 理解Go逃逸分析的决策

## 对话探索

**问题1：一个运行中的进程，它的虚拟地址空间是怎么划分的？**

💭 思考方向：
- 代码（指令）和数据需要分开吗？
- 函数局部变量和全局变量在同一个区域吗？
- `malloc`/`make` 分配的内存在哪里？

📖 参考答案：

经典的进程内存布局（从低地址到高地址）：

```
高地址 0xFFFFFFFF...
┌─────────────────────────┐
│        内核空间           │  用户程序不可访问
├─────────────────────────┤ ← 内核/用户分界
│         栈 (Stack)       │  ↓ 向低地址增长
│  函数局部变量、参数、返回值  │
│                         │
│    ........空闲........   │
│                         │
│         堆 (Heap)        │  ↑ 向高地址增长
│  动态分配的内存            │
├─────────────────────────┤
│   .bss (未初始化全局变量)  │  程序启动时清零
├─────────────────────────┤
│   .data (已初始化全局变量) │  var count = 42
├─────────────────────────┤
│   .rodata (只读数据)      │  字符串常量、const
├─────────────────────────┤
│   .text (代码段)          │  编译后的机器指令
└─────────────────────────┘
低地址 0x00000000...
```

| 段 | 存什么 | 权限 | 大小 |
|---|--------|-----|------|
| `.text` | 机器指令 | 只读+可执行 | 编译时确定 |
| `.rodata` | 字符串常量、const | 只读 | 编译时确定 |
| `.data` | `var x = 42` | 读写 | 编译时确定 |
| `.bss` | `var x int` (零值) | 读写 | 编译时确定大小，不占磁盘空间 |
| **堆** | `make`/`new` 分配 | 读写 | 运行时动态增长 |
| **栈** | 局部变量、函数参数 | 读写 | 运行时动态伸缩 |

**问题2：堆和栈有什么区别？为什么不能全用栈或全用堆？**

💭 思考方向：
- 栈的分配和释放有什么特点？
- 堆的分配和释放有什么特点？
- 函数返回后，局部变量还在吗？

📖 参考答案：

| 特性 | 栈 (Stack) | 堆 (Heap) |
|------|-----------|-----------|
| **分配速度** | 极快（移动栈指针） | 较慢（查找空闲块） |
| **释放** | 函数返回时自动释放 | 需要GC或手动释放 |
| **大小** | 较小（Go goroutine初始几KB） | 很大（几乎等于可用内存） |
| **生命周期** | 函数执行期间 | 直到被回收 |
| **碎片** | 无（LIFO结构） | 可能有碎片 |
| **适用于** | 生命周期明确的局部变量 | 需要跨函数使用的数据 |

```
为什么不能全用栈？
  func createUser() *User {
      u := User{Name: "Alice"}
      return &u  // ← 返回局部变量的地址！
  }
  // 如果u在栈上，函数返回后栈帧销毁，&u指向无效内存

为什么不能全用堆？
  for i := 0; i < 1000000; i++ {
      x := i * 2  // ← 每次循环分配和回收
  }
  // 如果x在堆上，每次迭代都要GC参与，性能差
```

**问题3：Go的变量到底分配在栈上还是堆上？谁决定的？**

💭 思考方向：
- Go没有 `malloc`/`free`，程序员不手动管理
- 编译器如何决定？
- 什么情况下变量会"逃逸"到堆上？

📖 参考答案：
Go编译器通过**逃逸分析（Escape Analysis）**决定：

**规则**：如果编译器能证明一个变量在函数返回后不会被引用，就分配在栈上；否则分配在堆上。

```go
// 情况1：不逃逸（栈分配）
func sum(a, b int) int {
    result := a + b  // result在函数返回后不再使用 → 栈
    return result
}

// 情况2：逃逸（堆分配）
func newUser() *User {
    u := User{Name: "Alice"}  // u的指针被返回了 → 堆
    return &u
}

// 情况3：逃逸（堆分配）
func process() {
    data := make([]byte, 1024*1024)  // 太大了 → 堆
    _ = data
}

// 情况4：逃逸（堆分配）
func save(users []*User) {
    u := User{Name: "Bob"}
    users = append(users, &u)  // u的地址存到了外部切片 → 堆
}
```

```bash
# 查看逃逸分析结果
$ go build -gcflags="-m" main.go
# 输出：
# ./main.go:10:2: moved to heap: u    ← 逃逸到堆
# ./main.go:5:2: result does not escape  ← 留在栈上
```

**常见逃逸原因**：
1. 返回了局部变量的指针
2. 变量被存到了interface{}中（编译器不确定具体类型）
3. 变量太大（超过一定阈值）
4. 闭包引用了外部变量
5. 切片/map的值包含指针且被传到函数外

**问题4：Go的goroutine栈和操作系统线程栈有什么不同？**

💭 思考方向：
- 线程栈通常有多大？
- goroutine栈初始有多大？
- 栈能增长吗？线程栈能吗？

📖 参考答案：

| 特性 | OS线程栈 | Goroutine栈 |
|------|---------|-------------|
| **初始大小** | 1-8MB（固定） | 2-8KB（可配置） |
| **能否增长** | 不能（溢出=崩溃） | 能（自动扩展到最大1GB） |
| **数量限制** | 几千个线程 | 轻松十万个goroutine |
| **内存消耗** | 1000线程 × 8MB = 8GB | 10万goroutine × 8KB = 800MB |

**Goroutine栈增长机制**：

```
1. 编译器在每个函数入口插入检查代码：
   if 当前栈空间 < 需要的空间:
       runtime.morestack()

2. morestack() 的工作：
   a. 分配一个2倍大小的新栈
   b. 复制旧栈的全部内容到新栈
   c. 更新所有指向旧栈的指针
   d. 释放旧栈
   e. 继续执行
```

```
初始:  [2KB]      栈帧占满时:  [4KB新栈]     再次不够:  [8KB更大的栈]
       ┌──┐                   ┌────┐                   ┌────────┐
       │满│   → 复制+扩展  →  │旧数据│   → 复制+扩展  →  │ 旧数据  │
       └──┘                   │新空间│                   │        │
                              └────┘                   │ 新空间  │
                                                       └────────┘
```

**问题5：为什么理解内存布局对日常开发有帮助？**

💭 思考方向：
- 内存泄漏怎么排查？
- pprof看到的内存信息和内存布局的关系
- 怎样写出对GC友好的代码？

📖 参考答案：

**实际应用场景**：

1. **排查内存泄漏**：
   ```bash
   # 堆持续增长 → 某些对象没被释放
   # 用pprof查看堆上分配最多的代码路径
   go tool pprof http://localhost:6060/debug/pprof/heap
   ```

2. **优化内存分配**：
   ```go
   // 差：循环中反复堆分配
   for i := 0; i < N; i++ {
       buf := make([]byte, 1024)  // 每次循环分配（可能在堆上）
       process(buf)
   }
   
   // 好：复用buffer
   buf := make([]byte, 1024)  // 一次分配
   for i := 0; i < N; i++ {
       process(buf)  // 复用
   }
   ```

3. **减少GC压力**：
   ```go
   // 栈分配不需要GC → 尽量让变量不逃逸
   // 值类型(struct)不逃逸时在栈上 → 比指针类型更GC友好
   ```

## Go语言实践

```go
package main

import (
    "fmt"
    "runtime"
    "unsafe"
)

var globalVar = 42        // .data 段
var zeroVar int           // .bss 段
const constStr = "hello"  // .rodata 段

func stackDemo() {
    localVar := 100  // 栈上
    fmt.Printf("局部变量(栈)地址:    %p\n", &localVar)
}

func heapDemo() *int {
    x := 200         // 逃逸到堆上（因为返回了指针）
    fmt.Printf("逃逸变量(堆)地址:    %p\n", &x)
    return &x
}

func main() {
    fmt.Printf("全局变量(.data)地址: %p\n", &globalVar)
    fmt.Printf("零值全局(.bss)地址:  %p\n", &zeroVar)
    fmt.Printf("代码段(main)地址:    %p\n", main)

    stackDemo()
    heapDemo()

    fmt.Printf("\n指针大小: %d 字节\n", unsafe.Sizeof(uintptr(0)))

    // 内存统计
    var m runtime.MemStats
    runtime.ReadMemStats(&m)
    fmt.Printf("\n堆分配: %.2f MB\n", float64(m.HeapAlloc)/(1024*1024))
    fmt.Printf("栈使用: %.2f MB\n", float64(m.StackInuse)/(1024*1024))
    fmt.Printf("GC次数: %d\n", m.NumGC)
}
```

```bash
# 运行并观察不同段的地址差异
$ go run main.go

# 查看逃逸分析
$ go build -gcflags="-m -m" main.go 2>&1 | grep -E "escape|heap"
```

## 小结

⭐ **核心要点**：
1. **五大区域**：代码段（只读指令）、数据段（全局变量）、BSS（零值全局）、堆（动态分配）、栈（函数局部）
2. **逃逸分析决定栈/堆**：编译器自动判断，栈分配更快且免GC
3. **goroutine栈可增长**：初始很小（几KB），按需倍增，所以可以轻松创建十万个goroutine
