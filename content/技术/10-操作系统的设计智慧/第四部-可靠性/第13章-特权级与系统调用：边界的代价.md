# 第 13 章　特权级与系统调用：边界的代价

> 前面三部，我们一直在"内核"的视角和"应用"的视角之间来回切换。
> 这一章，我们正面拆一个问题：**应用和内核之间的那道"门"，到底是怎么开的？开一次要花多少钱？**
>
> 这道门，就是**特权级**（privilege level）和**系统调用**（system call）。
>
> 它看似平淡无奇——不就是 `read()`、`write()` 吗？但它是整个操作系统"安全"和"性能"的枢纽。理解了它，你就理解了：
> - 为什么 `getpid()` 这种"无害"的调用，也要陷入内核？
> - 为什么系统调用比普通函数调用贵 20 倍？
> - 以及 eBPF 这个"内核里的沙箱"，为什么被称为"可编程性革命"。

---

## 引子：一个函数调用，和一个系统调用，差在哪？

看两行代码：

```c
// 普通函数调用
int x = add(1, 2);       // 约 1 纳秒

// 系统调用
int pid = getpid();      // 约 50-100 纳秒
```

`add` 和 `getpid` 都是"调用一个函数"，但成本差了 **50-100 倍**。为什么？

因为 `add` 是"函数调用"（同一特权级，直接跳转），而 `getpid` 是"系统调用"（跨越特权级，陷入内核）。

这一章，我们拆开这道"门"：它为什么存在？跨越它要花多少钱？以及，怎么"能不开门就不开门"。

给你一句总纲：

> **特权级（ring 0 / ring 3）是 CPU 硬件提供的一道"墙"，把"可信的内核"和"不可信的应用"隔开。**
>
> 系统调用是这道墙上的"受控门"——应用通过它，请求内核代劳"特权操作"。
>
> 这道墙保证了安全，但"跨墙"是有代价的：**每次系统调用，都是一次"世界切换"（用户态 ↔ 内核态），代价远高于函数调用。**
>
> 所以系统设计的一个永恒主题是：**怎么在"安全"的前提下，尽量减少"跨墙"的次数。**

# 第一幕：为什么要有一道墙

## Q1　为什么不能让应用程序直接访问硬件？特权级解决什么问题？

**问题：如果应用程序能直接访问硬件，会发生什么？**

```
1. 恶意程序直接读写磁盘 → 偷你的数据
2. 有 bug 的程序写坏硬件寄存器 → 整台机器崩溃
3. 程序 A 读取程序 B 的内存 → 隐私泄露
4. 程序直接操作网卡 → 绕过防火墙、篡改流量
```

**所以必须有一道"墙"：**

```
让"普通的应用程序"不能直接碰硬件，
只能通过"内核"这个"可信的中介"来操作硬件。

这就是特权级的核心思想：
  内核 = 可信的，拥有最高权限，能碰硬件
  应用 = 不可信的，权限受限，要碰硬件必须请求内核
```

**特权级解决了三个问题：**

```
1. 隔离（isolation）：
   应用不能碰别的应用的内存（第 1 章的虚拟内存）
   应用不能碰内核的内存

2. 保护（protection）：
   应用不能直接操作硬件（要经过内核的检查和代理）

3. 抽象（abstraction）：
   应用通过"系统调用"这个干净接口操作硬件，
   不用知道硬件的具体细节
```

**类比：银行金库。**

```
金库（硬件）：只有银行职员（内核）能进
客户（应用）：不能直接进金库，只能通过"柜台"（系统调用）办业务

为什么？
  1. 安全：客户不能直接拿钱（会乱拿）
  2. 规范：客户通过柜台，银行能"检查"（取钱要验证身份）
  3. 抽象：客户不用知道金库怎么开门，只需填单子（系统调用）
```

> **特权级的本质：把"危险的、可信的"操作，集中到"内核"这个受控的地方，让"应用"只能通过"受控的接口"请求这些操作。**

## Q2　ring 0 和 ring 3 是什么？为什么中间还有 ring 1、2？

**x86 的四个特权级（ring 0-3）：**

```
ring 0：最高权限（内核）
ring 1：次高权限（历史上给设备驱动）
ring 2：更低（历史上给某些系统服务）
ring 3：最低权限（用户应用程序）

数字越大，权限越低。
```

**但现代操作系统只用了两个：ring 0 和 ring 3。**

```
为什么 ring 1、2 被"废弃"了？

1. 历史原因：早期设计时，设想"内核 ring0、驱动 ring1、服务 ring2、应用 ring3"
2. 现实：这种"四级分层"太复杂，而且驱动的可信度和内核差不多
   （驱动也要碰硬件，给它 ring1 和 ring0 区别不大）

所以现代 OS：
  - ring 0：内核 + 驱动（都是"可信的"）
  - ring 3：所有用户程序（都是"不可信的"）
  - ring 1、2：基本不用（形同虚设）
```

**ring 0 和 ring 3 的区别（关键）：**

```
ring 0（内核态）：
  - 可以执行所有指令（包括特权指令）
  - 可以访问所有内存（包括内核内存）
  - 可以操作硬件

ring 3（用户态）：
  - 只能执行"非特权"指令
  - 只能访问"自己的"内存（用户空间）
  - 操作硬件必须通过系统调用
```

**特权指令（privileged instructions）的例子：**

```
- 修改页表（CR3 寄存器）→ 用户态不能碰，否则能改内存映射
- 开关中断（CLI/STI）→ 用户态不能碰，否则能屏蔽时钟中断
- 读写硬件端口（IN/OUT）→ 用户态不能碰，否则能直接操作硬件
- 修改特权级（切换到 ring 0）→ 用户态不能碰，否则能提升权限
```

> **ring 0/3 的"两分法"，是一个工程简化：**
>
> 与其搞复杂的"四级权限"，不如简单粗暴地"两级"——可信的内核 vs 不可信的应用。
>
> 这反映了一个设计原则：**安全模型越简单，越不容易出错。** 复杂的权限分级（ring 1、2），历史上证明了"用不上还添乱"。
>
> 类似的，你在设计系统权限时，也倾向于"少而清晰"的角色，而不是"多而复杂"的权限矩阵。

# 第二幕：系统调用 —— 墙上的门

## Q3　一次系统调用，从用户态到内核态，完整流程是什么？

以 `getpid()` 为例（虽然它简单到可以优化，但正好看完整流程）：

**用户态（发起调用）：**

```c
// 应用调用 getpid()
// 1. 把系统调用号（getpid 是 39）放进 rax 寄存器
// 2. 把参数放进寄存器（getpid 无参数）
// 3. 执行 syscall 指令（x86-64）
```

**`syscall` 指令（硬件做的事）：**

```
1. 保存"返回地址"（syscall 下一条指令）到 RCX
2. 保存"当前标志寄存器"到 R11
3. 从 MSR 寄存器加载"内核入口地址"和"内核栈指针"
4. 切换到 ring 0（特权级提升）
5. 跳转到内核入口
```

**内核态（处理调用）：**

```
1. 内核入口：保存用户态寄存器的现场
2. 根据 rax 里的系统调用号，查"系统调用表"
   → 找到对应的内核函数（sys_getpid）
3. 执行 sys_getpid：从当前进程的 task_struct 读 pid
4. 把返回值（pid）放进 rax
5. 恢复现场
```

**返回用户态（sysret 指令）：**

```
1. 从内核栈恢复用户态寄存器
2. 切换回 ring 3（特权级降低）
3. 跳转回用户态（RCX 里的返回地址）
```

**完整流程图：**

```
用户态                    内核态
  │                         │
  ├─ getpid()               │
  ├─ mov $39, %rax          │
  ├─ syscall ──────────────→│
  │                         ├─ 保存现场
  │                         ├─ 查表（rax=39 → sys_getpid）
  │                         ├─ 执行 sys_getpid
  │                         ├─ 返回值放 rax
  │                         ├─ 恢复现场
  │←────────────── sysret ──┤
  ├─ 从 rax 读返回值         │
  │                         │
```

> **关键理解：系统调用的本质，是"一次受控的特权级切换"。**
>
> 硬件（syscall/sysret 指令）负责"切换特权级"这件事，内核负责"处理请求"这件事。
>
> 而"切换特权级"本身有成本（保存/恢复现场、切换栈、可能刷 TLB），这就是系统调用比函数调用贵的原因。

## Q4　系统调用为什么比函数调用贵那么多？

对比一下两者的成本：

```
函数调用（call 指令）：
  1. 把返回地址压栈（1 条指令）
  2. 跳转到函数（1 条指令）
  → 约 1-5 纳秒

系统调用（syscall 指令）：
  1. 保存返回地址、标志寄存器
  2. 切换到内核栈（换栈指针）
  3. 切换特权级（ring 3 → ring 0）
  4. 查系统调用表（跳转）
  5. 执行内核函数
  6. 切回用户态（ring 0 → ring 3）
  7. 恢复现场
  → 约 50-100 纳秒（甚至更多）
```

**为什么贵这么多？**

**原因一：特权级切换本身。**

```
ring 3 → ring 0 的切换，要经过硬件的一系列检查：
  - 检查权限（这次切换是否合法）
  - 切换栈（用户栈 → 内核栈）
  - 更新特权级状态

这些"安全检查"是必须的，但耗时。
```

**原因二：栈切换。**

```
函数调用：在同一个栈上（用户栈）
系统调用：从用户栈切换到内核栈（每个进程有独立的内核栈）

栈切换 = 改栈指针 + 可能的内存访问
```

**原因三：保存/恢复现场。**

```
系统调用要保存"所有用户态寄存器"（内核可能用到它们），
返回时要恢复。这是一笔不小的开销。
```

**原因四：可能刷 TLB（KPTI 之后更贵）。**

```
第 1 章讲过 Meltdown 漏洞和 KPTI 修复。
KPTI 让内核页表和用户页表分离，
系统调用时要切换页表 + 刷 TLB，
这让系统调用变贵了 2-5 倍。
```

**一个反直觉的事实：`getpid()` 比 `add(1,2)` 贵 100 倍，但它做的事（读一个 pid）比 add 还简单。**

```
getpid 做的事：读当前进程的 pid（一个整数）
add 做的事：两个整数相加

但 getpid 贵 100 倍，因为它"跨了那道墙"。
```

> **系统调用的昂贵，是"安全"的代价。**
>
> 那道墙（特权级隔离）保证了"应用不能胡作非为"，但每次"合法地跨墙"都要付"过墙费"。
>
> 这就是为什么：
> - 高性能系统要"减少系统调用次数"（批量、io_uring）
> - 有些系统调用被"搬到用户态"（vDSO，下一问）
> - 数据库要用"连接池"（减少 socket 的系统调用）

## Q5　系统调用怎么传参？怎么知道调用哪个？

**系统调用的"协议"（x86-64 Linux）：**

```
1. 系统调用号：放在 rax 寄存器
   （比如 0=read, 1=write, 39=getpid, 59=execve...）

2. 参数：放在寄存器
   rdi, rsi, rdx, r10, r8, r9（最多 6 个参数）

3. 发起：syscall 指令

4. 返回值：放在 rax
```

**内核侧：系统调用表（sys_call_table）。**

```c
// 一个"系统调用号 → 函数指针"的表
typedef long (*sys_call_ptr_t)(...);

sys_call_ptr_t sys_call_table[] = {
    [0]  = sys_read,
    [1]  = sys_write,
    [2]  = sys_open,
    ...
    [39] = sys_getpid,
    ...
};

// 内核入口：
// 1. 检查 rax（系统调用号）是否越界
// 2. 查表：sys_call_table[rax]
// 3. 调用对应的函数
```

**为什么用"寄存器"而不是"栈"传参？**

```
1. 寄存器传参快（不碰内存）
2. 系统调用要"换栈"（用户栈 → 内核栈），
   如果用栈传参，要先把参数从用户栈拷到内核栈（麻烦）
   用寄存器，参数"天然"就带过去了
```

**Go 里的系统调用：**

```go
// Go 标准库封装了系统调用，你通常不需要直接碰
// 但底层是类似的（通过 syscall 包）

// 直接调用（罕见）：
import "syscall"
pid := syscall.Getpid()

// 底层（runtime 内部）：
// MOVQ $39, AX   ; 系统调用号
// SYSCALL
```

> **系统调用的"协议"（寄存器传参 + 号索引表），是一个经典的"接口设计"：**
>
> - 用"号"索引（而不是字符串名字）→ 快（查表 O(1)）
> - 用寄存器传参 → 快（不碰内存，天然跨栈）
> - 固定 6 个参数上限 → 简单（不够用就传指针）
>
> 你在设计高性能接口时，也会用同样的思路：**用数字 ID 代替字符串、用紧凑的协议代替自描述、固定参数上限。**

# 第三幕：省掉开门

## Q6　vsyscall / vDSO 是怎么"能不进内核就不进"的？

**问题：有些系统调用"根本不需要进内核"，但每次都要付"过墙费"。**

```
getpid()：读当前进程的 pid，这个值内核知道，
  但"读 pid"这个操作本身，能不能不进内核？

gettimeofday()：读当前时间，
  内核维护了时间，但"读时间"能不能不进内核？
```

**答案：vsyscall / vDSO。**

**vDSO（virtual Dynamic Shared Object，虚拟动态共享对象）：**

```
思想：把一些"只读、无副作用"的系统调用，做成"用户态可读的内存数据"。

实现：
  1. 内核把"只读数据"（比如当前时间、pid）映射到用户态的一块内存
  2. 用户态直接读这块内存，不用陷入内核
  3. 内核更新数据时，同步更新这块映射的内存

效果：
  gettimeofday() 原本要 syscall（50-100ns），
  用 vDSO 后，就是一次普通的内存读（几纳秒）。
  → 快 10-20 倍
```

**哪些调用能"搬出内核"？**

```
条件：只读、无副作用、数据能"映射"给用户态

适合 vDSO 的：
  - gettimeofday（读时间）
  - clock_gettime（读时间）
  - getcpu（读当前 CPU 号）
  - getpid（读 pid，但 Linux 没把它搬出去，因为太简单了）

不适合的（有副作用、要特权）：
  - read/write（要操作硬件）
  - open（要访问文件系统）
  - fork（要复制进程）
```

**vDSO 的精髓：**

> **把"读数据"和"做操作"分开。**
>
> - "读数据"（时间、pid）→ 可以映射到用户态，不用进内核
> - "做操作"（读写文件、创建进程）→ 必须进内核
>
> 这又是一个"快路径"的实例（第 5 章 futex、第 9 章缓存）：**把"常见的、无副作用的"操作搬到快路径（用户态），"罕见、有副作用"的操作才走慢路径（内核）。**

**一个对比：vsyscall 和 vDSO。**

```
vsyscall（旧方案）：固定地址的"用户态内核代码"，有安全问题（固定地址可被攻击）
vDSO（新方案）：动态链接的共享对象，地址随机化（安全）

现代 Linux 用 vDSO，vsyscall 基本废弃（仅兼容）。
```

## Q7　系统调用的"税"，什么时候值得用"旁路"（批量、io_uring）来避？

前面讲了系统调用贵，那"怎么少付税"？

**手段一：批量（减少次数）。**

```
传统：100 次 write = 100 次系统调用
批量：writev（一次系统调用写 100 块） = 1 次系统调用

或者：攒够一批数据，一次 write 出去（第 12 章批量）
```

**手段二：io_uring（共享内存，接近零系统调用）。**

```
第 4 章讲过 io_uring：
  提交 I/O 请求 → 写共享内存环形队列（不用系统调用）
  内核处理 → 写回共享内存
  查结果 → 读共享内存（不用系统调用）

只有"通知内核"和"等待完成"才偶尔用系统调用。
```

**手段三：vDSO（搬到用户态）。**

```
gettimeofday 等只读调用，用 vDSO，直接用户态读。
```

**手段四：减少不必要的系统调用。**

```
例：不要每个请求都 open/close 文件（用连接池、复用 fd）
例：用内存池代替频繁 malloc（malloc 可能触发 brk/mmap 系统调用）
```

**什么时候值得"避税"？**

```
判断标准：系统调用的"税"占总成本的比例。

1. 低频操作（每秒几百次）→ 税可以忽略，别费劲优化
2. 高频操作（每秒几十万次）→ 税占比大，值得避
3. 极致性能（每秒百万次 I/O）→ 必须避（io_uring、DPDK）

核心：先测量"系统调用开销占多少比例"，再决定"值不值得避"。
```

> **避税的通用逻辑（第 12 章摊销的延伸）：**
>
> **系统调用是一种"固定开销"（每次跨墙都要付）。**
>
> - 批量 = 摊薄固定开销（N 次合并成 1 次）
> - io_uring = 用共享内存绕开固定开销（大部分时候不付）
> - vDSO = 把"无副作用"的操作搬出墙（根本不付）
>
> 都是"减少跨墙次数"的不同手段，适用不同场景。

# 第四幕：内核的可编程性

## Q8　eBPF 是什么？为什么它被称为"内核的可编程性革命"？

**问题：内核是"封闭"的，你没法往内核里加逻辑（改内核要重新编译、重启、还危险）。**

```
传统：想在内核里做"定制逻辑"（比如自定义的网络过滤、性能监控），
  只能：
  1. 改内核源码，重新编译（难，且要重启）
  2. 写内核模块（危险，bug 会崩溃整个系统）
```

**eBPF（extended Berkeley Packet Filter）：**

```
思想：允许你在"内核里"运行"沙箱化的用户代码"，安全、无需改内核。

原理：
  1. 你写一段 eBPF 程序（C 或受限的指令集）
  2. 编译成 eBPF 字节码
  3. 通过 bpf() 系统调用，把字节码"注入"内核
  4. 内核"验证器"（verifier）检查代码安全（不能死循环、不能越界）
  5. 验证通过后，eBPF 程序被 JIT 编译成机器码，挂载到某个"钩子点"
  6. 钩子触发时，执行你的 eBPF 程序
```

**eBPF 的"钩子点"（能挂在哪）：**

```
- 网络：收到包时、发送包时（XDP、tc）
- 追踪：函数调用时（kprobe）、用户态函数（uprobe）
- 安全：系统调用时（seccomp）
- 性能：perf 事件、tracepoint
```

**为什么它是"革命"？**

```
1. 安全：验证器保证 eBPF 程序不能崩溃内核
   （不能死循环、不能访问越界内存、指令集受限）
   → 这是"内核里的沙箱"（第 19 章会讲沙箱）

2. 无需改内核：eBPF 程序动态注入，不用重新编译内核、不用重启

3. 高性能：eBPF 程序被 JIT 编译成机器码，在内核里跑，接近原生速度

4. 生态：Cilium（网络）、Falco（安全）、bpftrace（追踪）
   都是基于 eBPF 的
```

**eBPF 的典型应用：**

```
1. 可观测性：不用改代码，就能追踪内核函数、监控性能
   （第 20 章会详细讲）

2. 网络：XDP 在网卡驱动层处理包（DDoS 防护、负载均衡）
   Cilium 用 eBPF 实现容器网络

3. 安全：seccomp 用 eBPF 过滤系统调用
   Falco 用 eBPF 检测异常行为

4. 性能：自定义的流量控制、性能分析
```

**eBPF 和"系统调用"的关系：**

```
系统调用：应用 → 内核（请求内核做事）
eBPF：应用 → 内核（往内核里注入代码，改变内核行为）

系统调用是"使用内核提供的功能"，
eBPF 是"扩展内核的功能"。
```

> **eBPF 的启示（比技术本身重要）：**
>
> **"可编程性"和"安全性"看似矛盾，但 eBPF 用"沙箱 + 验证器"同时实现了两者。**
>
> - 可编程：你能往内核注入代码
> - 安全：验证器保证注入的代码不会搞坏内核
>
> 这个"沙箱化扩展"的思想，在工程里很有用：
> - 插件系统：允许用户写插件，但用沙箱隔离
> - 规则引擎：允许用户写规则，但验证规则安全
> - Serverless：允许用户上传代码，但用容器/VM 隔离
>
> **核心：让"扩展"变得安全，是"可编程性"能落地的关键。**

## Q9　这道墙面临哪些结构性的问题？（Meltdown、KPTI 的代价）

最后泼冷水。特权级这道墙，有几个根子上的问题：

**问题一：Meltdown —— 墙被"推测执行"凿穿了。**

```
第 1 章讲过 Meltdown：
  特权级检查（用户态不能访问内核内存）会被"推测执行"绕过，
  攻击者通过"侧信道"（缓存时间），能读到内核内存。

根本原因：
  CPU 为了性能，会"推测执行"（先斩后奏），
  而"特权级检查"是"后奏"（检查失败才回滚），
  但"推测执行"的痕迹（缓存）没有回滚。
  → 墙有了漏洞
```

**问题二：KPTI 的代价 —— 修漏洞，性能掉一截。**

```
KPTI（Kernel Page Table Isolation）修复 Meltdown：
  把内核页表和用户页表"彻底分离"，
  系统调用时要切换页表 + 刷 TLB。

代价：
  系统调用变慢 2-5 倍（页表切换 + TLB 刷新）
  某些 syscall-heavy 的工作负载，性能下降 5-30%

这是"安全和性能"冲突的典型案例：
  为了堵住 Meltdown 漏洞，付出了性能代价。
```

**问题三：系统调用的"税"，随"安全和功能"的增长而增长。**

```
系统调用要做的检查越来越多：
  - 权限检查（这个进程有权做这个操作吗）
  - 参数校验（参数合法吗）
  - 安全检查（seccomp 过滤、LSM 检查）
  - ...

每加一层"安全"和"功能"，系统调用就慢一点。
```

**问题四：特权的"二分化"太粗糙。**

```
ring 0 / ring 3 的两分法，简单但粗糙：
  - 内核态 = 完全可信（但驱动真的可信吗？驱动 bug 是内核崩溃的主因）
  - 用户态 = 完全不可信（但有些用户态程序其实很可信）

结果：
  - 驱动在内核态，bug 就崩内核（蓝屏/panic）
  - 有些"半可信"的组件（比如数据库），
    想要"部分特权"，但没有这个选项

这催生了"用户态驱动"（DPDK/SPDK，第 4 章）和"微内核"的尝试。
```

> **这一章的最终落脚点：**
>
> **特权级和系统调用，是"安全"和"性能"的枢纽。**
>
> - 安全需要"墙"（隔离、保护、抽象）
> - 性能需要"少跨墙"（vDSO、批量、io_uring）
>
> 而"墙"本身有代价（系统调用贵、KPTI 更贵、Meltdown 是漏洞）。
>
> 理解这个"安全 vs 性能"的根本权衡，你就理解了：
> - 为什么系统调用要精心设计（尽量少、尽量快）
> - 为什么有 vDSO、io_uring、eBPF 这些"绕墙"和"在墙内扩展"的技术
> - 为什么"安全"和"性能"的博弈会一直持续（Meltdown 之后还会有新的漏洞）

# 思考题

## 思考题 1

面试官问："系统调用和普通函数调用有什么区别？为什么系统调用慢？"请从"特权级切换、栈切换、现场保存、安全检查"四个角度回答。

<details>
<summary>参考答案</summary>

**核心答案：系统调用要跨越"特权级"（用户态 → 内核态），涉及特权级切换、栈切换、现场保存、安全检查，所以比普通函数调用慢 50-100 倍。**

**区别一：特权级切换。**

```
普通函数调用：同一特权级（都是用户态），直接 call 跳转
系统调用：跨越特权级（ring 3 → ring 0），要经过硬件特权级检查

特权级切换的代价：
  - 检查这次切换是否合法（权限校验）
  - 切换到内核态（更新 CPU 的特权级状态）
  - 可能触发 TLB 刷新（KPTI 之后）
```

**区别二：栈切换。**

```
普通函数调用：同一个栈（用户栈），压栈返回地址即可
系统调用：从用户栈切换到内核栈（每个进程有独立的内核栈）

栈切换的代价：
  - 保存用户栈指针，切换到内核栈指针
  - 内核栈是"受保护的"（用户态不能访问）
```

**区别三：现场保存。**

```
普通函数调用：只保存"被调用者保存"的寄存器（约定，由编译器处理）
系统调用：保存"所有"用户态寄存器（因为内核可能用到任何寄存器）

现场保存的代价：
  - 保存/恢复所有通用寄存器
  - 相比函数调用只保存几个，开销大得多
```

**区别四：安全检查。**

```
普通函数调用：无安全检查
系统调用：内核要做一系列检查：
  - 系统调用号是否合法（越界检查）
  - 参数指针是否合法（指向用户态的有效地址）
  - 权限检查（这个进程有权做这个操作吗）
  - seccomp 过滤（如果有）

这些检查是"安全"的代价，每个系统调用都要做。
```

**量化对比：**

```
普通函数调用：约 1-5 纳秒（call 指令 + 压栈）
系统调用：约 50-100 纳秒（甚至更多，KPTI 后 2-5 倍）

差距：50-100 倍
```

**追问：getpid() 这种"无害"调用，为什么也要这么慢？**

因为它也"跨墙"了——无论系统调用做什么，都要付"跨墙"的固定成本（特权级切换、栈切换、现场保存）。getpid 的"业务"很简单，但"跨墙"的成本是固定的。

**追问：有什么办法让 getpid 快一点？**

有，vDSO——把"只读、无副作用"的调用（如 gettimeofday）搬到用户态，用内存读代替系统调用。

**这道题考察什么：**

1. 能不能说清"特权级切换"这个核心区别
2. 知不知道系统调用要"换栈"、"保存现场"、"安全检查"
3. 知不知道"跨墙"的固定成本（不管调用做什么都要付）
4. 知不知道 vDSO 这个"绕墙"的优化
</details>

## 思考题 2

你的服务每秒要读 10 万次当前时间（`time.Now()`）。你担心性能。`time.Now()` 底层是系统调用吗？如果是，怎么优化？如果不是，为什么？

<details>
<summary>参考答案</summary>

**核心答案：`time.Now()` 在 Go 里（以及 Linux 上）底层用的是 vDSO，不是真正的系统调用（大部分情况下），所以性能已经很好，通常不需要优化。**

**先看 `time.Now()` 的底层：**

```go
func Now() Time {
    sec, nsec, mono := now()  // 调用 runtime 的 now
    ...
}

// runtime 的 now，底层调用了 clock_gettime
// clock_gettime 在 Linux 上，通过 vDSO 实现（用户态直接读时间）
```

**Linux 的 `clock_gettime` 走 vDSO：**

```
1. 用户态调用 clock_gettime
2. glibc 发现可以用 vDSO（内核映射的共享对象）
3. 直接读 vDSO 里的时间数据（用户态内存读，几纳秒）
4. 不陷入内核（没有系统调用）

所以 time.Now() 的成本 ≈ 一次函数调用 + 一次内存读 ≈ 几十纳秒
```

**什么时候 time.Now() 会变慢（真的走系统调用）？**

```
1. 某些架构/内核版本没有 vDSO 支持
   → 退化到真正的系统调用（50-100ns）

2. 需要"纳秒级精度"且内核时间源不稳定
   → 可能需要额外的系统调用

3. 容器/虚拟化环境，vDSO 可能失效
```

**怎么验证 time.Now() 到底走不走系统调用？**

```bash
# 用 strace 看系统调用
strace -c ./your-program
# 如果 clock_gettime 出现了，说明真的走了系统调用
# 如果没出现（或次数很少），说明走了 vDSO
```

**如果你确实需要极致性能的时间读取：**

```go
// 1. 缓存时间（如果不需要精确到纳秒）
var cachedTime atomic.Int64

func init() {
    go func() {
        for {
            cachedTime.Store(time.Now().UnixNano())
            time.Sleep(time.Millisecond)  // 每秒更新 1000 次
        }
    }()
}

// 读缓存时间（原子读，几纳秒，无系统调用）
// 代价：时间精度是毫秒级（缓存更新间隔）
```

**但大多数情况下，time.Now() 已经够快了（vDSO），不需要优化。**

**这道题考察什么：**

1. 知不知道 vDSO（把只读系统调用搬到用户态）
2. 知不知道 time.Now() 底层走 vDSO 而不是系统调用
3. 知不知道"什么时候会退化到系统调用"
4. 会不会"过度优化"（time.Now() 已经够快，别瞎优化）
</details>

## 思考题 3

eBPF 和"内核模块"都能扩展内核功能，区别是什么？为什么 eBPF 被认为是"更安全"的？它安全性的代价是什么？

<details>
<summary>参考答案</summary>

**核心答案：内核模块是"完全信任的内核代码"（能崩溃内核），eBPF 是"验证器检查过的沙箱代码"（不能崩溃内核）。eBPF 的安全性来自"验证器 + 受限指令集"，代价是"表达能力受限"。**

**内核模块（kernel module）：**

```
特点：
  - 用 C 写，编译成 .ko 文件
  - 通过 insmod/modprobe 加载进内核
  - 在内核态运行，有完整的内核权限

问题：
  - 一个 bug（空指针、死循环、越界写）→ 整个内核崩溃（panic）
  - 恶意模块可以做任何事（提权、隐藏进程、偷数据）
  - 没有"验证"机制，加载了就信任
```

**eBPF：**

```
特点：
  - 用受限的指令集写（C 的一个子集，编译成 eBPF 字节码）
  - 通过 bpf() 系统调用注入
  - 内核的"验证器"（verifier）先检查代码，再允许运行

验证器检查什么：
  - 不能死循环（检查所有路径，保证会终止）
  - 不能越界访问内存（检查所有内存访问）
  - 不能访问任意内核内存（只能访问允许的数据结构）
  - 指令数量有限（早期 4096 条，现在更多但仍有上限）
  - 不能有不可达代码、不能有未初始化变量
```

**eBPF 更安全的代价：**

```
1. 表达能力受限：
   - 不能做任意的事（指令集受限）
   - 不能访问任意内存（要验证器允许）
   - 循环受限（早期禁止循环，后来允许但有次数限制）

2. 开发约束：
   - 要用 C 的受限子集（不是所有 C 特性都能用）
   - 要理解验证器的规则（"为什么我的代码被拒绝"）

3. 验证器的"误拒"：
   - 验证器是保守的（宁可拒绝，不可放过）
   - 有些"其实是安全的"代码，会被验证器拒绝
   - 你要想办法"改写"代码来通过验证
```

**对比总结：**

| | 内核模块 | eBPF |
|--|---------|------|
| 权限 | 完整内核权限 | 受限（沙箱） |
| 安全 | 无验证，bug 崩内核 | 验证器检查，不能崩内核 |
| 表达能力 | 完整 C | 受限指令集 |
| 开发难度 | 难（要懂内核） | 相对容易（但受验证器约束） |
| 加载 | insmod，要 root | bpf()，权限可配置 |
| 崩溃影响 | 整个内核 | 无（沙箱隔离） |

**为什么 eBPF 是"革命"？**

因为它第一次实现了"**安全地**在内核里运行用户代码"：

```
之前：内核扩展 = 内核模块（危险，bug 崩内核）
现在：内核扩展 = eBPF（安全，验证器 + 沙箱）

这让"内核可编程"从"只有内核开发者能做"，
变成"普通开发者也能做"（写 eBPF 程序监控网络、追踪性能）。
```

**这道题考察什么：**

1. 知不知道内核模块的危险（bug 崩内核）
2. 知不知道 eBPF 的验证器机制
3. 知不知道 eBPF 的代价（表达能力受限）
4. 能不能说出"安全沙箱"和"表达能力"的权衡
</details>

## 思考题 4（开放题）

"特权级隔离"和"微服务隔离"、"容器隔离"，本质上是同一个思想在不同尺度的体现。你认同吗？请说明它们的对应关系，以及各自的"墙"和"门"。

<details>
<summary>参考答案</summary>

开放题，考察你能不能把"特权级隔离"抽象成"通用的隔离思想"。

**核心对应：**

```
特权级隔离（单机）：
  墙 = ring 0/3（内核态 vs 用户态）
  门 = 系统调用（受控的跨墙通道）
  目的：保护系统不被不可信的应用破坏

容器隔离：
  墙 = namespace + cgroup（容器 vs 宿主机）
  门 = 系统调用（容器的进程通过系统调用请求宿主机内核）
  目的：保护宿主机不被容器破坏，隔离容器之间

微服务隔离：
  墙 = 进程边界 + 网络（服务 A vs 服务 B）
  门 = RPC/API（受控的跨服务调用）
  目的：隔离故障，独立部署
```

**它们的统一模式：**

```
1. 都有"墙"（隔离机制）：
   特权级：硬件特权级
   容器：namespace/cgroup
   微服务：进程 + 网络

2. 都有"门"（受控通信）：
   特权级：系统调用
   容器：系统调用 + 网络
   微服务：RPC/API/消息队列

3. 目的都是：隔离故障 + 保护资源 + 提供抽象
```

**"墙"和"门"的对应关系：**

| | 特权级 | 容器 | 微服务 |
|--|--------|------|--------|
| 墙 | ring 0/3 | namespace/cgroup | 进程/网络 |
| 门 | 系统调用 | 系统调用 | RPC/API |
| 跨墙代价 | 50-100ns | 系统调用 | 1ms（网络） |
| 隔离强度 | 强（硬件） | 中（OS） | 中（进程） |
| 通信开销 | 低 | 低 | 高（网络） |

**一个深刻的观察：**

> **"隔离"和"通信"是一对矛盾。**
>
> 隔离越强（墙越高），通信越难（门越窄、跨墙越贵）：
> - 特权级：强隔离，但系统调用贵（50-100ns）
> - 容器：中隔离，系统调用相对便宜
> - 微服务：隔离但通信贵（网络 1ms）
>
> 所以选择"在哪一层隔离"，本质是选择"隔离强度 vs 通信成本"的平衡点。

**这和"加一层抽象"（第 1 章）的呼应：**

```
特权级隔离 = 在内核和应用之间"加一层"（特权级墙）
容器隔离 = 在宿主机和进程之间"加一层"（namespace）
微服务隔离 = 在服务之间"加一层"（网络边界）

每一层隔离，都：
  1. 提供了"保护"（故障隔离、资源隔离、安全隔离）
  2. 引入了"通信成本"（跨墙要付代价）
  3. 需要"门"（受控的跨墙通道）
```

**这个思想的统一应用：**

```
设计任何系统，问自己：

1. 谁和谁需要隔离？
   （可信的 vs 不可信的？重要的 vs 不重要的？）

2. 隔离的强度够吗？
   （硬件隔离 > OS 隔离 > 进程隔离 > 逻辑隔离）

3. 跨墙通信的成本能接受吗？
   （隔离越强，通信越贵）

4. "门"设计得合理吗？
   （系统调用 / RPC / 消息队列，哪个适合？）
```

**这道题的价值：**

> 它让你看到，**"隔离 + 受控通信"是系统设计的一个根本模式**，从 CPU 特权级，到容器，到微服务，甚至到组织的权限管理，都是同一个模式。
>
> 理解了这个模式，你在设计任何"多组件系统"时，都能自觉地思考：
> - 组件之间怎么隔离？
> - 隔离的"门"（接口）怎么设计？
> - 跨墙的代价能不能接受？
</details>
