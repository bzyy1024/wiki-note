## 三、"懂微观"的长期意义

墨:讲了 26 章,我不想用"你学会了好多参数"来收尾——因为参数会过时。**我想跟你聊的是"懂微观"这件事,对你的长期意义。**

### 意义一:你从"调参民科"变成"能推演的人"

不懂微观的人调参,是**"网上说 swappiness=10 好,我设 10"**——这是民科,是把别人的结论当咒语念。懂微观的人调参,是**"我的负载是内存偏紧的数据库,swap 颠簸会冻请求,所以我把 swappiness 压到 10 来抑制换出积极性,代价是 page cache 可能被挤,但我的 buffer pool 够大所以可接受"**——这是推演,是"拿什么换什么"的自觉权衡(第 24 章母题)。

**前者在硬件/内核升级后必然翻车(母题五:成本假设反转);后者能任何环境自查。** 这一章学完,我希望你成为后者。

### 意义二:你能区分"相关性"和"因果性"

第 19 章 OOM 连环杀里,DB 慢查询日志"跟着涨"。不懂微观的人去优化 SQL,越优化越懵;懂的人看时间差,知道 DB 是受害者,源头是节点水位被顶高。**这种"谁先动谁才是源头"的判断力,只来自对请求微观时序的理解。** 它在你职业生涯里值钱的程度,远超任何单一技术。

### 意义三:你敢碰"别人不敢动"的系统

很多工程师对 `/proc/sys` 下的参数有本能恐惧——"动了会不会崩"。恐惧来自未知。当你知道每个参数**守的是哪道门、调大调小各换来什么、它的安全阀/泄洪阀属性(第 12 章分类)**,你就从"不敢动"变成"知道动哪个、动多少、怎么回滚"。**这种从容,是 senior 和 junior 的分水岭之一。**

### 意义四:你有了"向下钻"的本能

出问题,不懂的人往上层找(改代码、加机器、重启);懂微观的人**先向下钻一层**,问"内核那一刻在干什么"。第 18 章的幽灵卡顿,若只在上层找,永远找不到是 THP compaction——只有愿意往下钻到内核机制的人,才看得到 `compact_stall`。**"向下钻一层"的本能,是这套教程想种进你脑子里的东西。**

## 六、🔧 思考题(都配参考答案)

**思考题 1(基础):** 用你自己的话,画出"一次 Web 请求从网卡到你的 handler 函数"所穿越的主要层次(至少 5 层),并标注每一层可能引入延迟的机制。

<details>
<summary>【参考答案】</summary>

一次 Web 请求(入向)穿越:
1. **网卡 + DMA + 软中断(第 09 章)**:包到网卡→DMA 进 ring buffer→硬中断→软中断(ksoftirqd/NAPI)上送。延迟来源:多队列不均、softnet backlog 满丢包、CPU 软中断瓶颈。
2. **网络栈 IP/TCP(第 10 章)**:IP 校验/路由、TCP 收包(确认、重组、拥塞控制)。延迟来源:syn/accept 队列满(拒连)、TIME_WAIT、重传(MTU 黑洞)、窗口/拥塞退避。
3. **系统调用(第 04 章)**:内核把数据从内核缓冲 copy 到用户态(`recv`/`read`),经 syscall 陷态 + 上下文切换。延迟来源:频繁小 syscall、futex 锁竞争。
4. **应用运行时(Go runtime/调度,第 05 章)**:goroutine 被调度到某个 P/M,可能等 CPU(被 CFS 抢占/节流)或等锁。延迟来源:调度饥饿、GC STW、锁竞争。
5. **你的 handler + 可能的 I/O(第 06/07/08 章)**:handler 内若读文件→page cache 命中(快)或未命中(落盘,经文件系统→块层→磁盘);若访问 DB→又是一轮网络。延迟来源:cache miss、direct reclaim、磁盘排队、下游 RT。
6. **回程**:响应再经 TCP 发送→软中断→网卡→网络。
每一层都是潜在的"暂停点",定位靠"谁先动谁源头"+"分层工具"。
</details>

**思考题 2(深入):** 为什么说"参数会过时,但诊断环不会"?请结合书中至少两个"成本假设反转"的例子说明。

<details>
<summary>【参考答案】</summary>

参数会过时:参数是"在特定硬件/拓扑/负载成本假设下的最优解"。当假设变,最优解变。例:
- `swappiness=0`:当年内存贵、文件读是主角,设 0"保匿名页"合理;今天大内存+容器,设 0 反而 page cache 被挤、direct reclaim 抖(第 12/18 章)——昨天的优化今天变负担。
- `zone_reclaim_mode=1`:当年跨 node 访问极慢,保本地性合理;今天互连带宽充裕,本地回收的卡顿代价 > 偶尔跨 node 慢(第 23 章)——假设反转。
- `tcp_tw_recycle`:当年 NAT 少,激进回收 TIME_WAIT 合理;NAT 普及后它用时间戳 PAWS 把合法包当过期丢,4.12 被删(第 21 章)。
所以"抄今天的参数数值"必然在未来翻车。

诊断环不过时:现象→推断(带可证伪观测)→可能推错→调整→再观察→改进。这套**方法**不依赖任何具体参数值:假设变了,你用同样的"观测→证伪→回头"流程重新推演出新的合适值。结论会旧,方法不旧。这也是第 24 章"铁律一/母题六"的核心。
</details>

**思考题 3(权衡):** "懂微观让你可以动别人不敢动的参数"——但动参数也有风险。请给出你自己的"动生产参数"的安全守则(至少 3 条)。

<details>
<summary>【参考答案】</summary>

安全守则(基于全书):
1. **单变量实验**:一次只改一个参数,改完观察,绝不同时改五个然后不知谁生效(第 24 章母题六)。
2. **先确认负载画像 + 成本假设**:动前问"这个参数赌的假设在我这成立吗"(母题五)。例如设 `swappiness=10` 前确认我是"内存偏紧的 DB/容器",不是通用桌面。
3. **可在运行时临时改,验证后再固化**:先用 `sysctl -w`/`echo` 临时改观察,确认有效且无副作用,再写进 `/etc/sysctl.d/*.conf` 持久化;危险参数(`panic_on_oom`)绝不随手固化。
4. **可回滚 + 有监控**:改前记录原值,准备回滚命令;改后盯对应指标(P99/allocstall/retrans)确认无退化(第 25 章 benchmark 陷阱)。
5. **逃生口不掩盖真凶**:`oom_score_adj`/`overcommit=1` 等只作止血,必须同时查真凶(泄漏/水位顶高),否则把可determinable 问题变 delayed 灾难(第 19 章)。
6. **灰度/低峰操作**:生产参数变更尽量灰度 + 低峰,避免一次性全量翻车。
</details>

**参考答案要点(只给方向,不背,要能讲清机制)**

1. **僵尸占满 pid_max**(或容器 `pids.max`):`ps -eo stat | grep -c Z` + `sysctl kernel.pid_max`,根因父进程不 `wait()` 回收。
2. **cgroup `files.max`(v1)硬墙**:容器里 fd 受 cgroup 限,`ulimit`/`fs.file-max` 只是里面两道;`cat /sys/fs/cgroup/.../files.max`。
3. **MTU 黑洞 / TCP 重传**:`ss -ti` 看 `retrans` + `tracepath` 看 MTU 跳变;ICMP 通 TCP 重传→PMTU 问题。
4. **没泄漏**:`RES` 把共享库重复计,`Pss` 才公道;看 `Pss` 趋势判断泄漏。
5. **RCU 宽限期收不齐**(某 CPU 频繁短暂关抢占/中断,如软中断长循环):查软中断处理时长,非 soft lockup。
6. **脏页触顶前台同步刷**:`grep nr_dirty /proc/vmstat` 看是否到 `dirty_ratio` 线;降 `dirty_ratio`/`dirty_background_ratio`。
7. **cgroup OOM(非节点 OOM)**:`cat .../memory.events` 看 `oom` 计数 + `kubectl describe` 看 `OOMKilled`;说明 limit 太小,节点内存其实够。
8. **`biolatency`(eBPF)** 看延迟分布/长尾,`iostat` 平均掩盖长尾;`biosnoop` 归因到进程。
9. **vm.* 是宿主全局内核参数**,容器共享宿主内核、且多数不在 K8s sysctl 白名单;节点 init 统一设,容器用 cgroup `memory.swappiness`。
10. **SYN 队列(`tcp_max_syn_backlog`)溢出静默丢**:`sysctl net.ipv4.tcp_max_syn_backlog` 调大 + 应用 `listen` backlog 调大。

11. **swappiness=0 在内存紧时宁可回收 page cache 也不 swap → 反而 OOM**;设 1 留兜底。
12. 高=写合并好吞吐高、崩溃丢多;低=前台不卡延迟稳、带宽略降。
13. 收益=消除 khugepaged 卡顿 + GC 缺页尖刺;风险=失去一点 TLB 收益(堆访问分散,收益本就不大)。
14. 5=假死连接快暴露(内网好)、但慢链路可能被过早判死;15=慢链路耐受、但假死撑 30 分钟。
15. `max` 适合不可牺牲的硬限(杀就杀)、`high` 适合软节流(先挤慢不杀);核心保底用 `min`。

16. **节点级**(`/sys/block/<dev>/queue/`),容器改不了/影响整机;cgroup `io.max` 做容器级IO 隔离。
17. **无意义**,zone_reclaim 是宿主 NUMA 级,容器里调不生效且影响别的 node;靠 K8s `topologyManager`。
18. **不是一套**:inotify watch 是独立配额、按 uid 共享、宿主级;`ENOSPC` 误导成磁盘满。
19. `sysctl -p` 只加载 `sysctl.conf`;`--system` 才走 `sysctl.d/` 字母序后覆盖先;改完要验证真实值。
20. **limit 防 pod 自己胀爆,节点 OOM 是物理内存真没了**:超卖时节点 OOM 不care cgroup limit,按全局 `oom_score` 杀。

反向查法（用你自己的事故练手，模板如下）：
- **现象**：写一句话描述（如"订单接口 P99 从 80ms 蹦到 2s，CPU 没满，就几秒"）。
- **该怀疑的参数家族/机制**：从速查卡匹配——"偶发卡顿 CPU 没满"→ 内存回收/THP 规整/soft lockup，或"全链路某跳"→ 九级地图逐级。
- **用的工具**：对应 `perf stat`/`dmesg`/`ss -tni` 等。
- **1 分钟能否定位到层级**：能 = 反射建立；不能 = 缺那层知识，回去翻对应章。

常见"定位不到"的知识缺口：
1. **只会看应用层，不会往内核/网络栈钻**：现象是"接口慢"就只查 pprof/日志，不去 `ss -tni` 看 socket 缓冲区、`sar` 看磁盘——缺第 1 章九级地图的"从外往里"纪律。
2. **把两个独立阀门当成同一个**：如半连接满却调 somaxconn（全连接），脏页卡却调 swappiness（swap vs cache 混淆），vm 参数在容器里调（不隔离）——缺"参数分层"认知（第 12/15/23 章）。
3. **只有平均值没有分位**：说"慢"但拿不出 p99/p999、没有基线对照——缺第 0/24 章"先测量后优化"的纪律。
4. **改一个参数就宣布好了**：没对照实验、没记录代价——缺每章的"迭代环"（现象→推断可能推错→调整→再观察）。

这张卡的真正用法：它不让你"背参数"，而是让你在**混乱的现象里先锚定层级**（是内存？网络？IO？调度？容器？），层级定了，参数和工具自然浮现。绝大多数排障低效，是因为"还没定位层级就动手改"——改了一堆参数，问题在另一层，白忙。所以速查卡第一行永远该是"先问：这现象属于九级地图的哪一级"，而不是直接翻 sysctl。

最后一句收尾：这本书 30 万字，能压缩成"九级地图 + 迭代环 + 一张速查卡"。前两者是思维，速查卡是检索入口。你以后遇上问题，先想"在第几级、用什么工具看、改了拿什么换什么"——这三问能答，参数自然查得到，不需要背。
</details>
