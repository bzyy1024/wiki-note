> 这是全书的终点。前面 17 章，你在"读"协议、在"理解"协议。现在，你要亲手"造"一个——而且要用一份 21 条检查清单来验收它。

## 18.0 任务书

**你**：墨叔，最后一个任务来了。公司要统一微服务间的通信，让我设计一个 **RPC 协议**。

**需求**：
- 服务 A 调用服务 B 的一个方法，B 返回结果
- 要支持**流式**（大结果集分批发回）
- 要在**弱网/高延迟**下表现良好
- 要能**演进**（未来加字段、加特性，不破坏老服务）
- 要有**认证、超时、重试、限流**

**约束**：
- 数据中心内部（低延迟、高带宽、可信网络，但**不是绝对可信**）
- 语言：Go（但不排除未来有别的语言接入）
- 团队：5 个后端，水平参差

**墨叔**：好，这是一道综合题。**但在我让你动手之前，先问你一个"灵魂问题"：**

> **你为什么不用现成的 gRPC（HTTP/2 + Protobuf）？**

**你**：……（沉默）对啊，gRPC 不都满足吗？

**墨叔**：对。**这道毕业设计的第一关，不是"设计协议"，而是"论证你为什么不直接造轮子"。** 如果答不上来，你就应该用 gRPC。

**你**：那我如果要造，得有个理由——比如"gRPC 依赖 HTTP/2 和 Protobuf，对某些受限场景太重"，或者"我们需要极致的性能和完全的控制"？

**墨叔**：对。**"造轮子的正当理由"（第 11 章第 5 题讲过）：要么"现有方案覆盖不到我的场景"，要么"我的差异化优势足够大"。** 我们现在假设：你的场景有特殊约束（比如极致延迟要求、或私有定制），值得造。那么，开始。

## 18.1 第一步：需求分析 → 约束提取

**墨叔**：把需求翻译成"约束"，这是第 16 章学过的"第一步"。

| 需求 | 约束 | 设计影响 |
|---|---|---|
| 服务间调用 | 高频、低延迟 | 报文要小、解析要快 → 二进制 |
| 流式结果 | 大结果分批发 | 要支持"分帧/流" |
| 弱网表现好 | 要可靠 | 序号 + 重传 |
| 可演进 | 要兼容 | 扩展点 + 版本 + 降级 |
| 认证/超时/重试/限流 | 要健壮 | 元数据 + 错误模型 |

**你**：所以我的协议要点：**二进制、流式、可靠、可演进、带元数据。**

---

## 18.2 第二步：关键设计决策（每一步都问"为什么"）

**墨叔**：现在逐个决策，每个都要回答"为什么"。

### 决策一：传输层用什么？

**你**：TCP？还是学 HTTP/3 用 QUIC？

**墨叔**：**TCP**。因为数据中心内部，丢包率极低，TCP 的队头阻塞问题（第 7、13 章）不明显。QUIC 的"用户态、CPU 高、复杂"在这个场景是负资产。**记住：协议选型永远看场景，不是看"谁新"。**

### 决策二：报文骨架（帧）

```
帧头（定长）：
  [0]   Magic（魔数）1字节，固定 0xAB
  [1]   版本号 1字节
  [2]   帧类型 1字节
  [3]   Flags 1字节
  [4-7] 帧长度 4字节（大端）
  [8-15] 请求ID 8字节
负载（变长）：
  元数据（TLV）+ 方法名 + 序列化后的参数/结果
```

**你**：为什么要有 Magic（魔数）？

**墨叔**：**为了快速识别"这是不是我们的协议"**。端口上可能被误连（别的服务连错了端口），魔数让接收方能"一眼判断"——读到 `0xAB` 开头才是我们的协议，否则立即断开。**这是防"误连"的廉价手段**（第 14 章 Sec-WebSocket-Key 的同款思想）。

### 决策三：边界（第 2 章）

**你**：长度前缀。帧头里带"帧长度"，接收方按长度切帧。

**墨叔**：对。而且记住第 2 章的教训：**长度是承诺，不匹配就是错误**（防半包、防粘包）。

### 决策四：错误模型（第 4 章）

```
错误码 2 字节，分类 + 编号：
0x0000 成功
0x01xx 客户端错误（不可重试）：参数错、方法不存在、序列化失败
0x02xx 服务端错误（可重试）：超时、过载、依赖服务挂了
0x03xx 限流（可重试，带 Retry-After）
```

**你**：又是"第一位分类 = 能不能重试"？

**墨叔**：对。**这是全书反复出现的黄金标准。** 你在这里第三次用到了它（第 4 章、第 16 章、这里）。

### 决策五：幂等与重试（第 3 章）

**墨叔**：RPC 的超时重试，最容易出"重复执行"事故（第 3 章）。怎么防？

**你**：请求 ID（帧头里那个 8 字节）+ 服务端去重？

**墨叔**：对。设计：

- 每次调用生成唯一请求 ID。
- 服务端维护"最近处理过的请求 ID 及其结果"（带 TTL，幂等窗口）。
- 重复请求 ID → 直接返回缓存的结果。

**这就是第 3 章 Idempotency-Key 的完整落地。** 你在第 3 章学的三个坑（并发竞态、幂等窗口、失败也要存），这里全都用得上。

### 决策六：超时（第 3、7 章）

**墨叔**：RPC 的超时，有个第 3 章提过的精妙设计——**deadline 随请求传递**。

**你**：deadline 随请求传？而不是"本地设个超时"？

**墨叔**：对。这是关键：

```
客户端设 deadline = 现在 + 500ms，放进帧头（或元数据）
服务端 A 收到，看 deadline，发现自己只剩 300ms 了
A 调用服务 B 时，把"剩下的 300ms"传给 B（而不是 B 也等 500ms）
```

**为什么这很重要**：**如果每一跳都"重新设 500ms 超时"，那么一个 5 跳的调用链，总超时可能累积到 2500ms**——用户早就放弃了。**deadline 随请求传递，保证"全链路的总超时"是受控的。**

**你**：所以 deadline 是"绝对时间戳"，随请求一路传下去？

**墨叔**：对。**这是"超时"和"上下文传递"结合的精妙设计，gRPC 就是这么做的。**

### 决策七：演进机制（第 15 章）

**你**：版本号 + 扩展点（Flags、新帧类型、TLV 元数据），每个都配优雅降级。

**墨叔**：对。核心还是第 15 章那句：**"扩展点的精髓在降级"。** 每个扩展点，都要想清楚"老服务遇到新东西时会怎样"。

## 18.3 完整协议规范（输出）

**墨叔**：把决策汇总成规范：

```
【微服务 RPC 协议 v1 规范】

不变量：
- 帧 = 16 字节定长头 + 变长负载
- Magic 0xAB 固定，版本号在字节 1，字节序大端
- 边界靠帧头 Length

帧头（16 字节，大端）：
  [0] Magic  [1] Version  [2] Type  [3] Flags
  [4-7] Length  [8-15] RequestID

帧类型：0x01 REQUEST / 0x02 RESPONSE / 0x03 STREAM_DATA / 0x04 PING / 0x05 ERROR

错误码：0x0000 成功 / 0x01xx 客户端错（不重试）/ 0x02xx 服务端错（可重试）/ 0x03xx 限流

可靠性：RequestID 去重 + 幂等窗口

超时：deadline 随请求传递（绝对时间戳）

流式：STREAM_DATA 帧 + 流 ID 分片

演进：Version + Flags + 新帧类型 + TLV 元数据，均配降级

安全：可选 TLS；应用层 HMAC 签名（防篡改）

握手：连接建立后交换"能力位图"
```

## 18.5 Go 实现核心编解码（少量代码）

**墨叔**：把核心编解码写出来，锚定理解：

```go
type FrameHeader struct {
    Magic     byte
    Version   byte
    Type      byte
    Flags     byte
    Length    uint32
    RequestID uint64
}

func (h FrameHeader) Marshal() []byte {
    buf := make([]byte, 16)
    buf[0] = h.Magic
    buf[1] = h.Version
    buf[2] = h.Type
    buf[3] = h.Flags
    binary.BigEndian.PutUint32(buf[4:8], h.Length)
    binary.BigEndian.PutUint64(buf[8:16], h.RequestID)
    return buf
}

func UnmarshalHeader(b []byte) (FrameHeader, error) {
    if len(b) < 16 || b[0] != 0xAB {
        return FrameHeader{}, fmt.Errorf("不是本协议的报文")
    }
    return FrameHeader{
        Magic:     b[0],
        Version:   b[1],
        Type:      b[2],
        Flags:     b[3],
        Length:    binary.BigEndian.Uint32(b[4:8]),
        RequestID: binary.BigEndian.Uint64(b[8:16]),
    }, nil
}
```

**你**：这个和第 16 章的编解码器是一脉相承的。

**墨叔**：对。**协议设计的每一个决策，最终都要落到"编解码的每一行代码"上。** 协议是"纸上的约定"，代码是"约定被执行"。

## 参考答案

### 第 1 题答案

**为什么第一步是"论证不直接用 gRPC"**：

因为 gRPC（HTTP/2 + Protobuf）已经是一个**成熟、强大、生态极好**的 RPC 方案。如果你不先论证"为什么它不够用"，就盲目造轮子，等于**用几个月的开发、测试、维护成本，去重新实现一个"还不如现成的"东西**。

**第 11 章第 5 题的结论**：造轮子的正当理由只有两个——

1. **现有方案覆盖不到我的场景**（gRPC 满足不了的硬约束，比如极致的性能要求、私有的安全需求、受限的环境）。
2. **我的差异化优势足够大**（大到能抵消"没有生态、要自己维护"的代价）。

**本题的启示**：**"我会设计协议"和"我应该设计协议"是两回事。** 前者是能力，后者是判断。真正的高手，恰恰是**最克制地造轮子的人**——因为他们知道造轮子的真实账单。

### 第 2 题答案

**deadline 传递 vs 每跳各自超时**：

假设调用链：客户端 → 服务 A → 服务 B → 服务 C，共 3 跳。客户端希望"总耗时不超过 500ms"。

**方案 A（每跳各自设 500ms 超时）**：
- 客户端等 A 最多 500ms。
- A 等 B 最多 500ms。
- B 等 C 最多 500ms。
- **最坏情况：500 × 3 = 1500ms**，客户端早就超时放弃了，但 A/B/C 还在傻等，白白浪费资源。**而且总耗时不可控。**

**方案 B（deadline 随请求传递）**：
- 客户端设 deadline = 现在 + 500ms，放进请求。
- A 收到，发现自己还剩 400ms，调用 B 时把"剩余 400ms"传下去。
- B 收到，发现自己还剩 300ms，调用 C 时传"剩余 300ms"。
- C 在 deadline 前没完成，就**主动放弃并返回超时**。
- **总耗时严格控制在 500ms 内，且每一跳都"知道自己还剩多少时间"。**

**核心价值**：

> **deadline 传递，让"全链路的总超时"成为一个受控的、一致的目标，而不是每跳各自为政的累积。** 它把"时间预算"作为一个"上下文"贯穿整个调用链，避免了"前面超时放弃了、后面还在空转"的资源浪费。

**这也是 gRPC 的核心设计之一**——deadline 是"绝对时间戳"，随请求一路传播。

### 第 3 题答案

**服务发现 + 负载均衡的设计**：

- **服务注册**：服务启动时，向注册中心（如 etcd、Consul、Nacos）注册自己的地址 + 健康状态 + 心跳。
- **服务发现**：调用方从注册中心拉取"目标服务的所有实例列表"，并监听变化。
- **负载均衡**：调用方在实例列表里选一个（轮询、随机、加权、最少连接）。

**关键判断：这些是"协议层"该做的吗？**

**不是！这些是"协议之外"（基础设施层）该做的。**

为什么？回第 1 章"分层"约束：

> **每一层只做自己那一层该做的事。** RPC 协议的职责，是"一次调用怎么编码、怎么传输、怎么返回"。而"调用哪个实例"是**寻址/路由**问题，属于"服务发现"这个独立的层。

如果把"服务发现"塞进 RPC 协议里，会导致：

1. **协议膨胀**：RPC 协议要处理"注册、心跳、路由"这些本不属于它的事。
2. **耦合**：改负载均衡算法，就得改协议，牵一发动全身。

**正确做法（也是现实中的做法）**：**RPC 协议只管"怎么调"，服务发现（注册中心）+ 负载均衡（客户端或 sidecar）是独立的层，通过"标准接口"和 RPC 协作。** gRPC 就是这样的：协议是 HTTP/2 + Protobuf，服务发现靠 DNS/etcd/名字服务，负载均衡靠客户端或 proxy。

**一句话**：**"分层"约束的意义，就是让你知道"什么不该塞进协议里"。** 一个协议设计师的成熟，体现在他**知道边界在哪**——哪些是协议的职责，哪些该交给别的层。

### 第 4 题答案

| 公司内部沟通规范 | RPC 协议 |
|---|---|
| 邮件格式（标题、正文、签名） | 报文格式（帧头、负载） |
| 邮件的"紧急/普通"标记 | 错误分类（可重试/不可重试） |
| 新员工也能看懂邮件 | 协议简单、可理解、易实现 |
| "邮件必须当天回复"的规则 | 超时/deadline 语义 |
| "回复时引用原邮件" | 请求-响应的配对（RequestID） |

**深刻的相似之处**：

1. **格式 = 报文格式**：公司的邮件格式（标题怎么写、正文怎么排）是为了"让收件人快速理解"，协议的报文格式是为了"让接收方快速解析"。**都是"降低理解成本的结构约定"。**

2. **紧急标记 = 错误分类**：邮件标"紧急"让收件人"优先处理"，协议的错误分类（可重试/不可重试）让接收方"决定要不要重试"。**都是"用少量信息，触发正确的处理行为"。**

3. **新员工能看懂 = 简单可理解**：好的沟通规范，新员工一看就懂（降低培训成本）；好的协议，新语言/新实现者一看就能实现（降低采用成本）。**这和第 1 章"简单决定采用率"是同一个道理。**

4. **规则（当天回复）= 语义（超时）**：公司规则"邮件当天回"是"行为预期"，协议的超时是"时间承诺"。**都是"约定行为的时间边界"。**

**升华**：**协议，本质就是"一群机器之间'怎么沟通'的规范"，就像公司规范是"一群人之间'怎么协作'的规范"。** 设计协议和设计制度，用的是同一套底层智慧——**约定格式（降低理解成本）、约定语义（触发正确行为）、约定边界（处理异常）、预留弹性（适应变化）。**

### 第 5 题答案

**1. 是不是矛盾？**

**表面矛盾，本质不矛盾。** 关键在于**分清"两个层面"**：

- **"允许犯错还活下来"（能落地 > 正确）** 讲的是**"协议设计"层面**——协议要足够简单、足够宽容，让"不完美的实现"也能互通，这样才能被广泛采用。
- **"现代协议倾向严格"（Postel 法则反转）** 讲的是**"协议实现"层面**——当一个协议已经成熟、被广泛采用后，实现要"严格"，以消除"实现不一致"这个安全漏洞的根源。

**用一句话调和**：

> **"能落地"要求协议在"设计上"简单宽容（降低门槛）；"要安全"要求协议在"实现上"严格一致（消除漏洞）。两者不矛盾，因为一个是"设计"的事，一个是"实现"的事。**

**2. 分别适合什么场景：**

| | 简单宽容（允许犯错） | 严谨严格 |
|---|---|---|
| 场景 | 普及期、生态期（要快速被采用） | 成熟期、安全关键场景（要消除漏洞） |
| 例子 | 早期 HTTP、HTML | HTTP/2、TLS 1.3、QUIC |
| 目标 | 最大化采用率 | 最大化安全/一致性 |
| 代价 | 制造"事实标准"、实现不一致 | 门槛高、可能抑制普及 |

**3. 作为设计者，如何选择：**

**判断标准**（这是本题的核心）：

> **看你的协议处在"什么阶段"、面临"什么问题"。**

- **如果目标是"被广泛采用"**（新协议、新生态、要拼采用率）→ 倾向"简单宽容"，牺牲一点严谨，换取门槛低、上手快。
- **如果目标是"安全可靠"**（协议已成熟、涉及金融/安全、要长期演进）→ 倾向"严谨严格"，牺牲一点上手便利，换取"实现一致、无漏洞"。

**更深的洞察**：

> **"能落地"和"正确"，从来不是二选一，而是"时序"问题。** 一个协议的生命周期里，**早期靠"宽容"落地，成熟后靠"严格"续命。** 优秀的设计者，知道"什么时候该宽容、什么时候该严格"——而不是死守一个原则。

**最终收束**：这其实回到了全书的起点（第 1 章）和终点（第 15 章）的统一：

> **协议的第一性原理，不是"正确"，是"能落地"。但"能落地"之后，必须走向"正确"，否则会死在"不一致"上。** 先宽容求生存，再严格求长久——**这就是一个协议从"婴儿"到"成熟"的完整人生。**

---

## 一页纸小结

**毕业设计的第一关**：论证"为什么不直接用 gRPC"——造轮子的正当理由，要么"覆盖不到"，要么"差异化够大"。

**关键决策**：传输层 TCP（数据中心丢包低）、帧骨架（16 字节头 + 魔数）、长度前缀边界、错误分类（能不能重试）、RequestID 幂等、deadline 随请求传递、扩展点 + 降级。

**21 条检查清单**：地基/语义/扩展/可靠/安全/工程，六个维度。

**与 gRPC 对比**：自制协议的账单是"没有生态"，多数场景不划算。

**从使用者到设计者**：使用者想"怎么用"，设计者想"为什么这么设计、怎么演进"。

**全书收官的一句话**：协议不是规则，是一代代工程师在约束和事故面前做的一连串权衡。理解了权衡，你就成了设计者。
