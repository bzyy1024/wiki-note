# 第 17 章 Go 视角下的协议实现

> 前面 16 章，你在"协议"这一层思考。现在，我们钻到 `net/http` 里，看看那些你学过的概念——报文解析、隐式决策、连接管理、超时——是怎么被一行行代码"活"出来的。

## 17.0 引子：Go 的 net/http 为什么"偷偷"做事

**你**：墨叔，我有个困惑。写 Go 的时候，总觉得 `net/http` 在"偷偷"帮我做事——我没写状态码，它给我 200；我没写 Content-Length，它自动算；我没管连接，它自己复用。有时候这些"偷偷做的事"反而让我踩坑。

**墨叔**：你的感觉是对的。`net/http` 是"协议的实现"，而**协议实现的一个核心任务，就是"把协议的默认行为做对"**。你第 1 章就见过这个——"十六行代码，十个协议决策，你一个都没显式做，但它们全发生了。"

这一章，我们钻进源码，看看这些"默认行为"是怎么来的，以及怎么不被它坑。

## 17.1 结构映射：net/http 的每个类型，对应协议的什么

**墨叔**：先建立一个"源码 → 协议"的映射，这是理解 net/http 的地图：

| net/http 类型 | 对应协议概念 | 章节 |
|---|---|---|
| `http.Server` | 服务器（监听 + 连接管理 + 解析） | 02、07 |
| `http.Handler` | 请求处理器（你的业务入口） | — |
| `http.Request` | 请求报文（方法、URL、首部、body） | 02、06 |
| `http.ResponseWriter` | 响应报文（状态码、首部、body） | 02、04 |
| `http.Transport` | 客户端连接池 + 重定向 + 超时 | 07 |
| `http.Client` | 客户端的门面 | — |

**你**：所以 `Request` 就是"解析后的请求报文"，`ResponseWriter` 就是"你正在写的响应报文"？

**墨叔**：对。**net/http 的本质，就是"报文的编解码器 + 连接的管理器"。** 它把"字节流"解析成 `Request`（对象），把你写的 `ResponseWriter` 序列化成"字节流"。

## 17.2 请求解析：从连接字节到 Request 对象

**墨叔**：服务器收到一个连接，怎么变成你手上的 `*http.Request`？简化流程：

```
1. 连接被 accept
2. 包装成 bufio.Reader（缓冲读取）
3. readRequest() 读请求：
   a. 读请求行 "GET /path HTTP/1.1"（第 2 章：方法+路径+版本）
   b. 读首部（读到空行 "\r\n" 为止）
   c. 解析 Content-Length / Transfer-Encoding，决定怎么读 body
4. 组装成 *http.Request，交给你的 Handler
```

**你**：第 2 章学的"空行分隔首部"、"CL/chunked 定边界"，在这里就是具体的代码？

**墨叔**：对。`readRequest` 里，**读首部的循环就是"读到空行停"**，**读 body 的逻辑就是"看 CL 还是 chunked"**。你在第 2 章学的那套理论，在源码里就是几十行的实现。

**关键点**：`bufio.Reader` 的存在，说明了**为什么"缓冲"对协议解析这么重要**——你不可能一个字节一个字节地读（太慢），而是"攒一批字节再解析"。**这就是"缓冲"和"流式解析"的关系。**

## 17.3 ResponseWriter 的隐式决策：这是坑最多的地方

**墨叔**：现在讲 ResponseWriter，这是 net/http 里"隐式决策"最多、坑最多的地方。

### 隐式决策一：自动 WriteHeader(200)

第 4 章讲过：你一旦 `Write`，net/http 就**隐式**调用 `WriteHeader(200)`。之后你再 `WriteHeader(500)` 就无效了。

```go
w.Write([]byte("oops"))         // 隐式 WriteHeader(200)
w.WriteHeader(500)              // 无效！已经写了 200
```

**你**：这个我记得。根因是"响应行在 body 前面，body 一写出去，状态码就冻结了"。

### 隐式决策二：自动设置 Content-Length 或 chunked

第 2 章讲过：net/http 会根据"写之前是否知道总长度"自动决定用 CL 还是 chunked：

- 内容小、一次性写完 → 自动算 Content-Length。
- 内容大、或 Flush 了 → 自动切 chunked。

**关键**：**这个"自动"是 net/http 在替你实现第 2 章的"边界"决策。** 你了解了边界原理，就理解了为什么它这么干。

### 隐式决策三：Content-Type 嗅探（sniff）

**你**：还有 `Content-Type` 嗅探？

**墨叔**：对。如果你**没有显式设置** `Content-Type`，net/http 会**嗅探 body 的前几个字节**，猜它是什么类型：

```go
w.Write([]byte("<html>..."))   // 没设 Content-Type
// 响应里会自动变成：Content-Type: text/html; charset=utf-8
```

**你**：它是怎么猜的？

**墨叔**：它读 body 前 512 字节，匹配一个"魔数表"（比如 `<html` 开头 → text/html，`PK` 开头 → zip）。这个机制叫 `DetectContentType`。

**坑**：**嗅探可能猜错，而且和"安全"有冲突**（浏览器也会嗅探，导致"浏览器把 JSON 当成 HTML 执行"的 XSS 风险）。所以**涉及安全的地方，一定要显式设 Content-Type**，别让它嗅探。

## 17.4 超时四层：为什么 ResponseHeaderTimeout 最容易被忽略

**墨叔**：第 7 章讲过连接管理的五个超时。这里再强调一个 Go 特有的、最容易被忽略的——`ResponseHeaderTimeout`。

```go
Transport: &http.Transport{
    DialContext:           ... // 建 TCP 连接超时
    TLSHandshakeTimeout:   ... // TLS 握手超时
    ResponseHeaderTimeout: ... // 等响应头的超时 ← 最容易被忽略
    IdleConnTimeout:       ... // 空闲连接超时
}
```

**你**：为什么它最容易被忽略？

**墨叔**：因为它防的是一个"看起来不着急"的问题——**"对方接受了请求，但迟迟不返回响应头"**。

- 不设 `ResponseHeaderTimeout`：对方把你的连接**占住但不响应**，你的请求就一直等，**连接池被慢慢耗尽**（这和第 7 章"半死不活的请求耗尽连接池"是同一个问题）。
- 设了它：等响应头超过时限，就报错、释放连接。

**你**：所以这又是一个"慢速攻击"的防御？

**墨叔**：对。**"接受但不响应"是经典的 Slowloris 慢速攻击手法**——用最少的资源拖死你的服务器/客户端。`ResponseHeaderTimeout` 就是客户端侧的防御。

## 17.5 连接管理：Transport 参数的调优心法

**墨叔**：第 7 章讲过连接池。这里给一个"调优心法"，把参数串起来理解：

```go
Transport: &http.Transport{
    MaxIdleConns:        100,  // 全局池子多大
    MaxIdleConnsPerHost: 50,   // 每个 Host 留多少空闲连接（默认 2，太小！）
    MaxConnsPerHost:     0,    // 每个 Host 最多多少连接（0=不限）
    IdleConnTimeout:     30 * time.Second,  // 空闲多久关闭（要比 LB 短）
}
```

**心法**：

1. **`MaxIdleConnsPerHost` 要匹配你的"峰值并发"**——太小，池子不够用，频繁新建连接（第 7 章的性能坑）。
2. **`IdleConnTimeout` 要比中间设备的空闲超时短**——防"幽灵连接"（第 7 章）。
3. **`MaxConnsPerHost` 是"背压"工具**——如果下游扛不住，限制并发连接数，防止把下游打挂。

**你**：所以这三个参数，本质是"连接复用"、"防幽灵连接"、"背压"三件事？

**墨叔**：对。**理解了第 7 章的连接管理原理，这三个参数就不是"要背的数字"，而是"原理的自然映射"。**

## 17.6 中间件模式：协议层的三个坑

**墨叔**：Go 的中间件模式（`func(http.Handler) http.Handler`）很优雅，但在协议层有三个坑：

### 坑一：提前 WriteHeader

```go
func auth(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if r.Header.Get("Authorization") == "" {
            http.Error(w, "未认证", 401)  // 这里已经 WriteHeader(401)
            return
        }
        next.ServeHTTP(w, r)  // 后面的 handler 想再写 500 ？无效了
    })
}
```

**你**：所以中间件一旦写了状态码，后面的就改不了了？

**墨叔**：对。这是"响应是流式的、状态码只能写一次"的必然结果。**中间件的职责边界要想清楚：谁负责"定状态码"，谁负责"写 body"。**

### 坑二：读了 body 没还回去

```go
func logBody(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        data, _ := io.ReadAll(r.Body)  // 把 body 读光了
        // 忘了把 data 塞回 r.Body
        next.ServeHTTP(w, r)  // 后面的 handler 读到的是空 body！
    })
}
```

**你**：所以要读 body 做日志，就得"读出来再塞回去"？

**墨叔**：对。标准做法是：

```go
data, _ := io.ReadAll(r.Body)
r.Body.Close()
r.Body = io.NopCloser(bytes.NewReader(data))  // 还回去
next.ServeHTTP(w, r)
```

### 坑三：goroutine 泄漏（Handler 里起 goroutine 不等待）

**墨叔**：这个和第 7 章"连接泄漏"是不同的问题，但同样致命：

```go
func handler(w http.ResponseWriter, r *http.Request) {
    go func() {
        // 异步处理，但没等它结束就返回了
        saveToDB(r)  // r 是 handler 的参数，handler 返回后 r 可能被复用/释放
    }()
    w.WriteHeader(200)  // 立刻返回
}
```

**你**：这是经典的"handler 里起 goroutine 不等待"的坑？

**墨叔**：对。**Request 对象在 handler 返回后可能被 net/http 复用（sync.Pool）**，你在 goroutine 里继续用它，会读到脏数据。所以**要异步，就先把需要的数据拷出来，再起 goroutine**。

## 17.7 自己写一个解析器：三个关键决策点

**墨叔**：最后，讲一下"如果让你自己写一个 HTTP 解析器"，三个关键决策点。这能检验你是不是真的理解了协议。

### 决策点一：状态机 vs 手写循环

**你**：解析 HTTP 报文，用状态机还是手写循环？

**墨叔**：**请求行、首部的解析，用状态机**（清晰、可扩展）；**body 的读取，用"看 CL/chunked"的分支**。net/http 其实就是这么干的（`readRequest` 里是一个状态机式的读取）。

### 决策点二：缓冲边界

**墨叔**：读首部时，`bufio.Reader` 的缓冲是有限的。**如果首部特别大（超过缓冲）怎么办？**

**你**：要能"边读边扩展"，或者限制最大首部大小？

**墨叔**：对。net/http 的做法是**限制最大首部大小**（默认 1MB，`MaxHeaderBytes`），超了就报错。**这是防"超大首部"攻击（内存耗尽）的关键。**

### 决策点三：慢速攻击防护

**墨叔**：第 17.4 节提到 Slowloris。自己写服务器时，要防"客户端极慢地发送报文"：

- 设置**读超时**（`ReadTimeout`）——如果客户端 N 秒内没发完一个请求，就断开。
- 限制**并发连接数**——防止攻击者开一堆慢连接占满你的资源。

**你**：所以"写一个能用的 HTTP 服务器"和"写一个能扛住攻击的 HTTP 服务器"，是完全不同的事？

**墨叔**：对。**能用 = 正确解析；扛得住 = 处理异常、防攻击、控资源。** 后者才是协议实现真正的难度所在——**协议的第 4 要素（异常处理），才是实现者的分水岭**（第 1 章）。

## 参考答案

### 第 1 题答案

| 隐式决策 | 对应协议机制 |
|---|---|
| 自动 `WriteHeader(200)` | 响应行（状态码）在 body 前面，body 一写，状态码冻结（第 4 章） |
| 自动 Content-Length 或 chunked | 报文边界（第 2 章）：写前知道长度用 CL，否则用 chunked |
| 自动 Content-Type 嗅探 | 报文元数据（第 2 章）：读前 512 字节魔数判断类型 |
| 自动添加 Date 头 | 缓存基础（第 8 章） |
| 自动管理连接复用 | 连接管理（第 7 章） |

**核心**：**这些"隐式决策"，都是 net/http 在替你实现协议的"默认行为"。** 它们的存在，是为了"让你少写代码、少犯错"。但代价是——**你可能不知道它们发生了，从而踩坑**（比如自动 200 导致状态码无效）。

### 第 2 题答案

**核心**：HTTP 响应是**流式**的，body 可能没读完；而连接是"字节流"的复用载体。

具体：如果你不读 body 就 Close，意味着"响应 body 还有残留字节没消费"。如果 net/http 把这个连接放回池子复用，**下一个请求会读到上一个响应残留的字节**——数据串了。

所以 net/http 的策略是：**没读干净 body 的连接，直接关闭，不放回池子**。用"重建连接"的代价，换"数据不错乱"的安全。

**正确姿势**：`defer resp.Body.Close()` + `io.Copy(io.Discard, resp.Body)`，读干净才能复用。

**深层**：这是"性能和正确性"的权衡——net/http 选择"读不干净就关连接"，本质是"在错了会死人（数据错乱）的地方，宁牺牲性能（多握手）也要正确"。

### 第 3 题答案

| 措施 | 防什么 | 对应要素 |
|---|---|---|
| ReadTimeout（读超时） | 客户端极慢地发请求（Slowloris）——占着连接不发完 | 异常处理 |
| 限制并发连接数 | 攻击者开一堆慢连接，占满服务器资源 | 异常处理 |
| 限制请求头/body 大小 | 超大报文导致内存耗尽 | 异常处理 + 语法 |

**详细设计**：

1. **ReadTimeout**：`http.Server{ReadTimeout: 10 * time.Second}`——如果客户端 10 秒内没发完一个完整请求，服务器就断开这个连接。防的是 Slowloris（慢速攻击）：攻击者开一堆连接，每个连接以极慢速度发请求（比如 1 分钟发一个字节），占满服务器的连接数和内存。

2. **限制并发连接**：可以用一个信号量（channel）限制同时处理的请求数，超了就排队或拒绝。防的是"连接耗尽"——服务器能同时处理的连接是有限的（文件描述符、内存），攻击者开一堆连接就能耗尽它。

3. **限制大小**：`http.Server{MaxHeaderBytes: 1 << 20}`（1MB 首部），以及用 `http.MaxBytesReader` 限制 body 大小。防的是"内存耗尽攻击"——一个超大报文就能撑爆服务器内存。

**对应"四要素"**：这三个措施，**全部对应第 1 章说的"异常"要素**。

> **协议的"异常处理"不是"事后补救"，而是"实现者在设计服务器时，就要考虑的防御"。** 能用 = 正确处理正常报文；扛得住 = 正确处理恶意/异常报文。后者才是协议实现真正的难点。

### 第 4 题答案

**net/http 的"隐式决策"，像"贴心的助手"**：

你只说"把这个寄出去"，助手就自动帮你：
- 装信封（自动封装报文）
- 称重（自动 Content-Length）
- 贴邮票（自动加必要的头）
- 选快递（自动管理连接）

**好处**：
- **降低门槛**：你不懂"怎么寄"也能寄出去（不用懂协议细节也能写 Web 服务）。
- **减少错误**：助手按"标准流程"来做，比你手动做更不容易出错（net/http 的默认行为是"协议的正确默认值"）。

**坏处（"贴心"变"帮倒忙"）**：
- **你失去控制**：助手"自作主张"（比如自动嗅探 Content-Type），可能猜错，而你不知道。
- **默认值可能不是你要的**：助手默认"平信"（自动 200），但你可能要"挂号"（要 201）；助手默认"称重后寄"（自动 CL），但你要"边装边寄"（chunked）。

**什么时候"贴心"变"帮倒忙"**：**当你需要"精确控制"，而助手"按默认值行事"时。** 所以高手的做法是：**平时享受助手的贴心（少写代码），但在关键决策点（状态码、Content-Type、超时、连接），要"接管"——显式地自己指定，而不是让助手猜。**

**升华**：这和第 5 题"抽象该做什么决策"是同一个问题。**"贴心助手"的本质是"好的默认值"——它把"最常用、最不容易错"的决策做对了，但你必须知道"哪些决策它可以替我做、哪些我必须自己做"。**

### 第 5 题答案

**1. "框架替你做决策"的好处**：

- **降低门槛**：你不懂协议细节，也能写出"能用"的 Web 服务（自动 200、自动 CL、自动连接复用）。
- **减少错误**：框架的默认值是"协议的正确默认值"，比你手动做更不容易出错。
- **一致性**：所有人都用同一套默认，行为一致，减少"各自为政"的混乱。

**2. "框架替你做决策"的坏处**：

- **失去控制**：默认值可能不是你要的（自动 200 vs 你要 201；自动嗅探 vs 你要显式指定）。
- **隐式 = 不知道**：你不知道它做了什么，就可能在"关键处"被它坑（自动 200 导致状态码无效）。
- **抽象泄漏**：当你需要"精确控制"（比如自定义连接池、自定义超时）时，发现框架的"贴心"成了"障碍"。

**3. 好的抽象该做什么决策、留什么决策：**

**判断标准**（这是本题的核心）：

> **框架应该替你做"协议的正确默认值"（那些"最常用、最不容易错、且错了后果不严重"的决策），把"影响正确性、安全性、性能"的关键决策留给你。**

具体：

- **替你做**：报文边界（CL/chunked）、连接复用、必要的默认头（Date）——这些"大多数人不在乎、但必须做对"的事。
- **留给你**：状态码（语义攸关，不能替你猜）、Content-Type（涉及安全）、超时（涉及资源）、缓存策略（涉及业务）——这些"错了会死人、且只有你知道该怎么做"的事。

**最深一层**：

> **好抽象的本质，是"正确的默认值 + 明确的逃生舱"。** 默认值让你"不操心也能对"，逃生舱让你"需要时能精确控制"。而"坏抽象"是"错误的默认值 + 没有逃生舱"（要么坑你，要么锁死你）。

**这和第 1 章"约束之间互相打架"、第 9 章"复杂度放哪层"是同一个方法论**：**框架设计，本质也是在"省心"和"可控"之间找平衡。** net/http 的答案——**把"正确但不关键的"决策藏起来（隐式），把"关键且只有你知道的"决策暴露出来（显式）——就是它的平衡点。**

## 一页纸小结

**net/http 的本质**：报文的编解码器 + 连接的管理器。

**结构映射**：Request = 解析后的请求报文；ResponseWriter = 你正在写的响应报文；Transport = 连接池。

**隐式决策**（坑最多）：自动 WriteHeader(200)、自动 CL/chunked、自动 Content-Type 嗅探。**它们是"协议默认行为"的实现，但你要知道它们发生了。**

**超时四层**：DialContext / TLSHandshake / ResponseHeaderTimeout（最易忽略，防慢速攻击）/ IdleConnTimeout。

**中间件三坑**：提前 WriteHeader、读 body 不还、goroutine 不等待（Request 被复用）。

**自己写解析器三决策**：状态机、缓冲边界（限 MaxHeaderBytes）、慢速攻击防护。

**核心**：能用 = 正确解析；扛得住 = 处理异常。**协议的第 4 要素（异常），才是实现者的分水岭。**
