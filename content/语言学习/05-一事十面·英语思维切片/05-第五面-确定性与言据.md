# 第 5 面：确定性与言据

> 同一句话，你说的到底是「我亲眼看见的事实」，还是「别人嚼给我听的舌根」，还是「我拍脑门推出来的」？中文往往只差一两个词，英文却在动词的骨头上刻了记号。

## 开场：一个让你卡住的问题

先来一句中文，你试着翻成英文：

> 「**据说是 Lin 搞的事故。**」
> 「**是 Lin 搞的事故。**」

两句摆在一起，中文只差「据说」两个字。信息来源和确定性天差地别：第一句你根本不知道是谁说的、靠不靠谱；第二句是你拍板认账，这话你兜底。可中文就这么轻飘飘地用副词挂在外面，没动句子一根骨头。

现在换成英文。你大概率会脱口而出这一句——

```
*It is said that Lin caused the outage.
```

旁边再配一句平铺的：

```
Lin caused the outage.
```

（先别急着说「不就是加了个据说嘛，能有多大区别」。把这两句在心里各读一遍，想三秒：如果你是对外发公告的人，哪句你敢写进邮件？）

我先把那句带星号的搁这儿替你认了——八成你会写出 `It is said that Lin caused the outage.` 这种句子，然后心里的翻译是「lin caused the outage，哦顺便加个据说显得我没那么肯定」。**这答案语法没错，但只答对了一层皮。**

星号在这里不是「语法错」，是「你不过脑子会给出的那版」：你把 `it is said that` 当成「据说」这个副词的同义替换，等于在英文里也走中文的老路——把它当装饰。可英文没让它当装饰。它一进句子，就把「**这话不是我说的，是别人传的**」焊进了谓语结构本身。它改变的不是礼貌程度，是**这句话的责任归属和可信度来源**。

你可能会杠一句：「中文不也有『据说』吗？凭什么说英文特殊？」问得好，这正是要戳破的错觉。中文确实有「据说 / 听说 / 看来 / 应该」，但它们是**可选的副词装饰**——你加不加、加哪个，全凭你自觉，句子主干一个字不变。英文的 `it is said that` 不是副词，它是把「这话不是我说的」做成了一个**构式**（从句 + 被动引导词），你用了它，整句的信息来源就被语法强制改写为「第三方」。换句话说：中文让你「记得就加、忘了就裸奔」；英文逼你「要么明示来源，要么默认来源就是你」。这正是全书反复念的那句老经——**中文词汇化、英文形态化**——在态度族的第一站。你现在只要记住：同样两个汉字之差（「据说」vs 无），在英文里是两套不同的语法站位，不是同一个句子的两种润色。

先把这两句搁这儿，等你读完本章，会在最后一节回来亲手拆解它们各自填了哪两个字段。到那时你会笑着说：原来那颗星号，标的是「没过脑子」而已。

等你看完这一章回头，会明白这两句的差异不是一个副词，是两个不同的「说话人站位」（speaker stance）。这一面，我们就拆这个站位。

## 1. 言据性（evidentiality）：你是怎么知道这件事的？

先抛个卡点，判断题型：

> 下面三句话，英文里「确定性」是一样的吗？
> a. 警察报告写：Lin 执行了那条迁移。
> b. 我朋友圈有人八卦：Lin 搞的。
> c. 我看了一眼监控日志，推断：八成是 Lin 干的。

你先在心里答：这三句中文，是不是都「在说 Lin 干了这事」？是。那英文里它们该用一个句型还是三个？

（心里答一遍，最好出声。答不上来也算一种答案——很多人到这儿会卡，因为中文确实就用一套句型对付了。）

揭晓之前先说核心洞见：**语言不光在说「事」，还在说「我对这事的确信程度和信息来源」。**

语言学管这叫 **言据性（evidentiality）**。它是态度族的第一根支柱——你这一面、第 7 面（名词化旋钮）、第 8 面（数与限定）、第 9 面（语域与态度）都属于态度族，处理的都是「说话人怎么站位」。而「站位的地基」就是两个问题：

1. **你有多确定？**（确定性 / 确信度，certainty）
2. **你这消息从哪来的？**（信息来源，source）

信息来源粗略分三型：

- **直接证据（direct）**：我亲眼看见、亲耳听见、亲手干的。来源 = 我自己。
- **传闻 / 引述（reported / hearsay）**：别人说的、报告写的、新闻播的。来源 = 第三方。
- **推测（inferred）**：我没看见，但我从证据推出来的。来源 = 我的推理。

回到母案例 The Outage。同样是「Lin 锁了表」这个命题，三种来源说出来完全不是一回事：

```
a. I ran the migration and locked the orders table.        (直接：Lin 自述)
b. According to the postmortem, Lin locked the orders table.(引述：复盘报告说的)
c. The logs suggest Lin locked the orders table.            (推测：从日志推断)
```

这里有个细节值得停一下：三句的中文翻译「Lin 锁了订单表」几乎一字不差，但英文在动词前后的「周边装置」上花了完全不同的功夫。a 用第一人称 `I` 当主语，直接声明来源 = 我自己；b 用 `according to the postmortem` 这个介词短语把来源焊成「复盘报告」，Lin 仍是主语但责任被推到报告；c 用 `suggest` 这个动词把命题降级成「日志暗示的」，来源 = 我的推理。你看，**中文只动了一个副词的位置（「我 / 据报告 / 日志表明」），英文动的是整个句子的谓语组织和主语选择**——这又是镜头族（第 3 面语态、第 4 面焦点）和态度族的交叉：来源标记往往顺便把镜头从「人」挪到「证据」或「报告」。对工程师读者这特别好懂：就像你打日志时选 `level=INFO` 还是 `level=WARN` 还顺手选了 `logger=auth` 还是 `logger=db`——英文的言据标记就是同时定了 level 和 logger。

三句中文都能翻成「Lin 锁了订单表」，但英文把来源焊进了句子：

- a 是主动自述，来源 = 说话人自己，确定性最高，责任也最明确。
- b 用 `according to the postmortem` 把来源甩给复盘报告——**这话不是我编的，是报告写的**，说话人躲在报告后面。
- c 用 `suggest` 把来源标成「推测」——我看了日志推的，不是我亲眼盯着的。

**关键反差**：中文靠「据/看来/应该/据说/按说」这些副词挂在外面；英文把这些来源和确定性焊进动词形态或特定构式。这又是全书的老主题——

> 中文是 **词汇化** 的语言：确定性、来源都挂在动词外面当副词；
> 英文是 **形态化** 的语言：语气、情态、言据被焊进动词的骨头里。

类比，计算机那套你熟。把每句话想成一条日志（log line），英文里每条日志都带两个字段：

```
{
  "message":  "Lin locked the orders table",
  "source":   "direct | reported | inferred",   // 信息来源
  "confidence": 0.99 | 0.6 | 0.3                 // 确定性
}
```

具体落一下地。同一句「Lin 锁了表」，在英文里三种写法对应三条不同的「日志」：

```
// 直接证据：Lin 自述
{ "message": "I locked the orders table",
  "source": "direct", "confidence": 0.99 }

// 引述：复盘报告说的
{ "message": "Lin locked the orders table",
  "source": "reported(postmortem)", "confidence": 0.9 }

// 推测：从日志推断
{ "message": "Lin locked the orders table",
  "source": "inferred(logs)", "confidence": 0.8 }
```

中文呢？三句话可以都是「Lin 锁了订单表」，你顶多加「我 / 据报告 / 看日志推」几个字——而且**不加也没人罚你**。英文不让你不加：`source` 和 `confidence` 是必填字段，你不显式声明，系统就给你默认值 `source=说话人`、`confidence=高`。所以中文母语者写英文最容易出的 bug 就是「忘了填这两个字段，系统给你兜底成裸断言」——你本想说「可能」，英文默认你「肯定」。这就是为什么你老觉得英文「太绝对」，其实是你没手动把 `confidence` 调低。

中文的写法是：message 写清楚，source 和 confidence 用额外一行注释补（`「据说」「看来」`），而且**不强制**——你不写也没人拦你。英文的写法是：source 和 confidence 是 **必填字段**，你不填就编译不过，语言逼你把这两个值焊进句子形态。

这就是为什么你读英文新闻总觉得「绕」——人家不是啰嗦，是依法在每条 claim 上打 `source` 和 `confidence` 标签。你之前嫌它烦，是因为你脑子里没有这两个字段的意识。

回到卡点：警察报告、朋友圈八卦、工程师推理，三句话确定性天差地别。英文分别会用引述标记、传闻标记、推测情态去装这三个不同的 `source` 值。中文？三句全可以是「Lin 搞的」加个随意的「听说/我看/据说」。

生活类比：你家装了监控。警察来问，你说「监控拍到了，就是他」——这是直接证据。邻居跟你唠「听说那小子手脚不干净」——这是传闻。你回家看地砖有水渍，推「八成是他家水管漏了」——这是推测。三件事你跟老婆说的语气、用的词、敢不敢打包票，能一样吗？英文把这种「证据等级的自觉」直接做成语法。

再往深里说一层，为什么这件事值得你认真。你写英文最容易出的毛病，不是语法错，是**站位模糊**。比如你给老板发「The system is down because of the migration」，这句话在英文读者耳朵里是「我认定就是迁移搞的，我兜底」。你心里其实想的是「我猜的，还没查实」，可你没加 `may` / `according to`，英文就默认 `source=你`、`confidence=高`。老板拿这句去跟客户扛，你坑的不是别人是自己。反过来，你中文写「系统宕了，可能是迁移」，谁都懂你在猜——因为中文「可能」这个副词你天然会加。英文里这个「可能」不是可选项，是必填的状态位。

所以这一面你真正要练的，不是背情态动词表，而是**每说一句带 claim 的英文，先在脑子里填两个字段**：`source` 填谁、`confidence` 填多高。填完再选词。这套肌肉记忆练出来，你写英文邮件、看英文新闻，会突然「通」——原来人家绕来绕去，都是在调这两个旋钮。

还有个反直觉的点：确定性高 ≠ 好，确定性低 ≠ 弱。对内核复盘，你要 `confidence=0.99` 的断言才能改 bug；对客户公告，你要 `confidence=0.6` 的 `may have` 才不给自己埋雷。档位选错，不是「说得不准」，是「站错了位、担错了责」。这一面通篇就在讲：同样的事故，换档位就是换站位。

回到开场那个卡点的回扣：你刚才写的 `*It is said that Lin caused the outage.` 语法没错，但如果你以为它只是「加了个据说显得客气」，你就没看见它的真身——它是把 `source` 从「你」改成「别人」的语法操作。星号只是提醒你：这答案是不过脑子那版。现在你该明白了，它和 `Lin caused the outage.` 的差，是**责任归属**的差，不是礼貌的差。

## 2. 情态动词的确定性谱系

上节把「来源」拆了。这一节拆「确定性」——也就是那条 log 的 `confidence` 字段。先来个二选一卡点：

```
a. The lock must have come from the migration.
b. The migration may have triggered the lock.
```

中文都翻成「迁移导致了锁」。差别在哪？先想三秒，再往下。

（你大概率会说：a 肯定一点，b 不确定一点。对，但只答对了一半——你没答出「must 在这里根本不是必须」这个坑。）

英文用 **情态动词（modal verb）** 给命题贴确定性标签。从高确信到弱可能，是一条谱系：

```
must   > will  > would / should > can > may / might > could
(几乎肯定) (强预期) (合理预期)      (能力/可能) (弱可能)    (更弱)
```

母案例里，Lin 凌晨 2:31 盯着监控，能看到锁的痕迹，但看不到「谁按的回车」的全过程。他心里其实在跑两个不同确信度的判断：

```
a. The lock must have come from the migration.   // 看日志推断，高确信：锁只能是迁移来的
b. The migration may have triggered it.          // 不敢打包票：也许是迁移触发的，也许不是
c. It might just be a network blip.              // 弱可能：甩锅前的搪塞，万一是网络抖了呢
```

三句对应 `confidence` 从高到低：a 是 0.9+，b 是 0.5，c 是 0.2。注意 c 那句——「might just be a network blip（没准只是网络抽风）」——是工程师在还没定位时最爱用的托词句式，把确定性压到最低，给自己留退路。

**本章最容易翻车的点，单独拎出来说**：`must` 在这里不是「必须」，是「肯定 / 几乎一定」。

卡点，判断对错型：

```
*You must be tired.  =  「你必须累。」
```

顺不顺？顺。对不对？**错**。这里的 `must` 是「你肯定累了」（看你现在这德行推断的），不是「你必须累」（没人能命令你累）。中国学生十个有九个第一反应是「必须」。

为什么 `must` 一身二职？因为它本来就是「强断定」的模态：表「义务」时是对「该做之事」的强断定（你必须做），表「推测」时是对「事实」的强断定（这肯定是的）。二者共享「高确信」这个内核，只是断定的对象一个是规范、一个是事实。英文用同一个词包了，中文用「必须 / 肯定」拆开——又是词汇化 vs 形态化。

卫星案例，运动领域，给 `must` 的推断用法配个反差：

> 马拉松跑崩。2025 年北京马拉松，跑者老周 30 公里后小腿抽筋退赛。他老婆在终点等，看时钟过了，想：
> ```
> a. He must have hit the wall.        // 推断：他肯定撞墙了（跑崩的典型）
> b. He should be fine by now.         // 合理预期：这会儿该缓过来了
> ```
> 中文都像「他出事了 / 他该没事了」。但 a 是 `must` 高确信推断（从「过终点时间远超预期」反推撞墙），b 是 `should` 的合理预期（按经验该恢复了）。换 `may` 就成「他可能撞墙了」——老婆可不会这么含糊，她是基于多年观察的高确信推断。

再来个技术卫星案例（本章技术卫星案例之一），给 `may have` 的弱推测配母案例同构：

> 误删生产数据。2026 年 3 月，某团队脚本 bug 把一张配置表清空。值班工程师看监控，先说：
> ```
> a. The data must have been deleted by the script.   // 高确信推断：日志指向脚本
> b. A backup may have caught it.                     // 弱推测：备份也许兜住了，不敢定
> ```
> 注意 a 还顺手用了被动（详见第 3 面）——既推断来源，又把施事（脚本）当镜头。b 用 `may` 把「备份兜住」压成弱可能，因为他还没真去查备份。

类比钉一下：`must / may / might` 就像 API 返回的 `confidence` 字段取值。`must`=0.95，`may`=0.5，`might`=0.1。你调接口时不会把所有结果都标 0.95 就发出去——那叫吹牛。英文情态动词就是你给每个命题打的 `confidence`，打分要诚实。

再补一个中国学生最容易踩的坑，关于 `must` 的时态。`must` 表推测时，**没有「过去式」的独立词形**，要表达「过去肯定」得用 `must have + 过去分词`。卡点来了，判断对错型：

```
*He must be at home yesterday.   =  「他昨天肯定在家。」
```

顺吗？挺顺。错吗？**错**。`must be` 是现在推测，配不上 `yesterday`。正确是 `He must have been at home yesterday.`（用 `must have been` 把推测锚到过去）。这和你们在第 1、2 面学的时体是同一套逻辑——`must` 本身不 carry 时间，时间得靠后面的动词形态（`have been`）补。很多教材把 `must have done` 单列为「对过去的推测」，其实它只是 `must`（高确信推断）+ 完成时（锚到过去参照点），两个维度正交叠加，没有新语法。

反过来 `may / might / could` 表推测同理：`may have done` 是「过去可能做了」，不是「可以去做」。你读英文技术帖看到 `This could have been avoided`（这本来是可以避免的），那是 `could` 的推测 / 虚拟混合用法，指向「过去本可避免却没避免」——这已经踩到第 6 面「非真实」的边了，这里先记一句：情态动词 + 完成体，往往把推测的镜头拉向过去，甚至拉向「没发生的假设」。

卫星案例，日常生活，把 `should` 的合理预期讲透：

> 热水器坏了。2026 年 1 月，读者你家热水器半夜漏水泡了地板。你早上发现，跟物业说：
> ```
> a. The valve should have shut off by itself.    // 合理预期：阀门本该自动关的
> b. The valve must have failed.                  // 高确信推断：阀门肯定坏了
> ```
> a 用 `should have` 表达「按设计它该关，结果没关」的合理预期落差；b 用 `must have` 从「没关 + 漏水」反推阀门坏了。两句确定性不同：a 是「设计预期落空」的困惑，b 是「已定位根因」的断定。注意 `should have` 在这里不是「应该去关」（义务），是「本该（却没）」的预期——又是一个 `should` 跨确定性和语气两族的例子，和第 6 面呼应。

把谱系再压实一遍：`must`（肯定）> `will`（必将）> `would/should`（该会）> `can`（能/有时会）> `may/might`（可能）> `could`（或许）。你调 `confidence` 时，记住这条链就是刻度尺，不是一堆孤立单词。中文没有这把尺子焊在动词上，只能用「肯定/应该/可能/没准」近似——近似就意味着你每次都得重新掂量，而英文逼你一次选死。

## 3. 传闻标记（reported evidentiality）

上节是「我有多确定」。这节是「这话谁说的」——专门说来源 = 第三方的那一型，叫 **传闻言据（reported evidentiality）**。卡点，二选一型：

```
a. According to the postmortem, the root cause was a missing process.
b. Reportedly, the root cause was a missing process.
```

中文都翻「根因是流程缺失」。差别在哪？先想三秒。

（八成你会说「差不多，都是听来的」。对一半——`according to` 点名了信源，`reportedly` 没点名，这是责任归属的粗细差别。）

传闻标记家族主要的就这几个：

- `It is said that ...` —— 据说（最口语的传闻）
- `reportedly` —— 据报道 / 据悉（媒体最爱，常做插入语）
- `according to ...` —— 根据……（**点名**信源，最负责任）
- `sources say` —— 消息人士称（新闻腔，信源更模糊）
- `allegedly` —— 据称 / 涉嫌（法律和八卦交界，专门用来撇清「我没定罪」）

母案例里，写复盘报告的人不会写「Lin 搞砸了」这种断言，他会写：

```
According to the postmortem, the root cause was a missing process.
```

「根据复盘报告，根因是流程缺失」——这句话把责任源头钉死在**报告**上，不是说话人自己拍板的。如果报告写错了，锅是报告的，不是写这句话的人。这就是传闻标记的第一个本性：**它是免责声明**。

卫星案例，公共领域，明星塌房——`allegedly` 的经典现场：

> 明星塌房。2026 年 8 月，某顶流被曝税务问题。媒体写法：
> ```
> a. The star allegedly evaded taxes.            // 据称涉嫌逃税（没定性）
> b. The star evaded taxes.                      // 断言：他逃税了（定罪语气）
> ```
> 中文都像「他逃税了 / 他涉嫌逃税」。但 a 用 `allegedly` 把来源标成「传闻 + 未证实」，法律保护媒体不敢直接判；b 是断言，媒体敢这么写就等传票。换 `must` 成 `The star must have evaded taxes` 又是另一回事——那是「我推断他逃了」，来源变成说话人推理，一样要担责。

卫星案例，公共领域，小区停电——`reportedly` 的生活现场：

> 小区停电。2026 年 7 月，北京某小区半夜停电 3 小时。业主群传：
> ```
> a. Power was reportedly out in the complex for three hours.  // 据悉停电三小时
> b. The complex lost power for three hours.                   // 断言：小区停了三小时
> ```
> a 用 `reportedly` 没点名信源（「听物业说的？听邻居说的？」），b 是平铺断言。注意 a 还用了被动（详见第 3 面）把「谁停的」抹掉——居民关心的是「停了没」，不是「谁弄的」。

卫星案例，商业领域，投标失败——`according to` 点名信源：

> 投标失败。2026 年 5 月，Lin 所在团队（假设另一项目）竞标政府订单落选。负责人对内说：
> ```
> a. According to the bid committee, we lost on price.   // 据评标委员会，我们输在价格
> b. We lost on price.                                   // 断言：我们输在价格
> ```
> a 点名「评标委员会」这个信源，意思是「价格这结论不是我拍的，是委员会给的」；b 是自家兜底。对内向老板汇报用 a 更安全——把坏消息的来源甩给委员会。

语用小结：公司和法律爱用传闻标记，因为它把「我说的」变成「XX 说的」。你写邮件甩 `according to`、`reportedly`，等于在每句 claim 上贴了「信源已标注，责任不归我」。中文虽然也写「据悉」「据称」，但它是可选装饰；英文这些标记是语法化的来源字段，不标就默认「来源 = 你」，你自动兜底。

这里要戳破一个传统语法书的糊弄讲法。很多教材把 `It is said that...` 归到「被动语态」那一章，当成「据说」的句型背；把 `according to` 当介词短语随便带过。这种讲法漏了关键一层：**它们根本不是语法花活，是言据标记（evidential）**，功能是把信息来源从「我」转移到「第三方」。你若只当句型背，永远不懂为什么新闻满篇 `reportedly`、合同满篇 `according to`——因为那是人家的法务和编辑在强制填 `source` 字段。

再给一个卡点，判断型，关于 `allegedly` 的位置敏感性：

```
a. The suspect allegedly stole the data.
b. *Allegedly, the suspect is a thief.
```

b 看着也顺，但语用上更诡异——`allegedly` 必须紧贴它修饰的 claim，不能飘在句首管一整句「这人是个贼」的定性。它修饰的是具体行为「偷了数据」，不是人格「是个贼」。这也是为什么媒体写 `The star allegedly evaded taxes` 安全，写 `Allegedly, the star is a criminal` 就过界——后者把「是罪犯」这种定性也标成传闻，等于暗示自己没在定罪，但读者会觉得你在耍赖。中文「涉嫌」没有这种句法位置限制，你放句首句尾都行，因为中文的言据标记是松散副词，不跟具体谓词绑定。

卫星案例，公共领域，楼下店铺倒闭——`it is said` 的市井版：

> 楼下店铺倒闭。2026 年 4 月，小区门口开了三年的咖啡馆突然关了。邻居闲聊：
> ```
> a. It is said that the cafe closed for rent issues.   // 据说因租金问题关门了
> b. The cafe closed because of rent.                   // 断言：因租金关门
> ```
> a 用 `it is said that` 把信源推给「大家都在传」，邻居自己不背书；b 是认账。注意 a 是典型的「我不负责转述」句式，和明星塌房、小区停电同属传闻族，只是信源从「媒体」变成了「街坊」。这恰恰说明言据性是通用语法机制，不分高雅低俗——你妈在电话里说「听说是你表哥要离婚」，那句「听说」在英文里就是 `It is said that`，和《纽约时报》的 `reportedly` 是同一个 `source` 字段的两种取值。

总结这节的旋钮：`according to X` 是**具名引述**（最硬、最负责），`reportedly / it is said` 是**匿名传闻**（中等、滑头），`allegedly` 是**未定性传闻**（法律边界、最谨慎），`sources say` 是**新闻腔匿名**。四者在 `source` 字段上从「点名」到「隐名」到「未定性」递减，信源可信度也依次打折。中文用「据 X 说 / 据悉 / 听说 / 据称」近似，但没把这四档焊成不同构式，你只能靠副词自己掂量。

## 4. 语用：甩锅、免责、留余地（本章高潮之一）

这一节把第 3 面（被动抹施事）和第 5 面（言据 / 情态）合流——这是全书的「彩蛋级」组合技。先抛卡点，判断对错型：

```
*Mistakes may have been made.  =  「可能犯了一些错误。」
```

这句谁干的？你答得出来吗？先想三秒。

（你大概率答：「不知道谁干的，反正可能有错误。」——对了，**这正是它的目的**：既不说谁干的，也不说一定干了。）

看两个对撞的句式：

```
a. Lin definitely caused the outage.          // 主动 + 高确信：精准归责到 Lin
b. Mistakes may have been made.              // 被动 + 弱情态：施事抹掉，确定性压低
```

a 是「点名 + 拍板」：主语 Lin，情态 `definitely`（高确信），信息来源 = 说话人断言。这是最硬的归责句式。
b 是「抹名 + 留余地」：被动把施事（谁犯的错）吞了，`may have` 把「确实犯了」压成「可能犯了」。**比经典的 `Mistakes were made.`（见第 3 面甩锅被动）还滑**——`were made` 至少认了「错误发生了」，`may have been made` 连「发生」都不敢认死。

这就是态度族的终极免责句式：**被动 + 传闻 / 弱情态 = 施事消失 + 确定性消失**。两个维度一叠加，责任被双重擦除。

回到母案例。同一件事——「这次故障跟一次有风险的迁移有关」——对内外说法的确定性是故意不一样的：

- **对 Northwind 客户发通知**：Marcus Bell 不会写 `Lin caused the outage`（主动 + 高确信，精准归责还把客户吓死）。他会写：
  ```
  According to our investigation, a database migration may have contributed to the degradation.
  ```
  「据我方调查，一次数据库迁移**可能**加剧了服务降级」——`according to` 甩信源，`may have` 压确定性，连「caused（导致）」都换成温和的 `contributed to（促成）`。对外，确定性故意调低，保护公司和客户关系。

- **对内部复盘会**：Priya Nair 在 blameless 复盘上反而说得更直：
  ```
  The migration locked the orders table; that is confirmed by the logs.
  ```
  「迁移锁了表，日志确认」——对内不需要躲，来源 = 日志（直接证据），确定性高，但归责对象是「流程缺失」而非「Lin 个人」。

**同一件事，对外的确定性调低，对内的确定性调高**——这不是 hypocrite，是语用：对外你代表公司，每句话都是法律意义上的承诺，得给自己留 `confidence=0.6` 的余地；对内是工程复盘，要准、要能改。

卫星案例，社交领域，微信发错群——留余地的生活版：

> 微信消息发错群。2026 年 6 月，产品经理小赵把吐槽老板的消息误发到全员大群，3 秒后撤回。事后跟朋友解释：
> ```
> a. I might have sent it to the wrong group.   // 弱推测：我可能发错群了（留余地）
> b. I sent it to the wrong group.              // 断言：我发错群了（认了）
> ```
> a 用 `might have` 把「发错」压成弱可能，像是「万一是不是发错了呢」——其实是死认但嘴硬；b 是坦承。对比 `must`：`I must have sent it to the wrong group` 是「我肯定发错群了」（看记录推断），确信度反而高。同一种尴尬事，确定性档位一调，站位全变。

类比钉死：API 响应里的 `confidence` 字段。对外接口（客户通知）返回 `confidence=0.6` 的低置信度以保护自己，免得客户拿你的高确信去告你；对内接口（日志 / 复盘）返回 `confidence=0.99` 以便精准定位问题。英文的被动 + 弱情态，就是你在对外的那层 API 上加的 `confidence` 下限。

再往语用深处走一步。为什么「被动 + 弱情态」是终极免责，而单用被动或单用弱情态都不够？因为责任有两条腿：**施事（谁干的）**和**确定性（干没干 / 我多确定）**。第 3 面讲的被动只砍了第一条腿（抹施事），但 `Mistakes were made` 还是认了「错误发生了」；单用弱情态如 `Mistakes may have happened` 保留了施事可见性（你没抹，只是降确信）。只有两者叠加，`Mistakes may have been made`，才同时砍掉两条腿——既不说谁干的，也不说一定干了。这是态度族内部两个维度（第 3 面语态、第 5 面言据）的正交组合，两个旋钮都拧到「最小责任」档，等号出来的就是政客最爱、程序员最烦的那句废话。

卡点，翻译缺口型——给你一句中文，翻不动是因为缺信息：

> 「这事处理得不太妥当。」
> 英文你打算用主动还是被动？高确信还是弱情态？对谁说？

你大概率卡住，因为中文这句没给你「施事是谁、你多确定、对谁说」任何线索。补上语境就分叉了：对内复盘、点名自己，用 `I handled it poorly`（主动 + 高确信）；对外对客户、不想认，用 `The matter may not have been handled optimally`（被动 + 弱情态 + 委婉形容词 `optimally` 代替 `poorly`）。同一句中文，英文因站位不同能裂成两个极端。这正证明中文把站位信息当「语境暗含」，英文逼你显式选。你翻不动，不是你词汇量少，是中文没逼你填这两个字段，你脑子里根本没有这俩槽位。

卫星案例，社交领域，老同学失联十年后重逢——留余地的情感版：

> 老同学失联。2026 年端午，你偶遇十年没联系的老同学，事后跟老婆复盘：
> ```
> a. He might have moved abroad.                 // 弱推测：他可能出国了
> b. People say he went abroad.                  // 传闻：听说他出国了
> ```
> a 来源 = 你从「朋友圈停更 + 共同好友也联系不上」推的；b 来源 = 别人传的。两句确定性都低，但**来源类型**不同——a 是你担责的猜测，b 是你甩给「别人说」的转述。对比 `He must have moved abroad`（高确信推断，你查过出入境线索），档位一调，你在这件事上「多确定、信源哪来」全变。生活里这种「我猜 vs 我听说的」区分，中文靠「可能 / 听说」两个副词，英文靠情态动词和引述构式焊死。

再把母案例 Marcus 对 Northwind 的那封通知，和 Priya 内部复盘的话摆成最小对立对，你就能看见「同一事件、两套站位」的标准答案：

```
对外（Marcus → Northwind）：
    According to our investigation, a migration may have contributed to the degradation.
    （引述 + 弱情态：据调查，迁移可能促成了降级）

对内（Priya → 复盘会）：
    The migration locked the orders table; that is confirmed by the logs.
    （断言 + 引述证据：迁移锁了表，日志确认）
```

两句核心命题都是「迁移 → 故障」，但对外把 `source` 推给「我方调查」、`confidence` 压到「可能」；对内把 `source` 钉到「日志」、`confidence` 拉满到「确认」。这不是 Marcus 虚伪、Priya 诚实，是**同一事件在不同受众前的 `source`/`confidence` 配置不同**——就像你给老板汇报用 `according to` 点名数据看板，给老婆吐槽用 `might` 瞎猜，没人觉得你人格分裂。英文的高明（也让人头疼）之处，在于它**把这种配置差异做成了强制语法**，你绕不过。这也是为什么老外写邮件显得「绕、不肯给准话」——人家在依法填字段，不是性格犹豫。

卫星案例，工作领域，邮件发错收件人——减责的职场版：

> 邮件发错收件人。2026 年 3 月，财务小林把含 salaries 的邮件误发给全公司。她补救时写：
> ```
> a. The email might have been sent to the wrong list.   // 被动+弱情态：邮件可能被发错列表
> b. I accidentally sent the email to everyone.           // 主动+高确信：我误发给了所有人
> ```
> a 用被动抹施事 + `might` 降确信，是最软的补救口径（像在说「系统可能出错了」）；b 是死认。注意 a 没撒谎——「可能发错」在「还没确认影响范围」阶段是诚实的低确信表述，等确认了再切到 b。换档位 = 从「 tentative 补救」到「 fully owned」，危机沟通里这套切换是基本功。

最后点一句政治不正确的实话：对内对外用不同档位，不是 hypocrite，是**角色自觉**。你在家跟老婆说「我肯定搞砸了」是坦诚，在公司跟客户说「可能有些环节有待优化」是自保。英文把这种角色自觉做成了强制语法——你选不对档位，不是「不礼貌」，是「站错了位」。这和第 9 面「语域与态度」是亲戚，到时候你会看见态度族怎么收口。

## 5. 母案例十面之五（用本章维度重写）

这一节把母案例 The Outage 的「事件核命题」——`Lin 执行的一条数据库迁移锁住了 orders 表，导致 51 分钟的服务降级，但没有造成数据丢失`——用本章五个确定性档位重写一遍。每句都标：**确定性档位 / 信息来源 / 说话人站位**。

```
(1) 断言（高确信 · 主动）
    Lin caused the 51-minute outage by running an unsafe migration.
    确定性：高（断言）。来源：说话人直接认定。
    站位：点名 Lin，拍板归责。适合内部已定论的场合。

(2) must have（高确信 · 推断）
    The lock must have come from the migration Lin ran at 2:14.
    确定性：高（推断）。来源：从日志 / 时间线反推。
    站位：没亲眼看见回车，但从证据铁定推断是迁移。比 (1) 多一层「我推的」。

(3) may have（弱推测）
    The migration may have triggered the brief lock on orders.
    确定性：中低（可能）。来源：说话人推测，未证实。
    站位：不敢打包票，给「也许不是迁移」留门。对外初报常用。

(4) according to the logs（引述 · 点名信源）
    According to the logs, the migration locked the orders table.
    确定性：高（报告背书）。来源：日志（第三方证据）。
    站位：把信源甩给日志，说话人不兜底。工程复盘最爱。

(5) reportedly（传闻 · 不点名）
    The outage reportedly stemmed from a database migration.
    确定性：中（传闻）。来源：未点名的转述。
    站位：媒体 / 外界口径，不认死、不点名。对外最安全。
```

五句话，中文核心都是「迁移导致故障」。但英文每一句都在动词周边焊了不同的 `source` + `confidence`：

- (1) 是 `source=我, confidence=高`，最硬；
- (2) 是 `source=推理, confidence=高`，硬但留了「推断」的尾巴；
- (3) 是 `source=我, confidence=低`，软；
- (4) 是 `source=日志, confidence=高`，硬但责任在日志；
- (5) 是 `source=传闻, confidence=中`，最滑。

**一句话收束这一节**：同样的事故，你选哪个档位，等于选了「你在这件事上站哪儿、担多少责」。中文只让你用「据说 / 可能 / 肯定」在外面贴纸条；英文逼你在句子形态里选死。

卫星案例，工作领域，客户投诉——对照母案例 (4) 的引述站位：

> 客户投诉。2026 年 4 月，客服主管接到 Northwind 大客户投诉下单延迟。她写周报：
> ```
> a. According to the client, orders were delayed yesterday.  // 据客户说，订单昨天延迟了
> b. Orders were delayed yesterday.                           // 断言：订单昨天延迟了
> ```
> a 用 `according to the client` 点名信源——「延迟」这事实是客户反馈的，我先不自己认；b 直接认了。注意 a 还用被动（第 3 面）把「谁延迟的」抹了。跟 Marcus 对 Northwind 发通知同构：对外先引述，别急着兜底。

把这五档放回母案例完整时间线，你能看见站位随事态演化而移动——这也是「确定性是动态标签，不是静态事实」的活证据：

- **2:31 Lin 刚定位**：他只敢用 (3) `may have` 弱推测——「也许是迁移锁的」，因为还没看全日志，不背锅。
- **2:47 Priya 决定 KILL 后**：证据齐了，升级到 (2) `must have` 高确信推断——「锁肯定来自那条迁移」，可以给经理交差。
- **3:05 恢复、写内部时间线**：用 (4) `according to the logs` 引述——「日志显示迁移锁了表」，工程语言，信源钉死在日志。
- **11-13 blameless 复盘对外口径**：用 (5) `reportedly` 传闻级——「据悉一次迁移引发降级」，对客户和外界，永不直接点名 Lin、永不定死。
- **对内问责定论**：才用 (1) 断言级——但归责对象是「流程缺失」而非「Lin 个人」，即 `The missing process caused it` 而非 `Lin caused it`。

你看，同一场事故，从 2:31 到复盘，**确定性档位一路从 `may` 爬到 `must` 再对外降回 `reportedly`**。这不是说话人反复无常，是 `confidence` 字段随证据积累而涨、随受众切换而调。你中文描述全程也只会说「起先是可能，后来确定了，对外又说可能」——英文是把它做成了每个时间点的句子形态必选项。这再次说明：中文几乎一样，英文思维完全不同。

回扣卡点：本节开头那五句英文，中文核都是「迁移导致故障」。你现在该能闭眼填出每句的 `source` 和 `confidence` 了——(1) 我/高，(2) 推理/高，(3) 我/低，(4) 日志/高，(5) 传闻/中。填不出来，就倒回去重看这五档。这一节就是本章的「母案例样板间」，后面所有卫星案例都是它的复制品，只是换了事件壳。

## 6. 卫星案例（跨领域最小对立对）

这一节把剩余卫星案例摊开，每个都给「确定性 / 言据」的最小对立对，并说清楚：**换了档位，换了什么站位**。技术卫星案例上限 2 个，本章已在上节用过「误删生产数据」1 个，这里再补 1 个技术，其余走生活 / 商业 / 运动。

**案例 A｜竞品抢先（商业）**

> 竞品抢先发布。2026 年 2 月，对手在自己发布会前一周上线同类功能。产品经理复盘：
> ```
> a. The rival must have launched first.                  // 推断：对手肯定先发了
> b. The rival might have launched first.                 // 弱推测：对手可能先发了
> ```
> a 用 `must` 高确信推断（从对方宣传节点反推）；b 用 `might` 弱可能（没实锤）。换档位 = 换站位：a 是拍板「我们被抢了」，b 是「也许情报有误，再核实」。

**案例 B｜监控漏报（技术 · 本章第 2 个技术卫星）**

> 监控漏报。2025 年 12 月，某服务宕了 20 分钟才被人发现，因为告警没触发。值班同学写事故单：
> ```
> a. The alert must have been missed by the watcher.      // 推断：告警肯定被盯盘的人漏了
> b. The alert could have been missed.                    // 更弱：告警可能被漏了（也许系统没发）
> ```
> a `must have been missed`：被动抹施事（谁漏的不点名，见第 3 面）+ `must` 高确信推断；b `could have been` 更弱，给「也许是系统压根没发告警」留门。技术场景里这种「推断 + 被动」组合极常见。

**案例 C｜体检指标异常（医疗）**

> 体检指标异常。2026 年 3 月，读者你拿到体检单，转氨酶偏高。医生口头说：
> ```
> a. Your liver enzyme may be elevated.                   // 弱推测：你的酶可能偏高
> b. Your liver enzyme is elevated.                       // 断言：你的酶偏高
> ```
> a `may` 是「单看初筛，可能偏高，复查再说」；b 是确诊语气。医生对初筛结果几乎不用 `must`（那是推断不是确诊），也不用 `according to`（信源就是检测本身）。换 `may`→断言 = 从「待复查」变成「已下结论」，站位差一层诊断责任。

**案例 D｜马拉松跑崩（运动，呼应第 2 节）**

> 马拉松跑崩。再补一个角度——赛后朋友问老周咋退赛的：
> ```
> a. He might have hit the wall.                          // 弱推测：他可能撞墙了
> b. He reportedly hit the wall.                          // 传闻：据悉他撞墙了
> ```
> a 来源 = 朋友推测（没问本人）；b 来源 = 传闻（听别人说的）。同一事实，a 是「我猜」，b 是「听来的」——确定性都低，但**来源类型不同**，责任归属也不同：a 兜的是「我的猜测」，b 兜的是「别人的转述」。

**案例 E｜微信发错群（社交，呼应第 4 节）**

> 已在第 4 节用过 `I might have sent it to the wrong group`。这里补它的对撞句，强调档位差：
> ```
> a. Messages were possibly sent to the wrong group.      // 被动+弱情态：可能被发错群（抹施事）
> b. I definitely sent it to the wrong group.            // 主动+高确信：我肯定发错群了（认）
> ```
> a 是把「发错群」这件事用被动 + `possibly` 软化（适合跟不太熟的人解释，撇清「我故意的」）；b 是死认。换档位 = 从「可能失误」到「确认失误」，社交代价天差地别。

**案例 F｜投标失败（商业，呼应第 3 节）**

> 已在第 3 节用过 `According to the bid committee`。这里补传闻版：
> ```
> a. We allegedly lost the bid on a technicality.         // 据称：我们因技术细节丢标
> b. We lost the bid on a technicality.                   // 断言：我们因技术细节丢标
> ```
> a `allegedly` 把丢标原因标成「传闻 / 未坐实」，对内吹风用；b 是认账。注意 `allegedly` 在法律 / 商业里专门用来「说但没定性」，跟明星塌房同款机制。

八个卫星案例跨了 **公共（明星 / 小区）、商业（投标 / 竞品）、医疗（体检）、社交（微信）、工作（客户投诉）、运动（马拉松）、技术（误删 / 监控）** 七个领域，技术恰好 2 个，达标。每个都证明了同一件事：**确定性档位和言据标记不是装饰，是说话人站位的开关**。

再补三个跨领域案例，把「通用机制」钉死——证明这玩意儿不分高低贵贱，买菜和上市都用同一套。

**案例 G｜台风预警（公共 · 气象）**

> 台风预警。2026 年 8 月，超强台风「木兰」逼近东南沿海。气象台和邻居说法不同：
> ```
> a. The typhoon is expected to make landfall tonight.   // 合理预期：预计今夜登陆
> b. The typhoon will hit us for sure.                   // 强预期：肯定撞上我们
> ```
> a 用 `is expected to` 把来源标成「气象台预测」（引述 + 合理预期），确定性中等，因为路径还有变数；b 用 `will` 强预期，像是拍板「一定来」。a 是负责任的公共预警口径（留变数余地），b 是吓自己。注意 `expected` 在这里是「预期」不是「被期待」——又是 `expect` 跨确定性和态度两族，和第 6、9 面都有牵连。中文「预计 / 肯定」对应，但英文把 `expected` 焊成了「信源=预测机构」的标记。

**案例 H｜表白被拒（社交 · 情感）**

> 表白被拒。2026 年 5 月，同事小陈鼓起勇气表白，对方没明确回。他跟死党复盘：
> ```
> a. She might not be into me.                    // 弱推测：她可能对我没意思
> b. She said she needs time.                     // 引述：她说需要时间
> ```
> a 来源 = 小陈自己的推测（从「没回消息」推），`might` 弱确定，给「也许是我多想」留门；b 来源 = 对方原话引述（`said`），把信源甩给当事人，比 a 更硬因为「这是她亲口说的」。同一段暧昧，选 a 是自我安慰的猜测站位，选 b 是「有据可循」的引述站位。中文「她可能没意思 / 她说要时间」同样是副词和引述框架之差，但英文用情态和 `said` 把 `source` 焊明。

**案例 I｜项目延期（工作 · 商业）**

> 项目延期。2026 年 6 月，你带的项目比里程碑晚两周。跟老板 1:1 时两种说法：
> ```
> a. The project may slip by two weeks.           // 弱推测：项目可能延两周
> b. According to the tracker, we are two weeks behind.  // 引述：据看板我们落后两周
> ```
> a 用 `may` 把延期说成「可能」，还留着「也许能抢回来」的余地，适合早期预警、不想把坏消息坐实；b 用 `according to the tracker` 点名信源（项目管理看板），把「落后两周」变成数据事实而非你的猜测，适合复盘定责。换了档位 = 从「我怕要延期」变成「数据显示已延期」，老板听到的是两种完全不同的紧迫感。

把十一个卫星案例摆在一起做个矩阵，你会看见「同一机制，万变不离其宗」——所有案例只是把 `source` 和 `confidence` 两个旋钮拨到不同刻度，事件壳子换了而已：

| 案例 | 领域 | 确定性档位 | 信息来源 | 典型英文构式 |
|---|---|---|---|---|
| 明星塌房 | 公共 | 未定性低 | 传闻（不点名） | `allegedly` |
| 小区停电 | 公共 | 中（传闻） | 传闻（不点名） | `reportedly` |
| 台风预警 | 公共 | 合理预期 | 引述（气象台） | `is expected to` |
| 投标失败 | 商业 | 中（传闻） | 引述（委员会） | `according to` |
| 竞品抢先 | 商业 | 高确信推断 | 推理 | `must have` |
| 项目延期 | 工作 | 弱推测 / 引述 | 我 / 看板 | `may` / `according to` |
| 客户投诉 | 工作 | 引述 | 客户 | `according to` |
| 体检异常 | 医疗 | 弱推测 | 我（初筛） | `may` |
| 微信错群 | 社交 | 弱推测 / 被动 | 我 | `might have` / 被动 |
| 表白被拒 | 社交 | 弱推测 / 引述 | 我 / 对方 | `might` / `said` |
| 马拉松跑崩 | 运动 | 高确信推断 / 传闻 | 推理 / 传闻 | `must have` / `reportedly` |
| 误删数据 | 技术 | 高确信推断 / 弱推测 | 推理 / 我 | `must have` / `may` |
| 监控漏报 | 技术 | 高确信推断 / 更弱 | 推理 | `must have been` / `could` |

这张表就是本章的「状态机映射表」：横轴是 `source`（直接 / 引述 / 传闻 / 推理），纵轴是 `confidence`（高→低），每个案例落在某个格子里。母案例 The Outage 的五档（第 5 节）也不过是这张表上的五个点。你以后遇到任何新事件，先问自己「落在哪个格子」，英文句型自动浮现——这才是把规则变成系统认知，而不是背例句。

顺便提醒一个读表的常见误用：有人把这张表当成「选词翻译字典」，对着中文副词查英文词。那是倒果为因。正确用法是**先看事件本身在该语境下的来源和确信度，再让英文语法替你长出对应构式**。中文副词是「结果」，英文形态是「机制」——你从机制出发，才不会在「可能 / 也许 / 大概 / 没准」这些近义词里瞎纠结，因为它们在英文里只是 `confidence` 刻度尺上挨着的几格，本质是一回事的不同刻度。理解了这一点，「中文几乎一样，英文思维完全不同」就不再是一句口号，而成了你脑子里的操作手册。

把 G/H/I 算上，本章卫星案例达到 **十一个**，跨 **公共 / 商业 / 医疗 / 社交 / 工作 / 运动 / 技术** 七个领域，技术仍只有 2 个（误删、监控），完全达标且分布均匀。反复验证的那句话现在该刻进你脑子了：**确定性档位和言据标记，是说话人站位的开关；拨一下，你在这件事上「多确定、信源哪来、担多少责」全变。中文用副词近似，英文焊进形态逼你选死。**

## 7. 一面之得

收束这一面，给一句够你带走的话：

> **确定性不是事实的属性，是说话人给命题贴的可信度标签；言据性告诉你这个标签从哪来。**

展开三点：

1. 每句英文 claim 都自带两个隐藏字段：`confidence`（确定性）和 `source`（信息来源）。情态动词管前者，传闻标记管后者。中文把它们当可选副词，英文把它们焊进形态。
2. `must` 不是「必须」是「肯定」；`may / might / could` 是逐级下调的可能性；`according to / reportedly / allegedly / it is said` 是逐级「甩锅」的来源标记。
3. 被动（第 3 面）+ 弱情态 / 传闻 = 终极免责句式。同一件事对内外用不同档位，是语用自觉，不是虚伪。

记住这句就够了：**英文逼你在每个 claim 上标注「我多确定、这消息谁说的」，中文让你自己掂量着加副词。** 你以后读英文新闻、写英文邮件，先问自己这两个字段填没填、填的啥。

为什么这一面值得你花这么长？因为态度族（5/7/8/9）是英语和中文分道扬镳最狠的地带之一。前面时间族（1/2/6）你还能靠「加个时间词」勉强对齐，镜头族（3/4/10）靠「换主语、调语序」凑合；但态度族这套「每句话都要声明我多确定、信源哪来」，中文压根没有对应的语法槽位，只能靠副词和语境暗含。所以中国学生读英文新闻总觉得「绕、含糊、不肯给准话」，其实是人家在依法填 `confidence` 和 `source`；反过来你写英文容易「太满、太硬、站错位」，因为你没养成填这两个字段的习惯。练完这一面，你至少拿到了态度族的第一把钥匙：先辨来源，再定确信。第 7 面（名词化旋钮）会继续调「抽象度」，第 8 面（数与限定）调「范围边界」，第 9 面（语域与态度）调「正式度和褒贬」——它们都是态度族旋钮，这一面打的底，后面四章都接着用。

留一个钩子给你自己练：今天起，你每发一条英文消息（哪怕给同事），试着在脑子里标一下 `source` 和 `confidence`。标过一周，你再回看自己月初写的英文，会尴尬——那时候你八成全是裸断言，默认 `source=你`、`confidence=高`，替全世界兜底。

而这恰恰是全书的题眼：中文几乎一样，英文思维完全不同。你这一面练的不是「多背几个情态动词」，是换一套「说话先填字段」的思维习惯。习惯养成了，第 7、8、9 面只是顺着态度族往下拧别的旋钮，不会再卡。

## 8. 思考题（5 道带参考答案）

**第 1 题（辨析层）**
下面两句差别只在情态动词，请说明确定性档位和说话人站位的差别：
```
a. The migration must have caused the lock.
b. The migration may have caused the lock.
```

**参考答案**
两句中文都可翻「迁移导致了锁」，但 `confidence` 字段完全不同。a 用 `must have`，是**高确信推断**（从日志 / 时间线铁定反推），说话人站位 = 「我推的，但我敢拍板」；来源是直接证据推出来的，确定性约 0.9+。b 用 `may have`，是**弱可能推测**，说话人站位 = 「我不敢打包票，也许不是迁移」，确定性约 0.5。换了 `must`→`may`，等于把命题的 `confidence` 从 0.9 降到 0.5，责任也从「我认定」变成「我猜」。注意 `must` 在这里是「肯定」不是「必须」——这是中国人最容易翻车处。

再补一层：这两句话的 `source` 其实都是「说话人推理」，差别只在 `confidence`。可一旦你把它误读成「a 是必须、b 是可以」，整句意思就崩了——`The migration must have caused the lock` 绝不能被翻成「迁移必须导致了锁」（那语法逻辑都不通）。所以辨析这类题，第一步永远是先判情态动词在这里表「推测」还是「义务 / 能力」：后面跟 `have done` 表过去推测的 `must`，一律解「肯定（已经）」；只有光杆原形 `must do` 才可能表「必须」。母案例里 Lin 凌晨定位时用 a 级别推断（看锁痕），初报对外用 b 级别留余地——同一个锁，对内敢 `must`、对外只敢 `may`，这正是本章核心。

**第 2 题（辨析层）**
下面两句都表「传闻」，差别在哪？什么场合该用哪个？
```
a. According to the postmortem, the root cause was a missing process.
b. Reportedly, the root cause was a missing process.
```

**参考答案**
两者来源都是第三方（传闻言据），但**信源是否点名**不同。a 用 `according to` **点名**了信源「the postmortem（复盘报告）」，责任归属最清晰——「这结论不是我拍的，是报告写的」，适合对内 / 对需要知道出处的读者。b 用 `reportedly` **没点名**信源，只说「据悉」，适合媒体对外、不想 / 不能暴露消息来源时。换了 `according to`→`reportedly`，等于把 `source` 字段从「具名」变成「匿名」，说话人的免责程度更厚，但可信度也更低（读者不知道你听谁说的）。法律 / 八卦里的 `allegedly` 比 `reportedly` 还谨慎，专用于「没定性」。一句话：要负责任用 `according to` 点名，要滑头用 `reportedly` 隐名。

再给一个判断口诀：`according to X` 后面必须跟**具体信源 X**（人 / 机构 / 文件），它把责任钉在那个 X 上；`reportedly` / `it is said` 后面**没有**具体信源，责任漂在空中。所以如果你能说出「据谁说」，优先 `according to`；如果信源模糊或不宜曝光，用 `reportedly`。还有个位置细节：`according to` 是介词短语，可前可后（`According to the report, ...` 或 `..., according to the report`）；`reportedly` 是副词，常插在句中或句首。母案例里 Marcus 对 Northwind 用 `According to our investigation`（点名「我方调查」），就是负责任的具名引述；若他写 `The outage reportedly stemmed from a migration`，客户会觉得「你到底听谁说的，能不能给准话」——对外用匿名传闻反而显得不专业。这点常被人忽略：匿名传闻对媒体安全，对企业对客户未必。

**第 3 题（应用层）**
你是工程经理，要在一封对**外部大客户**的故障通知里写「这次故障可能是一次数据库迁移引起的，具体还在查」。请用本章维度写一句英文，并说明理由（确定性档位、信息来源、站位）。

**参考答案**
推荐写法：
```
According to our preliminary investigation, a database migration may have contributed to the degradation.
```
理由拆三个字段：`source` 用 `according to our preliminary investigation` 点名「我方初步调查」作信源，把结论甩给调查而非个人断言；`confidence` 用 `may have` 压到中低（「可能」），不替客户下定论；动词用温和的 `contributed to（促成）`而非 `caused（导致）`，进一步降归责。站位 = 对外代表公司，每句都是法律意义上的承诺，必须留 `confidence` 余地、标信源以自保。对比不要写的：`Lin caused the outage`（主动 + 高确信，精准归责还吓客户）或 `The migration caused it`（断言无余地）。这正是母案例里 Marcus 对 Northwind 的口径逻辑。

为什么不直接说 `The migration caused the outage`？因为那句话三个字段全是「最硬」：来源 = 你（无引述）、确定性 = 高（断言）、归责 = 直接（caused）。客户读完会：(1) 认定你已定责，(2) 把「迁移 = 你方失误」当事实传播，(3) 拿去跟法务商量索赔。你一句裸断言，给自己挖了三个坑。而推荐写法让客户读到的是「据我方初步调查（信源可查）、可能（未坐实）、促成（非唯一原因）」——既通报了进展，又把责任锁在「调查」和「可能性」里。这正是第 4 节讲的「对外 `confidence` 调低」原则的现场应用。再提醒：本句还顺手用了 `our preliminary investigation` 而非 `me`，把施事从「我个人」换成「机构调查」，和第 3 面被动抹施事是同一个减责思路，只不过这里用引述框架代替被动。

**第 4 题（应用层）**
同事在全员会上问「谁把生产配置表清空了？」你心里从日志推断「八成是那个定时脚本干的」，但还没 100% 确认。你想既给出方向又不背锅。写一句英文。

**参考答案**
推荐：
```
The data must have been deleted by the script, but I'm still verifying.
```
或纯推断版：
```
The logs suggest the script deleted the data.
```
第一句拆字段：`confidence` 用 `must have` 高确信推断（「八成是脚本」从日志反推），但补 `but I'm still verifying` 留核实余地；`source` 用推断（我看的日志）；被动 `been deleted by the script` 把施事点名成「脚本」而非「某个人」，既给方向又抹人（参见第 3 面）。第二句用 `suggest` 把来源标成「推测」而非断言，更软。不要写 `The script deleted the data`（断言，等于你已定罪）——没确认前用断言是给自己挖坑。档位选择 = 在「给方向」和「不背锅」之间取 `must` 推断 + 被动点名脚本，而非 `may` 弱推或裸断言。

这里有个值得品的细节：为什么用被动 `been deleted by the script` 而不是主动 `the script deleted`？因为你想点名的是「脚本」这个机制，不是「谁跑的脚本」那个人。如果写 `Tom deleted the data with the script`，你就把锅精准扣到 Tom 头上——在没确认前这是职场事故。被动让你把施事定位在「脚本」（物），把「人」那一层轻轻抹掉（第 3 面语态的减责功能），同时 `must have` 又告诉全场「我是从日志推的，不是我盯着 Tom 干的」。两个维度配合：`source` = 我的推理，`confidence` = 高，`agent` = 脚本而非人。这三旋钮一起拧，才是工程现场最稳妥的「给方向不背锅」站位。若你用 `may have been deleted by the script`，则 `confidence` 再降一档，更适合「连日志都没完全看明白」的更早阶段。

**第 5 题（拔高层）**
中文怎么表达「传闻 / 推测」？中文有哪些词汇手段？为什么中文没有把「确定性」焊进动词形态——这跟中文「主观性表达靠副词」的传统有什么关系？这一问可顺带引出第 6 面「语气 / 非真实」。

**参考答案**
中文表达传闻 / 推测，靠的是**词汇手段（副词和引述框架）**：「据说 / 听说 / 据称 / 据悉 / 按说」表传闻；「看来 / 好像 / 应该 / 大概 / 可能 / 八成 / 没准」表推测；还能用「有人说 / 消息称」点名或隐名信源。这些都是**挂在动词外面的修饰语**，不动句子骨架——「Lin 搞的」和「据说 Lin 搞的」主谓宾完全一样，只多了一个副词性成分。

为什么中文不焊进形态？根子在汉语的**形态贫乏（isolating / analytic）**传统：中文靠语序和虚词表语法关系，动词本身不因人称、数、时、确定性变形。主观性（speaker stance：确定性、来源、态度）历来交给**副词、语气词、句式**承担，而不是屈折形态。英文是形态化语言，把时 / 体 / 语气 / 言据都做成了动词的必填字段；中文是词汇化语言，这些字段是「选填」的注释。所以同一命题，英文逼你标注 `confidence` 和 `source`，中文让你「凭感觉加副词」——这正呼应全书母题「形态化 vs 词汇化」。

顺带引出第 6 面：确定性（这面）说的是「我对命题多确信、信源哪来」，而**语气 / 非真实（第 6 面）**更进一步——它管的是「这句话落在哪个世界」：真实世界（陈述）、假设世界（if 虚拟）、祈愿世界（wish）、义务世界（should / must 表必须）。`must` 在这一面表「肯定推测」，在第 6 面表「必须」——同一个词横跨确定性和语气两族，正好说明态度族（5/7/8/9）内部是连着的状态机：先定「我多确定、信源哪来」（第 5 面），再定「这句话进哪个可能世界」（第 6 面）。

最后给你一个能马上练的翻译小游戏，体会「中文主观性靠副词」的弹性：把下面的中文逐句翻英文，注意每句确定性 / 来源不同，英文几乎句句要换构式，中文却只用副词挪腾——

- 「他来了。」（你看见的，高确信断言）→ `He came.`
- 「他应该来了。」（推测他会来，合理预期）→ `He should have come.`
- 「据说他来了。」（传闻，不点名）→ `He reportedly came.`
- 「听说是他搞的。」（传闻 + 归因）→ `It is said that he did it.`
- 「他可能来过。」（弱推测）→ `He might have come.`

五句中文都绕着「他来」转，副词一换意思就转；英文却动用了断言、情态、引述、传闻四种构式，动词形态各不相同。这游戏做十遍，你会彻底相信：中文把「我多确定、信源哪来」当软修饰，英文把它焊死在句子里。**这，就是第 5 面要你带走的那个「为什么」。**

回扣开场卡点收个尾：你最初写的 `*It is said that Lin caused the outage.` 现在读起来，应该不再是「加了个据说」的装饰，而是「把 `source` 从说话人改成第三方、把责任推出去」的语法动作。星号那层「不过脑子答案」的提醒，到此可以擦掉了——你现在已经过脑子了。带着这把钥匙，下一面我们看语气怎么把句子送进另一个世界。

## 9. 附：本面速查表

**确定性谱系（情态动词，从高到低）**

| 情态动词 | 确定性档位 | 含义 | 母案例例句 |
|---|---|---|---|
| `must` | 几乎肯定（高确信推断） | 肯定 / 一定是 | `The lock must have come from the migration.` |
| `will` | 强预期 | 肯定会 / 将会 | `The error rate will climb.` |
| `would` / `should` | 合理预期 | 应该会 | `It should recover soon.` |
| `can` | 能力 / 一般可能 | 能 / 有时会 | `This can happen on big tables.` |
| `may` / `might` | 弱可能 | 可能 / 没准 | `The migration may have triggered it.` |
| `could` | 更弱可能 | 或许 | `It could be a network blip.` |

**言据标记（信息来源）**

| 标记 | 来源类型 | 是否点名信源 | 母案例 / 卫星例句 |
|---|---|---|---|
| `It is said that ...` | 传闻 | 否 | `It is said that Lin caused it.` |
| `reportedly` | 传闻（媒体） | 否 | `The outage reportedly stemmed from a migration.` |
| `according to ...` | 引述 | 是 | `According to the postmortem, the root cause was a missing process.` |
| `sources say` | 引述（新闻腔） | 否 | `Sources say the bid was lost.` |
| `allegedly` | 传闻（未定性） | 否 | `The star allegedly evaded taxes.` |
| `suggest`（动词） | 推测 | 推理 | `The logs suggest the migration caused it.` |

**母案例各档例句（十面之五）**

| 档位 | 英文 | 中文 | 说话人站位 |
|---|---|---|---|
| 断言（高确信主动） | `Lin caused the 51-minute outage.` | Lin 导致了 51 分钟的故障。 | 点名 + 拍板 |
| `must have`（高确信推断） | `The lock must have come from the migration.` | 锁肯定来自那次迁移。 | 我推的，敢拍板 |
| `may have`（弱推测） | `The migration may have triggered the lock.` | 迁移可能触发了锁。 | 我猜，留门 |
| `according to the logs`（引述） | `According to the logs, the migration locked the table.` | 据日志，迁移锁了表。 | 甩给日志 |
| `reportedly`（传闻） | `The outage reportedly stemmed from a migration.` | 据悉故障源于一次迁移。 | 对外最滑 |

**思维差异一句话**：中文靠「据说 / 可能 / 肯定」等副词挂在外面表达确定性与来源；英文把它们焊进情态动词和言据构式，成为句子的必填字段。

**怎么用这张表（实操三问）**：

1. **先定来源**：这句话的消息是我亲历（direct）、别人说的（reported）、还是我推的（inferred）？亲历用主动断言，别人说用 `according to / reportedly / allegedly`，我推用 `must / may / suggest`。来源定错，整句站位就歪。
2. **再定确信**：高确信推断上 `must have`，未证实用 `may / might`，强预期用 `will / should`，能力 / 一般可能用 `can`。记住 `must` 是「肯定」不是「必须」，`should have` 常是「本该（却没）」的预期落差。
3. **最后定受众**：对外（客户 / 媒体 / 合同）把 `confidence` 调低、把 `source` 甩给第三方；对内（复盘 / 日志 / 定责）把 `confidence` 调高、信源钉死。被动（第 3 面）可随时叠加，砍掉施事那条腿。

三问走完，你基本不会写错站位。这张表建议截图当书签——它不是字典，是「说话人站位的选择菜单」。

**一个常见误解的澄清**：有人以为「确定性越低越礼貌、越高越粗鲁」。不对。确定性是**诚实度**标签，不是态度标签（褒贬归第 9 面）。对内核你说 `must have` 是高确信，不是没礼貌；对客户你说 `may have` 是留余地，不是心虚。把「确定性」和「礼貌」混为一谈，是中文母语者的典型迁移错误——因为中文「可能 / 大概」确实常带「客气」色彩，但英文 `may / might` 首先是 `confidence` 字段，礼貌是副产品。分清楚，你才不会在该硬的时候软、该软的时候硬。
