## 引入场景

编译器把每个源文件翻译成了目标文件（.o），但这些文件各自独立——文件A调用的函数可能定义在文件B中。链接器的工作就是把这些碎片拼成一个完整的、可以运行的程序。

想想拼图：每块拼图（.o文件）上有凸起（导出的符号）和凹槽（需要的外部符号），链接器负责把它们拼在一起。

## 对话探索

**问题1：文件A调用了文件B中的函数 `Calculate()`。编译文件A时，编译器不知道 `Calculate()` 的地址。那它怎么办？**

💭 思考方向：
- 编译器能跳过这个问题吗？
- 它会不会先放一个"占位符"？
- 谁来填充正确的地址？

📖 参考答案：
编译器做两件事：

1. **在符号表中记录**："我需要一个叫 `Calculate` 的外部符号"
2. **在代码中留占位**：调用 `Calculate` 的地方，地址先填0（或特殊标记）
3. **在重定位表中记录**："代码偏移量第42字节处，需要填入 `Calculate` 的地址"

```
文件A的目标文件：
┌────────────────────────────┐
│ .text (代码段)              │
│   ...                      │
│   CALL 0x00000000  ← 占位  │
│   ...                      │
├────────────────────────────┤
│ 符号表                      │
│   需要: Calculate (未定义)   │
│   提供: main (已定义)       │
├────────────────────────────┤
│ 重定位表                    │
│   偏移42: 需要 Calculate    │
└────────────────────────────┘
```

链接器的任务就是查找 `Calculate` 在哪个.o文件中定义，然后把那个 `0x00000000` 替换为真实地址。

---

**问题2：链接器如何找到符号？如果找不到会怎样？如果找到多个呢？**

💭 思考方向：
- 想象一个巨大的"电话簿"——所有.o文件贡献各自的符号
- 名字冲突怎么办？
- 你见过 "undefined reference to xxx" 的错误吗？

📖 参考答案：
链接器执行**符号解析（Symbol Resolution）**：

1. **收集**：遍历所有.o文件，建立全局符号表
2. **匹配**：每个"未定义"的引用，找到对应的"已定义"符号
3. **检查冲突**：

| 情况 | 结果 |
|------|------|
| 找到唯一匹配 | ✅ 成功，记录地址 |
| 找不到 | ❌ `undefined reference to 'Calculate'` |
| 找到多个强符号 | ❌ `multiple definition of 'Calculate'` |
| 一个强符号+多个弱符号 | ✅ 使用强符号 |

**强符号 vs 弱符号**：
- **强符号**：函数定义、已初始化的全局变量
- **弱符号**：未初始化的全局变量

```c
// file1.c
int count = 10;    // 强符号

// file2.c  
int count;          // 弱符号 → 链接时选择file1的强符号
```

Go的符号解析更简洁——包名.函数名的命名规则，基本不会出现名字冲突。

**问题3：找到符号地址后，链接器如何把地址"填"回去？**

💭 思考方向：
- 每个.o文件的代码段从偏移0开始
- 链接时多个.o的代码段要合并——地址会变
- 重定位表的作用在此

📖 参考答案：
这就是**重定位（Relocation）**：

```
链接前：
  文件A .text: [指令...] [CALL 0x0000] [指令...]    起始偏移: 0x0000
  文件B .text: [指令...] [Calculate代码] [指令...]   起始偏移: 0x0000

链接后（合并后）：
  .text: [文件A的指令...] [CALL 0x1234] [指令...] [文件B的指令...] [Calculate代码...]
         │                      │                                  │
         │  地址0x0000           │  重定位填入                       │ 地址0x1234
```

重定位分两步：
1. **合并段**：把所有.o的同名段（.text、.data）拼接，确定每段的最终地址
2. **修正引用**：根据重定位表，把占位地址替换为最终地址

**问题4：静态链接和动态链接有什么区别？Go为什么默认静态链接？**

💭 思考方向：
- 静态链接后，所有代码都在一个文件里
- 动态链接在运行时才加载库
- Docker容器里部署Go程序特别方便，为什么？

📖 参考答案：

| 特性 | 静态链接 | 动态链接 |
|------|---------|---------|
| **时机** | 编译时完成 | 运行时加载 |
| **文件大小** | 大（包含所有库代码） | 小（只有自己的代码） |
| **依赖** | 无外部依赖 | 需要目标机器有对应.so |
| **内存** | 每个进程独立副本 | 多进程共享库代码 |
| **更新** | 需重新编译 | 替换.so即可 |
| **部署** | 简单（单文件） | 复杂（需管理依赖） |

**Go选择静态链接的原因**：
1. **部署极简**：一个二进制文件扔到服务器就能跑
2. **容器友好**：可以用 `FROM scratch` 的最小Docker镜像
3. **避免"DLL地狱"**：不会因为库版本不同而崩溃
4. **跨平台编译**：`GOOS=linux GOARCH=amd64 go build` 在Mac上就能编译Linux程序

权衡：二进制文件大（通常10-20MB），但在服务端部署场景下，稳定性比文件大小重要。

**问题5：链接时还会做优化吗？**

💭 思考方向：
- 如果某个函数从来没有被调用呢？
- 链接器能看到"全局信息"，编译器只能看到单个文件

📖 参考答案：
是的，链接器可以做**链接时优化（LTO, Link-Time Optimization）**：

1. **死代码消除**：移除从来不会被调用的函数
2. **跨文件内联**：把小函数的代码直接插入调用处
3. **全局布局优化**：把经常一起调用的函数放在相邻位置（提高缓存命中）

Go编译器天然做了一些类似的事情：
- 编译时的**逃逸分析**跨越多个函数
- 链接时会**剥离**未使用的包中的代码（不是整个包都链接进来）

## Go语言实践

```go
// main.go
package main

import "fmt"

func main() {
    fmt.Println("Hello, Linker!")
}
```

```bash
# 查看Go编译+链接的详细过程
$ go build -x main.go 2>&1 | tail -20
# 你会看到 compile 和 link 两个阶段

# 查看可执行文件的符号表
$ go tool nm ./main | head -30
# T = text段（代码）, D = data段, B = bss段

# 查看文件大小（感受静态链接的代价）
$ ls -lh ./main
# 通常1-2MB（Hello World也有这么大）

# 去掉调试信息缩小文件
$ go build -ldflags="-s -w" -o main_stripped main.go
$ ls -lh ./main_stripped
# 能减少30-40%

# 使用 objdump 查看链接后的机器码
$ go tool objdump ./main | grep "main.main" | head -10
# 可以看到最终的机器指令和地址（已经是真实地址了）
```

## 深入细节

### Go的链接器特点

Go有自己的链接器（`cmd/link`），和传统的ld不同：

1. **纯Go实现**：不依赖系统的ld
2. **增量链接**：利用编译缓存，只重新链接变化的部分
3. **并行化**：符号解析和重定位可以部分并行
4. **内建支持CGO**：可以链接C库（此时切换到外部链接器）

### 常见链接错误及诊断

```
# 找不到符号
undefined reference to 'xxx'
→ 检查：是否忘记导入包？函数名拼写正确吗？

# 重复定义
multiple definition of 'xxx'  
→ 检查：是否在多个文件中定义了同名全局变量？

# 架构不匹配
incompatible library  
→ 检查：.o文件和目标架构是否一致？
```

## 小结

⭐ **核心要点**：
1. **符号解析**：在所有.o文件中查找匹配的函数/变量定义。找不到就报 `undefined reference`
2. **重定位**：把编译时的占位地址替换为最终的真实地址
3. **Go默认静态链接**：牺牲文件大小换取部署简单性——这是一个工程权衡
